# LoRA Studio モバイル UI/UX 仕様（レビュー確定版）

- **対象**：LoRA Studio のモバイル表示、Step 1「生成」、Step 2「選別」、Step 3「キャプション」、Step 4「学習」、Step 5「評価」。
- **確定範囲**：2026-10-19 までの対話レビューで承認された**UI/UXの見た目・操作導線**。本番の保存方式、生成・出力API、確定状態の永続化の承認・実装を意味しない。
- **参照**：本番基準 `main` の `frontend/src/pages/DatasetStudioPage/` と、隔離モック `prototype/ui-review` の `ui-prototype/`。
- **比較**：[Baseline](https://take4548.github.io/comfy-create-helper2/studio?ui=baseline) ／ [Proposal](https://take4548.github.io/comfy-create-helper2/studio?ui=proposal)。
- **レビュー基準のコミット**：`cfbe12c75457ca6bcb1dedefef938fbd4a9eb027`（UI Prototype Check / Pagesともに成功）。
- **基本原則**：Baseline-Preserving, Problem-Driven Design。不要な変更を避け、既存のダークテーマ・配色・タイポグラフィ・共通コンポーネント・基本操作を維持する。

## 1. 目的と確定した全体構成

モバイルでの視認性、移動、編集、確認と主要操作への到達性を改善する。Studio の作業フローは次の **5タブ**とし、タップおよび左右スワイプで移動できるようにする。

1. 生成
2. 選別
3. キャプション
4. 学習
5. 評価（現行の「学習後評価」相当）

- ヘッダーの **プロジェクト選択／新規作成／保存状態**を同じ行に整理し、その下にタブを配置する。
- 「評価」タブを含め、アイコンとラベルの間隔を他タブと揃える。
- タブ切替時に、必要な編集内容・確認状態が意図せず失われないようにすること。ただし確定状態の永続保存は別課題（§7）。
- スワイプは入力、スライダー、スクロール可能領域、ダイアログなどの操作と競合させない。
- **対象はモバイルProposal**。デスクトップや共通コンポーネントの全面変更は承認範囲に含めない。

## 2. Preserved / Modified / New

| 範囲 | 区分 | 確定仕様 |
|---|---|---|
| Studioの配色・書体・基本コンポーネント | Preserved | 現行をベースラインとして継承 |
| 生成処理・ワークフロー・パラメータの意味 | Preserved | UI整理によって既存処理を変更しない |
| プロジェクトの編集内容 | Preserved | 名前、トリガー、ワークフロー、ノード情報など既存の編集項目を残す |
| Studioナビゲーション | Modified | 5タブ化、横スワイプ対応、ヘッダーの操作群を1行に整理 |
| 生成の設定カード | Modified | 常時表示を減らし、プロジェクト／トリガー編集は初期状態で折りたたむ |
| 重複設定 | Modified | バイパスは生成パラメータ側に集約し、ノード再割当はプロジェクト編集内に集約 |
| 生成マトリクス表示 | Modified | 内容確認中心の長いプロンプト一覧を、因子ごとのドーナツグラフ中心に変更 |
| 生成主要操作 | Modified | 再計算・生成投入を画面下部固定バーに配置 |
| 選別 | Modified | 20素材を揃えるための「確定／要再生成」中心のUIに整理 |
| キャプション | Modified | サムネイルと編集欄を併記、テキスト／タグチップ切替、Step 2に準じた確定表示 |
| 学習／評価 | Preserved | 現行UIに不満なしとの判断により、個別の再設計は行わない |

## 3. Step 1「生成」（UI確定）

### 3.1 設定の情報階層

- **プロジェクト＆トリガー連動設定**は、日常の生成作業では常時展開しない。「編集する」で展開・「閉じる」で折りたためる。
- プロジェクトの編集項目とワークフロー選択、および **ノード再割当**へのアクセスを保持する。
- **バイパス**は既存の生成パラメータ側で操作できれば十分。重複していた「バイパス・ノード詳細設定」セクションは表示しない（ノード再割当の重複も解消）。
- その他の生成パラメータ、マトリクス因子、衣装設定は維持する。
- モバイルでは必要な範囲でカードの内外余白・セクション間隔を縮小する。ただしタップ領域、可読性、入力操作性を犠牲にしない。

### 3.2 生成マトリクスの可視化

- プレビューの第一目的は、**本命衣装と別衣装、表情、構図、アングル、ポーズ等のバランス**を直感的に把握すること。
- 各因子を小型ドーナツグラフで示す。**中心には因子名**（例：衣装／表情／構図）を表示し、共通の総件数を各グラフの中央に重複表示しない。
- 各色の扇形に触れると、**分類名・件数・比率**をポップオーバー表示する。キーボード操作でも情報を参照でき、画面端でポップオーバーが切れないこと。
- 総件数はグラフ群の上部にまとめる。因子の元データにない分類は推測しない。「未設定」は集計上の状態として表示できること。
- スロット別のシード・プロンプトは主表示に並べず、**詳細の折りたたみ**から確認可能にする。
- グラフは**構成分布の可視化**であって、「生成可能」「問題なし」の自動判定ではない。モック中の数値や本命／別衣装の配分をハードコードした正しい判定値として本番仕様に移植しない。
- 2軸ヒートマップは議論した代案であり、**今回の確定仕様には含めない**。

### 3.3 下部固定アクション

- **「直交マトリクス再計算」「生成に投入」**を画面スクロールに依存しない下部固定バーへ配置し、モバイルナビゲーションと重ならないようにする。
- 2つの主要操作を横2列に配置。Step 2への遷移は補助操作として扱う。
- ボタンの実行処理、無効化条件、処理中表示は原則現行の挙動を維持。
- コンテンツ最下部が固定バーに隠れないよう、必要な下部余白と safe-area を設ける。

## 4. Step 2「選別」（UI確定）

### 4.1 20枠の完成を目的とした状態表示

- 作業のゴールは**20件の素材を揃えること**。素材数を減らす「除外」を主操作にはしない。
- 表示を**「確定済み」「要再生成／未確定」**の作業状態中心に変更する。
- 英語の `Approved` と日本語の「確定済み」が**二重表示されない**こと。
- 上部に `確定 X / 20枠`、未確定・再生成対象の件数を表示する。
- 各素材の状態切替を維持し、確定できない素材を再生成対象として扱う。
- **未確定枠の一括再生成**の操作導線を設ける。再生成後は自動確定せず、ユーザーが確認する。
- ただし一括再生成の実バックエンド連携・既存状態の意味の再定義は、UI確定とは別の実装課題とする。

### 4.2 画像確認

- 画像サムネイルをタップすると拡大プレビューを**モバイルのボトムシート**で開く。
- 既存の画像表示・操作との整合性を維持し、閉じる操作とフォーカス制御を考慮する。

### 4.3 一括出力

- **「学習用フォルダ一括出力」**は画面下部に固定し、スクロールせずアクセス可能にする。
- UI上は全20枠確定を出力可能条件として扱い、未確定があれば無効状態と理由を示す。全件確定で有効になること。
- **現行の実出力APIが編集後の最新画像・キャプション・確定状態を永続化していることは未保証**。API連携を「UIの承認済み実装」と誤認しないこと（§7）。

## 5. Step 3「キャプション」（UI確定）

### 5.1 画像とキャプションの対応付け

- 各キャプションカードに**対応画像のサムネイルと枠番号**を並べる。モバイルではカードを縦に積み、カード内部を**左：画像／右：キャプション編集**とする。
- キャプションの各項目は**既存のタグチップ入力**および**通常のテキスト入力**を切り替えられるようにする。
- 2モードは同一の値を扱い、切替によって入力内容を失わない。
- タグ入力の既存の削除／追加操作、カンマ区切りの意味をできるだけ再利用する。

### 5.2 カード上部と確定表示

- 余分な「キャプション」ラベルは削除する。
- **入力モード切替はカード右領域の左上**、**「確定する／確定済み」は右上**に配置。Step 2の確定操作と位置・意味を揃える。
- 編集によって「確定済み」を解除するUIを表現する。
- Step 2同様に `キャプション確定 X / 対象件数` の進捗と、**画面下部固定の一括確定操作**を示す。
- 全対象件数の確定で一括確定が活性化するUIを再現する。

### 5.3 明確な境界

- **キャプションの確定・一括確定は現段階ではUIモックのみ**。現行コードは編集するとStudioのフロントエンド状態を更新するが、キャプション本文・確定状態のサーバー永続保存や出力確定を保証する実装とは区別する。
- モックの一括確定は保存・出力APIを呼ばず、**実際のデータ出力が行われたように見せない**。
- 本番のキャプション保存、確定管理、再編集による確定取消、Step 2一括出力との統合は**別案件**（§7）。

## 6. Step 4「学習」と Step 5「評価」

- **現行UIを維持する**。レビューで追加の問題指摘がなく、見た目の改修は要求されていない。
- 全体共通の5タブナビゲーションには含めるが、学習設定、学習の実行処理、評価マトリクス、ステータス、データ表示、各モーダル等の既存の振る舞いを変更しない。
- モック上の学習・評価データは**オフラインの架空データ**。本番の評価結果や実API接続を意味しない。

## 7. UI仕様の対象外・別チケットで扱う課題

今回のUI合意を根拠として、下記の内部機能変更を実施済み／承認済みと扱わない。

1. **キャプション永続化**：タグ・テキスト編集後のキャプションをどのAPI、保存単位、タイミングで保持するか。
2. **キャプション確定状態**：20件の確定／未確定管理、編集時の確定解除、再読込・プロジェクト切替時の復元。
3. **学習用フォルダ出力整合性**：最新の確定画像と最新キャプションを確実に出力し、保存失敗・件数不足を扱うこと。
4. **一括再生成の本実装**：未確定枠の抽出、バッチ実行、画像更新、処理失敗と再試行、自動確定しないルール。
5. **状態・件数の定義**：現行の `APPROVED/REJECTED/PENDING` 等のAPI状態を、完成フローの「確定／要再生成」にどう対応付けるか。
6. **因子別分布データ**：具体的な別衣装の種類・表情・構図など、モックで読めないメタデータの取得・定義。

※ Step 2 / Step 3 のモックはこの操作概念を**架空データ／ローカル表示状態**で試している。動作イメージの合意が、そのまま本番ロジックの仕様決定を意味するものではない。

## 8. レスポンシブとアクセシビリティ

- 確定対象は主に**モバイルの狭い画面**。デスクトップは原則既存UIを維持する。
- 入力やタブで横方向のはみ出しを起こさず、ボタンのタップ可能範囲とキーボードフォーカスを確保する。
- 固定バーは画面内のナビゲーション、OSのセーフエリア、ソフトキーボード、モーダル／ボトムシートと重ならないこと。
- アイコンだけに頼らず、状態・操作名を判別できる。ドーナツの色分類は視覚色に加え、操作時のテキスト情報で参照できること。
- 表示上の「確定」や「一括出力」が本番のデータ永続化を伴うかは、実装時に明確なフィードバックを設けること。

## 9. 受け入れ条件（UIレベル）

- **AC-01**：モバイルで5タブが表示され、タップおよび競合しない左右スワイプで移動できる。学習・評価の中身は従来どおり。
- **AC-02**：プロジェクト選択、新規作成、保存状態がヘッダー内で1行に整理され、ラベル・アイコン間の不自然な余白がない。
- **AC-03**：生成のプロジェクト詳細は初期状態で閉じ、編集で開閉できる。バイパスとノード再割当の重複導線を表示しない。
- **AC-04**：生成マトリクスの各因子がドーナツで表示され、扇形操作により分類・件数・比率を確認できる。内側は因子名であり共通総件数の反復ではない。
- **AC-05**：生成の再計算・投入操作は画面下部でアクセスでき、本文を隠さない。
- **AC-06**：選別のサムネイルで拡大ボトムシートが開く。20枠の状態が日本語で重複なく確認できる。
- **AC-07**：選別で未確定枠を一括再生成するUIがあり、ユーザーの確認前に確定済みと表示しない。全件確定で一括出力のUIが有効になる。
- **AC-08**：キャプションの画像と編集欄が同じカード内にあり、タグチップ／テキストを往復しても値が保持される。
- **AC-09**：キャプションの入力切替は左上、個別確定は右上。編集で確定が解除され、進捗および下部固定の一括確定が追従する。
- **AC-10**：モック内の一括確定／一括再生成は実サーバーへリクエストせず、実保存や実出力に成功したような誤表示をしない。
- **AC-11**：Baselineは比較可能なまま保持し、モバイルProposal以外の本番実装を変更しない。
