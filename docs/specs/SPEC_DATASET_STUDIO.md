# Dataset Studio — 仕様書 (SPEC_DATASET_STUDIO)

**バージョン**: 1.0  
**最終更新**: 2026-10-08  
**ステータス**: REQ-323 準拠 (プロジェクト即時永続化・オートセーブ・下書き復元・楽観的競合検知)

---

## 1. 概要 (Overview)
Dataset Studio は、直交計画マトリクス生成から画像キュレーション・LoRA 学習設定・4軸ストレステスト評価までを統合するデータセット作成支援ワークフローである。
ユーザーの入力消失（入力途中の離脱や通信不整合）を防止するため、即時プロジェクト永続化、デバウンスオートセーブ、リアルタイム sessionStorage 下書き退避、および楽観的競合検知・復元機能を備える。

---

## 2. データ永続化ライフサイクル (Persistence Lifecycle)

### 2.1 新規プロジェクト作成の即時永続化 (AC-1)
- ユーザーが `CreateProjectModal` で名前やワークフロー、初期トリガーを入力して作成ボタンを押下した際、サーバー API (`POST /api/dataset/projects`) へ即時に永続化リクエストを送信する。
- サーバーより確定 ID (`DatasetProject.id`) を受領後、アクティブプロジェクトとして設定し、ヘッダーに確定情報を反映する。
- 万一作成に失敗した場合（400/500 等）、モーダルを閉じずに入力値を完全に保持し、エラーメッセージを表示して再試行を可能とする。

### 2.2 750ms デバウンス・オートセーブ (AC-2)
- プロジェクト編集中の各フォーム項目変更に対し、750ms のデバウンスタイマーを設定する。
- 連続入力停止後 750ms 経過でサーバー API (`PUT /api/dataset/projects/{id}`) を自動発行する。

### 2.3 リアルタイム sessionStorage 下書き退避 (AC-3)
- デバウンス待ち時間および通信中を含め、ユーザーの入力が行われるたびに直ちに `sessionStorage` の `dataset_studio_draft_{id}` キーへ最新フォーム状態を同期退避する。
- `sessionStorage.setItem` が `QuotaExceededError` をスローした場合でも画面クラッシュを防止し、例外安全にオートセーブ動作を継続する。

### 2.4 画面再訪・リロード時の自動復元 (AC-4)
- ページアンマウントやブラウザリロード後、該当プロジェクト画面が再マウントされた際、`sessionStorage` の下書きが存在し、かつサーバーの `updated_at` より新しいタイムスタンプを持つ場合、未保存の下書きを自動復元する。
- 自動復元時は UI 上に復元通知アラート (`draft-restored-alert`) を表示する。
- サーバー側の `updated_at` が下書きより新しい場合、古い下書きで最新サーバーデータを上書きしない（サーバー最新優先）。

### 2.5 成功時キャッシュ同期 (AC-5)
- サーバーへのオートセーブまたは明示的保存が成功した際、`sessionStorage` 内の下書きを同期済み (`is_synced: true`) に更新し、最新の `base_server_updated_at` を同期する。

### 2.6 保存ステータス表示 (AC-6)
- 状態遷移に応じて UI 上のインジケーター (`autosave-status`) を以下のように更新する：
  - `idle`: 初期状態（保存完了と同じ表示または非表示）
  - `unsaved`: 入力中・デバウンス待機中（「未保存（下書き保持）」）
  - `saving`: オートセーブ通信中（「変更を保存中...」）
  - `saved`: 保存成功（「保存完了」）
  - `error`: 保存失敗（「保存失敗（下書き保持中）」）

### 2.7 楽観的排他制御と競合解消 (Optimistic Locking & Conflict Resolution)
- 下書き保持中に別タブや他セッションによってサーバーデータが更新された場合（`draft.base_server_updated_at !== activeProject.updated_at`）、自動上書きを停止し、競合アラートバナー (`draft-conflict-alert`) を表示する。
- ユーザーに以下の2つの明示的解消選択肢を提供する：
  1. **下書きで上書き (`resolveConflictWithDraft`)**: 下書きの内容でサーバーへ更新を即時送信し、競合を解消する。
  2. **サーバーの最新を読込 (`resolveConflictWithServer`)**: 下書きを破棄し、サーバー側の最新データにフォームを巻き戻す。

### 2.8 Step 1 生成通信
- Step 1の各生成リクエストは `scope=studio` として扱い、リクエストごとに独立したbatchとして進捗・待機状態を表示する。別のStudio batchや通常生成の進捗を同じbatchへ合算しない。
- 待機中は競合するscopeまたは別Studio batchの待機数を区別する。batchにプロジェクトが紐づく場合は、そのプロジェクト名を併記してよい。
- Studio batchのキャンセル済みjobは成功・失敗とは別の終端状態として扱う。batchの総数 `N` は元のリクエスト件数のまま保持し、キャンセルを完了数 `F`（成功数＋失敗数）へ加算しない。通常生成のみを対象にするキャンセルモードではStudio batchを保護する。既存の全体キャンセルの既定動作は維持する。
- この節はStep 1の生成リクエストとbatch表示に限る。StudioのStep遷移、フォームの競合解消、750msデバウンス、sessionStorage下書き保持の動作は変更しない。
