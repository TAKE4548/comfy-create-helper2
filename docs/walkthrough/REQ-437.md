# Walkthrough: REQ-437 プリセット一括削除時の孤立 `workflow_preset_values` 残存によるプリセット新規作成 `IntegrityError` 修正

> **凍結注記 (`[W-DV-FREEZE]`)**: 本ファイルは `.agents/verification.json` の `identity.input_dirs`（`docs/`）配下にあるため、最終 Gate 1〜3 の実行前に内容を確定・凍結しています。Gate 1〜3 の実行結果・RecordV1 パス／ハッシュ・実測メトリクスは `docs/logs/verification/` および `docs/logs/REQ-437/verify-summary.md` に記録されます。

## 1. PBI サマリーと設計判断

- **PBI ID**: `REQ-437`（`docs/backlog/pbi/active/REQ-437.md`）
- **種別 / 優先度**: bug（Type A: 実装欠陥） / P1
- **対象領域**: Backend（API ルーター / 起動時マイグレーション）
- **根本原因**:
  1. `bulk_delete_presets`（`backend/app/routers/presets.py`）が `Query.delete(synchronize_session=False)` を用いて `workflow_presets` のみをバルク SQL 削除し、ORM の `cascade="all, delete-orphan"` を迂回していた。
  2. `configure_sqlite_pragmas`（`backend/app/database.py`）で `PRAGMA foreign_keys=ON` が有効化されていないため、SQLite 側の `ON DELETE CASCADE` も発火せず、子テーブル `workflow_preset_values` に孤立行が残存していた。
  3. `workflow_presets.id` が `AUTOINCREMENT` なしの `INTEGER PRIMARY KEY` であるため、最大 ID のプリセット一括削除後の `POST /api/workflow-presets` で同一 ID が再利用され、残存していた孤立行と `uq_workflow_preset_values_preset_variant_sub_key` が衝突して `IntegrityError`（HTTP 500）を引き起こしていた。
- **採用した解決方針（`docs/design/REQ-437.md`）**:
  - `backend/app/database.py` への `PRAGMA foreign_keys=ON` グローバル追加は見送り（`dataset_projects.workflow_id` の既存孤立データや既存マイグレーションへの影響を遮断）、別 PBI へ分離する。
  - **REQ-437-T1**: `bulk_delete_presets` 内で `target_ids = list(dict.fromkeys(payload.ids))` を生成し、同一トランザクション内で子テーブル `models.WorkflowPresetValue` を先行削除してから親テーブル `models.WorkflowPreset` を削除し `db.commit()` する。
  - **REQ-437-T2**: 起動時マイグレーション `step_037_cleanup_orphaned_workflow_preset_values` を `backend/app/migrations/steps.py` に追加し、`ALL_MIGRATION_STEPS` 末尾へ登録して既存 DB の孤立行を冪等に浄化する。
