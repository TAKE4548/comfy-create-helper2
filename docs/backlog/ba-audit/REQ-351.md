# Business Analyst Reasoning Gate Analysis: REQ-351

## Executive Summary
REQ-351 introduces granular control over ParamSync synchronization, allowing users to select specific "Stages" within a broader Role hierarchy. While the business intent (reducing manual editing) is clear, the requirement contains semantic ambiguities regarding "Role vs. Stage," potential state management conflicts in AC-5, and risks of circular dependency propagation not addressed by current constraints.

---

## 1. Logical Consistency & Semantic Audit

### A. Terminology Ambiguity: "Same Role" vs. "Different Stages"
*   **Requirement Text:** "同一ロールの別ステージを個別選択" (Select different stages of the same role individually).
*   **AC-1 Analysis:** AC-1 describes selecting `Main/Steps` as a source and having `Rough/Steps`, `Detail/Steps` appear as sub-candidates. In existing architecture (`SPEC_GENERATE.md §2-8`), Main, Rough, and Detail are typically distinct **Roles**, not stages of one role.
*   **Contradiction:** The title implies a hierarchy (Role > Stage), but the ACs describe cross-role synchronization with finer granularity. If "Main" and "Rough" are different Roles, REQ-351 is effectively allowing multi-target sync within a specific workflow type, not just intra-stage selection.
*   **Risk:** Developers may implement this as filtering existing Role candidates rather than creating a new "Stage" dimension, leading to UI confusion where users expect to see sub-steps of *one* role but are actually seeing other roles.

### B. The "Self-Reference" Definition (AC-2)
*   **Requirement:** "代表そのものの Main/Steps は選べないこと" (The representative's own Main/Steps cannot be selected).
*   **Logical Gap:** This prevents a Role from syncing to itself. However, it does not prevent a cycle (e.g., Main -> Rough -> Main). If the system allows bidirectional sync or if "Main" is also a target for another role in a loop, AC-2 alone does not guarantee data integrity.

---

## 2. Edge Case Analysis

### A. State Capture Ambiguity (AC-5)
*   **Scenario:** Detail/Steps is synced to Main/Steps (Value = 40). User unchecks Detail/Steps from the sync list. Later, Main/Steps updates to 50.
*   **Question:** AC-5 states "Detail keeps 40." But what if Detail was *also* a source for another role? Or what if the system performs a background refresh of all roles?
*   **Edge Case:** If `Main=20, Rough=30, Detail=40`. User syncs Main to Rough. Then unchecks Detail. If the user later edits Detail manually to 100, does it break the "keep value" logic? The requirement implies a passive freeze, but doesn't define how that state is stored (is it a flag on the target role?).

### B. Empty/Null Stage Handling
*   **Scenario:** A workflow has `Main/Steps` selected as source, but `Rough/Steps` does not exist in the current workflow instance yet (e.g., new workflow type).
*   **Gap:** The requirement assumes existing stages are present ("Given..."). If a stage is missing, does the sync fail silently? Does it create the stage? This overlaps with feature creation logic not covered here.

### C. Concurrent Updates (Race Condition)
*   **Scenario:** User selects Main -> Rough and Main -> Detail simultaneously. While syncing, another user or process updates `Main` again.
*   **Gap:** The requirement does not specify transaction boundaries. If the sync is batched, partial failures could leave the system in an inconsistent state where Rough has 50 but Detail still has 40 despite a global update event.

---

## 3. Overlap & Conflict Check

### A. Overlap with REQ-336
*   **Context:** REQ-336 likely established the base Role-to-Role sync mechanism.
*   **Conflict:** REQ-351 introduces "Stage" selection. If `SPEC_GENERATE.md` defines a Stage as an immutable execution step, allowing users to arbitrarily map Roles to Stages might violate the intended workflow rigidity. The requirement needs to clarify if this overrides existing Role mappings or sits alongside them.

### B. Operational Need vs. Implementation
*   **Need:** "Independent adjustment and separate role linkage."
*   **Conflict:** AC-6 requires persistence of selection ("restored when displaying"). However, if the user changes the workflow structure (e.g., renames a stage), the saved mapping might break or map to the wrong entity. The requirement lacks validation logic for structural changes post-sync configuration.

---

## 4. Recommendations & Fixes

1.  **Clarify Hierarchy:** Rename "Same Role's Different Stage" to "Multi-Target Sync within Workflow Type." Explicitly define if Main/Rough are Roles or Stages in the glossary referenced by `SPEC_GENERATE.md`.
2.  **Refine AC-5 (Freeze Logic):** Define *how* the value is kept. Is it a snapshot? A flag preventing future syncs to that target until re-enabled?
3.  **Cycle Detection:** Add an inferred point or constraint to detect circular dependencies when multiple stages are selected, not just self-reference.
4.  **Null Handling:** Add AC for behavior when a target stage is missing (e.g., "Skip" vs. "Error").

---

## Final Verdict
**Status: Conditional Approval with Clarification Required.**
The requirement solves a valid business problem but lacks precision in defining the data model relationship between Roles and Stages. The logic in AC-5 requires further technical specification to ensure state consistency without unintended side effects on existing workflows.
