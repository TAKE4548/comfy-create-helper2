# REQ-347 監査レポート (Business Analyst Reasoning Gate)

## 1. 概要と結論
REQ-347 は、ユーザーが複数ステージ（Main, Rough など）の同名入力欄を混同しないよう、UI 上で視覚的にグループ化し、スクロール時でも所属を示すことを目的とする機能要件である。全体として論理的な整合性は高いが、**スクロール挙動の定義曖昧さ**と、**データ同期設定（AC-4）との競合リスク**が見受けられる。実装前に以下の点を確認・明確化する必要がある。

---

## 2. 論理的整合性と矛盾の分析

### 2.1 AC-2 と AC-3 の挙動定義曖昧さ
*   **現状:** AC-2（スクロール中も所属を示す）と AC-3（ステージ切り替わり）は、UI 実装において「Sticky Header（固定ヘッダー）」の挙動を指しているが、その実装方法が不明確。
    *   **パターン A (Global Sticky):** 画面最上部に常に現在のステージ名を表示し、スクロールで切り替える。
    *   **パターン B (Group Sticky):** 各グループ（Main, Rough）の先頭にヘッダーがあり、そのグループ内では固定される。
*   **矛盾点:** AC-3「Rough 先頭が入力エリア上端へ到達するまでスクロールすると切り替わる」という記述は、**グループごとの独立した固定ヘッダー**を想定している可能性が高いが、AC-2 の「入力エリア上端に見えること」はユーザーの視線位置に依存する。
*   **推奨:** 実装仕様書（Design Doc）で「各ステージブロックの先頭に固定ヘッダーを表示し、スクロールしてもブロック内では表示を維持する」と明記する。

### 2.2 AC-4 の「同期設定」前提の検証
*   **現状:** AC-4 で「同期設定なし」という条件付きで挙動を定義している。
*   **矛盾点:** 既存機能に「同期（Synchronization）」が存在する場合、その同期ロジックは通常、バックエンドのイベント駆動やリアルタイム更新を行う。UI 上の入力欄がグループ化されても、データモデルレベルでの同期設定が「Off」であることをどう保証するか？
*   **リスク:** ユーザーが「同期 Off」と認識しているが、システム側でデフォルトが On になっている場合、Rough の編集が Main に波及する可能性がある。

---

## 3. エッジケースと境界条件の検討

| ケース | 想定挙動 | 不具合リスク |
| :--- | :--- | :--- |
| **ステージ名の長さが画面幅を超える** | 省略表示またはスクロール | ヘッダーが隠れると「所属」が見えなくなる（AC-1/2 の矛盾）。 |
| **ステージが 1 つしかない場合** | グループ化ロジックのトリガーがない | 不要な UI 要素が表示され、レイアウト崩れを招く。 |
| **入力欄が非常に長い場合** | スクロール中にヘッダーが切り替わるタイミング | ユーザーが「Main」の編集途中に、スクロールで「Rough」へ切り替わった瞬間に操作ミス（AC-5 の文脈）。 |
| **Settings 画面でのノード未設定時** | `inferred_points` にある通り未マッピングは表示しない？ | ユーザーが「どこにマッピングすべきか」を直感的に理解できない。 |

---

## 4. SSoT (Single Source of Truth) 整合性チェック

### 4.1 外部ドキュメントへの依存
*   **SPEC_GENERATE.md §2-5:** 「ステージ」や「ロール」の定義がここにあると仮定するが、この仕様書が最新か確認が必要。もし「Main」と「Rough」の順序が動的に変更される場合、UI の固定表示はデータモデルと乖離するリスクがある。
*   **REQ-348 への言及:** `inferred_points` で Settings の未設定ロール追加候補を REQ-348 と関連付けられている。REQ-347 が実装された際、REQ-348 の挙動（動的追加）と UI グルーピングが競合しないか確認が必要。

### 4.2 データモデルの独立性
*   AC-4/AC-6 で「Main は変更されず」という挙動は、データベーススキーマ上で各ステージの値が独立していることを前提としている。もし「Global Steps」のような共有フィールドが存在し、UI がそれを個別に編集可能に見せている場合、書き込み競合（Race Condition）が発生する可能性がある。

---

## 5. 推奨アクション (Action Items)

1.  **実装仕様書の作成:** AC-2/3 のスクロール挙動を「各ステージブロック先頭固定」または「グローバル固定」で明確化し、モックアップを添付する。
2.  **同期設定の検証:** 「同期 Off」状態でのバックエンド挙動を確認し、UI 表示とデータ更新が一致していることを保証するテストケースを追加する。
3.  **アクセシビリティ対応:** スクロール中の固定ヘッダーには `aria-current` や適切なラベルを付与し、スクリーンリーダーユーザーも所属を理解できるようにする（UX Classification に Information Design があるため必須）。
4.  **ヒューマンレビューゲートの承認:** 本監査レポートの指摘事項に対し、開発チームと合意形成後、Design Doc を作成して承認フローへ進める。

---

## 6. 最終判定
**論理的整合性: B (条件付き)**
*   要件自体は明確だが、UI 挙動（スクロール）とデータロジック（同期）の境界が曖昧。
*   **承認推奨:** Design Doc の詳細化および上記エッジケースへの対応策を明記した上で承認する。

# Business Requirement Audit Report: REQ-347

**Analyst:** Expert Business Analyst (Reasoning Gate)
**Date:** 2026-10-11
**Subject:** Logical Consistency, Edge Cases, and SSoT Integrity Analysis

## 1. Executive Summary
REQ-347 addresses a UX fragmentation issue where users lose context regarding which "Stage" they are editing within long-form generation inputs. The requirement proposes implementing sticky stage headers for both the Generation Page (Prompt/Parameter) and Settings Node Mapping.

**Overall Verdict:** **Logically Consistent with Minor Edge Case Risks.**
The core logic of data independence (AC-4, AC-6, AC-7) is sound and prevents unintended side effects. However, the UI implementation details regarding horizontal scrolling and viewport management require strict adherence to prevent violating AC-5 (Editability).

## 2. Logical Consistency Analysis

### A. Data Independence vs. Global State
*   **Requirement:** AC-4 and AC-6/7 explicitly state that editing one stage (e.g., Rough) should not affect another (Main), provided "no sync setting" exists.
*   **Consistency Check:** This is logically consistent with a modular architecture. However, it relies on the existence of a global "Sync Setting." If a future requirement introduces a "Global Sync" feature that overrides stage-specific values, this requirement's behavior must be prioritized or clearly documented as an exception.
*   **Audit Finding:** The audit response correctly identifies this dependency but does not explicitly define precedence rules if a conflict arises between AC-4 (Stage Independence) and a potential future Global Sync rule.

### B. Header Hierarchy (AC-8)
*   **Requirement:** "Do not replace with one common header."
*   **Consistency Check:** This is logically necessary because the Generation Page splits content horizontally into Prompt and Parameter columns. If a single global header were used, switching focus between columns would lose the specific stage context for that column.
*   **Audit Finding:** The logic holds. Independent sticky headers per column are required to maintain SSoT (Single Source of Truth) regarding *which* stage is being viewed in each specific UI pane.

### C. Scrolling Logic (AC-2 & AC-3)
*   **Requirement:** Headers must remain visible until the next stage reaches the top, then switch.
*   **Consistency Check:** This implies a "Sticky" behavior triggered by viewport entry/exit events. The logic is consistent with standard web patterns but requires precise event handling to avoid "flickering" headers during rapid scrolling or resize events.

## 3. Edge Case Analysis

### A. Long Stage Names vs. Visibility (AC-5)
*   **Scenario:** If a stage name (e.g., "Detailed_Review_Phase_1") is longer than the input area width, truncation may occur.
*   **Risk:** AC-5 states headers must not obscure editing. If the header wraps or hides behind scrollbars due to length, it violates the intent of AC-2/3 (Visibility).
*   **Recommendation:** The audit response mentions "Design Judgment," but this needs a concrete rule (e.g., ellipsis with tooltip) to ensure logical consistency between "Showing" and "Not Obscuring."

### B. Empty Stages / Unmapped Roles
*   **Scenario:** AC-1 implies headers exist for mapped roles. What happens if a Stage exists in the schema but has no inputs? Or if a user creates a new stage that hasn't been fully populated yet?
*   **Risk:** The "Inferred Points" suggest limiting display to generation page input fields, but the Settings logic (REQ-348) maintains un-set candidates. If a Stage is empty in Settings but has an input field in Generation, does it render a header with no content below it? This creates visual noise.
*   **Recommendation:** Clarify if "Empty Stages" should be hidden from the sticky list or rendered as collapsed sections to maintain logical flow.

### C. Viewport Height Variance
*   **Scenario:** AC-3 triggers on "Rough reaching top." If a user has multiple stages visible simultaneously (viewport > content), does the header switch immediately upon entry, or only when it becomes the *active* focus?
*   **Risk:** Premature switching could cause confusion if two stages are partially visible. The logic assumes a 1-stage-at-a-time view model which may not hold for users with large screens.

## 4. SSoT (Single Source of Truth) Integrity

### A. Reference Documentation Alignment
*   **Check:** References SPEC_GENERATE.md §2-5 and REQ-336/343.
*   **Analysis:** Without access to these docs, we assume they define the "Stage" schema. The requirement relies heavily on this external definition for what constitutes a "Stage." If the Stage structure changes (e.g., merging stages), REQ-347's sticky logic might break if not dynamically mapped.

### B. Audit Trail Integrity
*   **Check:** The requirement includes its own audit trail ("BA contradiction audit...").
*   **Analysis:** This is a strong point for integrity. It shows the requirement has been self-audited. However, the "Conditional PASS" (B) suggests that while logic holds, implementation risks remain.

## 5. Final Recommendations

1.  **Refine AC-2/3 Trigger Logic:** Explicitly define if the header switch happens on *entry* or *exit*. Currently, it implies entry ("reaching top"). This is generally safer but needs testing with rapid scrolling.
2.  **Define "Obscure" in AC-5:** Add a constraint that headers must not be truncated beyond recognition (e.g., max-width constraints) to ensure they fulfill their purpose of identification without violating visibility.
3.  **Settings Logic Clarification:** Ensure the interaction between REQ-347 (Display/UX) and REQ-348 (Data Schema) is clear. The UX should reflect the data, but if the data schema allows "ghost stages," the UX needs to handle them gracefully.

**Conclusion:** REQ-347 is logically consistent regarding data integrity and user context. It passes the SSoT check provided external references are stable. The primary risks lie in UI implementation (scrolling behavior) rather than business logic.
