# Business Analyst Reasoning Gate Analysis: REQ-345

## 1. Executive Summary
REQ-345 addresses a data integrity issue where temporary generation assets ("original images") vanish while their metadata (thumbnails) persists, leading to user confusion and redundant processing attempts. The requirement proposes hiding these "orphaned" trials from the Frontend history rather than deleting them immediately or attempting automatic repair.

**Verdict:** Logically consistent within its narrow scope but introduces complexity in state management and SSoT alignment regarding data availability. Requires clarification on manual interaction vs. automated healing to avoid user friction.

---

## 2. Logical Consistency & Contradictions

### 2.1 The "Availability Contract" Paradox
*   **Requirement:** "Maintain SPEC_GENERATE original image availability contract."
*   **Conflict:** The core function of this requirement is to acknowledge that the asset *is not available* (404) and then hide it. If the contract implies a guarantee of existence upon generation, acknowledging failure contradicts the guarantee.
*   **Resolution:** This is likely a semantic interpretation where "contract" refers to the data structure integrity (metadata exists), not the physical file persistence. However, this ambiguity risks future disputes regarding SLA compliance for generated assets.

### 2.2 Automatic vs. Manual Re-acquisition
*   **Requirement:** "Suppress re-acquisition."
*   **Conflict:** The requirement explicitly targets *automatic* suppression ("auto-reacquisition"). It does not explicitly forbid a user from manually clicking a hidden item (if they are somehow visible) or triggering a fetch via another path.
*   **Risk:** If the system suppresses background healing but allows manual triggers, users might still encounter 404s when actively trying to use the asset, violating the "business problem" of preventing user effort.

### 2.3 Asymmetry in Error Handling (AC-1 vs AC-4)
*   **Observation:** AC-1 treats original image disappearance as a reason for exclusion. AC-4 explicitly states that thumbnail errors or timeouts should *not* trigger this exclusion logic.
*   **Analysis:** This creates an asymmetry where "partial failure" (thumbnail only) keeps the record, but "critical failure" (original gone) removes it. While logical, it implies a higher tolerance for metadata inconsistency than asset consistency.

## 3. Edge Cases & Missing Scenarios

### 3.1 The "Zombie Record" State
*   **Scenario:** A trial is excluded from FE history but remains in the DB (per AC-5).
*   **Impact:** Future queries for analytics or debugging might return these records as "active" when they are effectively "dead."
*   **Recommendation:** The requirement should specify a TTL (Time-To-Live) for these hidden records to prevent database bloat, even if FE hides them.

### 3.2 Snapshot Dependency Failure (AC-6 Ambiguity)
*   **Scenario:** AC-6 states "Snapshot display... is retained." However, if the original image was embedded in the snapshot metadata and is now missing, viewing that snapshot will fail or show a broken placeholder.
*   **Gap:** The requirement focuses on *history* exclusion but ignores the *snapshot playback* experience. A user might view a saved Snapshot expecting to see the result, only to find it broken because the history logic hid the source but didn't fix the reference.

### 3.3 Race Condition in "Disappearance Confirmation"
*   **Scenario:** The background job checks for 404s (AC-1). If the job runs while a user is actively generating new assets that might overwrite or move temp files, false positives could occur.
*   **Recommendation:** Implement a debounce window (e.g., wait 5 minutes after generation before marking as disappeared) to allow for transient file system issues.

### 3.4 Snapshot vs. History Overlap
*   **Scenario:** A trial exists in both "History" and "Snapshot." If the history entry is excluded, does the snapshot retain a link to that now-missing original?
*   **Recommendation:** Clarify if snapshots are immutable copies or live links. If live links, they need similar protection logic.

## 4. SSoT (Single Source of Truth) Integrity

### 4.1 Status Flag Location
*   **Issue:** The requirement states "History exclusion is FE non-display and NOT DB record deletion."
*   **SSoT Gap:** If the DB still holds the record, where is the "Excluded" flag stored? Is it a boolean in the `status` column or computed via query logic?
*   **Risk:** If computed (e.g., `WHERE status = 'active' AND has_original = true`), and the original disappears later, the FE might still show the item until the next refresh. The SSoT for "Availability" must be centralized in a database flag to ensure consistency across page reloads.

### 4.2 Availability Contract Definition
*   **Issue:** `SPEC_GENERATE.md availability` is referenced but not defined here.
*   **SSoT Integrity:** Without a clear definition of what constitutes an "availability breach" (e.g., HTTP 404 vs. 503 vs. Timeout), the system cannot reliably determine when to exclude a record. The requirement assumes this contract exists externally, which is acceptable but requires verification against existing documentation.

---

## 5. Recommendations for Implementation

1.  **Clarify "Re-acquisition":** Explicitly define if manual user actions (e.g., clicking a thumbnail) trigger re-acquisition logic or are suppressed entirely.
2.  **Define TTL for Hidden Records:** Even if FE hides them, DB records should have a cleanup policy to prevent accumulation of "zombie" data.
3.  **Snapshot Decoupling:** Ensure that excluding history does not break existing Snapshots. If the original is gone, the Snapshot should either regenerate on demand or display a fallback state without crashing the UI.
4.  **SSoT Flagging:** Implement a `visibility_status` field in the database (e.g., `visible`, `hidden_due_to_missing_asset`) to ensure FE queries are deterministic and do not rely solely on external availability checks during render time.

---

## 6. Final Conclusion
REQ-345 is logically sound for its primary goal of reducing user friction caused by missing assets. However, it relies heavily on the assumption that "disappearance" can be detected reliably without impacting performance (AC-1). The SSoT integrity is maintained provided a database flag is used to track exclusion status rather than relying on FE-side computation. The main risk lies in the interaction between this logic and existing Snapshot features, which may require further integration testing.
