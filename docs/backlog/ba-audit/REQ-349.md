# Business Analyst Reasoning Gate Analysis: REQ-349

## 1. Executive Summary
REQ-349 proposes a UI/Validation change to allow **LoRAStack-type Mapping Masters** to exist without a mandatory "Parameter Name". While this solves a specific UX friction for complex LoRA configurations, it introduces significant risks regarding data integrity (SSoT), backend validation consistency, and future maintainability. The requirement is logically sound in intent but lacks robustness in implementation details.

---

## 2. Logical Consistency & Contradiction Audit

### A. The "Identifier Paradox"
*   **The Conflict:** Mapping Masters typically function as keys or indices within the system (referenced by `SPEC_SETTINGS.md §4-1`). If a master has no name, how is it uniquely identified in queries, logs, or API calls?
*   **Risk:** If two LoRAStack masters are created with empty names, they become logically indistinguishable to any downstream process that relies on the "Name" field for grouping or filtering.

### B. Type Transition Logic (AC-4 vs AC-5)
*   **The Conflict:** AC-4 states the field becomes input-enabled when switching types. AC-5 states saving with an empty name triggers an error.
*   **Gap:** The requirement does not define the behavior *during* the switch.
    *   Does the system migrate existing data?
    *   If a user switches Type from LoRAStack to Float, keeps the field empty (inherited state), and saves—does AC-5 trigger immediately or only on subsequent save?
    *   **Logical Inconsistency:** The requirement implies the Name is optional for LoRAStack but mandatory for Float. However, if the database schema enforces `NOT NULL` globally, this UI logic will fail at the API layer unless backend changes are also made.

### C. "Disabled" vs. "Hidden"
*   **The Conflict:** AC-1 says the field is "disabled" (無効化).
*   **Edge Case:** If a user edits an *existing* LoRAStack master that previously had a name, and then changes the type to Float, does the system force them to input a name immediately? Or does it allow saving with empty first? The flow is ambiguous.

## 3. Edge Cases & Operational Risks

| Edge Case | Impact Analysis | Severity |
| :--- | :--- | :--- |
| **Import/Export** | If data is exported (JSON/CSV) with an empty name, importing it into a new environment might fail validation if the target system expects names. | High |
| **Search & Filter** | Users cannot search for "LoRAStack Master X" by name. They must rely on ID or list view. This degrades discoverability. | Medium |
| **API Contract Violation** | If the backend API validates `parameter_name` as a required string, the frontend disabling it will result in 500/400 errors upon save unless backend logic is updated to allow `null`. | Critical |
| **Rollback/Migration** | Reverting this feature requires handling existing "empty name" records. A schema migration might be needed to backfill IDs or generate default names. | Medium |
| **Duplicate Creation** | Users can create multiple LoRAStack masters with empty names. There is no UI constraint preventing duplicates (unlike a unique Name field). | Low/Medium |

---

## 4. SSoT (Single Source of Truth) Integrity Check

1.  **Database Schema:**
    *   Does the `mapping_masters` table allow `NULL` for `parameter_name`? If not, this requirement requires a schema migration (`ALTER TABLE ... ALTER COLUMN parameter_name DROP NOT NULL`).
2.  **Global Search Index:**
    *   If there is a global search bar (e.g., "Find Settings"), does the index handle empty strings correctly? Empty strings often break `LIKE` queries or full-text searches depending on implementation.
3.  **API Documentation:**
    *   The API spec (`SPEC_GENERATE.md §2-5`) must be updated to reflect that `parameter_name` is conditional based on `master_type`. Failure here creates a disconnect between frontend and backend contracts.

---

## 5. Recommendations & Gate Decision

### Pre-Implementation Fixes Required:
1.  **Backend Validation Update:** Explicitly document in API specs that LoRAStack types allow `null` parameter names. Add server-side validation to prevent accidental saves of empty names if the type is changed later.
2.  **Unique Identifier Strategy:** Ensure each Master has a unique internal ID (UUID) so functionality isn't lost even without a human-readable name.
3.  **Migration Script:** Create a script to handle existing records where `parameter_name` might be null, or generate a default placeholder (e.g., "LoRAStack_[ID]") for display purposes only.

### Gate Decision: **CONDITIONAL PASS**
*   **Status:** Approved for Development *provided* the backend schema and API contracts are updated concurrently with this frontend change.
*   **Condition:** The BA must verify that the database column `parameter_name` is altered to allow NULLs before deployment, or a default value logic is implemented in the service layer.
