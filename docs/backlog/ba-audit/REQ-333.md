# Business Analyst Review Report: REQ-333 (Prompt Surgeon Redesign)

**Date:** 2026-10-10
**Reviewer:** Expert Business Analyst (Reasoning Gate)
**Subject:** Logical Consistency, Edge Cases, and SSoT Integrity Analysis

## 1. Executive Summary
REQ-333 proposes a significant architectural shift to unify management UIs and enable cross-device synchronization for generative AI workflows. While the functional requirements are detailed, there are critical logical gaps regarding state persistence during network partitions, ambiguity in "session" definitions, and potential conflicts with existing system policies (`SKILL.md`). The requirement is **conditionally viable** but requires clarification on data consistency guarantees before implementation begins.

## 2. Logical Consistency Analysis

### 2.1 Architectural Contradictions
*   **Policy Reversal Risk:** The document explicitly states a reversal of `SKILL.md` ("FastAPI proxy forbidden"). While acknowledged, the ACs do not define a migration path for existing workflows relying on direct ComfyUI access. This creates a risk of "silent failure" where legacy features break without explicit error reporting in the new UI.
*   **Manager vs. Backend Roles:** The architecture introduces a Manager BE (8899) and a Main Backend (8000). AC-05 suggests restarting the backend via the UI, but AC-13 implies the app syncs state *from* the server. If the server restarts during an active session, the "resume" logic must handle re-authentication or token refresh, which is not covered in the ACs.

### 2.2 State Consistency Logic
*   **The "Offline" Paradox:** The requirement aims for resilience ("Resume after reconnect"), but AC-08 defines `OFFLINE` as a UI state when the backend stops while the screen is open. However, if the network drops (not just the server), does the app enter `OFFLINE` mode or attempt to queue requests locally? The distinction between "Server Down" and "Network Partition" is blurred in AC-10/AC-11.
*   **Queue State Ambiguity:** AC-12 states jobs are displayed based on "actual state at reconnect." If the server restarts and loses its internal job queue (stateless), how does it map local history to new server IDs? This assumes a persistent DB or external ID mapping not detailed in the requirements.

### 2.3 Network Logic
*   **Origin Restriction:** AC-30 allows `192.168.x.x` hosts, but AC-31 restricts "External Site Origin." If the app is deployed to a cloud environment later, the logic for determining "Internal vs. External" becomes complex. The current definition relies heavily on local network topology which may not hold in production.

## 3. Edge Cases & Missing Scenarios

### 3.1 Session Identity
*   **Definition of "Session":** AC-15/AC-20 rely on "Self Session" vs. "Other Sessions." It is unclear if a session is tied to a User Account, a Browser Instance, or a Device ID. If two users share one PC (same browser profile), do they see each other's jobs?
*   **Session Persistence:** AC-16 implies toggling "Self Session Only" persists the state. However, if the app refreshes or loses connection, is this preference stored locally or server-side?

### 3.2 Data Lifecycle & Limits
*   **History Truncation (AC-27):** The history is limited to 1000 items. If a user has exactly 1000 items and generates one more, the oldest is deleted immediately. However, AC-28 suggests "Snapshots" are protected separately. There is no logic for how long an item stays in "History" before becoming eligible for deletion or moving to "Snapshot."
*   **Image Resolution (AC-24):** The requirement specifies 256–512px thumbnails but does not define the aspect ratio handling if the original image is non-standard. Cropping vs. Letterboxing logic is missing.

### 3.3 Failure Modes
*   **Partial Sync:** If AC-13 (sync) fails halfway through a batch of jobs due to network instability, what state does the UI show? Does it retry indefinitely or mark specific items as "Sync Error"?
*   **Manager BE Crash:** If Manager (8899) crashes while ComfyUI is running, AC-02/AC-03 imply control via Manager. The app needs a fallback mechanism to restart ComfyUI if the Manager is unreachable but the backend (8000) is alive.

## 4. SSoT Integrity Check
*   **External Dependencies:** The requirement relies heavily on `SKILL.md` and `server_manager_guide.md`. Since these are not embedded in this PBI, any contradiction with their "Single Source of Truth" status requires a formal change request or versioning update before development.
*   **Audit Log Integrity:** The internal audit log (`ba-audit`) reports a failure (`WinError 10013`) yet concludes the document is ready for review. This suggests the automated validation pipeline itself has integrity issues, requiring manual verification of the logic described in REQ-333.

## 5. Recommendations
1.  **Clarify Session Logic:** Explicitly define "Session" (e.g., Device ID + Auth Token) to resolve AC-15/AC-20 ambiguities.
2.  **Define State Recovery:** Add ACs for how the system handles server restarts regarding job queue mapping (ID preservation).
3.  **Refine Network Rules:** Clarify if `8000` is strictly internal or if it supports external access via tunneling/proxy when deployed externally.
4.  **Policy Migration Plan:** Create a sub-task to migrate existing direct ComfyUI workflows to the new API contract without breaking user history.

**Final Verdict:** The requirement is logically sound in its functional intent but lacks robustness in state management and edge case handling. Proceed with **Draft Status**, pending clarification on Session Identity and Server State Persistence.

## 1. Logical Contradictions Analysis

### Issue #1: AC-08 vs AC-09 State Hierarchy Ambiguity
| AC | Requirement | Conflict Point |
|----|------------|----------------|
| AC-08 | Defines composite labels (READY, OFFLINE) based on multiple services | Requires all three services to be "online" for READY |

### Issue #2: Progress Recalculation Logic (AC-27 vs AC-29)
```
Scenario Trace:
├── Initial: 8 jobs, 3 completed → 3/8
├── AC-27 Cancel: Remove from pool → 3/7 (remaining = 8-1)
└── AC-29 Failure: Add to completed count → 4/8 ❌
```

**Contradiction**: If cancellation reduces denominator to 7, a subsequent failure should yield **4/6**, not 4/8. The requirement implies the cancelled job re-enters the pool after cancellation.
