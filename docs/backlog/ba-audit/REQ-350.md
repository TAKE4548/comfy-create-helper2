# REQ-350 要件監査レポート (Reasoning Gate)

## 1. 概要
REQ-350 は、マッピングシステムにおける「Seed」の扱いを静的な値から動的な生成モード（ランダム/固定）へ拡張し、バッチ生成時の挙動を定義する機能要件である。既存の生成フロー（SPEC_GENERATE.md §2-5）および設定仕様（SPEC_SETTINGS.md §4-1）との整合性を検証した結果、以下の論理矛盾、境界条件の欠落、SoT 整合性の懸念点が見出された。

## 2. 論理的矛盾と不整合 (Logical Contradictions)

### 2.1 AC-4 と AC-5 の確率論的対立
*   **事象**: AC-5 はランダムモードで「0〜4294967295」の整数を生成すると定義する（真のランダム性）。一方、AC-4 は「検証条件として 11・22・33」と特定値を出力することを要求している。
*   **矛盾点**: 真のランダム性では、特定の順序で特定値が連続して出現する確率は極めて低く、要件として「Then...使用されること」は不整合である。
*   **推論**: 「バッチ生成インデックスをシードとする擬似乱数（PRNG）」を使用している可能性が高いが、実装詳細が欠落している。AC-4 は「検証用シナリオ」としての記述であり、本質的な動作定義ではないと解釈すべきだが、仕様として曖昧である。

### 2.2 「固定」モードの増分挙動
*   **事象**: AC-3（100→101→102）および AC-6（Main:100/101, Rough:200/201）から、インデックスが 1 ずつ増加する規則が見える。
*   **矛盾点**: AC-6 の「同期なし」条件において、Main と Rough が独立してカウントされるのか、それともグローバルなシードプールを共有しているのかが不明確である。「同期なし」が既存機能（同期あり）との比較であることを示唆しているが、既存機能が何であるか文脈がない。
*   **SoT 影響**: システムの状態管理において、各ステージ（Main/Rough）が独立したカウンタを持つか、それとも階層構造を持つかが SoT に影響する。

## 3. 境界条件とエッジケース (Edge Cases)

### 3.1 整数オーバーフロー
*   **ケース**: 固定モードで Seed が最大値（例：4294967295）に達し、バッチ生成でインデックスが増加した場合。
*   **現状**: 仕様未定義。通常はラップアラウンド（0 に戻る）か、エラーになるが、ビジネスロジックへの影響（重複 Seed の発生）が不明。
*   **推奨**: 仕様書に「オーバーフロー時の挙動（ラップアラウンド/上限停止）」を明記する必要がある。

### 3.2 バッチ生成中の同時アクセス
*   **ケース**: マッピングマスタ編集画面でバッチ生成を実行中、他ユーザーが同じ Seed 設定のワークフローを変更した場合。
*   **リスク**: AC-1 で「選択が保持されること」とあるが、トランザクションレベルでの整合性（Consistency）が保証されていない。Seed の順序性が崩れる可能性がある。

### 3.3 既存マッピングへの影響 (Backward Compatibility)
*   **ケース**: 既に Seed 値を静的に設定済みのマッピングに対し、この機能を実装・適用した場合。
*   **リスク**: AC-7 で「通常 float 型には Seed 切替を追加しない」とあるが、「Seed 専用型」への移行タイミングで既存データがどう扱われるか（リセット/保持）が不明。

## 4. SoT (System of Truth) 整合性

### 4.1 「Seed 専用型」の定義欠如
*   **問題**: 「Seed 専用型」という状態が、データベーススキーマ上のフラグなのか、UI 上の表示モードなのか、ワークフローの状態遷移なのか明確でない。
*   **SoT 影響**: 後続の API 設計やデータ永続化において、この「型」をどう扱うかが決定的な要因となる。

### 4.2 既存機能との重複 (Overlap)
*   **問題**: `SPEC_SETTINGS.md §4-1` に Seed に関する設定が存在するが、REQ-350 はその一部を再定義している可能性がある。
*   **整合性チェック**: 「ランダム=32bit 乱数」という実装詳細は、既存の乱数生成ロジック（例：UUID や Timestamp ベース）と競合しないか確認が必要。

### 結論
REQ-350 は業務課題（Seed の再現性と探索性の両立）に即しているが、**「ランダム性の定義」**と**「境界値の挙動」**において論理的な抜けがある。開発着手前に、AC-4 の検証ロジックを具体化し、オーバーフロー時の挙動を SoT として確定させる必要がある。
