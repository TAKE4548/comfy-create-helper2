### REQ-417: ノードマッピング再設計：Master/Variant/判定定義の3層分離とスキャンロジック刷新

- **Type**: feature
- **Status**: done (2026-11-07)
- **Priority**: P1
- **Surface**: DB (`models.py`, `migrations/steps.py`, `seed_data.py`), Backend (`workflow_scanner.py`, `mapping_service.py`, `routers/mapping_masters.py`, `routers/workflows.py`, `routers/binding_rules.py`, `routers/node_selectors.py`), Frontend (`types.ts`, `workflowParamInjector.ts`, `seedInputResolver.ts`, `MappingMasterEditModal.tsx`, `UploadWorkflowModal.tsx`)
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: MappingMasterが値の定義と判定条件を兼ねており、roleの一意性も判定条件の組もDBで表現できていないため。
  2. なぜその課題が発生するか: `expected_class_types`、`param_name`、`fallback_param_names`が独立リストであり、「KSamplerならseed、KSamplerAdvancedならnoise_seed」といった個別ノードとパラメータの組を表現できず、param照合が候補抽出に寄与しないため。
  3. なぜ現状の仕組みで不十分か: 「どの入力か（class_type × param_name）」と「どのノードか（title pattern）」は共有の軸が異なるにもかかわらず（RuleSetは同Masterのステージ間、NodeSelectorは同ステージのMaster間）、Masterに混在しているため重複定義が発生し、タイトル照合とクラス条件が混同されているため。また解決結果のinput_nameが保存されず、フロントエンド適用時に毎回フォールバック解決しているため。
  4. なぜこのアプローチを採用するか: Master（値の意味と型）、Variant（roleの最小単位）、判定定義（BindingRuleSet: どの入力か、NodeSelector: どのノードか）の3層に分離し、判定ロジックを段階・優先度による辞書式比較に刷新することで、一意性・整合性・決定論的バインドを担保できるため。
  5. 根本原因: 初期設計において値のメタデータ定義とワークフロー上の解決ルールが1つのマスタテーブルに混在し、共有軸の違い（入力名とノードタイトル）に応じた正規化と解決結果（input_name）の永続化が行われていなかったこと。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - Master（値の意味と型）、Variant（roleの最小単位）、BindingRuleSet（入力候補の組）、NodeSelector（ノード特定条件）の3層構造により、設定情報の役割と参照関係を明確化する。
    - スキャン判定結果における段階（完全一致、部分一致、セレクタ不一致）と優先度の辞書式ソートにより、候補判定の透明性と予測可能性を向上させる。
  - **Interaction (インタラクション)**:
    - スキャン確定時に確定したノードIDと入力名（input_name）が自動バインドされ、手動選択や曖昧なフォールバックを排除する。
    - 重複候補（duplicated）や未検出（not_found）の明確な警告提示と、曖昧な場合のユーザー手動解決。
    - 設定画面で共有RuleSet/NodeSelectorを編集・削除する際、影響を受ける参照元role一覧を表示し、意図しない他ステージへの波及を防ぐための「複製して編集」機能を提供する。
  - **Visual (視覚デザイン)**:
    - Master編集モーダルをMaster編集、RuleSet編集、NodeSelector編集に分離・整理し、現在の設定と共有先を視覚的に把握可能にする。
- **Requirement**:
  - **1. 3層スキーマの定義とDBマイグレーション**:
    - テーブル新設および制約:
      - `binding_rule_sets`: `UNIQUE(name)`、参照中は削除不可
      - `binding_rule_entries`: `UNIQUE(rule_set_id, class_type, param_name)`
      - `node_selectors`: `UNIQUE(name)`、参照中は削除不可
      - `node_selector_patterns`: `UNIQUE(selector_id, pattern)`
      - `mapping_variants`: 列追加（`role NOT NULL`, `binding_rule_set_id NOT NULL`, `node_selector_id` NULL許容）、制約（`UNIQUE(role)`, `UNIQUE(master_id, stage_id)`, `UNIQUE(master_id, node_selector_id)`。※SQLiteではNULL同士は重複扱いにならないため、node_selector_idがNULLのVariantは同一master内で複数存在可能）
      - `workflow_mappings`: 列追加（`input_name NOT NULL`）、`master_id` 列削除
    - 既存データ変換:
      - 入力条件（`expected_class_types`, `param_name`, `fallback_param_names`）を展開して各Master用の `binding_rule_entries` に移行（priority 1, 2, …）。
      - タイトル条件（`title_patterns`, `extra_title_patterns`, `StageMaster.search_keywords`）を `node_selector_patterns`（exact / contains）に移行（クラス名一致はEntryへ）。
      - `MappingVariant.computed_role` を `role` 列へ永続化（重複は事前検出）。
      - `workflow_mappings.master_id` を削除し既定Variantに付け替え、`mapping_slot_states` の `m:<id>` キーを `v:<id>` に置換。
  - **2. 辞書式スキャン判定ロジックとinput_name永続化**:
    - Entry（`class_type` と入力名の組）への一致を必須条件とし、タイトルのパターンは候補の順位付けにのみ使用する。
    - 判定段階（辞書式ソート: 段階 -> Entry priority -> パターン priority -> ノードID昇順）:
      - 段階1: Entry一致 ＋ 自分のセレクタに完全一致（1件なら自動確定）
      - 段階2: Entry一致 ＋ 自分のセレクタに部分一致（`contains`）（1件なら自動確定）
      - 段階3: Entry一致 ＋ セレクタ未設定またはどのセレクタにも不一致（候補。1件なら自動確定、複数なら `duplicated` 警告）
      - 段階4: Entry一致 ＋ 同じMasterの別Variantのセレクタにのみ一致（除外）
      - 候補外: Entry不一致（除外）
    - 確定手順:
      1. VariantごとにRuleSetのEntryで候補ノードを抽出。
      2. 各候補を自セレクタおよび同Masterの他セレクタに照らして段階判定。
      3. 1つのノードが複数ステージのセレクタに一致した場合、より具体的に一致した側（完全一致 ＞ 部分一致、部分一致同士ならより長いパターン文字列）のステージに割り当てる。
      4. 同一MasterのVariantを `StageMaster.sort_order` の小さい順に確定させ、確定済みの `(node_id, input_name)` は残りのVariantの候補から除外する。
      5. 採用ノードの `node_id` と一致した入力名を `input_name` として `WorkflowMapping` に永続化する。
  - **3. フロントエンド値適用ロジックの刷新**:
    - `workflowParamInjector` および `seedInputResolver` において、保存済み `input_name` を直接使用してパラメータを注入し、実行時の古いフォールバック探索処理を廃止する。
  - **4. 共有定義のCRUD APIおよび編集UI対応**:
    - BindingRuleSet / NodeSelector の CRUD API を提供し、削除時は参照元role一覧を返す（参照中は削除不可）。
    - 設定UI（MappingMasterEditModal等）をMaster/RuleSet/NodeSelectorの各編集に分離し、参照元一覧表示および「複製して編集」をサポートする。
  - **5. 旧経路・旧カラムの段階的整理と制約付与**:
    - 動作検証後、旧スキャン分岐や不要カラム（旧系統フィールド、`WorkflowMapping.master_id`、`m:<id>` スロットキー等）を安全に整理する。
    - SQLiteはALTER TABLEでの制約後付けに対応しないため、フェーズ5において対象テーブル（`mapping_variants` 等）を再作成して上記の一意性制約（`UNIQUE(role)`, `UNIQUE(master_id, stage_id)`, `UNIQUE(master_id, node_selector_id)`）および NOT NULL 制約を物理適用する。
- **Acceptance criteria**:
  - [ ] AC-1: Given 既存の旧マスタ定義を含むDBにおいて, When マイグレーション（フェーズ2）が実行されたとき, Then 新テーブル（binding_rule_sets, node_selectors等）が作成され、既存の入力判定・タイトル判定条件が新構造へ無損失で移行され、MappingVariantが新定義を参照していること
  - [ ] AC-2: Given BindingRuleSetに (class_type, param_name) の組が定義された状態でワークフローをスキャンしたとき, When ワークフロー内のノードがEntry条件に一致した場合, Then ノードタイトルとNodeSelectorPatternの一致段階（完全一致＞部分一致＞セレクタなし）および優先度に基づく辞書式判定により、最適な (node_id, input_name) が決定論的に選定され、WorkflowMappingに保存されること
  - [ ] AC-3: Given 同一Masterで複数のStage/Variantが存在する状態で、同一ノードが複数ステージのセレクタに一致した場合, When スキャンを実行したとき, Then より具体的に一致した側のステージ（完全一致 ＞ 部分一致、部分一致同士なら長いパターン文字列）に割り当てられ、StageMaster.sort_order 順に確定された (node_id, input_name) は残りのVariantの候補から除外されること
  - [ ] AC-4: Given スキャンにより確定されたワークフローにおいて, When 生成パラメータ注入（workflowParamInjector / seedInputResolver）を実行したとき, Then WorkflowMappingに保存されたinput_nameが直接使用され、実行時フォールバック再解決なしに正しいノード・入力スロットへ値が注入されること
  - [ ] AC-5: Given 設定画面において共有されているBindingRuleSetまたはNodeSelectorを編集・削除しようとしたとき, When 編集画面を開くまたは削除操作を行ったとき, Then その定義を参照しているroleの一覧が表示され、参照中の削除は拒否されるか、または「複製して編集」により安全に切り離せること
  - [ ] AC-6: Given フェーズ5の旧経路削除と制約付与が完了したDBにおいて, When mapping_variants テーブルに同一の role 文字列（NOT NULL）を持つレコードを重複登録しようとしたとき, Then mapping_variants テーブルの UNIQUE(role) 制約により重複が拒否されエラーとなること
  - [ ] AC-7: Given フェーズ5の旧経路削除と制約付与が完了したDBにおいて, When 同一の master_id に対して重複する stage_id または重複する non-NULL の node_selector_id を持つ mapping_variants レコードを登録しようとしたとき, Then mapping_variants テーブルの UNIQUE(master_id, stage_id) および UNIQUE(master_id, node_selector_id) 制約により重複が拒否され、node_selector_id が NULL の Variant のみ同一 master_id 下で複数共存できること
- **Inferred points**:
  - `node_selector_id` が NULL のVariantは「タイトル条件なし（Entry一致のみ）」として許容し、1ノードのみ存在すれば自動確定、複数ノード存在すれば duplicated 警告としてユーザーに選択させる。
  - RuleSet の各 Entry が持つ型と Master の `input_type` の整合性は、バリデーションまたはUI保存時チェックにより担保する。
  - `StageMaster.search_keywords` は移行時に各ステージのセレクタパターンに `contains` として取り込み、セレクタ未設定時の補助または後方互換として段階的に整理する。
  - プリセットやスナップショット等の既存の role 文字列参照は本PBIではそのまま維持し、Variant の永続化 `role` 列で一意性を保証する。`variant_id` 参照への完全切り替えは後続PBI（REQ-418）として分離・起票する。
  - 移行計画の全5フェーズ（1. 準備 → 2. スキーマ追加・変換 → 3. スキャナ・API切替 → 4. 編集UI切替 → 5. 旧経路削除と制約付与）を本PBI内で一気通貫で実装・検証・完了させる。
