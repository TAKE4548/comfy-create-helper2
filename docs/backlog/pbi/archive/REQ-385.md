### REQ-385: 生成完了プレビュー表示遅延およびジョブキャンセル処理の遅延解消

- **Type**: bug (Type A: Implementation Defect)
- **Status**: done (2026-10-20)
- **Priority**: P1
- **Surface**: backend/app/services/generation_service.py, backend/app/services/comfy_generation_bridge.py, frontend/src/components/JobManagementModal.tsx
- **Incident Report**: docs/incident_report.md
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: 画像生成完了からプレビュー（生成結果）が表示されるまでに約2.5秒の著しい遅延が発生し、またジョブのキャンセル操作（待機中および実行中）の反映も異常に遅いため。
  2. なぜその課題が発生するか: 
     - プレビュー遅延: ComfyUIは完了時にWebSocketで `execution_success` を送らず `executing` (node: null) を送るが、バックエンドが `execution_success` のみで完了処理を行い `executing` (node: null) を無視しているため。
     - キャンセル遅延: FE側で待機中ジョブ削除に3秒タイマーが介在しているほか、BE側で中断前に冗長な `queue()` 問い合わせを多重実行し、サンプラー停止直後に同期照会して未確認（unconfirmed）となり2.5秒ポーリング待ちになるため。
  3. なぜ現状の仕組みで不十分か: リアルタイムWebSocket通知が機能せず、バックグラウンドワーカーのフォールバックポーリング周期（_RECONCILE_SECONDS = 2.5秒）に依存しているため、ユーザー体験上耐え難い待ち時間となっている。
  4. なぜこのアプローチを採用するか: ComfyUIの正規の完了イベント `executing` (node: null) を即時検知してhistory取得・succeeded遷移を行い、キャンセル処理における冗長なHTTP呼び出しと不必要な待機を削減・即時反映化するため。
  5. 根本原因: REQ-333設計時にComfyUIがWebSocket上で `execution_success` を送信するという誤った前提で実装・テスト（合成イベントによるモックテスト）が作成され、実際のComfyUIプロトコルとの不整合がフォールバックポーリングで隠蔽されていたこと。またキャンセル処理における過剰な同期確認シーケンス。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - ジョブ完了ステータスおよび出力画像URLをComfyUI終了直後に即座に確定・配信する。
  - **Interaction (インタラクション)**:
    - 生成完了と同時にプレビュー画像が1秒未満（即時）で切り替わり、体感待機時間を大幅に短縮する。
    - キャンセル操作時、待機中・実行中ともに無駄な待機なく速やかに取り消し結果を反映する。
  - **Visual (視覚デザイン)**:
    - 生成ステップ100%後のスピナーや古いプログレスバーが長く残り続ける問題を解消する。
- **Requirement**:
  - **1. WebSocket `executing` (node: null) による即時完了ハンドリング**:
    - `GenerationService.on_event` において、`event_type == 'executing' and data.get('node') is None` を検知した契機で即時に upstream history を照会し、job を `succeeded` へ遷移させてスナップショットを配信する。
  - **2. キャンセル処理の高速化と冗長通信削減**:
    - `ComfyGenerationBridge.interrupt()` 内の冗長な二重 `await self.queue()` 呼び出しを整理・削減する。
    - `GenerationService._cancel_single` において、interrupt送信後の同期待ちでロックを不必要に滞留させず、`execution_interrupted` イベント受信時および完了検知時に即座に `cancelled` 状態を配信する。
    - `JobManagementModal.tsx` の単件待機キャンセルにおける3秒遅延タイマー（取消予約）を即時実行へ見直すか、意図的なUndo猶予として最小限の挙動に最適化する。
- **Acceptance criteria**:
  - [ ] AC-1: Given ComfyUIでジョブが実行中である, When ComfyUIから `executing` (node: null) WebSocketイベントが届く, Then 2.5秒ポーリングを待つことなく即時に history が照会され、該当ジョブが `succeeded` に遷移し出力画像URLを含むスナップショットが配信されること。
  - [ ] AC-2: Given 生成が完了した直後, When フロントエンドが `succeeded` スナップショットを受信する, Then 自動追従（auto-follow）により1秒以内に最終生成プレビューが表示されること。
  - [ ] AC-3: Given 実行中のジョブに対して中断（cancel/interrupt）を実行する, When `interrupt` がリクエストされる, Then 冗長な多重 `queue()` 通信を行わず速やかにComfyUIへ中断要求が送信され、中断完了時に遅滞なく `cancelled` が反映されること。
  - [ ] AC-4: Given 待機中ジョブをキューから削除する操作を行う, When キャンセルボタンを押下する, Then 不要な遅延なく即時にキャンセルリクエストが送信されキューから除外されること。
- **Inferred points**:
  - `execution_success` は将来の互換性のためハンドラ自体は残して問題ないが、主要パスは `executing` (node: null) とする。
  - 待機キャンセル3秒タイマーの撤廃または最適化に伴い、`JobManagementModal` のUIステータス表示（「取消予約（3秒後）」）も整合を取る。
