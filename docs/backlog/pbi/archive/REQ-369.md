### REQ-369: ノードリマッピング時の孤立マッピング引き継ぎ排除・自動入力確定抑止およびDB孤立レコード修復

- **Type**: bug (Type A: Implementation Defect)
- **Status**: done (2026-10-16)
- **Priority**: P1
- **Surface**: Frontend (`useMasterMappingRows.ts`, `RescanModal.tsx`), Backend (`workflows.py`, `migrations/steps.py`)
- **Incident Report**: `docs/incident_report.md`
- **5 Whys / Root Cause**:
  1. なぜ生成画面に大量の「マッピングエラー検出」が表示されるか: ワークフローの `mappings` に `role == null` となるレコードが多数含まれているため。
  2. なぜ `role == null` となるレコードが存在するか: `mapping_masters` から削除済みの旧マスタID（33〜62）を参照する孤立レコードが `workflow_mappings` に存在し、`variant` も `master` も解決できないため。
  3. なぜノードリマッピング後にそのエラーが顕在化・再保存されるか: `useMasterMappingRows.getMappings()` が `knownKeys` に含まれない `storedMappings.current` の要素を実在確認なしに無条件で引き継ぎ保存し、かつ未割り当てスロットに `scanDefaults` を自動代入して保存するため。
  4. なぜDBとAPIで孤立レコードが排除されなかったか: SQLiteで外部キーCASCADEが発火せず `step_029` でも実在マスタのみを更新対象とし、さらに `PUT /api/workflows/{id}` でも `master_id` / `variant_id` の実在性を検証していなかったため。
  5. 根本原因: フロントエンド保存時の未知キー引き継ぎ処理におけるマスタ/バリアント実在性チェックの欠如、既存ワークフロー再スキャン時の未割り当てスロットへの自動確定代入、バックエンド更新時の外部キー整合性検証欠如、およびDBマイグレーションでの孤立レコード未清掃の複合要因。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 有効なマスタ・バリアントに紐づくマッピングのみを保持・表示し、削除済み旧マスタの孤立レコードによる誤警告を排除する。
  - **Interaction (インタラクション)**:
    - 既存ワークフローのリマッピングでは、既存割当がないスロットに対してスキャン候補を無操作のまま自動保存せず、明示的に選択・入力されたスロットのみを保存する（新規ワークフロー登録時はスキャン初期値採用を維持）。
  - **Visual (視覚デザイン)**:
    - 変更なし（既存の `RescanModal` および `MappingErrorPanel` の視覚仕様を維持）。
- **Requirement**:
  - **1. フロントエンド孤立マッピング引き継ぎの排除**:
    - `useMasterMappingRows.ts` の `getMappings()` において、`storedMappings.current` から引き継ぐレコードは現在のマスタ定義（`allDefinitions` / `masters`）に実在する `master_id`（および指定時は実在する `variant_id`）を持つものに限定し、存在しない旧マスタIDの孤立レコードを除外する。
  - **2. 既存ワークフロー再スキャン時の未割り当てスロット自動確定抑止**:
    - 既存ワークフローのリマッピング（`RescanModal` 等で `existingMappings` が与えられる場合、または再スキャンモード）において、保存済み割当が存在しないスロットに `scanDefaults` を自動代入して無操作で保存対象にすることを抑止する（候補リスト `candidates` は維持し、ユーザーが選択可能とする）。※新規登録（`UploadWorkflowModal`）での初期スキャン自動割当は維持する。
  - **3. バックエンド保存時のマスタ・バリアント実在性検証**:
    - `PUT /api/workflows/{workflow_id}` および `POST /api/workflows` において、`mappings` ペイロード内の各要素の `master_id` が `mapping_masters` に実在すること、および `variant_id` 指定時は `mapping_variants` に実在し `master_id` と整合することを検証し、孤立・不整合レコードを保存しない（またはバリデーションエラー/サニタイズする）。
  - **4. DBマイグレーションによる既存孤立レコードのクリーンアップ**:
    - マイグレーションステップ（`step_031`）を追加し、`workflow_mappings` テーブル内の `master_id` が `mapping_masters` に存在しない孤立レコード（および `variant_id` が `mapping_variants` に存在しない不整合レコード）を安全に削除・正規化する。
- **Acceptance criteria**:
  - [ ] AC-1: Given `storedMappings` に `mapping_masters` に存在しない `master_id`（孤立レコード）が含まれる状態, When `useMasterMappingRows` で初期化・`getMappings()` を実行したとき, Then 存在しない `master_id`（または不整合な `variant_id`）を持つ孤立レコードが結果から除外され、有効な休止/非表示マスタの既存割当は引き続き保持されること
  - [ ] AC-2: Given 既存マッピングを持つワークフローの `RescanModal` を開いた状態, When 未割り当てスロットに対してユーザーがノード選択を行わずに保存したとき, Then スキャン候補（`scanResult.matched` / `warnings`）が存在しても未割り当てスロットに自動的にノードIDが確定・追加保存されないこと
  - [ ] AC-3: Given 新規ワークフローのアップロード（`UploadWorkflowModal`）, When スキャン結果が返却されたとき, Then 従来通りスキャンでマッチした候補ノードが初期値として自動設定され保存可能であること
  - [ ] AC-4: Given バックエンドのワークフロー更新（`PUT /api/workflows/{id}`）, When ペイロードの `mappings` に存在しない `master_id` または不整合な `variant_id` が含まれるとき, Then 不正なレコードが `workflow_mappings` に永続化されないこと
  - [ ] AC-5: Given `mapping_masters` に存在しない `master_id` を参照する孤立レコードが `workflow_mappings` に残存しているDB, When マイグレーションを実行したとき, Then 孤立レコードが削除され、有効なマッピングレコードおよびワークフロー設定は損なわれずに保持されること
- **Inferred points**:
  - 意図的に無効化（`enabled: false`）された実在マスタ・バリアントの保存済みマッピングを保持する REQ-358 の仕様は維持しつつ、マスタ自体が存在しない孤立参照のみを排除する。
