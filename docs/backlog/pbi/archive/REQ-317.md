### REQ-317: 生成時メタ情報キャッシュの保持適正化とブラウザ保存領域の使用量可視化

- **Type**: feature
- **Status**: done (2026-10-05)
- **Current step**: User-accepted closure

- **Closure acceptance (2026-10-05)**: ローカルQA監査の推奨1・2を試験計画へ反映。実ブラウザ試験はユーザー指示により手動前提。開発用WebSocket転送設定の修正後、ユーザーがシステム指標の表示を確認し「クローズしよう」と指示。未検証の手動項目・BA監査の限界は `docs/walkthrough-REQ-317.md` に残してクローズする。
- **User wish**: localStorageの容量圧迫に対し、添付の方針で改修したい。
- **Operational need**: 古い生成時メタ情報による容量圧迫と保存失敗を軽減し、連続生成と記録済み生成条件の参照を継続できること。

#### 5 Whys / 背景

1. なぜ容量圧迫を解消したいか: 添付で生成成功時にも保存失敗通知が頻発すると報告されているため（資料申告、現環境は未検証）。
2. なぜ生成成功だけでは足りないか: 画像ごとの生成条件を後から確認する必要があるため（REQ-227 / REQ-316）。
3. なぜ大量保持を見直すか: 直近の画像はブラウザ、過去画像はサーバー記録を参照する方針だから（資料に基づく整理）。
4. なぜ単なる件数削減だけでは足りないか: 既存の容量限界付近の利用者も次回生成で回復する必要があるため（資料に基づく整理）。
5. なぜ運用要件とするか: 生成を続けながら、画像と生成条件を取り違えず振り返れる状態を維持するため（推論）。

#### UX Classification

- **Information Design（情報設計）**: 整理後も対象画像の記録済み生成条件を正しく表示する。
- **Interaction（操作）**: 手動の保存領域整理なしで連続生成と履歴参照を続ける。
- **Visual（視覚）**: 新しい装飾・配置の変更は要求しない。

#### Requirement

- 対象は `prompt-surgeon-meta-*` の生成時メタ情報キャッシュのみ。保持上限を200件から30件へ変更する。
- 添付の方針に従い、新規記録の保存枠を先に確保し、初回生成時に既存超過分も整理する。API・具体的アルゴリズムは設計へ委ねる。
- 記録timestampが新しい順の30件を保持する。閲覧で順位を更新するアクセスLRUとは区別する。新規記録は最新として扱う。
- 同一ID更新は1件。既存記録のtimestamp同値の場合の順位は指定しないが上限と新規記録の保持は満たす。
- 読取不能・timestamp欠落の記録は正常記録より整理を優先する。
- キャッシュヒットはメタ情報ネットワーク応答を待たず参照できる。キャッシュ外はサーバーに記録があり取得成功時に表示する。
- ローカルとサーバーの一方の保存失敗で他方を停止しない既存仕様を維持する。
- SPEC_GENERATE / SPEC_HISTORYの生成時メタ情報local200件は30件への改訂対象。server1000件と画像履歴・設定・保存済みスナップショットは変更しない。文書の「履歴上限」と対象キャッシュを設計時に区別する。
- 重複圧縮、保存方式全面変更、サーバー保持数変更、未記録データの復元は対象外。

#### Acceptance Criteria (AC)

独立試験で確認する。件数は対象キャッシュの画像ID異なり数。AC-1〜5・10・13・14は対象キャッシュの読み書き・整理が成功する通常条件を前提とする。

- [ ] AC-1: Given キャッシュ0件で新規記録を保存可能な容量がある, When 新規画像の生成が受け付けられる, Then その画像の生成時メタ情報が1件保持される。
- [ ] AC-2: Given timestampが異なる既存29件があり新規画像はそれらより新しい, When 新規画像の生成が受け付けられる, Then 既存29件と新規1件の計30件が保持される。
- [ ] AC-3: Given timestampが異なる既存30件があり新規画像はそれらより新しい, When 新規画像の生成が受け付けられる, Then 最も古い既存1件が外れ、新規画像を含む新しい30件が保持される。
- [ ] AC-4: Given 改修前のtimestampが異なる既存200件があり新規画像はそれらより新しい, When 改修後の初回生成が受け付けられる, Then 新規画像と最新の既存29件だけが保持される。
- [ ] AC-5: Given キャッシュ30件の画像Aを更新し更新timestampは最も新しい, When 更新が完了する, Then Aは更新後の値で1件だけ保持され他の29画像も保持される。
- [ ] AC-6: Given 既存30件によって容量が不足し最古1件の除外で新規記録と生成受付に伴う他のブラウザ記録を保存可能になり、サーバー保存も成功する, When 新規画像の生成が受け付けられる, Then 「生成時メタ情報の保存に失敗しました」の通知は表示されない。
- [ ] AC-7: Given 異なる生成条件を記録したキャッシュ内の画像AとBがありメタ情報ネットワーク応答を保留している, When AからBへプレビューを切り替えてメタ情報を開く, Then 応答を待たずBの記録済み生成条件が表示される。
- [ ] AC-8: Given キャッシュ外の画像Aの生成条件がサーバーに記録済みでスナップショットは未保存, When Aのメタ情報取得が成功する, Then 記録済みプロンプト・アスペクト比・実使用シード・ステップ数が記録値と一致して表示される。
- [ ] AC-9: Given 画像Aのキャッシュとサーバー記録がなく現在入力に別画像用の値がある, When Aのメタ情報を開く, Then 現在の入力値はAの生成条件として表示されない。
- [ ] AC-10: Given 超過キャッシュと設定値・画像履歴・保存済みスナップショットの試験データがある, When 生成受付に伴う整理が完了する, Then 対象キャッシュ以外の試験データは整理前と一致する。
- [ ] AC-11: Given ブラウザ保存は容量不足で失敗しサーバー保存は成功する, When 新規画像の生成が受け付けられる, Then その画像のメタ情報はサーバーから取得できる。
- [ ] AC-12: Given サーバー保存は失敗しブラウザ保存は成功する容量がある, When 新規画像の生成が受け付けられる, Then その画像のメタ情報はキャッシュから参照できる。
- [ ] AC-13: Given キャッシュ30件のうち1件が読取不能で他29件はtimestampが異なる正常記録で新規記録を保存可能な容量がある, When 新規画像の生成が受け付けられる, Then 読取不能1件が外れ正常29件と新規1件が保持される。
- [ ] AC-14: Given キャッシュ30件のうち1件がtimestamp欠落で他29件はtimestampが異なる正常記録で新規記録を保存可能な容量がある, When 新規画像の生成が受け付けられる, Then timestamp欠落1件が外れ正常29件と新規1件が保持される。

#### Inferred points

<inferred_points>

- 30件は画像ID単位のメタ情報上限。初回生成前の既存超過状態に遡及適用しない。
- timestamp順を採用。同一ID更新・同時刻・破損記録は補足した仮定。
- 初回200件と新規1件から30件を残す場合、既存171件を除外する。「約170件」は概算。
- 約85%削減、1.5MB、0ms、全条件でエラー0%、全過去記録の無損失は保証しない。データサイズ・他保存値・環境・サーバー保存成功と保持期限に依存する。
- サーバー未保存・削除済みの画像は復元できない。保存失敗状態でキャッシュ除外されれば記録を失う可能性がある。既存非同期保存を超える無損失保証や削除前の保存確認は追加しない。この制約を人間レビューで確認する。
- 重複圧縮は今回対象外。バッチでもID単位で上限を満たす。複数タブ同時更新の瞬間の厳密な上限保証は要求せず、単一タブの各受付完了状態を検証する。
- 添付のApproved表示は今回のPBI承認ではない。実装コード例は設計案、測定値は資料申告として扱う。

</inferred_points>

#### 追加要望（2026-10-05）: リソースモニタへの保存領域使用量表示

- **User wish**: 合わせて、localStorage/SessionStorageの使用量もリソースモニタへの表示項目に追加しておきたい。
- **Operational need**: キャッシュ整理後の容量変化や再び増加した状態を、開発者ツールなしで把握すること（推論）。
- **5 Whys整理**: 使用量を知りたい → 容量圧迫を早く認識したい → 手動調査だけでは通常作業中に確認しにくい → 既存リソースモニタで他指標と確認したい → 連続生成時の保存状態を継続把握したい（最初はユーザー要望、以後は仮定）。
- **UX**: Information Designは2種類の保存領域と使用量の意味の区別、Interactionは作業中の自動更新、Visualは既存モニタ内でのラベル付き表示。
- デスクトップHUDとモバイルリソース表示の双方を対象と仮定。CPU/GPU/RAM/VRAMも引き続き参照できる。
- localStorageは現在オリジン、sessionStorageは現在オリジンの現在タブの全キー・全値が対象。メタ情報キーだけでなく設定等も含む。別オリジン・別タブのsessionStorageは合算しない。
- 使用量は各キーと値のUTF-16コード単位数の合計に2 bytesを乗じた**推定使用量**。実ファイルサイズ・実クォータ消費・ブラウザ全体の空き容量と同一とは扱わない。推定であることと対象範囲をUIから確認できる。
- 1 KiB = 1024 bytes、1 MiB = 1048576 bytes。1 MiB未満はKiB、それ以上はMiB、小数点以下1桁に四捨五入して表示する。真の空領域は0.0 KiBと表示する。
- 読取拒否・列挙失敗・計測失敗の領域は「取得不可」と表示し、0や部分合計を正常値として表示しない。他方の正常な領域は参照できる。
- SPEC_GENERATE 2-10の2.5秒更新周期に沿い、表示中・アクティブタブ・計測が正常に完了する条件で初回表示と各2.5秒更新機会に現在量を反映する。非アクティブ時は即時性を保証せず、復帰後の最初の更新機会に再計測する。サーバー応答の到着に依存させない（ブラウザ内の利用量であるため、仮定）。
- 固定10MB上限、使用率%、空き容量、警告閾値は導入しない。保存内容をモニタ表示に出さず数値と状態のみ示す。

#### 追加 Acceptance Criteria (AC)

- [ ] AC-15: Given 現在オリジンのlocalStorageと現在タブのsessionStorageが読取可能, When リソースモニタを表示する, Then 「localStorage」と「sessionStorage」が別項目として表示される。
- [ ] AC-16: Given localStorageの全キー・値が合計524288 UTF-16コード単位、sessionStorageが合計1024単位である, When 計測が完了する, Then それぞれ「1.0 MiB」「2.0 KiB」の推定使用量が表示される。
- [ ] AC-17: Given 別オリジンのlocalStorageと別タブのsessionStorageにもデータがある, When 現在のモニタの計測が完了する, Then 表示値は現在オリジンのlocalStorageと現在タブのsessionStorageのみから算出した期待値と一致する。
- [ ] AC-18: Given 一方の保存領域は読取拒否され他方は正常に計測可能, When 計測が完了する, Then 拒否された項目は「取得不可」、他方は正常な推定使用量を表示する。
- [ ] AC-19: Given 保存領域が正常に読取可能で全キーが0件, When 計測が完了する, Then 該当項目は「0.0 KiB」を表示する。
- [ ] AC-20: Given アクティブタブでモニタ表示中に保存領域のキーや値を追加・更新・削除し計測が正常に完了する, When 次の2.5秒更新機会が完了する, Then 該当項目は変更後の推定使用量を表示する。
- [ ] AC-21: Given 非アクティブ中に現在オリジンのlocalStorageが変更された, When タブへ復帰し最初の更新機会の計測が正常に完了する, Then 変更後の推定使用量を表示する。
- [ ] AC-22: Given デスクトップまたはモバイルでモニタを表示できる, When 保存領域の項目を確認する, Then 対象オリジン・現在タブの区別とUTF-16換算の推定値である旨を確認できる。
- [ ] AC-23: Given CPU/GPU/RAM/VRAMの正常な試験値がある, When 保存領域の項目を加えたモニタを表示する, Then 既存4指標のラベルと試験値も参照できる。

#### 追加スコープの仮定・関連要件

<inferred_points>

- 使用量表示はキャッシュ容量対策の効果と継続状態の確認という同じ運用目的で本PBIへ含める。キャッシュ適正化と表示追加は個別に検証できるようACを分け、設計で独立タスク化することを想定する。
- 2026-10-05のユーザー確認: REQ-312の目的は余分な表示を削ってスリム化すること。3行にすること自体は目的ではなく、今回の必要な使用量表示に伴う行数増加は許容する。全体3行固定は適用しない。既存4指標と追加2項目を重複なくコンパクトに表示し、具体的な配置は設計へ委ねる。この方針はユーザー確認済みであり、未解決の要件衝突として扱わない。
- 2.5秒は既存文書にある監視周期を採用した仮定。更新周期を独立させるという実装手段は指定しない。
