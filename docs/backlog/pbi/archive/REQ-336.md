### REQ-336: Prompt Surgeon: ワークフローマッピング新アーキテクチャ統合（2軸正規化・動的Role・拡張可能適応型UI）

- **Type**: feature
- **Status**: done (2026-10-11)
- **Priority**: P2
- **Surface**:
  - `backend/app/models/` (MappingGroupMaster, StageMaster, MappingMaster, MappingVariant, WorkflowMapping)
  - `backend/app/services/` (マッピング管理・動的Role導出・データ駆動ステージ判定・カスケード一括置換サービス)
  - `backend/app/routers/` (マッピンググループ・ステージ・マスター・バリアントAPIエンドポイント)
  - `frontend/src/features/settings/` (MappingMasterSection, グループ管理モーダル, ステージ管理モーダル, バリアント統合編集モーダル, ClassTypeチップ入力/候補パレット)
  - `frontend/src/features/workflow/` (ワークフロー配線画面・データ駆動ステージ適応型配線UI)
- **5 Whys / Root Cause**:
  1. **なぜ新設・改修が必要か**: 近年の多段階サンプリング（Rough/Detail、3段以上のRefiner）、リージョン分け（Region Conditioning）、タイルアップスケール、複数パーツディテイラー等の多様かつ高度なComfyUIワークフローを登録する際、固定的なマッピング設定や自動検出が破綻しているため。
  2. **なぜその課題が発生するか**: 「1つの物理ノード入力 ＝ 1つのマスターレコード」というフラット構造を採用しており、同一パラメータ（steps, cfg, プロンプト等）がステージごとに別行として重複定義され、マスターレコードが40〜50件超に肥大化しているため。また、ステージ種別がコードや固定仕様に縛られており、未知のワークフロー構成に対応できないため。
  3. **なぜ現状の仕組みで不十分か**: クラス型や引数の変更時に各ステージの行を個別に修正する手間が生じ、設定画面が1列の長大なリストとなって一覧性・並び替えが困難になり、3段サンプラやリージョン別ワークフローを導入するたびにマスタやコードの個別修正が必要となるため。また、クラス名の手動入力でタイポが発生しやすい構造のため。
  4. **なぜこのアプローチを採用するか**: 「セマンティックロール（普遍的親定義）× ステージ（ユーザー拡張可能な適用工程マスタ）」の2軸正規化を行い、交差エンティティ（バリアント）で結ぶことで、親定義を集約しつつ、マスタの追加・編集のみで任意のN段サンプラやリージョン分割等の未知のワークフローにも柔軟に適応でき、設定画面でチップ入力と代表的候補パレットにより入力ミスを抑制できるため。
  5. **根本原因 (Root Cause)**: パラメータの普遍的性質と実行ステージが単一のRole文字列として密結合しており、ステージの概念がオープン拡張可能なマスタとして独立定義されておらず、クラス型や検索キーワードの直感的なチップ入力・候補提示UIが欠落していたこと。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 「大カテゴリ（Group）」「普遍的親定義（Master）」「ユーザー拡張可能な適用工程（Stage）」「交差紐付け（Variant）」の4層構造による情報整理。
    - 1段/2段サンプラにとどまらず、3段以上のサンプラ構成やリージョン分割（Region Conditioning）等、任意のワークフロー構成をマスタ駆動で表現可能なオープンデータモデル。
    - 設定画面（純粋な物理配線定義）と生成画面（実行時ParamSync制御）の責務分離。
    - ワークフロー内の全ノードメタデータと各StageMasterの検索キーワードを照合し、該当ノードが存在するステージのみを動的展開する完全データ駆動型アダプティブ・ステージング判定。
  - **Interaction (インタラクション)**:
    - ユーザーがステージ管理画面から任意の新規ステージ（例: 3段目サンプラー、リージョン別プロンプト等）を随時追加・編集・定義可能。
    - グループタブによるマッピングマスタ一覧のカテゴリ別絞り込み表示。
    - チップ式入力（Enter/カンマ）による期待Class Types・検索キーワードの追加・削除、および代表的候補パレット（+ PrimitiveStringMultiline, + BasicScheduler, + SamplerCustom, + KSampler, + FaceDetailerPipe, + UltimateSDUpscale 等のワンクリック追加）による直感的な入力支援。
    - ステージ接尾辞変更時の影響範囲事前検証・変更差分プレビューおよびトランザクション一括置換（Cascade Rename）。
    - 組み込み保護（is_builtin）および参照中保護（usage_count > 0）による3重削除ガードと論理非表示（is_active）推奨フロー（非活性化時は紐づくバリアントも連動して非表示化）。
    - ワークフロー配線画面における動的ステージタブ切り替えとノード割り当て操作。
  - **Visual (視覚デザイン)**:
    - 1行に「通常」「Rough」「Detail」「Region」等の各ステージバリアントがバッジ表示でコンパクトに同居する統合テーブル。
    - ワークフローノードとの合致状態（完全一致、複数合致警告、未合致）のリアルタイム視覚フィードバック（色分けバッジ）。
    - 存在しないステージのスロットは自動非表示となり、余分な空欄や警告のない洗練されたレイアウト。
    - Prompt Surgeon公式デザインルール（SPEC_COMMON.md / SPEC_SETTINGS.md、shadcn/ui、Tailwind CSS）に完全準拠したダークテーマUI。
- **Requirement**:
  - **1. 2軸正規化データモデルと動的Role導出（Backend/DB）**:
    - `mapping_group_masters`, `stage_masters`, `mapping_masters`, `mapping_variants` の4層リレーショナルモデルを導入すること。
    - `stage_masters` はユーザーが任意の工程（1段/2段/3段サンプラ、各種リージョン、各種ディテイラー等）を追加・編集可能なオープンモデルとし、`key`, `name`, `suffix`, `search_keywords`, `is_builtin`, `is_active` を保持すること。
    - `mapping_variants` は `custom_role_override`（任意文字列カラム）を保持し、未設定時は親の `base_key` とステージの `suffix` から動的に `computed_role` を導出し、設定時はオーバーライド値を優先すること（循環参照のない単方向導出）。
    - 実ワークフローとの物理配線（`workflow_mappings`）は数値の `variant_id` で結合し、Role名やサフィックスの変更で配線が切断されない構造とすること。
    - 既存の `mapping_masters` データを欠損なく安全・冪等（Dry-run検証付き）に自動移行し、異常時は即座にロールバックされるアトミックなマイグレーションを提供すること。
  - **2. ステージマスタ編集時の一括置換（Cascade Rename）と排他制御・履歴保護**:
    - ステージの接尾辞（suffix）変更時、行ロック（排他制御）を伴う単一トランザクション内で、影響を受けるバリアント、ワークフロープリセット（`param_values`）、スナップショット（`params`）のRoleキーを一括置換すること。
    - 保存前に変更対象件数と差分プレビューを提示し、ユーザーの確認を経て実行すること。
    - 外部保存済みPNG画像（DB外）の互換性保護のため、`stage_masters.previous_suffixes` に過去の旧接尾辞履歴（上限付きJSON配列、直近10件）を保持し、未知キー読み込み時に履歴チェーンを用いたフォールバック解決（履歴外の場合はbase_keyによるグレイスフル解決）を行うこと。
    - システム既定（is_builtin）および参照中（usage_count > 0）のマスタに対する削除ブロック、および安全な論理非表示（is_active=False）をサポートすること。非活性化時は紐づくバリアントも連動して非活性化されること。
  - **3. Settings画面の統合マッピング管理UIとClass Typesチップ入力・候補パレット（Frontend）**:
    - マッピングマスタ設定を大カテゴリタブ（プロンプト系、サンプラー系、モデル・基盤等）で整理し、1設定グループに対して全ステージのバリアントを同居表示するテーブルを提供すること。
    - 編集モーダルにおいて、共通設定（親の型・引数・期待クラス・基本検索パターン）とバリアント一覧を1画面で統合編集可能とすること。
    - 期待Class Typesの入力欄において、チップ式入力（Enter/カンマで追加、✕で削除）および主要ノードクラスの候補パレット（+ PrimitiveStringMultiline, + BasicScheduler, + SamplerCustom, + KSampler, + FaceDetailerPipe, + UltimateSDUpscale 等をクリックで即時追加）を提供し、手動入力のタイポ防止と直感的な入力を両立すること。
    - 検索パターンのチップ式入力UIと、ワークフローノードとのリアルタイムマッチング検証ボックスを提供すること。
    - グループ管理モーダルおよびステージ管理モーダル（ユーザー独自のステージ追加・編集・差分プレビュー・削除ガード付き）を提供すること。
  - **4. ワークフロー配線画面の完全データ駆動型アダプティブ配線UI（Frontend）**:
    - ハードコードされた1段/2段の分岐ではなく、登録されている全 `stage_masters` の `search_keywords` とワークフローノードのメタ情報を動的に走査・照合すること。
    - ワークフロー内に合致するノードが存在するステージ（および常に表示すべきシステム必須ステージ）のみを動的にタブ/セクションとして展開し、該当ノードが存在しないステージ（count==0）やバリアントが未定義の空ステージは自動的に非表示化すること。
    - 3段以上のサンプラ構成やリージョン分割（Region Conditioning）等、新形式のワークフローであっても、マスタにステージを追加・設定するだけでコード変更なしに自動認識・マッピング可能とすること。
    - 存在しないステージの空欄や不要な未割当警告を排除し、各スロットへのノード割り当て・自動判定理由を明瞭に表示すること。
- **Acceptance criteria**:
  - [ ] AC-1: Given 既存のマッピングマスタと配線データが存在する環境, When 冪等なDBマイグレーションを実行したとき, Then 既存データがグループ・親マスター・ステージ・バリアントへ欠損なく2軸正規化され、既存ワークフローの物理配線および生成機能が同一挙動を維持し、失敗時は安全にロールバックされること。
  - [ ] AC-2: Given 設定ページのマッピングマスタ管理画面を表示したとき, When 大カテゴリタブ（プロンプト系、サンプラー系など）を切り替える, Then 該当カテゴリの親設定のみが絞り込まれ、同一行内に紐づくステージバリアント群（通常、Rough、Detail、カスタムステージ等）が集約表示されること。
  - [ ] AC-3: Given マッピングマスタ編集モーダルを開いたとき, When 期待Class Typesまたは基本検索パターンをチップ入力で追加・削除して保存する, Then 配下の全有効バリアントに共通設定が一元反映され、ワークフローノードとの自動合致プレビューがリアルタイムに更新されること。
  - [ ] AC-4: Given 親定義に対してバリアントを追加・変更するとき, When 対象ステージを選択する, Then `computed_role`（base_key + suffix、またはcustom_role_override）が単方向で動的に導出され、一意なRoleキーとして利用可能となること。
  - [ ] AC-5: Given ステージマスタ管理でステージの接尾辞（suffix）を変更・保存するとき, When 排他ロック下の一括置換確認ダイアログで実行を承認する, Then 影響を受けるバリアントのオーバーライド、保存済みプリセット、スナップショット内のRoleキーが単一トランザクションで一括置換され、ノード配線ID（variant_id）は維持されること。
  - [ ] AC-6: Given 参照中のマスタまたはシステム既定（is_builtin=True）のステージ/グループを削除しようとしたとき, When 削除を実行する, Then 削除ガードにより操作がブロックされ、警告理由が表示されるか論理非表示（is_active=False）に案内され、非活性化時は配下のバリアントも連動して非表示化されること。
  - [ ] AC-7: Given ユーザーがステージ管理画面で新しいステージ（例: 3段目サンプラ、リージョン別プロンプト等）を追加・編集しバリアントを登録したとき, When そのステージに対応するノード群を含むワークフローを読み込む, Then コードの変更なしに該当ステージが動的に展開され、適切なノードが自動マッチングされること。
  - [ ] AC-8: Given 読み込んだワークフローにおいて合致するノードが0件のステージがあるとき, When ワークフロー配線ビューを表示する, Then システム必須ステージを除き該当ステージは自動的に非表示化され、空欄行や不要な未割当警告が発生しないこと。
  - [ ] AC-9: Given 外部PNG画像（DB外）から過去のRoleキーが読み込まれたとき, When StageMasterに過去の旧接尾辞履歴（previous_suffixes配列）が記録されている場合, Then 履歴チェーン（最大10件）から最新のRoleキーへとフォールバック解決され、履歴チェーン外の場合もbase_keyによりグレイスフル解決されること。
- **Inferred points**:
  - 本PBIは「tmp/SPEC_WORKFLOW_MAPPING_V2.html」の基本アーキテクチャに準拠し、1段/2段サンプラに限定されない「完全データ駆動・ユーザー拡張可能なステージ管理システム（3段サンプラ・リージョン分割等への汎用対応）」およびチップ入力＋候補パレットによる入力支援を実装する。なお、外部ComfyUI `/object_info` APIとの動的通信によるオートコンプリートは、ネットワーク依存・キャッシュ・外部接続状態の責務分離の観点から本PBIスコープ外とし、静的な候補パレットおよびチップ入力に純化する。
  - `custom_role_override` は `mapping_variants` テーブル固有のカラムとして保持され、親の `mapping_masters` との循環依存は発生しない。
  - 生成画面における ParamSync（パラメータ連動制御）などの実行時機能は本PBIのスコープ外（設定画面・配線画面の純粋な物理配線定義に責務を限定）。
  - UI実装においては、モックの操作フローを検証基準としつつ、カラー・コンポーネント・レスポンシブ設計はPrompt Surgeon公式デザイン規約（SPEC_COMMON.md / SPEC_SETTINGS.md、shadcn/ui、Tailwind CSS）を最優先とする。
