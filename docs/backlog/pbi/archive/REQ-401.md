### REQ-401: prompt_id確定後の上流消失ジョブがrunning/queuedのまま残留し取消・解除できない不具合の修正

- **Type**: bug
- **Status**: done
- **Priority**: P1
- **Surface**: backend/app/services/generation_service.py, docs/specs/SPEC_COMMON.md, docs/specs/SPEC_GENERATE.md
- **Incident report**: [調査報告](../../../incident_report.md)
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: ComfyUI停止・再起動等で上流queue/historyから消失したprompt_id確定済みの生成ジョブが、FE上で実行中・待機中として恒久的に残留し、normal_group_idが閉じず、単件取消・一括取消・未確認解除のいずれでも解消できないため。
  2. なぜその課題が発生するか:
     - Reconcile照会において、上流queue（running/pending）とhistoryの双方が消失した際にstatusをunconfirmedへ遷移させずスキップしているため。
     - 取消操作（単件・待機・一括）において、上流不在や照会エラーで取消未確認となったactiveジョブのDB statusをunconfirmedへ遷移させず、一括取消の対象からも漏れているため。
  3. なぜ現状の仕組みで不十分か: REQ-335ではprompt_id=nullの孤立ジョブのみを起動時回復対象とし、prompt_id確定後の上流消失や取消未確認時のjob.status遷移が実装・SSoT双方で抜け落ちていたため。
  4. なぜこのアプローチを採用するか: 上流queue/history消失時のunconfirmed遷移と、取消未確認時のunconfirmed遷移・一括取消対象への包含を実装し、状態未確認セクションからの手動解除（release）を可能にするため。
  5. 根本原因: GenerationService._reconcile_lockedおよび取消フロー（_cancel_single, cancel_queued, _cancel_global, _cancel_normal）において、prompt_id確定済みジョブが上流から消失または取消確認不能となった際のstatus='unconfirmed'への遷移処理が欠落していること。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 上流queue/historyから消失したジョブや取消未確認となったジョブを「実行中」「待機中」から「状態未確認」へと即時分離し、待機件数・全体進捗・normal groupを正常化する。
  - **Interaction (インタラクション)**:
    - 取消未確認となったジョブが「状態未確認の記録」セクションに表示され、ユーザーが「記録を解除」によって確実にUIおよびactive対象から除外できるようにする。
  - **Visual (視覚デザイン)**:
    - 実際には上流に存在しないジョブが「実行中」「待機中」バッジやプログレスバーの母数に残り続けないようにする。
- **Requirement**:
  - **1. Reconcileにおける上流消失ジョブのunconfirmed遷移**:
    - prompt_idを持つ非終端ジョブ（queued/submitting/running）について、成功したbridge.queue照会でrunning/pendingの双方に不在であり、かつ成功したbridge.history(prompt_id)照会でもレコード不在であることが確認された場合、statusを'unconfirmed'へ遷移させる。
  - **2. 取消フローにおける取消未確認ジョブのunconfirmed遷移と一括取消網羅**:
    - 単件取消（_cancel_single, cancel_queued）において、上流queue照会エラーまたはqueue/history不在により取消確認できないprompt_id!=nullのactiveジョブのDB statusを'unconfirmed'へ遷移させる。
    - 一括取消（_cancel_global, _cancel_normal）において、上流queueに不在のprompt_id!=nullのactiveジョブ（queued/submitting/running）も取消対象・未確認項目として扱い、status='unconfirmed'へ遷移させてCancelOperation.itemsに報告する。
  - **3. 解除およびNormal Group管理との整合・SSoT明文化**:
    - unconfirmedへ遷移したジョブは_ACTIVE_STATUSESから除外され、normal groupが正常に閉じること。
    - FEの「状態未確認の記録」欄（selectUnconfirmedJobs）に現れ、POST /api/generation/releaseによって解除（released）可能となること。
    - SPEC_COMMON.mdおよびSPEC_GENERATE.mdに上記遷移契約を反映すること。
- **Acceptance criteria**:
  - [x] AC-1: Given prompt_idを持つqueued/submitting/runningジョブが存在し上流queueおよびhistoryから消失している場合, When reconcileが実行される, Then 当該ジョブのstatusが'unconfirmed'へ遷移し、待機中・実行中から除外されnormal_group_idが閉じること。
  - [x] AC-2: Given prompt_idを持つqueued/runningジョブが存在し上流queueに不在または上流不通である場合, When 単件取消（_cancel_singleまたはcancel_queued）を実行する, Then outcome='unconfirmed'が返るとともにDB上のjob.statusが'unconfirmed'へ更新され、状態未確認の記録として表示されること。
  - [x] AC-3: Given 上流queueに不在のprompt_id確定済みactiveジョブが存在する場合, When 一括取消（cancel mode=all/queued）を実行する, Then 当該ジョブがitemsにoutcome='unconfirmed'として含まれ、DB上のjob.statusが'unconfirmed'へ更新されること。
  - [x] AC-4: Given 上記によりunconfirmedへ遷移したジョブ, When ユーザーがrelease（記録を解除）を実行する, Then 正常にstatus='released'へ遷移し、待機・進捗・未確認のいずれからも解消されること。
  - [x] AC-5: Given SPEC_COMMON.mdおよびSPEC_GENERATE.md, When 仕様書を同期する, Then prompt_id確定後の上流消失時および取消未確認時のstatus='unconfirmed'遷移契約が明記されていること。
- **Inferred points**:
  - ComfyUIの一時的な照会エラー（timeout/接続拒否）時は、reconcileでの誤判定を避けるため成功した応答（queue不在かつhistory空）のときのみunconfirmed遷移させる保守的判定を基本とする。
  - 一方、取消操作時は明示的なユーザー指示であるため、上流不通時であってもstatusをunconfirmedへ遷移させて手動解除の出口を開くことがUX上求められる。
