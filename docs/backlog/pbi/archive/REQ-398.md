### REQ-398: scripts/run_e2e.py が :8000 の実バックエンド稼働を検出して警告する

- **Type**: chore
- **Status**: abandoned（2026-10-26 独立PBI廃止・警告の目的をREQ-396へ引継ぎ）
- **Priority**: P4
- **廃止・引継ぎ決定（2026-10-26）**:
  - ユーザーが独立PBI廃止と、警告を出すべき場合の要求をREQ-396へ追加することを指示した。
  - ポート8000が開いているだけで出す警告は採用しない。必要な警告は通信隔離の未適用・中継への退行・隔離確認不成立を検出した場合の診断として、REQ-396の要求4およびAC-7/8へ引き継いだ。
  - 本文の旧要求・旧ACは適用終了の経緯であり、REQ-396へそのまま移したものではない。統合先は docs/backlog/pbi/active/REQ-396.md 。実装完了・受入PASSを意味しない。
- **Surface（以下は廃止前の記録）**: scripts/run_e2e.py（Gate 3 固定コマンド）
- **リスク区分**: 検証インフラの変更（高リスク）。Gate 3 の固定コマンド `python scripts/run_e2e.py` を変更するため、受け入れ検証は全スイートを再実行する（証拠の再利用や範囲の縮小をしない）。
- **起点**: REQ-395 の設計（`docs/design/REQ-395.md` §7）で別 PBI の候補とした再発防止策。REQ-396 の任意項目を、リスク区分が異なるため分離した。
- **根拠資料**: `docs/incident_report_e2e_ws.md`（`run_e2e.py` は :8000 の稼働を検査しない）。
- **依存関係**: REQ-396 のクローズ後を推奨する。REQ-396 で E2E が実バックエンドに依存しなくなれば、本 PBI の警告は防御の多重化（情報提供）の位置づけになる。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: ローカルのバックエンドが稼働していると、E2E が実データを受信して失敗する事例があった（REQ-395）。
  2. なぜその課題が発生するか: 失敗の時点で、結果が実行環境に依存していることが実行者に示されない。
  3. なぜ現状の仕組みで不十分か: `run_e2e.py` は :8000 の稼働を検査せず、失敗の原因調査にバックエンドを止めた対照実験が必要だった。
  4. なぜこのアプローチを採用するか: 稼働中であることを警告として出せば、失敗時の原因の切り分けが速くなる。警告のみで実行結果と終了コードは変えない。
  5. 根本原因: Gate 3 の実行が、環境の前提（実バックエンドの有無）を実行者に開示しない。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 警告メッセージの出力先を標準エラー出力（stderr）とし、形式を `WARNING: [scripts/run_e2e.py] Port 8000 is open. E2E test results may depend on active local backend.` と定義する。
  - **Interaction (インタラクション)**:
    - 変更なし（コマンドの引数と終了コード、テスト実行順は維持）。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement（廃止前の経緯・適用終了）**:
  - **1. 稼働の検出と警告**:
    - `scripts/run_e2e.py` は、実行時にローカルポート 8000 のリッスン（稼働）を検出した場合、標準エラー出力（stderr）に `WARNING: [scripts/run_e2e.py] Port 8000 is open. E2E test results may depend on active local backend.` を出力する。
    - 警告の出力のみを行い、テストの選択・実行順・終了コードおよびファイル・DB 等のシステム状態への副作用を生じさせない。
- **旧Acceptance criteria（適用終了）**:
  - 旧AC-1: Given ポート 8000 でバックエンドがリッスン中である, When `python scripts/run_e2e.py` を実行する, Then 標準エラー出力（stderr）に `WARNING: [scripts/run_e2e.py] Port 8000 is open` を含む警告行が 1 行以上出力されること。
  - 旧AC-2: Given ポート 8000 が使用されていない（リッスンしていない）, When `python scripts/run_e2e.py` を実行する, Then 標準エラー出力にその `WARNING:` 警告行が含まれないこと。
  - 旧AC-3: Given 変更前後, When 同一の引数（引数なし、または `frontend/e2e/...` などの spec パス指定）と同一環境で `python scripts/run_e2e.py` を実行する, Then 実行されるテスト一覧と件数、PASS/FAIL の結果、終了コードが同一であり、標準出力やファイル・DB 等への副作用が生じないこと。
  - 旧AC-4: Given 変更後, When 既存の呼び出し方（引数なし、および spec パス指定）で実行する, Then そのまま実行でき、新たな必須引数がなく、終了コードやテスト結果解析に干渉しないこと。
  - 旧AC-5: Given ポート 8000 へのソケット接続試行がタイムアウト（上限 1.0 秒）または例外となる環境, When `python scripts/run_e2e.py` を実行する, Then E2E の実行が中断・停止せず、判定処理による遅延が最大 1.0 秒以内で通常のテスト実行が開始されること。
- **Inferred points**:
  - 分離の判断理由: (1) Gate 3 の固定コマンドの変更は高リスクで、受け入れ検証にフルスイートの再実行が必須になる。REQ-396 に含めると、spec とヘルパーだけのリファクタが高リスク扱いになり、リスク区分が混在する。(2) REQ-396 が構造的に WS の中継を防ぐため、本 PBI は必須ではなく、採否を独立に判断できる。(3) REQ-396 の AC は「バックエンド稼働中・停止中の両方で PASS」で検証でき、本 PBI の挙動に依存しない。
  - 警告ではなく失敗にする案（:8000 稼働中は実行を拒否する）は、ローカルで通常バックエンドを動かしている開発者の作業を妨げるため、本 PBI では採らない。
  - 検出の方法（ポート接続・HTTP ヘルスなど）と、待ち時間の上限は設計で決める。
  - :8000 は `frontend/vite.config.ts` のプロキシ先の既定。ポートが変更可能な場合の扱いは設計で確認する（未確認）。
- **Design doc**: docs/design/REQ-398.md
