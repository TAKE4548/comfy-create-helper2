### REQ-356: テストスイートをテストアーキテクチャ設計仕様(SPEC-TESTING v2.1)に沿って再構成する

- **Type**: feature
- **Status**: done (2026-10-14)
- **Priority**: P2
- **Surface**: frontend/src (tests, test/utils, e2e); backend/tests (conftest, unit, integration, governance)
- **Reference**: docs/specs/SPEC_TEST_ARCHITECTURE.md (原本: tmp/prompt_surgeon_test_architecture.html) (テストアーキテクチャ設計仕様書 SPEC-TESTING v2.1, 製品スタック x テスト境界マップ)
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: テストが肥大化し、全件実行が約113秒かかり、エージェント開発の待ち時間とトークン消費が増えている。
  2. なぜその課題が発生するか: PBI単位でテストファイルが増殖し (例: `e2e_req347_*.test.tsx`)、単体/結合/E2Eの区別と実行コスト別の置き場がない。
  3. なぜ現状の仕組みで不十分か: 「どこまで本物を動かし、どこをモックするか」の境界が統一されておらず、DB/ネットワーク/ディスク隔離が個別実装で重複し、二重テストや漏れが判別できない。
  4. なぜこのアプローチを採用するか: 製品アーキテクチャとテスト境界(Seam Map 境界A〜J)を対応付けた設計仕様が整理済みで、これに沿う再構成が局所実行・高速化・リファクタ耐性に直結する。
  5. 根本原因: テストの階層・配置・隔離境界・PBIトレーサビリティの規約が無く、PBIごとに場当たり的にテストが追加されてきた。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - テストの配置(unit/integration/e2e/governance)、命名、PBIトレーサビリティ(`[REQ-xxx/AC-n]`)の規約を統一する。
  - **Interaction (インタラクション)**:
    - 開発者/エージェントが Gate 1(静的検証+単体) / Gate 2(統合) / Gate 3(E2E) を階層・パス単位で局所実行できる。
  - **Visual (視覚デザイン)**:
    - 該当なし (製品UIの見た目変更は行わない)。
- **Requirement**:
  - **1. テスト階層とディレクトリ再配置**:
    - Frontend/Backend のテストを仕様書「ディレクトリ配置 (To-Be)」の階層(Unit / Integration / E2E / Governance)へ再配置し、PBI番号入りのフラットなファイル名を廃止する。
  - **2. テスト境界(Seam)の隔離規約**:
    - 仕様書の境界C〜J(Zustand完全置換、React Query短命Client、WebSocketモック制御、fetch遮断、TestClient直呼び、SAVEPOINT付きインメモリDB、tmp_pathディスク隔離、httpxトランスポート遮断)を共通ヘルパー/共通Fixtureとして提供し、各テストはそれを利用する。
  - **3. モック禁止規約**:
    - 境界A/B規約(sticky/実スクロールの検証はPlaywrightのみ、jsdomでの擬似スクロール禁止)およびサービス内部関数のパッチ禁止(I/O境界のみ遮断)を満たす。
  - **4. PBIトレーサビリティ**:
    - テスト名に PBI番号とAC番号のプレフィックスを付与し、ファイル名からPBI番号を除去してもPBI番号で全テストを逆引きできる。
  - **5. 実行ゲート**:
    - Gate 1/2/3 をパス/マーカー単位で個別実行でき、全件の成功判定が再構成前と同等以上であること。
  - **6. 非破壊リファクタ**:
    - 再構成により既存テストが担保していた検証内容を失わない (削除は重複と判定したものに限り、記録を残す)。
  - **7. 検証項目の対応表**:
    - 再構成の着手前に、既存テストが担保している検証項目の一覧(対応表)を作成し、AC-10/AC-13 の比較基準とする。
- **Acceptance criteria**:
  - [ ] AC-1: Given 再構成完了後のリポジトリ, When `frontend/src` と `backend/tests` を走査する, Then テストファイルのファイル名(ディレクトリ名を含むパス)に `req[0-9]+` / `REQ-[0-9]+` を含むものが0件であること(テスト名 `it` / `def test_*` は対象外)。
  - [ ] AC-2: Given 再構成完了後のBackend, When `backend/tests` の直下構成を確認する, Then `conftest.py` と `unit/` `integration/` `governance/` のみが存在し、各テストファイルがいずれかの階層に1つだけ属すること。
  - [ ] AC-3: Given 再構成完了後のFrontend, When Unit/Integration/E2Eテストの配置を確認する, Then 純粋関数・単一UIパーツ・純粋Hookは隣接 `__tests__/` に、Playwrightは `frontend/e2e/` に、共通ヘルパーは `frontend/src/test/utils/` に配置されていること。
  - [ ] AC-4: Given Backendの統合テスト, When テストがコミット操作を行った後に正常終了・失敗・中断のいずれかで終わる, Then 次のテスト開始時にDBが空であり、本番 `db/prompt_surgeon.db` が変更されないこと。
  - [ ] AC-5: Given Backendの全テスト, When 実行する, Then 本番 `db/snapshots/` および本番DBファイルへの書き込みが0件(テスト用一時領域 `tmp_path` への書き込みは許容)で、ComfyUI(8188)/LM Studio(1234)への実通信が発生せず、許可リスト(allowlist)に無い宛先への通信は即座にエラーとなること。
  - [ ] AC-6: Given Frontendの統合テスト, When テストを連続実行する, Then 直前テストのZustand状態、React Queryキャッシュ、WebSocketイベント、IndexedDB(`fake-indexeddb`)、localStorage/sessionStorage が次のテストへ持ち越されないこと(`resetTestStore` / `createTestQueryClient` / `MockWebSocketController` を共通ヘルパーとして利用)。
  - [ ] AC-7: Given Frontendのテスト群, When 実fetch/実WebSocket通信を検出するガードを有効にして全件実行する, Then 実ネットワーク通信が0件であること。
  - [ ] AC-8: Given `position: sticky` および実スクロールの検証, When テストの所在を確認する, Then それらの検証がPlaywright(`frontend/e2e/`)のみに存在し、jsdomでの擬似スクロールテストが0件であること。また、Playwrightのsticky検証がデスクトップとモバイルの2種類のviewportで実行されること。
  - [ ] AC-9: Given 再構成後の各テスト, When `grep -rn "REQ-<番号>"` でPBI番号を検索する, Then 再構成前にそのPBIを担保していた各テストが `[REQ-xxx/AC-n]` 形式のテスト名でヒットすること。
  - [ ] AC-15: Given 再構成完了後の全テスト, When テスト名の形式検証スクリプトを実行する, Then PBIに紐づく全テスト名が `[REQ-xxx/AC-n]` 形式であり、スクリプトが成功(終了コード0)すること。PBIに紐づかないテストは「PBI紐づけなし」として一覧に明示されること。
  - [ ] AC-10: Given 再構成前後, When フルテストスイート(Frontend `npm test` / Backend `pytest`)を実行する, Then 失敗0件、かつ再構成前に担保していた検証項目の一覧(対応表)に欠落が0件であること。
  - [ ] AC-11: Given 再構成完了後, When Backend `pytest tests/unit` とFrontend単体テスト対象パスのみを実行する, Then DB/jsdom重厚セットアップを使わず単独で成功すること。
  - [ ] AC-12: Given 再構成完了後, When Gate 1/2/3 を順に実行する, Then Gate 2(Frontend+Backend統合)の合計実行時間が再構成前のフルスイート実行時間(約113秒)より短縮され、計測値が記録されること。
  - [ ] AC-13: Given 再構成作業, When 重複等でテストを削除する, Then 削除対象と理由が対応表に記録され、記録のない削除が0件であること。
  - [ ] AC-14: Given Backend/Frontendのテストを並列実行する設定, When 全件を並列実行する, Then `tmp_path` や共有リソースの衝突による失敗が0件であり、並列と逐次の実行で成功/失敗判定が一致すること。
- **Inferred points**:
  - 仕様書の対象製品「Prompt Surgeon」は本リポジトリのプロダクトと同一と仮定。
  - 目標値(Gate 2は15〜20秒、Unit 3〜5秒、E2E 10秒前後、ピラミッド比率70/25/5)は仕様書の目安であり、AC-12は「旧113秒より短縮」のみを必須とし、目標値の達成は未確定。
  - 規模が大きいため、設計フェーズでBackend基盤→Backend移行→Frontend基盤→Frontend移行→E2E/Gate整備のタスクへ分割する想定(PBIは1本のまま、分割するか要確認)。
  - 仕様書の実装ブループリント(conftest.py)は参考例であり、既存実装との差異は設計フェーズで調整する。
  - 対象外: SQLiteバージョン差によるSAVEPOINT挙動差の網羅、ネットワーク遮断時のライブラリ内部の未処理rejection対策(必要なら別PBI)。
