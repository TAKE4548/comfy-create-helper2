### REQ-362: Prompt Surgeon: プレビュー高速化と200件三位一体キャッシュ実装

- **Type**: feature
- **Status**: done (2026-10-15)
- **Priority**: P1
- **Surface**: バックエンドComfyUI通信・キャッシュレイヤー (`app/routers/comfy.py`, `app/routers/prompt_metadata.py`) および フロントエンドプレビュー表示コンポーネント (`GenerateParallelPreview.tsx`)
- **Origin**: ユーザーからの生成履歴プレビュー表示遅延解消および SPEC-CACHE-2026-10-REV3 仕様書に基づく改修要望。生成完了時の先行WebPキャッシュ生成要件、および整合性監査に基づく健全性ガードレールを追加反映。
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: 生成履歴プレビューやモーダルで画像を切り替える際、パラパラめくる操作で十数MBの画像転送や不要なプローブ通信により数百ミリ秒の表示遅延（もたつき・待たされ感）が発生しているため。
  2. なぜその課題が発生するか: プレビュー表示のたびにComfyUIから十数MBの未圧縮PNG画像を取得し、さらにローカルキャッシュの有無にかかわらずComfyUIへのHTTPプローブ（HEAD/GET）が発生しているため。
  3. なぜ現状の仕組みで不十分か: バックエンドがフルサイズプレビュー用のWebPキャッシュ機構を持たず、またサムネイル・プレビュー取得エンドポイントでキャッシュヒット時にもComfyUI生存確認プローブを毎回実行しているため。
  4. なぜこのアプローチを採用するか: 生成完了イベント（WebSocket）契機でのフルサイズWebP先行生成およびローカルヒット時ゼロプローブ（外部HTTP通信0）により表示待機を0ms化し、さらにComfyUI履歴窓・WebPキャッシュ・SQLiteメタデータの3層を最新200件で一致させることでストレージと整合性を両立できるため。
  5. 根本原因: プレビュー表示がComfyUI（WSL2）からの都度取得・未圧縮PNG転送・不要プローブに依存しており、かつメタデータ保持枠（1,000件）と画面履歴枠（200件）の不一致による孤児データや無駄な通信が生じていたこと。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - ComfyUI履歴窓（最新200件）、フルサイズWebPディスクキャッシュ（最新200件）、SQLiteメタデータ（最新200件）のライフサイクルを同期し、UIからアクセスできない孤児データを根絶。
  - **Interaction (インタラクション)**:
    - 画像生成完了時点で即座にフルサイズWebPがキャッシュされるため、生成直後のプレビュー切り替えやモーダル表示でも待たされ感・カクつきをゼロ化。
  - **Visual (視覚デザイン)**:
    - 万が一の未キャッシュ時もサムネイルWebPを先行描画するプログレッシブプレビューにより、画面のチラつきや空白状態を防止。
- **Requirement**:
  - **1. ローカルキャッシュヒット時のゼロプローブ・高速WebP返却**:
    - /api/comfy/view および /api/comfy/thumbnail エンドポイントにおいて、ローカルディスク上に有効なキャッシュ（サイズ > 0）が存在する場合はComfyUI（WSL2）への外部HTTP通信（HEAD/GET）を一切行わず、即座にWebP画像を返却する。ローカルファイルが存在しない場合はオンデマンド取得へフォールバックする。
  - **2. 生成完了時（WebSocket）のフルサイズWebP先行生成（Eager Cache）**:
    - ComfyUIの画像生成完了イベント（WebSocket / executed）受信時、ComfyUI側のファイル書き込み完了を確認した上で、サムネイルWebP生成と連動してフルサイズWebP（Quality 90, sRGB）も先行して非同期生成し、ディスクキャッシュ（`db/full_cache/`）へ保存する。
  - **3. キャッシュミス時のオンデマンドWebP生成（Lazy Fallback）**:
    - キャッシュが存在しない画像について /api/comfy/view 要求があった場合、ComfyUIから元画像を取得してQuality 90 WebPへ変換・キャッシュ保存した上で返却する。
    - ディスク容量不足や書き込み異常時は適切にハンドリングし、システムダウンや空レスポンスを防止する。
  - **4. フルサイズWebPディスクキャッシュの上限管理と排他制御**:
    - フルサイズWebPキャッシュディレクトリ内のファイル数は上限200件（バッファ許容最大220件）で自動間引き（更新日時昇順）され、ディスク消費を約300MB以内に抑制する。
    - 複数リクエストによる並行間引き競合時もファイル未検出エラー等を安全にハンドリングする。
  - **5. SQLiteメタデータ保持上限の200件同期**:
    - `prompt_metadata` テーブルの最大保持件数を従来の1,000件から200件へ適正化し、アクティブでない古いレコード（created_at昇順）をトランザクション内で自動パージする。
  - **6. フロントエンドでのプログレッシブプレビュー表示**:
    - プレビュー表示コンポーネントにおいて、フルサイズ画像のロードが完了するまでの間、キャッシュ済みのサムネイルWebPをプレースホルダーとして先行描画する。
- **Acceptance criteria**:
  - [ ] AC-1: Given 対象画像のフルサイズWebPキャッシュがローカルディスク上に存在する（サイズ > 0）, When /api/comfy/view エンドポイントへ画像要求が行われる, Then WSL/ComfyUIへの外部HTTP通信（HEAD/GET）が一切発生せず、5ms未満でWebP形式の画像がステータスコード200で返却されること。
  - [ ] AC-2: Given 対象画像のサムネイルキャッシュがローカルディスク上に存在する（サイズ > 0）, When /api/comfy/thumbnail エンドポイントへ画像要求が行われる, Then WSL/ComfyUIへの存在確認HTTPプローブが発生せず、即座にキャッシュ済みのサムネイル画像が返却されること。
  - [ ] AC-3: Given 新たな画像生成ジョブが完了しバックエンドが完了通知（WebSocket / executedイベント）を受信する, When 生成完了ハンドラが出力画像を処理する, Then 出力画像の書き込み完了を確認した上で、サムネイルWebP生成と同時にフルサイズWebP（Quality 90, sRGB）も先行して非同期生成されディスクキャッシュ（`db/full_cache/`）へ保存されること。
  - [ ] AC-4: Given ローカルディスクにフルサイズWebPキャッシュが存在しない画像について/api/comfy/view 要求が行われる（キャッシュミス時）, When ComfyUIから元画像が正常に取得される, Then オンデマンドでWebP形式（Quality 90）に変換されてディスクキャッシュへ保存され、クライアントへWebP形式で返却されること。
  - [ ] AC-5: Given フルサイズWebPキャッシュディレクトリ内のファイル総数が220件を超過した状態, When 新たなフルサイズWebPが保存・キャッシュ整理処理が実行される, Then 並行競合時にも安全に最も古いキャッシュファイル（最終アクセス/更新日時昇順）から間引かれ、総ファイル数が200件以下に維持されること。
  - [ ] AC-6: Given SQLiteの prompt_metadata テーブルの総レコード数が200件を超過した状態, When 新たなプロンプトメタデータが追加保存される, Then 実行中・キュー待機中のアクティブプロンプトを除外した古いレコード（created_at昇順）からトランザクション内で自動削除され、テーブル内の保持件数が200件以下に抑制されること。
  - [ ] AC-7: Given プレビュー対象の画像が切り替えられた, When フルサイズWebPの取得・ロードが完了するまでの間, Then 先行して取得済みのサムネイルWebPがプレースホルダーとして描画され、空白やガタつきを生じないこと。
- **Inferred points**:
  - ComfyUIの元PNG画像に埋め込まれていたプロンプト・ワークフロー情報は、Prompt Surgeonの手元SQLite（`prompt_metadata`）に構造化データとして保持されているため、プレビュー表示用画像を軽量WebPに置き換えてもワークフロー再構成・再利用の機能性は担保される。
  - キャッシュキーは `type:subfolder:filename` の組合せをSHA256ハッシュ化したものを想定。
  - 生成完了時の先行生成（AC-3）により、ユーザーが生成結果プレビューをクリックまたは切り替えた瞬間にはすでにキャッシュが命中しゼロ遅延で描画される。
  - 「ゼロプローブ」とはComfyUIへのHTTP通信の撤廃を指し、ローカルディスク上のファイル存在・実サイズ確認はエンドポイント内で実施される（ファイル未存在時はAC-4へ安全にフォールバック）。
  - 同一LAN内のモバイルブラウザ等からのアクセス時も、転送データ量が十数MBから約1.5MBへ圧縮されることでWi-Fi帯域の圧迫や描画遅延が解消される。
  - AC-6における「アクティブプロンプト」は、生成処理中またはキューに滞留しているプロンプトID群を指し、これらは削除対象から保護される。
