### REQ-424: 生成キューの単一キャンセル即時実行と3秒間アンドゥ機能

- **Type**: feature
- **Priority**: P2
- **Surface**: `frontend/src/components/` (Queue/Generation管理UI、トースト/アンドゥ通知コンポーネント、キュー操作関連フック/ストア)
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: 生成キューで特定の待機ジョブをキャンセルしようとすると3秒のディレイ（待機カウントダウン）が入り、即座にキャンセルしたい作業テンポを阻害しているため。
  2. なぜその課題が発生するか: 誤操作によるジョブ喪失を防ぐため、事前の安全策として固定の3秒ディレイ（待機時間）が設けられていたため。
  3. なぜ現状の仕組みで不十分か: 意図的にキャンセルしたい大半の通常ケースでも毎回3秒待たされ、不要なジョブの早期排除や次の生成への切り替えが遅れるため。
  4. なぜこのアプローチを採用するか: キャンセル自体は操作時に即座に実行（即時除外）し、実行後3秒間「取り消し（Undo）」アクションを提供する事後救済アプローチへ切り替えることで、即応性と誤操作防止を両立できるため。
  5. 根本原因: 誤操作防止の安全ガードが事前ディレイ（待機時間）として実装されており、ユーザーの即時操作ニーズと相反していたこと。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 即時キャンセルされたこと（例: 「ジョブをキャンセルしました」）と、取り消し可能な残り時間（3秒）および「取り消し」ボタンが明確に視覚表示されること。
  - **Interaction (インタラクション)**:
    - 待機ジョブの単一キャンセルボタン押下時、事前ディレイを挟まず即座にキャンセルが実行される。
    - キャンセル実行直後に「取り消し（Undo）」アクションを含む通知UIが3秒間表示される。
    - 3秒以内に「取り消し」を押下した場合、キャンセルされたジョブが待機キューに即座に復帰する。
    - 3秒経過した場合は、取り消し通知が自然に消去され、キャンセルの確定状態が継続する。
- **Requirement**:
  - **1. 単一キャンセルの即時実行**:
    - キュー内の待機中ジョブ（queued）の単一キャンセル操作において、3秒の事前ディレイを廃止し、操作と同時に即時キャンセル処理（キューからの除外）を実行する。
  - **2. 3秒間のアンドゥ（取り消し）猶予と復元**:
    - 単一キャンセル実行直後から3秒間、画面上に取り消し（Undo）用のアクションUI（トーストまたはバナー等）を表示する。
    - ユーザーが3秒以内に「取り消し」を実行した場合、該当ジョブを元のパラメータ・ワークフロー設定のままキューに復帰させる。
    - 3秒が経過した場合、またはユーザーが明示的に閉じた場合は、取り消しUIを非表示としキャンセル確定とする。
- **Acceptance criteria**:
  - [ ] AC-1: Given 生成キュー内に待機中ジョブが存在する, When ユーザーが該当ジョブの単一キャンセル操作を行う, Then 事前ディレイ（カウントダウン待機）を挟まず即座に該当ジョブがキューから除外（キャンセル実行）されること
  - [ ] AC-2: Given 単一キャンセルが即時実行された, When キャンセル直後, Then 「取り消し（Undo）」ボタンを伴う通知UIが画面に表示され、3秒間の有効期限タイマーが開始されること
  - [ ] AC-3: Given キャンセル後の通知UIが表示されている（3秒以内）, When ユーザーが「取り消し」ボタンをクリックする, Then キャンセルされたジョブが元の設定（ワークフロー・プロンプト・パラメータ等）を保持した状態でキューに即座に復帰すること
  - [ ] AC-4: Given キャンセル後の通知UIが表示されている, When ユーザーが取り消しを行わず3秒が経過する（または明示的に閉じる）, Then 通知UIが閉じ、キャンセルの確定状態が維持されること
  - [ ] AC-5: Given 一括キャンセル（全件キャンセル）など単一キャンセル以外の操作, When ユーザーが実行する, Then 既存の一括キャンセル動作や確認仕様が阻害されず正常に機能すること
- **Inferred points**:
  - 対象は待機中ジョブ（queued/pending）の単一キャンセル操作であり、現在実行中のジョブ（running）の緊急停止（Abort/Interrupt）はハードウェアリソース解放の観点から即時停止のみ（Undo不可）とする想定。
  - 3秒以内のUndo実行時、キュー内での投入順序は末尾への再追加または元の位置への復元のいずれかになるが、UIおよび機能として確実にジョブが再投入・復元されることを主要件とする。
