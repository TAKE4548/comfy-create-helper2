### REQ-387: Generation snapshot の全件同期読込によるイベントループ占有でBE全体の応答が遅延する

- **Type**: bug
- **Status**: new
- **Priority**: P1
- **Surface**: backend/app/services/generation_repository.py, backend/app/services/generation_service.py, backend/app/routers/generation.py, backend/app/database.py, docs/specs/SPEC_GENERATE.md
- **Incident report**: [docs/incident_report_generation-snapshot-perf.md](../../../incident_report_generation-snapshot-perf.md)（Classification: Type B: Specification Gap）。設計はこのレポートを起点とする。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: バイパス切替、キュー取消、履歴プレビュー、画像/サムネ取得、管理画面マスタ取得など、BE全APIが同時に遅延する（10/24実測: 軽量マスタAPI最大32-35秒、cancel 中央値53秒・最大277秒）。BE端末のlocalhostでも再現する。
  2. なぜ発生するか: `GenerationRepository.snapshot()` が終端済みを含む `generation_jobs` 全件（874行。主に metadata_json が約23.7MBで、各行で prompt 抜粋のため2段の json.loads を行う）を同期読込し（約370ms/回）、async経路からイベントループ上で直接呼ばれている。
  3. なぜ高頻度か: worker の0.2秒周期（pending/VRAM待機時は毎周期）、2.5秒毎 reconcile で計3回、プレビュー1フレームごとに3回（asyncio.Lock保持下）、`/state`・`/preview/{job_id}`・`/images/{job_id}/availability` のリクエストごとに実行され、約917KBの全状態をWS配信している。
  4. なぜ現状の仕組みで不十分か: generation_jobs に保持上限がなく、生成を重ねるほど単調に悪化する。cancel は同じロックを待つため長時間化する。
  5. 根本原因: SPEC_GENERATE.md:197 が「snapshotは全状態を一体で扱う」とのみ規定し、snapshot対象範囲（終端jobの窓/上限）、履歴保持方針、イベントループ非ブロックの非機能制約、プレビュー時の再計算/配信上限を定義していない。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 変更なし（Job管理表示の情報項目は維持する）。表示対象の終端jobの範囲はSSoT改訂で明示する。
  - **Interaction (インタラクション)**:
    - 生成中でもバイパス切替・取消・プレビュー・画像取得が即時に応答すること。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. SSoT改訂（SPEC_GENERATE）**:
    - Generation snapshot の対象を「非終端job + 有界な直近終端job窓」に限定する規定、generation_jobs の保持方針、同期DB I/Oでイベントループをブロックしない非機能制約、プレビュー受信時の再計算/配信上限を追記する。
  - **2. snapshot取得の有界化**:
    - repository.snapshot をアクティブ集合と有界な終端窓のクエリに限定し、snapshot 経路で metadata_json 等の大きい列の全件読込・全件JSON解析を行わない。必要な索引を追加する。
  - **3. イベントループ非ブロック化とロック保持短縮**:
    - on_preview はプレビューrevision更新と通知のみにして DB 再読込を行わない。worker の pending/VRAM 待機周期で毎回 DB 全件を読まない。残る同期DB呼出はスレッドへオフロードし、cancel 経路のロック待ちを短縮する。`/preview/{job_id}` は job_id→prompt_id の軽量参照にする。
  - **4. 副次要因の是正**:
    - SQLite を WAL + busy_timeout に設定する。ComfyUI不通時の reconcile 失敗ログを状態変化時/バックオフに抑制する。httpx ロガーを WARNING に下げる。
- **Acceptance criteria**:
  - [ ] AC-1: Given 終端job 1000件を含む generation_jobs, When `GenerationRepository.snapshot()` を取得する, Then jobs は (a)非終端job全件 (b)非終端jobを含むbatchの全job (c)現在の `normal_group_id`（app_settings保存値、空なら無し）の全job (d)受付が新しい直近20 batchの全job (e)session毎に `released_at` が新しい直近10件のreleased job、の和集合だけであること。
  - [ ] AC-2: Given 実行中jobがプレビューフレームを連続受信している, When フレームを30枚受信する, Then generation_jobs を対象とするSELECTの回数がフレーム数に比例せず（区間内のrevision変化回数+2以下）、各フレームでプレビューrevisionの更新とWS通知が行われること。
  - [ ] AC-3: Given 終端job 1000件を含むDBで生成実行中かつプレビューフレームを30枚受信している, When `GET /api/generation/state`・`GET /api/generation/preview/{job_id}`・`GET /api/generation/upstream-queue` を並行して呼ぶ, Then 10ms周期tickで測るイベントループの最大遅延が150ms以下、preview応答の最大が300ms以下であること。
  - [ ] AC-4: Given 実行中/待機jobがあり、プレビューフレームを受信している, When 単件・一括（通常生成）取消を要求する, Then 応答が2秒以内に返り、取消結果の種別（already_terminal / not_cancelled / already_released / job not found 等）が snapshot 配信窓の外にあるjobに対しても従来と同一であること。
  - [ ] AC-5: Given `docs/specs/SPEC_GENERATE.md` L197 の snapshot 定義, When 改訂後を確認する, Then 直後に (1)AC-1の配信窓 (2)窓外jobのjob単位照会 (3)イベントループ非占有とプレビュー時の全件再読込禁止 (4)reconcile連続失敗のログ抑制 (5)WAL・busy_timeout 5秒 (6)DB終端job保持1000件は不変、が明記され、L197/L199/L200/L206 の既存文言が変更されていないこと。
  - [ ] AC-6: Given ComfyUI が停止し reconcile が連続して失敗する, When 失敗が連続n回目になる, Then 例外詳細（exc_info）付きWARNINGは n=1 の1回だけで、要約WARNINGは n ∈ {24,48,96,192} および n>192 で (n−192) が240の倍数のときだけ記録され、それ以外はDEBUGとなり、成功に戻った時点で回復INFOが1回記録されること。
  - [ ] AC-7: Given SQLite ファイルDBへの engine, When 接続を確立する, Then `PRAGMA journal_mode` が `wal`、`PRAGMA busy_timeout` が `5000` を返し、`:memory:` DB でも接続が例外にならず、`setup_logging` 後の `httpx` / `httpcore` ロガーが WARNING であること。
  - [ ] AC-8: Given AC-1 と同じDB, When snapshot を取得する, Then FEの通常生成・Studio batch の N/F と解除済み直近10件の算出結果が全件snapshotからの結果と一致し、取得時間がキャッシュミス時150ms以下、revision不変時のキャッシュヒット時10ms以下であること。
- **Inferred points**:
  - 窓の件数（20 batch / released 10件/session）は現DBのbatchサイズ分布（最頻3件・最大25件）とFE表示（解除済み直近10件）から決めた。
  - FEは snapshot の jobs を現在group・Studio batch・unconfirmed・released 上位10の算出に使い、それ以外の終端jobを表示に使わない（`frontend/src/utils/generationSelectors.ts`、`JobManagementModal.tsx` で確認済み）。
  - `prune_terminal` の未配線（REQ-333 の1000件保持方針とのずれ）、BaseHTTPMiddleware、ログ量全般は本PBIの対象外とし後続課題とする。
