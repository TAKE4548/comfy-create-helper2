### REQ-418: プリセット・スナップショット・同期グループの role 参照から variant_id 参照への移行

- **Type**: refactor
- **Status**: done (2026-11-07)
- **Priority**: P2
- **Surface**: DB (`models.py`, `migrations/steps.py`), Backend (`preset_service.py`, `snapshot_service.py`, `routers/presets.py`, `routers/snapshots.py`), Frontend (`types.ts`, `presetState.ts`, `snapshotState.ts`)
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: プリセット、スナップショット、同期グループがパラメータ参照キーとして文字列の `role` を使用しており、外部キー制約による整合性が保証されていないため。
  2. なぜその課題が発生するか: 旧データモデルでは `MappingVariant` に一意な永続IDや一意性制約がなく、動的に計算された `role` 文字列で各エンティティを紐付けていたため。
  3. なぜ現状の仕組みで不十分か: マスタのベースキーやステージ名の変更時に文字列参照が切断されるリスクがあり、カスケード更新やDBレベルでの孤立参照防止ができないため。
  4. なぜこのアプローチを採用するか: REQ-417 で確立される `MappingVariant` の永続エンティティ（`variant_id`）を外部キーとして参照させることで、参照整合性とリファクタリング耐性を担保できるため。
  5. 根本原因: パラメータ値の保持エンティティがVariantの永続キーではなく計算上のロール文字列に依存していた設計残債。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - プリセット値、スナップショット値、同期グループメンバーシップを `role` 文字列から `variant_id` (FK) 参照に正規化。
  - **Interaction (インタラクション)**:
    - マスタ定義やステージ名の変更時にもプリセットやスナップショットの設定値が自動追従し、設定の切断を防止。
  - **Visual (視覚デザイン)**:
    - 既存のプリセット選択・スナップショット復元・同期設定UIの表示および操作感はそのまま維持。
- **Requirement**:
  - **1. プリセット（Presets）テーブルの variant_id 移行**:
    - REQ-417 で mapping_variants テーブルが確立されていることを前提とし、前提テーブルが存在しない場合はマイグレーションを実行せずエラーとする。
    - マイグレーションは単一トランザクション内で実行する。
    - プリセット値テーブルに `variant_id` 列を追加し、`mapping_variants.role` と完全一致するレコードの `id` を `variant_id` 列に設定してデータを移行する。
    - 空テーブルの場合はスキーマ変更と制約付与が成功すればコミットされ、データ移行ステップはスキップされる。
    - 既存データが存在する場合、全行が正常に解決できた場合のみコミットされて外部キー制約が付与される。1件でも未解決行（mapping_variants テーブルに該当する role が存在しない行）が検出された場合は、トランザクション全体がロールバックされ、既存の role 参照データは変更されない。
    - 全行の解決成功後に `mapping_variants(id)` への外部キー制約を付与する。
  - **2. 生成スナップショット（Snapshots）の variant_id 移行**:
    - スナップショット保存時（DB永続化時）において `variant_id` をキーとして保存する。
    - DB内に保存された過去の旧スナップショット（roleキー）を画面フォームへ復元（展開）する際の後方互換リゾルバを提供する。復元実行時において、旧スナップショット内のキーに対応する `variant_id` が存在しないキーがある場合は警告ログ（logger.warning）に欠落キーを明示的に記録した上で、画面フォーム上の該当入力フィールドは初期値（未設定）のまま維持し、有効なパラメータのみ画面展開を完了する。
  - **3. パラメータ同期グループ（Sync Groups）の variant_id 移行**:
    - 同期グループの対象パラメータ一覧を `variant_id` の配列または中間テーブルとして管理し、外部キー制約を担保する。
  - **4. APIおよびフロントエンドの移行**:
    - プリセット・スナップショット・同期グループの入出力スキーマを `variant_id` 基準に更新し、フロントエンドの状態管理および適用ロジックを整合させる。
    - MappingVariant の属性（role, display_name等）が変更された場合も、variant_id の外部キー参照により一覧API等で即座に最新のマスタ情報が取得される。
- **Acceptance criteria**:
  - [ ] AC-1: Given プリセットテーブルのマイグレーションにおいて, When mapping_variants テーブルが存在しない場合は実行が中断されてエラーとなり、mapping_variants が確立された状態では空テーブルならスキーマ変更と制約付与のみコミットされ、既存データがある場合は全行解決時に variant_id 列へ格納されて外部キー制約が付与され、未解決行が存在する場合はトランザクション全体がロールバックされて既存の role 参照データは変更されないこと
  - [ ] AC-2: Given DB内に旧形式の role キーを持つスナップショットデータが存在する状態, When スナップショット復元を実行したとき, Then 後方互換リゾルバにより対応する variant_id へマッピングされたパラメータのみ画面フォームへ展開され、対応する variant_id が存在しないキーは復元実行時に警告ログ（logger.warning）が出力されて画面フォーム上の該当入力フィールドは初期値（未設定）のまま維持されて画面展開が完了すること
  - [ ] AC-3: Given パラメータ同期グループを登録・更新するとき, When 同期グループを設定したとき, Then variant_id の組として永続化され、グループ内でのパラメータ変更が同一グループ内の他Variantへ正しく同期されること
  - [ ] AC-4: Given MappingVariant の属性（roleやdisplay_name）が更新された状態, When プリセット一覧APIまたは同期グループ一覧APIを呼び出したとき, Then variant_id の外部キー参照により更新後の最新のVariant情報を含むレスポンスが返却されること
- **Inferred points**:
  - 本PBIは REQ-417（Master/Variant/判定定義の3層分離とスキャンロジック刷新）の実装・完了を前提条件（依存先）とする。
  - 旧スナップショットのマイグレーションは、DB内のJSONフィールドに対する移行スクリプト、または読み取り時のフォールバック解決（role -> variant_id）により後方互換性を担保する。
