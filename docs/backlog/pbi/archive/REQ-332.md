### REQ-332: APIキャッシュの保存領域分離による生成時メタ情報の保存安定化

- **Type**: feature
- **Status**: done (2026-10-08)
- **Current step**: 実装完了（T1〜T12）— Gate 1/2 PASS、Gate 3はINCONCLUSIVE。2026-10-08にユーザーが既知の検証限界を確認してクローズを承認
- **Priority**: P2（資料申告の再発障害に基づく仮定）
- **Surface**: 「添付に従ってキャッシュ最適化のPBI起票して」
- **Operational need**: 大量のワークフロー・カタログがあっても手動整理なしで生成を継続し、画像の記録済み生成条件と編集中の入力を失わず参照できること。
- **Root Cause**: 添付はAPIバルクキャッシュがメタ情報・設定と同じ容量枠を圧迫していると報告する。現環境の容量・障害は本起票では未検証。

- **Test plan**: `docs/design/REQ-332-test-plan.md`（2026-10-08承認済み）

- **Design review**: 2026-10-08、設計書・AC18件の試験計画・DAG・リスク・監査の非PASS結果を提示後、ユーザー「OK」により承認。実装フェーズ完了。
- **Closure review**: 2026-10-08、ユーザー「確認した。クローズして、ビルドしよう」と明示。クローズは人間承認による。Gate 3のINCONCLUSIVEと未確認の実ブラウザー/mobile/quota/frame/multitab/実ジョブ環境は、そのまま残して追跡する。

#### 5 Whys / 運用上の背景

1. なぜ最適化が必要か: 30件へ保持数を減らした後も生成時メタ情報の保存失敗が再発するため（添付申告）。
2. なぜ保存失敗が作業を妨げるか: 画像の生成条件を後から確認する際に記録が必要なため（既存仕様）。
3. なぜ件数削減だけで不足するか: ワークフロー・一覧の巨大なキャッシュも同じ保存枠を占有するため（添付申告）。
4. なぜ単純な全削除では不足するか: 再読み込み時のデータ再利用、入力復元、直近画像の条件表示が必要なため（既存仕様から整理）。
5. なぜ運用要件とするか: データ増加によって生成作業と振り返りの継続性が損なわれることを防ぐため（推論）。

#### UX Classification

- **Information Design（情報設計）**: 画像に対応する記録済み条件を維持し、既存モニタで容量変化を確認できる。
- **Interaction（操作）**: 手動整理なしの連続生成、再読み込み時のデータ再利用、設定・入力・下書きの復元。
- **Visual（視覚）**: 直近画像の切替で他画像の値や空の仮表示を挟まず条件を表示する。新しい装飾・配置は対象外。

#### Requirement / 対象と境界

- 添付の再配置方針を設計入力とする。APIキャッシュはIndexedDBへ移し、旧 `prompt-surgeon-rq-cache` は初回移行で除去・再取得可能とする。パッケージ、DB名、API、コード差分は設計担当が検討する。ACはユーザーが確認できる結果で定義する。
- メタ情報30件、設定・ワークフロー入力、画像URL履歴・選択状態の永続保持を維持する。Studio下書きのタブ内保持、サーバーメタ情報1000件、保存済みSnapshotを変更しない。
- 既存のAPIキャッシュ有効期限10分とデータ別再検証方針を維持する。動的ノード定義、スナップショット一覧、ワークフロープリセットの永続再利用除外を維持する（SPEC_COMMON 6）。
- 初回移行は旧APIキャッシュだけの破棄を許容する。サーバー利用可能時に再構築し、必要なワークフローの準備前投入を防止する（REQ-161）。初回のオフライン起動保証は追加しない。
- キャッシュ利用不能でもサーバー取得に成功すれば生成を実行可能とする（補足した耐障害性の仮定）。全保存領域・サーバーの同時障害の無損失保証は追加しない。
- IndexedDBの実容量はブラウザのクォータに従い、固定50MB・無制限という保証はしない。容量不足・利用拒否・キャッシュ削除時はAPIをサーバーから再取得し、永続保存の成功を生成受付の前提としない。期限切れキャッシュの整理・上書きとスキーマ互換性、複数タブ競合の方式は設計で決める。
- 移行対象は再取得可能なAPIキャッシュだけであり、メタ情報は既存localStorageの直近30件（画像ID単位の単一保持枠）のままとする。IndexedDBごとにメタ情報30件枠を追加しない。localStorageモニタはその領域の推定量のみを示し、新保存領域の健全性はAC-8・11・16〜18で判定する。
- 旧APIキャッシュ除去後に移行が中断しても、再起動時にサーバーから必要データを取得して復旧する。容量圧迫の原因となる旧localStorage API保存方式への復帰は要求しない。非APIデータ保護はAC-12・13で検証する。
- 直近の記録はメタ情報ネットワーク応答を待たず表示する。キャッシュ外はサーバー取得成功時に参照する。現在入力から過去の生成条件を補完しない。
- IndexedDB使用量の新規モニタ表示、圧縮、サムネイルBlob保存、サーバー改修は対象外。既存localStorage/sessionStorage推定量モニタを維持する。

#### 試験条件と判定語

- 通常条件: 保存領域を利用可能、サーバー応答成功、単一アクティブタブ、他アプリ・他タブの書換えなし。デスクトップとモバイルの双方で確認する。
- 大容量フィクスチャ: API保存用文字列2,097,152 UTF-16コード単位（換算4 MiB）、メタ情報は異なる画像ID30件・timestamp相異・合計786,432コード単位（換算1.5 MiB）。その他の設定等は固定する。改修前データを準備可能なブラウザで試験する。
- APIキャッシュ除去後には非APIデータと新規記録1件に必要な容量を確保できる試験環境とする。実クォータは対象ブラウザで確認し、UTF-16推定量と同一視しない。
- 初回表示: 操作後に対象欄が初めて描画されるフレーム。空の仮表示: 記録がある対象欄を空欄・未記録・読込中として表示する状態。
- 各ACは独立した初期状態で試験する。取得完了は成功応答後の描画完了、保存完了は当該保存処理完了を待つ。期限試験は時刻制御下で9分と11分を使用し、10分境界の丸めは新規規定しない。

#### Acceptance Criteria (AC)

- [ ] AC-1: Given 大容量フィクスチャと固定非APIデータを持つ改修前状態, When 通常条件で改修後の初回起動とAPI再取得・保存が完了する, Then 既存モニタのlocalStorage表示値は、旧APIキャッシュを除いた非APIデータのUTF-16換算量に既存の単位・小数点以下1桁の丸めを適用した期待値と一致する。
- [ ] AC-2: Given 移行済みで非APIデータが固定されAPIワークフローの内容だけを4 MiB相当に更新できる状態, When そのデータの取得・保存が完了する, Then 既存モニタのlocalStorage推定量は更新前の値と一致する。
- [ ] AC-3: Given 大容量APIキャッシュとメタ情報30件があり非APIデータの保存容量を満たす通常条件, When 異なる画像ID・timestamp昇順の生成を31件連続して受け付け各保存が完了する, Then 「生成時メタ情報の保存に失敗しました」の通知回数は0回である。
- [ ] AC-4: Given AC-3と同じ開始状態, When 31件の生成受付とメタ情報保存が完了する, Then 直近30件それぞれの記録済み生成条件を参照できる。
- [ ] AC-5: Given 直近画像AとBの異なる条件がブラウザに記録済みでメタ情報取得応答を保留している, When メタ情報欄を開いた状態でAからBへ切り替える, Then 対象欄の初回表示はBの記録値と一致する。
- [ ] AC-6: Given AC-5と同じ状態, When Bへの切替から保留した応答の到着前までを観測する, Then Bの対象欄にAの記録値または空の仮表示が出現するフレーム数は0である。
- [ ] AC-7: Given 直近30件外の画像Cの条件がサーバーに記録済みでSnapshot未保存, When Cのメタ情報取得が成功する, Then プロンプト・シード・ステップ数の表示はCの記録値と一致する。
- [ ] AC-8: Given ワークフロー一覧キャッシュを保存して9分経過し再読込後の同一覧取得応答を保留している, When 同ブラウザ・オリジンで再読み込みして一覧を開く, Then 応答到着前に保存時の一覧を参照できる。
- [ ] AC-9: Given 同一覧キャッシュを保存して11分経過し再読込後の取得応答を保留している, When 再読み込みして一覧を開く, Then 期限切れ一覧は再利用データとして表示されない。
- [ ] AC-10: Given 初回移行で必要なワークフローが未読込で取得応答を保留している, When Generate Batchの状態を確認する, Then ワークフローを必要とする投入操作は非活性である。
- [ ] AC-11: Given IndexedDBキャッシュの読取りが利用拒否で失敗するケース、または書込みが容量不足で失敗するケースのそれぞれで、サーバーから必要データを取得可能で通常の生成前提を満たす状態, When 取得完了後に1画像生成設定でGenerate Batchを1回実行する, Then 受付済みジョブが1件登録される。
- [ ] AC-12: Given 移行前に設定・ワークフロー入力・画像URL履歴・選択画像・保存済みSnapshotの固定試験データがある, When 初回移行と再読み込み後に各データを開く, Then 各表示値と対象IDは移行前の期待値と一致する。
- [ ] AC-13: Given 同じタブにサーバーより新しいStudio未保存下書きがあり競合がない, When 初回移行後に同タブを再読み込みして対象プロジェクトを開く, Then フォーム表示値は下書きの期待値と一致する。
- [ ] AC-14: Given ブラウザメタ情報保存は容量不足で失敗するがサーバー保存は成功する状態, When 新規画像の生成受付後にサーバーからメタ情報を取得する, Then 取得条件は当該画像の投入時記録と一致する。
- [ ] AC-15: Given ワークフロープリセットが別端末で更新されている通常条件, When 改修後に再起動して未編集のプリセットを取得する, Then 表示値はサーバー最新値と一致する。
- [ ] AC-16: Given 旧APIキャッシュ除去後かつ新APIキャッシュ保存完了前に起動処理を中断した状態で非APIデータは保存済み, When サーバー利用可能な状態で再起動して必要データ取得後に1画像生成を1回実行する, Then 受付済みジョブが1件登録される。
- [ ] AC-17: Given 移行済みのAPIキャッシュだけをブラウザから削除し非APIデータを維持した状態, When サーバーから必要データを取得後に1画像生成を1回実行する, Then 受付済みジョブが1件登録される。
- [ ] AC-18: Given 保存済みAPIワークフロー一覧キャッシュを持つ通常条件, When 再読み込み後にサーバーから更新済み一覧を取得・保存しさらに期限内に再読み込みして一覧応答を保留する, Then 応答到着前の一覧は更新後の保存値と一致する。

#### Inferred points

<inferred_points>

- 添付のReady to Implementは資料上の状態で本PBI承認ではない。パッケージ導入コマンド・コード差分は実行指示として扱わない。
- 「0ms」は初回表示が正しい条件と解釈した。絶対経過時間0msは保証しない。「1.5MB」「84%削減」「容量無制限」「完全根絶」は環境依存の説明で一般保証としない。試験量はUTF-16単位とMiBを明示する。
- 移行初回はサーバー接続が必要になり得る。旧APIキャッシュだけの破棄を許容する。全過去記録復元・無期限保持・オフライン生成保証は対象外。
- キャッシュ読書き拒否時のサーバー取得による回復（AC-11）は補足した仮定。複数タブ同時移行の詳細・最低ブラウザバージョンは設計で確認する。
- 添付のStudio下書き「DB同期完了時に破棄」はSPEC_DATASET_STUDIO 2.5「同期済みに更新」と異なる。今回下書き方式を変更せず現行正本を維持する。添付のキー表記も現行正本と異なるため改名を要求しない。
- REQ-161のlocalStorageキャッシュ保存・5MB上限は再配置に伴う置換対象。準備前投入防止とPC/モバイルでの正常投入という目的を維持する。
- SPEC_COMMON 6の保存先記述は承認後の改訂対象。現時点では正本を編集しない。REQ-317の30件保持・サーバー1000件・使用量モニタ、REQ-331のStudio編集保持を回帰境界とする。
- 未解決: 現環境の容量内訳・実クォータは未測定。設計時の再現条件確認で扱う。一般数値の効果保証は行わない。
