#### 運用上の目的 / 5 Whys

1. なぜ管理UI統合・通信見直しが必要か：PCとスマホから、生成・進捗確認・サービス復旧を同じアプリで行いたい。
2. なぜそれが困難か：管理画面が別になり、スマホで進捗や画像が取得できないこと、生成中のブラウザ切断で記録が欠落することが資料で問題視されている。
3. なぜ操作の中断が困るか：PCで開始した処理をスマホで見守り、画面ロックや移動後も結果を確認したいから。
4. なぜ表示だけの変更では不十分か：プロセス稼働と接続状態、通常生成とStudio、自端末と他端末、試行履歴と確定成果物を区別できないと、待機を故障と誤認し結果を失うため。
5. 根本の運用ニーズ：端末・画面の継続接続に依存せず、生成の状態と成果物を追跡し、障害時にも復旧経路を確保したい。

資料からの分析と2026-10-10のユーザー回答を統合した運用目的。2026-10-10、ユーザーは改訂35 ACを承認し、残る自動監査指摘を後続設計確認事項として扱って設計工程へ進むことを承認した。これは設計レビューへの進行承認であり、設計レビュー後の実装開始承認とは区別する。

#### UX Classification

- **Information Design**：プロセス状態と接続状態の識別、スコープ別進捗、待機理由、セッション絞り込み、一時履歴と永久保存の区別。
- **Interaction**：既存設定カードでのサービス操作とログ閲覧、切断復帰、端末間見守り、通常生成取消・失敗通知。スナップショット操作は既存維持。
- **Visual**：既存2段プログレスバーの配置を維持し、状態ラベル・色と待機バッジを加える。全面的な外観刷新は含めない。

#### 要件と変更範囲

1. 日常のサービス操作・ログ閲覧を設定ページの「システム」欄に統合する。8000停止時の非常復旧には既存8899の埋め込みFEを使う。
2. 生成投入・進捗・キュー照会・画像取得は、PCとスマホともメインアプリの接続先で利用可能とする。Managerは独立維持し、管理通信は生成通信とは別の経路を利用できる。
3. 本体と生成基盤が稼働したままブラウザが切断されても、受理済み生成の完了記録を残し、再接続でキューと結果を復元する。
4. 全端末同期を既定とし、自セッション絞り込みを提供する。未フィルタ時はセッション横断で通常生成の同じ進捗を表示し、他セッション待機は表示しない。フィルタON時だけ他セッション待機を表示する。通常生成とStudio間の待機はフィルタと独立して表示する。
5. 通常生成の取消は母数から除いて進捗を再計算する。生成失敗は通知し、進捗計算では終了分として扱う。Studioは1回のバッチリクエストごとに独立管理し合算しない。対象はStep 1の生成管理と通常生成との分離のみ。
6. 試行原画が欠損した結果は試行履歴表示から除外する。サムネ・メタデータは既存一時保存上限による自動削除に任せる。スナップショット品質・保存・削除、性能・資源上限・編集同期・表示アスペクト比等、アーキ変更に伴わない既存仕様は維持する。
7. 後続設計のユーザーレビューゲートで、既存仕様との衝突点一覧と各改修案を提示する。全ライフサイクル刷新ではなく既存仕様に対する変更差分を整理する。

#### アーキテクチャ意図（設計入力、ACではない）

- 管理UIは設定「システム」欄へ統合し、Manager BE（8899）は独立スーパーバイザーとして維持。生成関連HTTP/WS・画像取得は本体（8000）へ集約し、ComfyUI（8188）のブラウザ直接アクセスを廃止する。
- 既存 `SKILL.md` の「ReactからComfyUI直接アクセス」「FastAPIプロキシ禁止」、`docs/specs/server_manager_guide.md` の8188端末直接アクセス案は今回のアーキ変更による更新対象。衝突を理由に構想を撤回するのではなく、設計レビューで衝突一覧と改修案を提示する。
- `docs/specs/SPEC_SETTINGS.md` は既にsystemタブを定義。`SPEC_GENERATE.md` の非同期metadata往復保存は集約化との差分候補。`SPEC_GENERATE.md` / `SPEC_HISTORY.md` の30件/1000件cache上限・Snapshot独立保持、`SPEC_DATASET_STUDIO.md` の下書き/競合復元、`SPEC_COMMON.md` の画像比率設定は今回全面刷新する対象ではない。
- `scope` は通常生成/Studioの種別（normal/studio）を指し、Studioプロジェクト識別とは別。待機表示にプロジェクト名を併記してよいが必須ではない。
- 添付のAPIパス、イベントJSON、DBテーブル、ファイルパス、ライブラリは設計候補であり、本PBIのACで実装方式を指定しない。資料のロードマップは分割候補・実装順の根拠としても利用しない。

#### Acceptance Criteria (AC)

試験共通条件：同一の信頼済みLAN内の個人利用PCとスマホ、既知のジョブID・生成パラメータ・画像を用い、通信と状態変化を制御する。状態取得完了時点で同期結果を確認し、未指定の秒数を合否条件にしない。ブラウザ切断試験中は本体・生成基盤を稼働維持する。表示の「完了数」は正常完了と失敗終了の合計であり、失敗を生成成功として表示することを意味しない。

- [ ] **AC-01**: Given メインアプリ表示中, When 設定ページの「システム」欄を開く, Then サービス管理とログ閲覧のUIが同欄に表示される。
- [ ] **AC-02**: Given ComfyUIが停止中かつManager利用可能, When 同欄でComfyUI「起動」を実行し起動が成功する, Then ComfyUI稼働表示が起動状態になる。
- [ ] **AC-03**: Given ComfyUI稼働中かつManager利用可能, When 同欄でComfyUI「停止」を実行し停止が成功する, Then ComfyUI稼働表示が停止状態になる。
- [ ] **AC-04**: Given ComfyUI稼働中かつManager利用可能, When 同欄でComfyUI「再起動」を実行し再起動が成功する, Then ComfyUIが再び稼働状態として表示される。
- [ ] **AC-05**: Given メインアプリとManager利用可能, When 同欄で本体バックエンド「再起動」を実行し復帰後にアプリを開く, Then 本体バックエンド稼働状態が表示される。
- [ ] **AC-06**: Given 本体（8000）が停止しManager利用可能, When PCホストの既存8899埋め込みFEで本体を起動し成功する, Then メインアプリへ再アクセスできる。
- [ ] **AC-07**: Given 各サービスのログに識別可能な最新行がある, When 設定「システム」欄で対象サービスのログを選択する, Then 対象サービスの最新行が表示される。
- [ ] **AC-08**: Given 次の状態表の各前提, When メインアプリの状態取得が完了する, Then 対応するヘッダー総合ラベルが表示される。
