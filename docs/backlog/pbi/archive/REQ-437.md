### REQ-437: プリセット一括削除時の孤立workflow_preset_values残存によるプリセット新規作成IntegrityError修正

- **Type**: bug
- **Priority**: P1
- **Surface**: backend (API / DB / Migration)
- **Incident Report**: `docs/incident_report.md`
- **Defect Classification**: Type A — Implementation Defect（実装欠陥）
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: 生成画面でプリセットを新規追加（`POST /api/workflow-presets`）すると `IntegrityError`（HTTP 500）で作成不能になるため。
  2. なぜその課題が発生するか: 削除済みの `preset_id`（実DBでは `1900` など26件・1,872行）に紐づく `workflow_preset_values` の孤立行が DB に残存しており、再利用された `preset_id` と `(preset_id, variant_id, sub_key)` の UNIQUE 制約が衝突するため。
  3. なぜ現状の仕組みで不十分か: `bulk_delete_presets`（`backend/app/routers/presets.py:230-237`）が `Query.delete(synchronize_session=False)` で直接 SQL DELETE を実行し ORM の `cascade="all, delete-orphan"` を迂回している一方、`configure_sqlite_pragmas`（`backend/app/database.py:9-22`）が `PRAGMA foreign_keys=ON` を設定していないため SQLite の `ON DELETE CASCADE` も発火せず、さらに `workflow_presets.id` が `AUTOINCREMENT` なしのため削除済み最大 ID が再利用されるため。
  4. なぜこのアプローチを採用するか: 一括削除経路で子テーブル `workflow_preset_values` を確実に連動削除し、既存 DB の孤立行をマイグレーションで安全に浄化することで、新規作成のブロッカーと再発の双方を根本解消できるため。
  5. 根本原因: `bulk_delete_presets` の ORM カスケード迂回と SQLite `PRAGMA foreign_keys=ON` 未設定により、`workflow_preset_values` の孤立行が残存し、再利用された `preset_id` と UNIQUE 制約衝突を起こしている（詳細根拠は `docs/incident_report.md` 参照）。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 該当なし（バックエンド永続化・データ整合性の不具合修正）
  - **Interaction (インタラクション)**:
    - 生成画面からのプリセット追加・一括削除・再作成がエラーなく完了すること
  - **Visual (視覚デザイン)**:
    - 該当なし
- **Requirement**:
  - **1. 一括削除時の子レコード連動削除**:
    - `DELETE /api/workflow-presets/bulk`（`bulk_delete_presets`）実行時に、削除対象 `preset_id` に紐づく `workflow_preset_values` 行が確実に削除され、孤立行が残らないこと。
  - **2. 既存 DB の孤立 `workflow_preset_values` 行クリーンアップ**:
    - 起動時マイグレーションにおいて、`workflow_presets` に親が存在しない孤立 `workflow_preset_values` 行を冪等に削除すること（実DBで確認された 1,872 件を安全に除去）。
  - **3. SQLite 外部キー制約方針の整理（設計時確認）**:
    - `configure_sqlite_pragmas` での `PRAGMA foreign_keys=ON` 有効化の可否・影響範囲（実DBで検出された `dataset_projects.workflow_id` の孤立4件を含む）を設計フェーズで評価し、安全な方針を確定すること。
  - **4. 回帰テストの追加**:
    - プリセット作成 → `DELETE /api/workflow-presets/bulk` → 再作成のシーケンスで `IntegrityError` が発生せず 201 で作成成功することを検証する統合テストを追加すること。
- **Acceptance criteria**:
  - [ ] AC-1: Given プリセットと紐づく `workflow_preset_values` 行が存在する状態, When `DELETE /api/workflow-presets/bulk` で当該プリセットを一括削除する, Then 対象の `workflow_presets` 行と対応する `workflow_preset_values` 行がすべて削除され孤立行が 0 件であること。
  - [ ] AC-2: Given 最大 ID のプリセットを `DELETE /api/workflow-presets/bulk` で削除した直後の状態, When `POST /api/workflow-presets` で同じバリアントキーを含むプリセットを新規作成する, Then `IntegrityError` が発生せず HTTP 201 で正常に作成・保存されること。
  - [ ] AC-3: Given `workflow_presets` に親が存在しない孤立 `workflow_preset_values` 行を含む既存 DB, When マイグレーションを実行する（および再実行する）, Then 孤立行のみが冪等に削除され、有効なプリセットおよびその `workflow_preset_values` 行は破損せず保持されること。
  - [ ] AC-4: Given 既存のプリセット CRUD・単件削除・並び替え・楽観ロック（409）・ワークフロー複製機能, When 修正後のバックエンドテストスイートを実行する, Then 既存機能に回帰が発生せず全テストが PASS すること。
- **Inferred points**:
  - `PRAGMA foreign_keys=ON` のグローバル有効化は、`dataset_projects.workflow_id`（実DBで4件の孤立行）など他テーブルの既存孤立データへ影響する可能性があるため、設計フェーズで影響調査のうえ採否を決定する。
