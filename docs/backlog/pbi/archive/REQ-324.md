### REQ-324: Prompt Surgeon: フロントエンド肥大化モジュールおよびコンポーネントの構造分割整理 (api/client.ts & HistoryModalPreview)

- **Type**: refactoring
- **Status**: done (2026-10-08)
- **Current step**: none
- **Priority**: P1
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-01 (Task 1.1) および REF-06 (Task 2.2) に基づき、フロントエンドにおける 2 大肥大化ファイル（API 通信層 `api/client.ts` および UI プレビュー層 `HistoryModalPreview.tsx`）の構造分割整理を実施する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: 新機能の急速な追加により、`client.ts` (35KB/800行超) と `HistoryModalPreview.tsx` (500行超) に責務が集中し、可読性低下・エディタ負荷・マージ競合が頻発しているため。
  2. なぜ肥大化したのか: API エンドポイントやモーダル機能を追加する際、既存の巨大ファイルに追記する方が手軽であったため。
  3. なぜ既存ファイルに追記し続けたのか: ドメイン境界ごとのモジュール分割指針や Atomic コンポーネント設計が明文化・分離されていなかったため。
  4. なぜ分割整理を今行うのか: 全体テスト 100% 成功の強固な検証基盤がある今こそ、外部コードへの破壊的変更なしにリファクタリングを安全に完遂できる絶好のタイミングであるため。
  5. 根本原因: 急速な機能拡張を優先した結果としての技術的負債であり、集約 re-export ハブおよび Atomic サブコンポーネント化により後方互換性を保ちながら負債を解消する必要がある。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - `api/` レイヤーを純粋トランスポート層 (`core/`) とドメイン別リソース層 (`domains/`) に分離整理
    - `client.ts` を集約 re-export ハブとして維持し、外部インポート文の後方互換性を 100% 担保
  - **Visual / Interaction (UI/インタラクション設計)**:
    - `HistoryModalPreview.tsx` のプレビュー表示、メタデータ解析表示 (`SnapshotMetadataTab`)、動的タグ PATCH エディタ (`TagAssociationEditor`) を分離
    - 適切なメモ化 (`React.memo`) によりタブ切替時の不要な再レンダリングを抑制

#### Acceptance Criteria (AC)

- [ ] **AC-1 (API Core 分割)**: Given 肥大化した単一の `frontend/src/api/client.ts` が存在するとき、When HTTP 通信基盤（`request<T>`, `getApiBaseUrl`, 共通ヘッダー・認証・共通例外生成）が `frontend/src/api/core/base.ts` に、SSE/NDJSON イベントストリーム処理が `frontend/src/api/core/stream.ts` に責務分離して切り出された場合、Then コア層が自己完結して動作し、循環参照なく各ドメイン層から再利用できること。
- [ ] **AC-2 (API Domains 分割)**: Given 各種 API 群が `client.ts` に集中しているとき、When ドメイン別モジュール（`frontend/src/api/domains/` 配下の `workflows.ts`, `snapshots.ts`, `speech.ts`, `translation.ts`, `loraStudio.ts`, `settings.ts` 等）へ分割配置された場合、Then 各ドメインモジュールが自身の責務に応じたエンドポイント・関数のみをカプセル化していること。
- [ ] **AC-3 (API 後方互換 re-export & 型契約整合)**: Given 既存のすべてのコンポーネント・フック・テストが `@/api/client` または `../api/client` から API オブジェクトおよび関数をインポートしているとき、When `frontend/src/api/client.ts` が各ドメインモジュールおよびコア層からの透過的 re-export ハブとして機能するようにリファクタリングされた場合、Then 既存のインポート元コードを 1 行も修正することなく従来と完全同一のシンボル・型定義・実行時インスタンスが解決され、型欠落が発生しないこと。
- [ ] **AC-4 (UI HistoryModalPreview 分割 & メモ化)**: Given 肥大化した `HistoryModalPreview.tsx` において、When メタデータ正本解析・表示領域（例: `SnapshotMetadataTab`）および動的タグ PATCH エディタ領域（例: `TagAssociationEditor`）が独立したサブコンポーネントに切り出され、適切なメモ化（`React.memo` 等）が施された場合、Then スナップショット情報表示およびタグ編集操作が劣化なく動作し、親コンポーネントのコード量が削減されること。
- [ ] **AC-5 (循環参照ゼロ & パフォーマンス)**: Given モジュールおよびコンポーネント分割後において、When 依存関係および再描画挙動を検証したとき、Then コア層・ドメイン層間で循環参照（Circular Dependency）が 0 件であり、モーダル内タブ切替時にモーダル全体の不要な再レンダリングが発生しないこと。
- [ ] **AC-6 (3-Gate ベースライン維持)**: Given リファクタリング適用後のフロントエンドコードベースにおいて、When TypeScript 型検査 (`npm run typecheck`) および Vitest 全体テスト (`npm test`) を実行したとき、Then 型エラー 0、テスト失敗 0 件（100% PASS）で既存のすべての振る舞い・契約が完全に維持されていること。
