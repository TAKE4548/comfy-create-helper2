### REQ-366: デザインルールの定義にアンチパターンの定義を追加（UI/UX ガバナンス・3層パイプライン整備）

- **Type**: feature
- **Status**: done (2026-10-15)
- **Priority**: P2
- **Surface**: Docs, Governance, Frontend
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: UI/UXの不具合修正時に「CSS一括文字サイズ底上げ（11px Floor）」や「二重パディング」などの対症療法が施され、新たなレイアウト崩壊や文字突き破りなどの二次災害が誘発されているため。
  2. なぜその課題が発生するか: デザイン仕様書に「推奨事項」はあっても「やってはいけない具体的なコード構文・アンチパターン」が明文化されていないため。
  3. なぜ現状の仕組みで不十分か: 単に一般的なアンチパターン18項目を長大ドキュメントとしてシステムプロンプトやエージェント定義に常時注入すると、コンテキストトークンの恒常的浪費（2,000〜3,000トークン）と注意力の希釈（バックエンド改修時のノイズ）が生じるため。
  4. なぜこのアプローチを採用するか: 「SSoTカタログ」「共通6大ハード制約」「Task Cardへのサージカル注入」「Linter/Gate 1機械的即死」からなる3層パイプラインに構造化することで、コンテキスト汚染をゼロにしつつ機械的にアンチパターンを排除できるため。
  5. 根本原因: デザインガイドラインにおけるアンチパターンの未体系化と、エージェント駆動開発（Antigravity SDD）に適したコンテキスト注入・静的検証パイプラインの欠落。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - SSoTとしてのUI/UXアンチパターンカタログ（モバイル10選・PC8選）の仕様書体系化（`docs/specs/SPEC_COMMON.md` への正本同期）。
    - エージェント向け共通コンテキスト（`.agents/context.md`）における6大ハード不変条件（および詳細SSoTへの参照ポインタ）の分離配置。
  - **Interaction (インタラクション)**:
    - モバイルでの中央モーダル禁止（ボトムシート強制）、入力フォーカス時のアクションバー退避除外ガード（checkbox/radio/button保護）、Flex内truncate時のmin-w-0担保、overscroll-behavior-yによるジェスチャー競合防止。
    - PCでの超ワイド画面コンテナ上限（max-w-7xl）、OS拡大率（125%/150%）対応（固定px高さを排除しmax-h/overflowでスクロール担保）、モーダル多重ネスト禁止。
  - **Visual (視覚デザイン)**:
    - グローバルCSS（`index.css` や `html/body` セレクタ）によるフォントサイズ一括底上げ（Global Font Floor）の禁止と、コンポーネント内個別トークン指定（`text-[11px]` / `text-xs`）の徹底。
    - Hit-Slop拡張（見た目は小さく、透明な判定領域を44px確保）による視覚的な密集と誤操作防止の両立。
- **Requirement**:
  - **1. SSoTアンチパターンカタログの正式策定 (Layer 1)**:
    - モバイル10選（Global Font Floor、Flex truncate不発、中央モーダル、二重パディング、タッチ判定密集/誤肥大、IME衝突、input判定雑駁、英単語突き抜け、ジェスチャー競合、過剰ブラー）およびPC8選（超ワイド崩壊、OS拡大率崩れ、ペイン幅固定、ホバー依存、ショートカット欠落、一括操作欠落、多重スクロールバー、多重モーダル）をSSoT仕様に定義する。
    - エラーメッセージ、ID、ステータス表示（`<code>`, `<span class="status">`, `data-id` 等）に対する安易なtruncateの禁止ガイドラインを明記する。
  - **2. 共通ハード不変条件のコンテキスト配置 (Layer 2)**:
    - 全エージェントが初動で読み込む `.agents/context.md` に、構文レベルで判定可能な「UI 6大ハード不変条件」をコンパクト（約300〜500トークン）に追記し、詳細な根拠・事例は `SPEC_COMMON.md` への参照ポインタとする。
  - **3. dev-design タスクカード自動注入プロトコルの策定 (Layer 3)**:
    - フロントエンド改修を伴うタスク（フロント単体またはフルスタック改修のフロント対象スコープ）にのみ、該当するUI制約をTask Cardの `<constraints>` にピンポイント注入する設計手順を確立する。
  - **4. Gate 1 機械的即死検証ルールの導入と例外機構 (Gate)**:
    - 構文・単位違反（グローバルセレクタでのpx底上げ、`!important`、コンテナの生 `vh` 単位等）を検証する静的Linterまたはスクリプトを導入し、Gate 1で機械的に即座に失敗（Exit Code 1）させるガードレールを整備する。
    - 移行期におけるレガシーコード保護のため、コメントによる正当な理由付き例外（Allowlist / ignoreコメント）機構を設ける。
- **Acceptance criteria**:
  - [ ] AC-1: Given プロジェクトのSSoT仕様（`docs/specs/SPEC_COMMON.md`）, When 仕様書を参照した際, モバイル10選およびPC8選のUI/UXアンチパターンと正当な防御策（コード例・重要情報の非省略ルール含む）が体系的に記載されていること。
  - [ ] AC-2: Given エージェント設定ファイル（`.agents/context.md`）, When コンテキストファイルを検証した際, 「UI 6大ハード不変条件（No Global Font Floor, Viewport Units, Mobile Modals, Strict Input Guard, Flex Truncate, Desktop Container）」が約300〜500トークン以内で簡潔に定義され、SSoTへの参照ポインタが含まれていること。
  - [ ] AC-3: Given dev-designスキル仕様およびタスクカード生成規則, When フロントエンド対象のTask Cardが生成される際, 該当するアンチパターン防止制約が `<constraints>` タグ内にサージカル（局所的）に自動挿入される規約が明文化されていること。
  - [ ] AC-4: Given 静的検証コマンド（Gate 1）, When グローバルCSSでのフォント底上げや禁止構文（`!important`, `vh` 等）が含まれるコードを検証した際, Linterまたは検査スクリプトが Exit Code 1 で即座に検出しコミット・検証通過をブロックすること。例外が必要な場合は明示的な許可機構（Allowlist/コメント）を介して制御できること。
  - [ ] AC-5: Given バックエンドのみを変更するTask Card, When エージェントが実装を実行する際, UIアンチパターンによるコンテキスト汚染が生じず、Task Card内に余計なUI規約が含まれないこと。
- **Inferred points**:
  - Gate 1での禁止CSS検出には、Stylelint導入または軽量な静的チェックスクリプト（例: `scripts/verify_ui_invariants.py`）を配置し、CIおよびローカル検証のGate 1（3〜5秒以内）で実行する。
  - 既存画面（REQ-357対象等）の既存コードに影響を与えないよう、新規/ステージング変更差分のみを対象とするか、レガシー除外設定を併用してスムーズに導入する。
