### REQ-248: OpenAPI JSONへの一本化とopenapi-typescriptによるFE型生成・同期チェック

- **Type**: enhancement
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: FastAPIのAPI定義、保存済みOpenAPI、フロントエンドAPI型と型参照、契約テスト・開発用チェックコマンド。OpenAPI JSONへ一本化し、既存ツールでFE型生成と同期漏れ検出を自動化する。
- **現状確認（2026-10-26）**:
  - 正本は仕様上`backend/openapi.json`だが、保存データはJSONが115path、`docs/openapi.yaml`が120pathで、パス集合と全文が一致しない。
  - 一部の契約テストはWorkflow/Mappingの特定契約を実行時OpenAPI・JSON・YAMLと比較する。全APIの静的出力CLI、FE型生成または全体照合、同期チェックの仕組みは調査範囲では見つからなかった。
  - API型は`frontend/src/api/types.ts`だけでなく`frontend/src/api/domains/generation.ts`等にもある。生成元を持たない型を残したまま生成ファイルだけを追加しても、実際のクライアントの同期は保証できない。
- **UX Classification**: Information Design / Reliability（API契約の正本統一と、開発時の同期漏れ検出）。利用者向けの通信・画面操作は変更しない。
- **Requirement**:
  - FastAPI定義から、Uvicorn起動や稼働APIへのHTTP取得を必要とせず、再現可能な`backend/openapi.json`を出力するコマンドを整備する。出力のためにアプリのlifespan・生成worker・外部推論等を起動したり、実DBの初期化・移行・データ変更を行わない。
  - OpenAPIの保存形式をJSONへ一本化する。`docs/openapi.yaml`を参照する現行のテスト・仕様・運用手順を調査してJSON参照へ移行した後、YAML版を廃止する。過去の完了・廃止PBIやログの記述は履歴として扱い、一括改変しない。
  - `openapi-typescript`を使用し、保存済みJSONからFEのAPI型を生成する。生成物を手編集せず、生成ツールのバージョン・オプション・出力先を固定して再現可能にする。
  - API層で使う手書き型を調査し、生成型への参照・互換alias等へ移行する。画面専用状態などAPI契約外の型は区別し、独立した手書きAPI型の二重管理を残さない。
  - 既存APIクライアントと通信制御を維持する。応答不明時のrequest照合、再送防止、キャンセル・エラーの意味を変えない。HTTPクライアント・React Queryフック・MSWモックの全面自動生成や置換は本PBIの必須範囲に含めない。
  - JSON出力とFE型生成に更新用コマンドと検査用コマンドを設ける。検査では実装と保存JSON、保存JSONと生成型の同期漏れを検出し、管理対象ファイルを書き換えず非ゼロ終了する。開発時・自動検証時の正式な実行経路へ組み込む。

#### Acceptance criteria（2026-10-26レビュー後の現行AC）

- [ ] AC-1: Given API定義と必要なローカル依存がある, When OpenAPI更新コマンドを実行する, Then サーバー起動やHTTP取得なしで最新のbackend/openapi.jsonを生成でき、同じ入力・設定で再実行して不要な差分が生じず、実DB・生成worker・外部サービスに副作用がないこと。
- [ ] AC-2: Given 保存済みOpenAPI JSON, When 固定バージョン・設定のopenapi-typescriptで型生成する, Then リクエスト・レスポンス・パラメータ等のAPI型が再現可能に生成され、生成物を手編集する必要がないこと。
- [ ] AC-3: Given FE API層の型を生成型への参照へ移行した状態, When 型チェックおよび既存クライアントの正常・失敗・応答不明フローを検証する, Then 型が整合し、既存の通信・照合・再送防止・エラー/キャンセル動作と公開された型参照の互換性が維持されること。API型の移行対象・残す画面専用型とその理由が追跡できること。
- [ ] AC-4: Given API定義だけを変更した場合、または保存JSONだけを変更して生成型が古くなった場合, When 正式な同期チェックを実行する, Then それぞれの同期漏れを検出して非ゼロ終了し、管理対象のJSON・生成型・手書きソースを更新しないこと。同期済みなら同チェックが成功し、チェックの実行方法が開発・自動検証経路に明記されること。
- [ ] AC-5: Given 現行テスト・仕様・運用手順でYAML参照をJSONへ移行した状態, When YAML版を廃止して検証する, Then docs/openapi.yamlがなくても現行の契約テスト・開発コマンドが成立し、JSONがOpenAPI保存物の正本として参照され、YAMLを現行契約として読む利用箇所が残らないこと。履歴資料の参照は除外理由を記録すること。

- **設計・検証への引継ぎ**:
  - 公式ツールを利用し、独自のOpenAPI→TypeScript生成器を実装しない。採用バージョンの`--check`等の挙動を確認し、実装→JSONの検査と合わせて非更新チェックを設計する。
  - OpenAPIに宣言されていない例外応答は、型生成だけで補われない。REQ-391の`GET /api/generation/state` 503記載修正は別の具体的残件として維持し、YAML廃止と競合しない順序・対象を設計前に整理する。REQ-391の「他ファイル差分なし」という旧制約を、本PBIのYAML移行へ暗黙に適用しない。
  - 型生成後も実データのランタイム検証の代替にはならない。既存decode/validationや応答不明処理を型生成だけを理由に削除しない。
  - ツール導入・検証経路・公開API契約を扱うため、適用される全スイートfallbackを含む現行検証規約に従う。機械的な型生成成功だけで意味上の互換性をPASSにしない。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: OpenAPI スキーマ静的同期自動化と TypeScript 型安全性の静的検証（Contract Drift 防止）

- **Type**: enhancement
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**:
  - バックエンドの FastAPI エンドポイント定義・Pydantic スキーマの更新と、`docs/openapi.yaml`、およびフロントエンドの TypeScript 型定義（`frontend/src/api/types.ts`）の同期が手動運用（バックエンド起動後に `/openapi.json` を手動取得）に依存している。
  - バックエンド側のリクエスト/レスポンス型を変更した際にフロントエンド側の型が追従せず、ランタイムまで API 契約のズレ（Contract Drift）が検知できないリスクがある。
- **Root Cause**:
  - (Lack of Automated Contract Verification / 開発環境・パイプライン欠如): スキーマ出力および型生成のビルドパイプラインが存在せず、人間による手動同期に依存している。
- **Requirement**:
  - バックエンドサーバーを起動することなく、FastAPI の `app.openapi()` から直接静的に `docs/openapi.yaml` / `openapi.json` を出力する CLI スクリプト（例: `scripts/export_openapi.py`）を整備すること。
  - 出力された OpenAPI スキーマからフロントエンド向け TypeScript 型定義を自動生成するツール（または手動型定義との整合性を検査する Linter スクリプト）を導入すること。
  - テストまたは CI コマンド（`npm test` / `pytest`）実行時に、スキーマの未コミット差分や型定義の乖離を自動検知できるようにすること。
- **旧Acceptance criteria（履歴・適用終了）**:
  - 旧AC-1: Uvicorn サーバーを立ち上げることなく、Python スクリプト単体実行で最新の `docs/openapi.yaml` が完全生成・更新できること。
  - 旧AC-2: バックエンドの Pydantic モデル変更時に、フロントエンド型定義との差異を静的に検出または自動生成する仕組みが提供されていること。
  - 旧AC-3: 既存のフロントエンド `api/client.ts` が壊れず、型定義の移行が安全に行えること。
