### REQ-339: プレビューエリアのアスペクト比非依存・高さ基準動的マルチ表示レイアウトおよびリソースモニタ移設

- **Type**: feature
- **Status**: done (2026-10-11)
- **Priority**: P2
- **Surface**: デスクトップ生成ページ メインプレビュー領域（`DesktopLayout` / `GenerateParallelPreview`）、デスクトップヘッダー領域、リソースモニタ（`ResourceGaugeHUD`）
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: プレビューエリアで複数画像を並列表示する際、固定の2:3縦長カード枠を前提としたレイアウトになっており、かつプレビュー右上にリソースモニタHUDが重畳しているため。
  2. なぜその課題が発生するか: ComfyUIで生成される画像は正方形（1:1）や横長（16:9）など多種多様なアスペクト比を持つにもかかわらず、固定の2:3枠を前提とした列数分割を行っているため。また、余白を使い切ってフル表示すると、右上に重畳しているHUDがプレビュー画像を直接覆い隠してしまうため。
  3. なぜ現状の仕組みで不十分か: 横長や正方形の画像を固定の2:3枠に当てはめると、不要な黒帯・余白（レターボックス）が生じるか画像が極端に縮小され、プレビューエリアの横幅が有効活用されない。さらにプレビュー画像を全面に広げるとHUDが画像閲覧を妨害するため。
  4. なぜこのアプローチを採用するか: プレビューエリアの高さを基準に全画像の高さを揃えた上で各画像本来のアスペクト比を維持して動的に並べ、併せてリソースモニタをプレビュー領域上からヘッダー部等のグローバル領域へ移設することで、一切の遮蔽と無駄な余白を排除した最適な閲覧環境を実現できるため。
  5. 根本原因: 固定アスペクト比（2:3）前提のカード配置設計と、プレビュー領域内オーバーレイに依存したリソースモニタ配置による表示領域の制約。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 多様なアスペクト比（1:1, 16:9, 9:16, 4:3等）の生成画像を、アスペクト比の歪みや不要なレターボックス/ピラーボックスなしでそのまま視認可能にする。
    - システム監視ステータス（CPU/RAM/GPU/VRAM/ストレージ）とプレビュー画像を明確に分離し、デスクトップヘッダー部へ情報集約する。
  - **Interaction (インタラクション)**:
    - ペイン分割比率のドラッグ変更やブラウザリサイズに応じて、利用可能横幅に収まる表示枚数を即座に動的再計算（過剰な再描画を防ぐデバウンス制御を含む）。
    - 現在の横幅に収まりきらない画像群に対して、スムーズなページネーション（左右矢印操作）を提供し、閲覧性を担保。
    - 画像クリック時の選択ハイライト、ActionBarや各種生成アクションとの連携を既存と同一の操作感で維持。
  - **Visual (視覚デザイン)**:
    - プレビュー領域の利用可能高さに合わせた均一なベースライン（高さ統一）による視覚的安定感。
    - 極端な縦長画像に対する最小幅ガードを設け、視認性を維持。
    - プレビュー画像上の重畳物を撤去したクリアなキャンバス表示。
    - ヘッダー内のデザインと調和したリソース表示（段階的警告カラー zinc-400 / amber-400 / red-400 の維持）。
- **Requirement**:
  - **1. 高さ統一と本来のアスペクト比の維持**:
    - デスクトップのプレビュー領域における実効描画高さに合わせて全画像の高さを揃え、各画像の元のアスペクト比（幅:高さ）を保持して表示すること。
    - 画像の引き伸ばし、クロップ（切り抜き）、不要な黒帯（レターボックス/ピラーボックス）を排除すること。
  - **2. 利用可能横幅に応じた動的表示枚数の算出**:
    - 各画像の表示幅（統一高さ × アスペクト比）と要素間ギャップに基づき、プレビューコンテナの横幅内に収まる最大枚数を動的に算出して1行に並べること。
    - 横長画像の場合は表示枚数が減り、縦長画像の場合は表示枚数が増えるなど、空きスペースに応じた柔軟な配置を行うこと。
    - 異なるアスペクト比の画像が混在する場合でも、先頭から累積幅を計算してコンテナ幅に収まる枚数を決定すること。
    - 極端な縦長画像であってもカードが極小化しない最小幅ガード（下限幅）を設けること。
  - **3. ペイン境界ドラッグ・リサイズへの追従**:
    - デスクトップのスプリッタードラッグによるペイン幅変更やウィンドウサイズ変更時に、即座に表示枚数を再計算して追従すること。
  - **4. 横幅超過アイテムのページネーション閲覧**:
    - 1行に収まらない余剰画像が存在する場合、左右のナビゲーション操作（矢印ボタン等）により前後の画像群へ切り替え可能とすること。
  - **5. リソースモニタのヘッダー部移設とプレビュー遮蔽排除**:
    - デスクトップ環境において、プレビューエリア右上に重畳表示されていたリソースモニタHUDをデスクトップ常設ヘッダー部へ移設し、プレビューエリアの画像上にUIが被らないようにすること。
    - ヘッダー部においてCPU, RAM, GPU, VRAM, ストレージ推定量がコンパクトかつ視認可能であり、警告カラー表示等の監視機能を維持すること。
  - **6. 既存インタラクション・状態およびモバイル仕様の保護**:
    - クリックによる画像選択、アクティブ枠表示、進捗表示、ActionBarとの連動が損なわれないこと。
    - モバイルレイアウト（`MobileLayout`）独自のプレビュー枠（42vh）およびヘッダーチップ表示と競合・退行しないこと。
- **Acceptance criteria**:
  - [ ] AC-1: Given デスクトッププレビューエリアに異なるアスペクト比（例: 1:1, 16:9, 2:3）の生成画像群が存在する, When プレビューエリアに画像を表示した際, Then 全ての画像がコンテナの利用可能高さに統一された同じ高さで表示され、画像が引き伸ばされたり切り抜かれたりすることなく本来のアスペクト比のまま表示されること。
  - [ ] AC-2: Given プレビューエリアのコンテナサイズが一定の状態で同アスペクト比の画像群を表示する, When 横長画像（16:9）を表示する場合と縦長画像（2:3）を表示する場合を比較した際, Then 横長画像では1枚あたりの横幅が大きいため少ない枚数が表示され、縦長画像では1枚あたりの横幅が小さいためより多くの枚数が空きスペースの許す限り自動的に横並びで表示されること。
  - [ ] AC-3: Given アスペクト比が混在する複数の生成画像群が存在する, When プレビューエリアに描画される際, Then 先頭アイテムから順に「統一高さにおける各画像の表示幅 + アイテム間ギャップ」を累積し、コンテナの利用可能横幅を超えない最大枚数の画像が1行に動的配置されること。
  - [ ] AC-4: Given プレビューエリアに複数画像が表示されている, When ユーザーがペイン境界のスプリッターをドラッグしてプレビューエリアの横幅を拡大または縮小する, Then リサイズ後の利用可能横幅に応じて滑らかに表示可能枚数が再計算され、横幅が広がれば表示枚数が増加し、狭まれば減少すること。
  - [ ] AC-5: Given 現在の横幅に収まりきらない複数画像（余剰アイテム）が存在する, When 左右のナビゲーション操作（矢印ボタン押下等）を行う, Then 現在の横幅に収まる次（または前）の画像セットへと表示が切り替わり、全ての画像を閲覧できること。
  - [ ] AC-6: Given デスクトップ環境で生成ページを表示した状態, When プレビューエリアおよびヘッダーが表示される際, Then リソースモニタがプレビューエリア内の重畳表示からデスクトップヘッダー部へと配置され、プレビューエリア内の画像表示がリソースモニタによって遮蔽されないこと。
  - [ ] AC-7: Given ヘッダー部に配置されたリソースモニタ, When システムリソースの監視情報を受信または逼迫（85%/95%超過）した際, Then 各指標（CPU, RAM, GPU, VRAM, ストレージ推定量）がヘッダーの既存要素と干渉せずに表示され、既存の段階的警告カラー（amber, red等）が正しく機能すること。
  - [ ] AC-8: Given 動的マルチプレビュー表示されている任意の画像, When ユーザーがいずれかの画像をクリックして選択する, Then 選択された画像がアクティブ状態として視覚的にハイライトされ、既存のGenerate状態（選択画像、ActionBarのアクション対象）へ正しく反映されること。
- **Inferred points**:
  - プレビュー領域の利用可能高さは、プレビューペインの親コンテナの高さ（上下のツールバー・ActionBar・パディング等を除いた実効描画領域）に追従することを想定。
  - 各画像のメタデータ（アスペクト比/元解像度）は、生成完了データや画像ロード時の自然解像度（naturalWidth / naturalHeight）から取得されることを想定。
  - ヘッダー部のリソース表示は、モバイル版のコンパクトなチップ表現（ResourceGaugeChips）やヘッダーユーティリティ領域のスタイルに合わせたコンパクト設計を想定。
  - モバイル環境（`MobileLayout`）は本改修の直接対象外とし、既存の42vh枠およびヘッダーチップ構成を維持することを想定。
