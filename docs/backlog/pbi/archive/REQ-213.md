### REQ-213: データベースマイグレーションの堅牢化（Alembic移行またはマイグレーション分離）とモデル定義SSoT化
- **Type**: refactor
- **Status**: done
- **Current step**: Phase 3: Verification & Closure (Done)
- **Priority**: P1
- **Surface**:
  - `backend/app/main.py` の `run_migrations()` 内に、180行以上の生SQL（`ALTER TABLE`, 一時テーブル作成、データ退避・コピー、外部キー付与）がハードコードされており、アプリケーションの起動ライフサイクルとスキーマ変更ロジックが密結合している。
  - カラム追加やインデックス変更のたびに `main.py` に手続き型SQLが追記されるため、マイグレーションのバージョン管理・ロールバック・実行順序の保証が存在しない。
  - `models.py` の定義と `run_migrations()` 内の生SQLの二重管理が発生しており、新規DB作成時（`Base.metadata.create_all`）と既存DBマイグレーション時でスキーマ定義のズレが生じる深刻なデグレリスクがある。
- **Root Cause**:
  - **Ad-hoc Migration Pattern**: SQLite向けの簡易マイグレーションをエントリーポイントにインライン記述し続けた結果、技術的負債として肥大化したこと。
- **Requirement**:
  - `main.py` から `run_migrations` を完全に分離し、Alembicによる標準的なリビジョン管理へ移行するか、専用の独立したマイグレーションランナー（`app/migrations/`）へモジュール化すること。
  - テーブルスキーマ（カラム型、制約、デフォルト値、外部キー）のSingle Source of Truth (SSoT) を `models.py` / Alembicリビジョンに一本化すること。
  - 新規DB作成時と既存DB更新時のスキーマ一致性を検証するテストを追加すること。
- **Acceptance criteria**:
  - [x] AC-1: `main.py` から生SQLマイグレーションロジック（約180行）が排除され、エントリーポイントがクリーンになっていること。
  - [x] AC-2: マイグレーションスクリプトが独立したモジュールまたはAlembicリビジョンとして管理され、べき等性（Idempotency）が担保されていること。
  - [x] AC-3: 空の新規DBおよび過去バージョンの既存DBの双方が、正しく最新スキーマへ整合することを確認するテストが存在すること。
  - [x] AC-4: 既存の全バックエンドテスト（`pytest`）がすべてパスすること。
