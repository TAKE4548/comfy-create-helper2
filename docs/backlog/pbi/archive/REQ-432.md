### REQ-432: VRAMガードが自セッション残留VRAMを判別できず同一セッションでも生成が解放待ちになる

- **Type**: bug
- **Priority**: P2
- **Surface**: backend/app/services/generation_service.py, backend/app/services/resource_monitor.py, docs/specs/SPEC_GENERATE.md
- **Incident report**: docs/incident_report_vram-guard-wait.md (Type B: 仕様欠落・暫定。実機での占有元切り分けと待機の実再現は未実施)
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: 生成完了後も VRAM 空きが閾値未満のままとなり、次 job が queued で保留される。
  2. なぜ発生するか: ComfyUI がモデルを保持し続け、Backend に生成後の自動解放(/free)経路がない。
  3. なぜ現状で不十分か: ガード判定(generation_service.py:713-727, 1602-1609)がマシン全体の空き VRAM のみを見て、占有元(自アプリ残留/他プロセス)を区別しない。
  4. なぜこのアプローチか: SPEC_GENERATE.md:478 が自セッション残留の扱いを規定していないため、仕様改訂を先行する。
  5. 根本原因: 仕様欠落(Type B・暫定)。加えて resource_monitor.py:164-168,272 が全アダプタ合算で primary_luid 未適用、値は 2.5 秒キャッシュ(実装欠陥の可能性)。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 保留理由(自アプリ残留/外部占有)を区別して表示するか設計で判断する。
  - **Interaction (インタラクション)**:
    - 手動「メモリ解放」との関係を設計で整理する。
  - **Visual (視覚デザイン)**:
    - 変更なし(設計で必要なら追記)。
- **Requirement**:
  - **1. 自セッション残留 VRAM の扱いの仕様化**:
    - 生成後の自動/オプトイン /free、または残留分のガード判定除外を設計で選定し、SPEC_GENERATE.md を改訂する。
  - **2. ガード判定用 VRAM 値の正確化**:
    - 対象アダプタを primary LUID に限定し、判定直前に再サンプリングする。
  - **3. 事前計測**:
    - 実装前に ComfyUI プロセス別 VRAM を実機計測して占有元を確定し、分類(Type A/B)を確定する。
- **Acceptance criteria**:
  - [ ] AC-1: Given 同一セッションで生成が完了し ComfyUI がモデルを保持している, When 次の生成が投入される, Then 自セッション残留 VRAM のみを理由に無期限の解放待ちにならないこと
  - [ ] AC-2: Given 他プロセスが VRAM を閾値以上占有している, When 生成が投入される, Then 従来どおり保留され、保留理由が自セッション残留と区別できること
  - [ ] AC-3: Given 複数 GPU アダプタが存在する, When VRAM 空きを算出する, Then primary LUID のアダプタのみが使用量に含まれること
  - [ ] AC-4: Given VRAM が解放された直後, When ガード判定が行われる, Then 古いキャッシュ値ではなく判定直前の値で判断されること
- **Inferred points**:
  - 分類は暫定。占有元の実機切り分け結果によっては Type A(実装欠陥)中心になり得る。
  - 自動 /free はモデル再ロード待ちを招くため、既定値とオプトイン可否は設計で判断する。
