### REQ-181: バッチ・複数プリセット生成時のキュー投入高速化と通信オーバーヘッド削減

- **Type**: performance
- **Status**: done (2026-08-26)
- **Priority**: P1
- **Surface**: 複数プリセットやバッチ数を指定して生成を実行した際、ComfyUIへのキュー投入完了までに1件ずつ数秒以上かかり、キューに積まれるまでの待機時間が長い。
- **Root Cause**:
  1. **WebSocket `status` 受信時の不要な `fetchHistory` 乱発**: ComfyUIにジョブが投入されるたびにWebSocket `status` イベントが届き、フロントエンドが毎回 `fetchHistory(100)`（最大100件の履歴全件取得・JSONパース・画像抽出・localStorage書き込み）を無条件に発火して通信帯域とメインスレッドを圧迫している。
  2. **バックエンドにおけるTCP接続の都度生成**: `backend/app/routers/comfy.py` のComfyUIプロキシ処理において、毎リクエスト `async with httpx.AsyncClient()` でTCP接続を都度生成・破棄しており、接続ハンドシェイクのオーバーヘッドが蓄積している。
- **Requirement**:
  1. WebSocket `status` 受信時の不要な `fetchHistory()` 呼び出しを廃止し、画像生成完了イベント（`executed` / `execution_complete`）時のみに限定する。
  2. バックエンド（FastAPI）で `httpx.AsyncClient` をシングルトン（Keep-Alive接続プール）として管理し、TCP接続を再利用する。
  3. プリセットおよびバッチの順次投入（FIFO順序）を確実に担保しつつ、最小限の通信オーバーヘッドで高速にキュー投入を完了させる。

---

#### Acceptance Criteria (AC)

##### 1. 不要な履歴フェッチの抑制
- [ ] AC-1-1: WebSocket `status` 受信時に `fetchHistory()` が発火せず、キュー投入中に不要な `GET /api/comfy/history` リクエストが多発しないこと。
- [ ] AC-1-2: 画像生成完了時（`executed` / `execution_complete`）およびアプリ起動・再接続時には従来通り正常に履歴が取得・更新され、生成画像がプレビュー・履歴一覧に正しく反映されること。

##### 2. バックエンド HTTP 接続のコネクションプール化
- [ ] AC-2-1: バックエンドの ComfyUI プロキシにおいて、共有の `httpx.AsyncClient`（コネクションプール）が利用され、HTTP Keep-Alive によるTCP接続再利用が行われること。
- [ ] AC-2-2: アプリケーションのライフサイクル（起動・終了）に合わせて `httpx.AsyncClient` の適切なオープンとクローズが行われること。

##### 3. 生成順序（FIFO）の担保とリグレッション防止
- [ ] AC-3-1: 複数プリセットおよび複数バッチ生成時に、ジョブがユーザーの意図した順序（FIFO）で確実にComfyUIキューへ順次投入されること。
- [ ] AC-3-2: バッチ投入中のキャンセル処理（`AbortController` 中断）およびエラー通知がリグレッションなく正常に動作すること。
- [ ] AC-3-3: 通常モード（デスクトップ）およびモバイルモードの双方において、生成・進捗表示・履歴同期がリグレッションなく正常に機能すること。
