### REQ-325: Prompt Surgeon: 共通プロンプト構文解析エンジン (PromptTokenEngine) の新設と統合

- **Type**: refactoring
- **Status**: done (2026-10-08)
- **Current step**: none
- **Priority**: P1
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-02 (Task 1.2) に基づき、現在複数箇所（`TagChipEditor`, `captionDecoupler.ts`, `promptUtils.ts` 等）で個別に実装されているプロンプト文字列・タグ構文の解析、重み付け `((tag:1.2))` の展開、カンマ正規化、デカップリング置換処理を統一する `PromptTokenEngine`（`frontend/src/utils/prompt/` 配下）を新設・統合する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: プロンプト文字列のパースや正規化が機能ごとに別個に書かれており、カンマ処理や空白トリム、重み付け展開の挙動に微妙な差異が生じているため。
  2. なぜ個別実装されたのか: 直近の機能追加（タグ翻訳、キャプションデカップリング等）の際に、既存の構文解析処理を流用せず専用ロジックを局所追加したため。
  3. なぜ専用ロジックを追加したのか: 共通のプロンプト AST（抽象構文木）やトークンエンジン基盤が存在しなかったため。
  4. なぜ基盤が必要なのか: エッジケース（連続カンマ、空白、ネスト括弧）における構文解釈差異をゼロ化し、保守コストを劇的に下げるため。
  5. 根本原因: コア機能であるプロンプト操作の共通抽象化モデルが欠如しており、単一責任のトークンエンジンが必要である。
- **UX Classification**:
  - **Interaction / Information Design**:
    - 単一の AST / `PromptToken` モデルによる一貫したプロンプト構文解析・シリアライズ
    - エッジケースでの構文崩れ（不要な連続カンマやスペースの重複）の自動正規化

#### Acceptance Criteria (AC)

- [ ] **AC-1**: Given 平文プロンプト文字列（重み付け、括弧ネスト、カンマ区切り、改行、空白を含む）が与えられたとき、When `PromptTokenEngine.tokenize(promptText)` を実行したとき、Then 各タグが `PromptToken`（`raw`, `text`, `weight`, `bracketDepth`, `enabled` 等）の構造化配列として正確にパースされ、連続カンマや無駄な空白が正規化されること。
- [ ] **AC-2**: Given `PromptToken` の配列が存在するとき、When `PromptTokenEngine.serializeToComfyPrompt(tokens)` を実行したとき、Then ComfyUI 構文に準拠した正当かつクリーンな平文プロンプト文字列（不要なカンマや空白のない形式）がシリアライズされること。
- [ ] **AC-3**: Given トークン配列と除外対象タグ配列が与えられたとき、When `PromptTokenEngine.decoupleTags(tokens, removeTags, injectTrigger)` を実行したとき、Then 対象タグが正確に除去され、オプションのトリガーワードが先頭または指定位置に注入された新たなトークン配列が返されること（`captionDecoupler.ts` の処理と等価な振る舞いを担保）。
- [ ] **AC-4**: Given 新設した `PromptTokenEngine` を用いて既存の `captionDecoupler.ts` をリファクタリングしたとき、When `captionDecoupler.test.ts` および既存のプロンプト関連テストを実行したとき、Then すべてのテストケースが成功し、後方互換性が完全に維持されていること。
- [ ] **AC-5**: Given 全体検証時、When `npm run typecheck` および `npm test` を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
