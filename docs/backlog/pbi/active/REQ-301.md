### REQ-301: ワークフロー置換モーダルのダークテーマ統一・要確認ノード優先表示・トポロジー図差分強調によるUI/UX刷新

- **Type**: improvement
- **Status**: new (2026-10-01)
- **Priority**: P2
- **UX Classification**:
  - **Visual Design**:
    - アプリ共通のダークテーマデザインシステム（SPEC_COMMON: `base-bg` / `surface` / `surface-2` / `border` / `zinc-200` 等）への完全準拠。
    - トポロジー差分およびノード名・端子名などのテキスト差分に対するセマンティックな色強調（変更された接続線、相手ノード枠線、テキスト差分ハイライト。WCAG AA準拠の高コントラスト設計）。
  - **Information Design**:
    - 役割移行一覧における要確認ノード（未検出 `not_found`、改名 `renamed`、代替 `substituted`、`false_reuse`、低信頼度）の最上部優先表示と完全一致ノードの優先度下げ（下方配置）。
    - 判定ステータスと信頼度を文字列結合しただけの冗長な「推測理由」列の撤廃によるテーブル幅の適正化および横スクロールの解消。
    - 局所トポロジー差分の視認性向上: テキスト列挙から、入力（上流）→ 対象ノード → 出力（下流）の接続構造を一目で把握できる軽量・カードベースの簡易ノード接続図への情報再構成。
  - **Interaction Design**:
    - 割当ノード一覧の表示領域拡大（縦スクロール負荷の低減と一覧性向上）。
    - モーダル初期表示時に、最上位の要確認ノード（要確認がない場合は先頭ノード）を自動アクティブ選択し、下段インスペクターの空表示を防止。
    - 上段（一覧テーブル）と下段（トポロジーインスペクター）それぞれに独立したスクロール機構（`.custom-scrollbar`）を持たせ、モーダルサイズ変動時にも双方が破綻しないレスポンシブな高さ配分を実現。
- **Surface**:
  - ワークフローの置換機能モーダル（WorkflowDiffReplaceModal）において以下の課題があり、使いづらい。
    1. アプリ全体がダークテーマであるのに対し、置換モーダルがダークテーマに準拠しておらず視覚的不調和が生じている。
    2. 判定が「完全一致」のノードは基本的に変更不要であるにもかかわらず、一覧に混在・上部に並ぶため、積極的な確認が必要な「未検出」「改名」等のノードを探す負担が大きい。
    3. 割当ノード一覧の領域が縦方向に狭くスクロールが大変である。さらに横スクロールも発生しているが、「推測理由」欄が判定ステータスと信頼度を組み合わせただけの内容になっており、その程度であれば不要。
    4. 下段のトポロジー欄での差分確認が難しい。接続関係を簡易的な図にし、接続差分は対象の接続線と相手ノードを強調し、名称等のテキスト差分は色付けで強調して、差分確認の負荷を下げたい。
- **5 Whys Analysis**:
  1. *Why*: 置換モーダルでの作業効率が低く、確認ミスや疲労を招きやすいのはなぜか？
     → ダークテーマ不整合による視覚的違和感、狭い領域での縦横スクロールの発生、変更確認が必要なノードの埋没、およびトポロジー差分の読みにくさが同時に発生しているため。
  2. *Why*: なぜノード一覧で確認作業に時間がかかるのか？
     → 変更が不要な「完全一致」ノードが一覧上位を占有し、ユーザーが対応・確認すべき「未検出（Removed）」「改名（Renamed）」「代替（Substituted）」ノードを見つけ出すためにスクロールと走査を強いられるため。
  3. *Why*: なぜノード一覧に横スクロールが発生し、画面が窮屈なのか？
     → モーダル横幅に対して「推測理由」列が存在しているが、中身がステータス名と信頼度スコアを文字列結合しただけの低付加価値な情報であり、横幅を浪費しているため。
  4. *Why*: なぜトポロジー欄の差分確認が難しいのか？
     → 前後接続がテキストの矢印やリストで羅列されているのみで、どの接続線が新設・変更され、どの相手ノードや端子名・タイトルが変わったのかが一目で直感的に識別できないため。
  5. *Why*: 根本原因（Root Cause）は何か？
     → 【Visual Design】アプリのデザインシステム（SPEC_COMMON）と不整合な配色が使われており、差分状態に応じた視覚的アクセント（色強調）が不足していること。【Information Design】ユーザーの確認優先度（要確認 vs 完全一致）に応じた情報階層化がなされておらず、冗長列（推測理由）によるレイアウト圧迫とトポロジーの図的構造化の欠如があること。【Interaction Design】モーダル内の高さ配分およびスクロール設計が実作業の導線（一覧俯瞰と差分注視）に最適化されていないこと。
- **Structural Blueprint (WorkflowDiffReplaceModal)**:
  ```text
  [Modal Container (Dark Theme: base-bg / surface / border)]
    ├── [Header: ワークフロー置換タイトル / ターゲット名 / トポロジーサマリーバッジ / 閉じるボタン]
    ├── [Upper Section: 役割引き継ぎマッピング一覧 (独立縦スクロール・横スクロール撤廃)]
    │     ├── [テーブルヘッダー: 役割(Role) | 旧ノード | 新割当ノード(選択可) | 判定ステータス・スコア]
    │     │     ※ 冗長な「推測理由」列は削除
    │     └── [テーブルボディ (要確認ノード最優先ソート・初期先頭行アクティブ)]
    │           ├── 【要確認グループ/上位表示】: 未検出(not_found), 改名(renamed), 代替(substituted), low confidence
    │           └── 【完全一致グループ/下位表示】: 完全一致(identical / exact match)
    ├── [Lower Section: 局所トポロジー前後比較インスペクター (簡易ノード接続図・独立スクロール)]
    │     ├── [旧ワークフロー接続図]
    │     │     [上流ノード群] ───(旧スロット)───> [旧ノード] ───(旧スロット)───> [下流ノード群]
    │     └── [新ワークフロー接続図]
    │           [上流ノード群] ───(新スロット)───> [新ノード] ───(新スロット)───> [下流ノード群]
    │           ※ 接続差分: 変更・新設・切断された線および相手ノード枠線をアクセント色で強調
    │           ※ テキスト差分: タイトルや端子名の変更箇所をハイライト色で強調
    └── [Footer: プリセット・ParamSync維持チェックボックス | キャンセル | 確定して置換]
  ```
- **Requirement**:
  - ワークフロー置換モーダル（`WorkflowDiffReplaceModal`）の全構成要素（モーダル背景、カード外枠、ヘッダー、テーブル、セレクトボックス、インスペクター、フッター）を、アプリケーション共通のダークテーマ（`SPEC_COMMON` トークン: `base-bg` `#0F0F11`, `surface` `#18181C`, `surface-2` `#1F1F25`, `border` `rgba(255,255,255,0.08)`, `text-zinc-200`, `text-zinc-400` 等）に完全準拠させること。
  - 役割引き継ぎ一覧テーブルにおいて、積極的な確認・手動修正が必要なノード（未検出 `not_found`、改名 `renamed`、代替 `substituted`、`false_reuse`、信頼度 1.0 未満）を最上部に優先してソート表示し、変更不要な完全一致（identical / exact match）ノードはその下部に配置すること。また、モーダル表示時には最上位の要確認ノード（すべて完全一致の場合は先頭ノード）を初期選択状態とすること。
  - テーブルから判定ステータスと信頼度を単に連結しただけの「推測理由（reason）」列を削除し、横スクロールの発生を排除すること。また、一覧テーブルの表示高さを拡大（適切な max-height 設定）し、縦スクロールの負荷を大幅に軽減すること。
  - 下段の局所トポロジーインスペクターにおいて、新旧の前後接続関係をカードと接続線からなる「簡易的な接続図（Flow Diagram）」形式で可視化すること。
  - 接続図において、旧接続と新接続の間で差分が発生している接続線（追加・削除・経路変更）および接続先相手ノードを視覚的に強調（境界線や配線色でのハイライト）すること。また、ノード名や端子名などのテキスト差分が発生している箇所を視覚的な色付け（diff ハイライト）で強調表示し、一目で差分を認識可能とすること。
  - 上段テーブルと下段インスペクターはそれぞれ独立したスクロール領域を備え、モーダル全体のレイアウトが画面サイズに応じて崩れないよう配慮すること。
  - 既存の割当ノード手動選択（ドロップダウン）、プロファイル・パラメータ同期維持フラグ、必須ロール未割当時の確定ボタン抑止バリデーション、置換確定 API 連携、ロールバック導線などの機能要件は完全に維持すること。
- **Acceptance criteria**:
  - [ ] AC-1 (ダークテーマデザインシステムへの完全準拠):
    - **Given**: ダークテーマが適用された Prompt Surgeon アプリケーションでワークフロー置換モーダルを開いた状態。
    - **When**: モーダルの背景色、カードコンテナ、テキスト色、テーブルヘッダー・行、ドロップダウン、ボーダーを確認する。
    - **Then**: 白背景やライトテーマ用のグレースケール色が排除され、アプリ共通のダークテーマ（`base-bg`, `surface`, `surface-2`, `zinc-200`, `zinc-400`, `rgba(255,255,255,0.08)` ボーダー）に統一されたスタイルで視覚的一貫性をもって表示される。
  - [ ] AC-2 (要確認ノードの最上部優先表示ソートと初期選択):
    - **Given**: 「完全一致（identical）」、「改名（renamed）」、「未検出（not_found）」、「代替候補（substituted）」など複数の状態判定が混在する新旧ワークフロー差分解析結果。
    - **When**: 役割移行一覧テーブルを表示する。
    - **Then**: ユーザーによる確認・対応が必要なノード（未検出、改名、代替、ID再利用、信頼度1.0未満の項目）が一覧の最上位に優先して並び、変更不要な完全一致ノードはその下部に並んで表示され、初期表示時点で最上位の要確認項目が自動選択されて下段インスペクターに連動表示される。
  - [ ] AC-3 (推測理由列の撤廃とテーブルスクロール性の改善):
    - **Given**: 役割移行一覧テーブルが表示されているモーダル。
    - **When**: テーブルの列構成およびスクロール動作を確認する。
    - **Then**: 判定ステータスと信頼度を反復するだけの冗長な「推測理由」列は存在せず、標準的なモーダル横幅において不要な横スクロールが発生しない。また、テーブル領域の表示高さが拡大され、より多くの行が一度に視認でき、縦スクロールのストレスが軽減されている。
  - [ ] AC-4 (簡易接続図による局所トポロジー表示):
    - **Given**: 役割一覧テーブルで任意のノードを選択した状態。
    - **When**: 下段のトポロジーインスペクター領域を確認する。
    - **Then**: 単なるテキストの羅列ではなく、上流（入力元ノード）→ 対象ノード → 下流（接続先端子ノード）の依存関係がカード形式と接続線で表現された「簡易的な接続図」として旧ワークフロー接続および新ワークフロー接続が対比表示される。
  - [ ] AC-5 (トポロジー差分の接続線・相手ノード・テキスト色強調):
    - **Given**: 新旧ワークフロー間で接続先スロットの変更、相手ノードの変更、またはノード名・端子名のリネーム差分が存在するノードを選択した状態。
    - **When**: 下段の接続図を確認する。
    - **Then**: 変更が発生した接続線および相手ノード枠線が目立つアクセント色で視覚的に強調され、名称等の変更されたテキスト部分は色付け（diff ハイライト）によって強調表示され、ユーザーが変更点を即座に識別できる。
  - [ ] AC-6 (既存機能・バリデーションの完全維持):
    - **Given**: 刷新された置換モーダルが表示されている状態。
    - **When**: 新ノードの手動ドロップダウン変更、維持チェックボックスの切り替え、必須ロール未割当時の確定ボタン活性状態、確定置換の実行を行う。
    - **Then**: すべての既存機能（手動割当、必須ロール未割当時の確定抑止バリデーション、PUT置換実行、ロールバック復元）が従来通り正常に機能する。
  - [ ] AC-7 (品質検証 - 型安全性とテスト通過):
    - **Given**: 実装完了後のリポジトリ。
    - **When**: `cd frontend; npm run typecheck` および `npm test` を実行する。
    - **Then**: 型エラーおよびテスト失敗が0件である。
