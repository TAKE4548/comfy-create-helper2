### REQ-373: モバイルGenerate：プロンプト／パラメータ／履歴のセクション切替（タブ・スワイプ）と縦方向の密度・スクロール末尾の整理

- **Type**: feature
- **Status**: ready
- **Priority**: P3
- **Surface**: モバイルGenerate（幅767px以下）のセクション切替、プロファイル／プリセット行、プロンプト種別タブ、スクロール領域
- **Reference**:
  - docs/design/mobile-ui-redesign/mobile-generate-redesign-proposal.md（§2〜§6、§9）
  - docs/design/mobile-ui-redesign/mobile-common-ui-redesign-proposal.md（COMMON-02 / 03 / 06 / 10）
  - docs/specs/SPEC_GENERATE.md（§3 モバイルレイアウト）
  - docs/specs/SPEC_COMMON.md（§1-3 モバイル操作対象44px、§1-5、§2-4）
  - 比較モック: Baseline `/?ui=baseline` ／ Proposal `/?ui=proposal`
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: モバイルGenerateは枠付きの3ボタン、プロファイル行、タグ周辺の重複した余白・枠により縦方向の編集面積が圧迫され、スクロール末尾に不要な空白も生じるため。
  2. なぜその課題が発生するか: 親・行・部品それぞれが余白と枠を持ち、AppShellの下部ナビ用領域とページの高さ指定が重なるため。
  3. なぜ現状の仕組みで不十分か: セクション移動がタップのみで、片手での移動負荷が大きい。
  4. なぜこのアプローチを採用するか: ベースライン（色・文字・既存機能）を維持したまま、局所的な余白整理と、タップを残した補助操作としてのスワイプを加える方向をユーザーがモックで評価した。
  5. 根本原因: モバイルで重複した枠・余白が積み重なり、入力面積と移動操作の効率が設計上考慮されていないこと。
- **UX Classification**:
  - **Information Design (情報設計)**: 3セクションの現在位置を控えめな下線で示す。縦方向の情報密度を上げる。
  - **Interaction (インタラクション)**: タップに加え、本文上の左右スワイプでセクションを隣へ移動する。
  - **Visual (視覚デザイン)**: 枠付きボタンから下線式タブへ。重複余白・枠の整理。
- **Requirement**:
  - **1. セクション切替**: タブのタップと左右スワイプの両方で「プロンプト↔パラメータ↔履歴」を移動できる。
  - **2. 縦方向の密度整理**: タブ・プロファイル行・プロンプト種別タブ周辺の重複した余白・枠を整理する（ページ側コンテナの範囲）。
  - **3. スクロール末尾**: 3セクションとも、末尾に不要な画面高相当の空白がなく、固定生成バーとボトムナビに内容が隠れない。
  - **4. 既存機能の維持**: Undo/Redo、プリセットの選択／チェック／管理／閉じる、タグのサブメニュー編集、生成・保存・キュー。
  - **5. 非対象**: 共通 `TagChipEditor` / `TagChip` のPadding・Gapの変更（共通部品の変更候補。別途ユーザーの明示的な採否判断を要する）、デスクトップ、API。
- **Acceptance criteria**:
  - [ ] AC-1: Given 幅767px以下のGenerate, When 画面を表示する, Then 「プロンプト／パラメータ／履歴」が画面幅に並び、選択中のセクションのみが下線と文字強調で示され、外枠付きの3ボタン表示にならないこと。
  - [ ] AC-2: Given いずれかのセクション, When 他セクションのタブをタップする, Then 対応するセクションへ切り替わり、現在位置が識別できること。
  - [ ] AC-3: Given 先頭または中間のセクション, When 本文上で左右へ十分な距離のスワイプを行う, Then 隣接するセクションへ移動し、端のセクションでは同方向のスワイプでそれ以上移動しないこと。
  - [ ] AC-4: Given 縦スクロール、テキスト入力・テキスト選択、スライダー、タグチップのドラッグ・サブメニュー、プリセットの選択／閉じる、プロンプト種別タブの横スクロール, When それぞれを操作する, Then 横スワイプによるセクション切替に奪われず、各操作が従来どおり動作すること。
  - [ ] AC-5: Given 3セクション各々, When 最下部までスクロールする, Then 最後の項目の下端と固定生成バー上端の間に、固定生成バーの高さを超える空白がなく、最後の項目が固定生成バーとボトムナビに隠れずに操作できること。
  - [ ] AC-6: Given プロファイル行・プロンプト種別タブ領域, When 画面を表示する, Then 重なる枠や背景が整理され、Undo/Redo、プリセットのチェック・選択・管理・閉じる、タグのサブメニュー編集、生成・保存・キューが従来どおり動作すること。
  - [ ] AC-7: Given セクションタブ・プリセットの閉じる・Undo/Redo・管理ボタン, When 操作領域を確認する, Then 各操作の有効タップ領域が44×44px以上（SPEC_COMMON §1-3）で、隣接する操作と誤タップしないよう分離され、フォーカスが視認できること。
  - [ ] AC-8: Given 幅360px、セーフエリアあり／なし、ソフトキーボードの開閉、長文タグ、支援技術（スクリーンリーダー・キーボード）での操作, When AC-1〜AC-6を実行する, Then レイアウトと操作が破綻しないこと。スワイプなしでもタブのみで全セクションに到達できること。
  - [ ] AC-9: Given 幅768px以上、Baseline、他ページ、本番API, When 操作する, Then 本PBI前から表示と挙動が変化しないこと。
- **Inferred points**:
  - 前提: REQ-378（モバイルUI共通規約のSPEC_COMMON反映）の完了後に設計に着手する。
  - REQ-372（常駐プレビュー廃止・履歴グリッド）の完了後の着手を推奨する。
  - **仕様の差異**: モックのタブは最小高42pxだが、SPEC_COMMON §1-3は「モバイル操作対象は最小44×44px」を定める。本PBIは仕様側（44px）を優先し、見た目を控えめにしつつ有効タップ領域で満たす想定（AC-7）。42pxの採否は設計で確定する。
  - 現行仕様（SPEC_GENERATE §3）はプロンプトタブを横スクロールとしている。横スクロールとスワイプの競合はAC-4で扱う。「履歴グリッドは横スクロール要素ではないため、スワイプ切替が可能」というモック方針に従う。
  - タグチップの寸法・Gap（モックの3px/8px、5px、6px）は共通部品の候補値であり、Generate限定の例外を作らない。採否は別途判断し、本PBIに含めない。
  - モックの数値（余白4px等）や固定生成バーの下部余白72px、およびCSSセレクタ／DOM監視による実装は本番の方式として採用しない。数値は設計で再確認する。
  - スクロール末尾の整理はAppShellの共有領域に及び得るが、Generate側から最小範囲で解決し、他ページのナビ・セーフエリアを変えない。
  - REQ-371（テキスト層による生成ボタンの被覆修正と固定方法の見直し）のACを回帰条件として引き継ぐ。固定方法・重なりの是正はREQ-371、本PBIはセクション移動・ページ側の密度・各セクション末尾の余白を担当し、固定領域と必要余白の契約を設計時に整合させる。
  - テスト規約: テスト名に `[REQ-373/AC-n]` を付与し、ファイル名・パスにチケット番号を含めない。
  - 監査記録（2026-10-18、ローカルモデル qwen/qwen3.5-9b、requirement）: ISSUES_FOUND（最終実行。スワイプ距離・寸法などの具体値は設計フェーズで確定）。ユーザーは、この状態を認識したうえで未解消の指摘を設計フェーズで扱うこととし、`ready` への移行を承認した（選択肢A）。監査はPASSではない。

## 個別レビュー・現行実装確認（2026-10-26）

- ユーザー指示「確認してから残そう」に基づき現行コードと既存テストを確認。残件があるため継続し、要求・9AC・P3・readyを維持する。以下の実装済み部分は回帰条件とし、全項目を未実装と扱わない。
- セクションのタップ切替（AC-2）は既存経路あり。MobileLayout.tsxのmobileSegmentと各panelのhidden/display切替により、プロンプト・パラメータ・履歴を選択し、非表示panelもマウントを維持する。既存テストで切替とドラフト・履歴panel保持を検証している。
- 下線式タブ（AC-1）は未対応。表示セクションはrole=group、aria-pressed付きの枠付き3ボタン（rounded-lg border）を使用している。
- 本文左右スワイプ（AC-3）とその競合回避（AC-4）は残件。GeneratePageとその配下の本番ソースにセクション切替用のtouch/pointer/swipe処理はなく、タップによるsetMobileSegmentが現行の操作経路である。
- 密度整理（AC-6）は残件。プロファイル領域、Undo/Redoの囲み、プリセット行、プロンプト種別タブには枠・背景・複数段の余白が残る。具体的に除去する箇所と視覚的な適否は実画面で設計・確認する。
- タップ領域（AC-7）は一部対応済み。セクションボタンはmin-h-[44px]、Undo/Redoとプリセット閉じるはmin-h-11/min-w-11、管理はmin-h-11がある。ただし全操作の幅・間隔・フォーカスの実測は未実施で、AC全体の完了とはしない。
- 末尾余白（AC-5）は実測未確認。MobileLayoutルートにはh-[100dvh]とoverflow-y-auto、nav高54px+safe-area+72pxのpadding/scroll-paddingがあり、AppShellのmainにもnav高+safe-areaの下部paddingがある。重複余白の確認対象として保持するが、画面高相当の空白や到達不能を今回再現したわけではない。REQ-371の固定方法見直しと整合させる。
- 実行：npm.cmd --prefix frontend test -- src/pages/GeneratePage/components/__tests__/MobileLayout.test.tsx。25件成功、exit 0。ただしbypass profiles取得で相対URLの解析エラーがstderrに出ており、API統合成功の証拠にはしない。既存テストの成功はREQ-373の下線表示・スワイプ・実レイアウトの受入PASSを意味しない。
- 前提のREQ-378と推奨先行REQ-372はarchiveでdone。今回、それらの完了を再受入検証したものではない。実装・テストソースの変更、実ブラウザでの寸法/スクロール/スワイプ/支援技術確認、新規監査は未実施。過去のISSUES_FOUNDは維持する。
