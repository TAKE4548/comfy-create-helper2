### REQ-393: REQ-387 の AC-2・RT5 テストを強化する

- **Type**: refactor
- **Status**: new
- **Priority**: P3
- **Surface**: backend/tests/integration/legacy/test_generation_integration.py（AC-2 の統合テスト）, backend/tests/integration/legacy/test_generation_api.py（RT5 のテスト）。テストのみで製品コードは変更しない。
- **起点**: REQ-387（commit fca9965）の後続課題。tester-reviewer が受入レポートの軽微 1 と軽微 3 として記録した（AC は充足、ゲートには影響しない）。
- **根拠資料**: `docs/logs/REQ-387/qa-code-report-r2.md`（軽微 1: AC-2 の実測が revision 変化 0、SELECT 0 で閾値が自明に近い／重点確認 (2) と軽微 3: `probe_image_availability` の関数置換）、`docs/design/REQ-387.md` §5（Seam Map: ComfyUI HTTP は `httpx.MockTransport` で切る）と §8-5（RT5）。`docs/logs/` は gitignore 対象のローカル資料。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: 受入テストの 2 点が、主張する性質を弱くしか検証していない。AC-2 のテストは revision の変化が起きない区間で閾値（revision 変化回数 + 2 以下）を測るため、閾値が自明に満たされる。RT5 のテストは、境界の内側にある関数を置換するため、境界をまたぐ挙動を検証しない。
  2. なぜ発生するか: AC-2 のテストは、プレビュー区間の間に revision が変化する状況を作っていない（実測 revision 変化 0、SELECT 0）。RT5 のテストは `comfy.probe_image_availability` を `monkeypatch.setattr` で置換し、ComfyUI への HTTP 呼出しを直接切っていない。
  3. なぜ現状の仕組みで不十分か: プレビュー受信ごとに誤って全件再読込する欠陥が入っても、revision が変化しない区間では SELECT 数の増え方が閾値に現れにくく、検出が遅れる。また、`probe_image_availability` の内部（HEAD から GET へのフォールバック、404 の判定、クエリの組み立て）が壊れても、置換したテストは通る。
  4. なぜこのアプローチ（強化）を採用するか: 受入の判定は変えず、検出力だけを上げる。設計の Seam Map に既に定めた境界へ揃えるだけである。
  5. 根本原因: テストの検出力を確認する基準（意図的な欠陥で失敗すること）と、外部 I/O を切る境界（Seam）の運用が、テスト実装時に厳密に適用されなかった。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 変更なし。
  - **Interaction (インタラクション)**:
    - 変更なし。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. AC-2 の統合テストの強化**:
    - プレビューフレームの受信区間で revision が実際に変化する状況を作り、そのときの `generation_jobs` の SELECT 回数を計数する。
  - **2. RT5 のテストの境界の是正**:
    - `probe_image_availability` の関数置換をやめ、ComfyUI への HTTP を `httpx.MockTransport` の境界で切る。
- **Acceptance criteria**:
  - [ ] AC-1: Given AC-2 の統合テスト（`test_req387_ac2_preview_frames_do_not_reload_generation_jobs`）, When プレビュー 30 フレームの受信区間に、別の job の受付または終端遷移などで revision を 3 回以上変化させる, Then テストが「区間内の revision 変化回数が 3 以上」であることを前提としてアサートし、`generation_jobs` の SELECT 回数が（revision 変化回数 + 2）以下で、かつフレーム数 30 より小さいことを検証し、各フレームでプレビュー revision の更新と WS 通知が行われること。
  - [ ] AC-2: Given AC-1 のテスト, When 製品コードに一時的な欠陥（プレビューフレーム 1 枚ごとに snapshot を全件再読込する）を仕込んで実行する, Then テストが失敗すること。欠陥を外すと成功すること。（検証結果を記録する。欠陥はコミットしない。）欠陥注入の手順・失敗したテスト名・アサーションの要旨は、`docs/design/REQ-393.md` の検証節に記録する。
  - [ ] AC-3: Given RT5 のテスト（窓外の終端 job への画像 availability 要求）, When 実装を確認する, Then `test_generation_api.py` に `probe_image_availability` を置換する `monkeypatch.setattr` が 0 件で、ComfyUI への HTTP が `httpx.MockTransport` のハンドラーで応答されていること。
  - [ ] AC-4: Given AC-3 のテスト, When availability を要求する, Then 応答の `availability` が MockTransport の応答から導かれ、(a) `HEAD /view` が 200 なら `present`、(b) `HEAD /view` が 404 なら `missing` になること。
  - [ ] AC-5: Given AC-3 のテスト, When availability を要求する, Then (c) `HEAD` が接続エラーで `GET /view` が 200 なら `present`、(d) `HEAD` も `GET` も失敗なら `unknown` になること。
  - [ ] AC-6: Given AC-3 のテスト, When availability を要求する, Then MockTransport が受けた要求の `filename` / `subfolder` / `type` のクエリが job の出力情報と一致することを検証し、(a)〜(d) の各ケースがそれぞれ別のテスト入力で検証されること。
  - [ ] AC-7: Given 強化後の 2 ファイル, When `python -m pytest backend/tests/integration/legacy/test_generation_integration.py backend/tests/integration/legacy/test_generation_api.py` と `-k req387` の選択を実行する, Then 変更前に通っていたテストはすべて引き続き通ること（失敗 0 件）。
  - [ ] AC-8: Given AC-7 の実行, When 回帰の基準と比較する, Then 基準は変更前に同一コマンドを実行した結果（失敗 0 件とテスト件数）を記録したものとし、変更後の件数が変更前の件数を下回らないこと。
  - [ ] AC-9: Given 強化後の 2 ファイル, When `scripts/verify_test_naming.py --strict` を実行する, Then テスト名と docstring の `[REQ-387/AC-2]` / `[REQ-387/AC-4]` プレフィックスが維持され、検査が通ること。
  - [ ] AC-10: Given 強化後, When 変更前のコミットを基準に `git diff <変更前のコミット> -- backend/app` を実行する（未コミットの作業ツリーでは `git diff HEAD -- backend/app` でもよい）, Then 出力が空で、製品コードに差分がないこと。
- **Inferred points**:
  - RT5 は設計 §8-5 の分類で AC-4（窓外 job の取消・プレビュー・availability の結果が従来と同一）に対応する。AC-3〜AC-6 は、そのうち availability を扱う 2 か所（`monkeypatch.setattr` で置換している箇所）が対象である。
  - ComfyUI クライアントの差替え口は既存の `get_comfy_client()` と、他のテスト（`test_comfy_generation_bridge.py` など）で使われている `httpx.MockTransport` の先例を使う想定である。差替え口が不足する場合は、製品コードの変更ではなくテスト側のフィクスチャで対応する。不可能なら設計へ戻す。
  - AC-1 の「revision を 3 回以上変化させる」「SELECT がフレーム数 30 より小さい」は、自明な閾値を避けるための確定値である（人レビューで承認済み）。
  - AC-2 の欠陥注入は手動の検証手順であり、恒久的なテストとして追加するものではない。
