### REQ-393: REQ-387 の AC-2・RT5 テストを強化する

- **Type**: refactor
- **Status**: ready
- **Priority**: P3
- **Surface**: backend/tests/integration/legacy/test_generation_integration.py（AC-2 の統合テスト）, backend/tests/integration/legacy/test_generation_api.py（RT5 のテスト）。テストのみで製品コードは変更しない。
- **起点**: REQ-387（commit fca9965）の後続課題。tester-reviewer が受入レポートの軽微 1 と軽微 3 として記録した（AC は充足、ゲートには影響しない）。
- **根拠資料**: `docs/logs/REQ-387/qa-code-report-r2.md`（軽微 1: AC-2 の実測が revision 変化 0、SELECT 0 で閾値が自明に近い／重点確認 (2) と軽微 3: `probe_image_availability` の関数置換）、`docs/design/REQ-387.md` §5（Seam Map: ComfyUI HTTP は `httpx.MockTransport` で切る）と §8-5（RT5）。`docs/logs/` は gitignore 対象のローカル資料。
- **現状確認（2026-10-26）**:
  - 対象のプレビューテストは30フレームの送信を開始し、最初のプレビューを待ってからSELECT計測を開始する。区間内にrevisionを変える受付・遷移操作や、revision変化3回以上・30フレーム全件処理・各フレーム通知のassertionはない。現在はSELECT数が観測したrevision変化回数+2以下であることを検証している。
  - `test_generation_api.py`には`probe_image_availability`の関数置換が2箇所残る。通常の画像identity確認と窓外終端jobの確認で、画像確認の実HTTP経路を通さずpresentを返している。
  - 現行の`probe_image_availability`は`get_comfy_client()`で取得したclientでHEAD /viewを実行し、200/404は直ちにpresent/missing、HTTP例外やその他statusではGETへ進み、GETの200/404をpresent/missing、それ以外をunknownとする。画像identityはGeneration routeで抽出して渡す。
  - 以上はコード読取確認。今回、テスト・欠陥注入・収集・性能計測は実施していない。revision変化0・SELECT0は過去記録であり、今回の実測ではない。
  - REQ-392はcaseメタデータへの移行を扱う。実施順序を設計で明記し、旧マーカー形式を固定せず名前選択・AC対応の互換性を保つ。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: 受入テストの 2 点が、主張する性質を弱くしか検証していない。AC-2 のテストは区間内のrevision変化を発生・確認する操作がなく、状態変化時の再計算を十分に検証していない。RT5 のテストは、境界の内側にある関数を置換するため、境界をまたぐ挙動を検証しない。
  2. なぜ発生するか: AC-2 のテストは、プレビュー区間の間に revision が変化する状況を作っていない（実測 revision 変化 0、SELECT 0）。RT5 のテストは `comfy.probe_image_availability` を `monkeypatch.setattr` で置換し、ComfyUI への HTTP 呼出しを直接切っていない。
  3. なぜ現状の仕組みで不十分か: revision変化0でも毎フレーム全件再読込する欠陥を既存のSELECT閾値で検出できる可能性はあるため、検出不能とは断定しない。未検証なのは状態変化を伴う区間での再計算上限と、意図的な欠陥に対する検出力である。また、`probe_image_availability` の内部（HEAD から GET へのフォールバック、404 の判定、クエリの組み立て）が壊れても、置換したテストは通る。
  4. なぜこのアプローチ（強化）を採用するか: 受入の判定は変えず、検出力だけを上げる。設計の Seam Map に既に定めた境界へ揃えるだけである。
  5. 根本原因: テストの検出力を確認する基準（意図的な欠陥で失敗すること）と、外部 I/O を切る境界（Seam）の運用が、テスト実装時に厳密に適用されなかった。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 変更なし。
  - **Interaction (インタラクション)**:
    - 変更なし。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. AC-2 の統合テストの強化**:
    - プレビューフレームの受信区間でrevisionが実際に変化する状況を作り、そのときの`generation_jobs`のSELECT回数を計数する。30フレームの送信・受信処理・通知を観測する境界と計測開始/終了を揃え、sleepや疎なpollingだけでフレーム処理やrevision変化を推測しない。
  - **2. RT5 のテストの境界の是正**:
    - `probe_image_availability` の関数置換をやめ、ComfyUI への HTTP を `httpx.MockTransport` の境界で切る。
- **Acceptance criteria**:
  - [ ] AC-1: Given AC-2 の統合テスト（`test_req387_ac2_preview_frames_do_not_reload_generation_jobs`）, When プレビュー 30 フレームの受信区間に、別の job の受付または終端遷移などで revision を 3 回以上変化させる, Then テストが「区間内の revision 変化回数が 3 以上」であることを前提としてアサートし、`generation_jobs` の SELECT 回数が（revision 変化回数 + 2）以下で、かつフレーム数 30 より小さいことを検証し、各フレームでプレビューrevisionの更新とWS通知が行われること。計測開始前のフレーム処理を除外したまま30件と扱わず、制御した受付/遷移によるDB revisionの変化とプレビューrevisionを区別して観測すること。
  - [ ] AC-2: Given AC-1 のテスト, When 製品コードに一時的な欠陥（プレビューフレーム 1 枚ごとに snapshot を全件再読込する）を仕込んで実行する, Then テストが失敗すること。欠陥を外すと成功すること。（検証結果を記録する。欠陥は隔離した検証用候補へ一時的に適用し、既存のユーザー変更を保護して復元を確認する。欠陥は最終候補に残さずコミットしない。）欠陥注入の手順・失敗したテスト名・アサーションの要旨は、`docs/design/REQ-393.md` の検証節に記録する。
  - [ ] AC-3: Given RT5 のテスト（窓外の終端 job への画像 availability 要求）, When 実装を確認する, Then `test_generation_api.py` に `probe_image_availability` を置換する `monkeypatch.setattr` が 0 件で、ComfyUI への HTTP が `httpx.MockTransport` のハンドラーで応答されていること。
  - [ ] AC-4: Given AC-3 のテスト, When availability を要求する, Then 応答の `availability` が MockTransport の応答から導かれ、(a) `HEAD /view` が 200 なら `present`、(b) `HEAD /view` が404ならmissingになること。どちらもGETを呼ばず、要求method/pathと呼出し回数を検証すること。
  - [ ] AC-5: Given AC-3 のテスト, When availability を要求する, Then (c) `HEAD` が接続エラーで `GET /view` が 200 なら `present`、(d) HEADもGETも失敗ならunknownになること。HEAD→GETの順序・回数を検証し、「失敗」の例外/HTTP status条件を具体的に固定すること。
  - [ ] AC-6: Given AC-3 のテスト, When availability を要求する, Then MockTransport が受けた要求の `filename` / `subfolder` / `type` のクエリが job の出力情報と一致することを検証し、(a)〜(d) の各ケースがそれぞれ別のテスト入力で検証されること。
  - [ ] AC-7: Given 強化後の最終候補, When 対象2ファイルと既存の`-k req387`選択を局所確認し、さらに適用規約に従うfreshなbackend全スイートをフィルターなしで独立実行する, Then 全必須ケースがPASSとなり、空収集・収集エラー・未承認のskip/deselect/xfail等がないこと。局所実行だけでbaseline PASSとしないこと。
  - [ ] AC-8: Given 着手前に同じ環境・コマンドで収集したケースID集合と実行結果, When 最終候補と比較する, Then 既存ケースが欠落せず、追加/パラメータ化したケースが識別でき、承認した選択集合が収集され全必須ケースのPASSが追跡できること。件数だけで維持と判断せず、着手前の失敗やskipを未確認のまま0件と仮定しないこと。
  - [ ] AC-9: Given 強化後の2ファイルとREQ-392との実施順序, When `scripts/verify_test_naming.py --strict`と収集メタデータを確認する, Then 既存のREQ-387/AC-2・AC-4への対応を維持し、本PBIのACと安定したケースIDの対応も追跡できること。REQ-392移行後は登録済みcase方式へ合わせ、コメント/docstringだけを明示メタデータの代替としないこと。
  - [ ] AC-10: Given 本件着手時の作業状態と欠陥注入前後の候補, When 本件所有の差分と復元後の最終候補を確認する, Then 本件によるbackend/appの変更がなく、一時欠陥が残らず既存ユーザー変更が保護されていること。HEADとの差分全体を本件差分と混同しないこと。変更した管理対象テキストはUTF-8（BOMなし）・LFであること。
- **Inferred points**:
  - RT5 は設計 §8-5 の分類で AC-4（窓外 job の取消・プレビュー・availability の結果が従来と同一）に対応する。AC-3〜AC-6 は、そのうち availability を扱う 2 か所（`monkeypatch.setattr` で置換している箇所）が対象である。
  - ComfyUI クライアントの差替え口は既存の `get_comfy_client()` と、他のテスト（`test_comfy_generation_bridge.py` など）で使われている `httpx.MockTransport` の先例を使う想定である。差替え口が不足する場合は、製品コードの変更ではなくテスト側のフィクスチャで対応する。不可能なら設計へ戻す。
  - AC-1 の「revision を 3 回以上変化させる」「SELECT がフレーム数 30 より小さい」は、自明な閾値を避けるための確定値である（人レビューで承認済み）。
  - AC-2 の欠陥注入は手動の検証手順であり、恒久的なテストとして追加するものではない。
- **設計・検証への引継ぎ**: 外部HTTPはMockTransportで切り、実ComfyUIや実DBへ接続しない。内部の画像判定ロジックは置換しない。revision操作自身が発生させるSELECTを含む計測範囲とキャッシュwarm-upを明示し、既存の確定閾値が成立しない場合は恣意的に緩めず設計へ戻す。検証基盤変更として現行V1 baselineと全スイートfallbackに従う。製品コードの恒久変更が必要なら本件で拡張せず設計へ戻す。
- **Review record（2026-10-26）**: ユーザーが現状確認と見直して継続する方針を承認。既存テストの計測開始・revision操作不足・画像確認2箇所の関数置換をコード照合し、既存テストの検出力を未実証で否定する説明を修正。計測区間、HTTP呼出し順序、REQ-392メタデータ移行、全スイート・ケース集合・ユーザー変更保護の条件を整合し、10AC・P3・既存readyを維持して本文Statusを統一。テストソース・製品コードは未変更。テスト・欠陥注入・新規監査・受入検証は未実施で、実装開始や受入完了の承認を示さない。
- **Design doc**: docs/design/REQ-393.md（今回確認時点では未作成。後続設計で作成する）
