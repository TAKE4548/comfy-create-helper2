### REQ-259: 通常生成の追加投入後におけるVRAM待機表示と実際のキュー状態の不整合

- **Type**: defect
- **Status**: ready
- **Current step**: none
- **Priority**: P3
- **Surface**:
  - 通常生成中に同一セッションから追加投入した後、ComfyUI側のQueueにも追加ジョブが表示される一方、アプリ側は「VRAM解放待ち」と表示する。
  - 2026-10-26のユーザー報告では、待ち表示が解消した後は進捗の合算ができている模様。上流投入済みと考えられる観測であり、ジョブごとの投入状態や表示原因をコード・実動作で確認したものではない。
- **Root Cause（現在）**:
  - 未特定。待機状態の解除漏れ、古い通知、別ジョブの待機状態による全体表示の上書きなどは調査候補であり、原因とは断定しない。
  - 同一セッションであることだけを根拠にVRAMガードを無効化しない。投入済みジョブの進行と、実際にVRAM不足で未投入のジョブの待機を区別する。
- **Requirement**:
  - 上流投入済みのジョブを、VRAM不足により上流投入を保留しているジョブとして表示しない。
  - 同じ通常生成グループに投入済みジョブとVRAM待機中の未投入ジョブが混在する場合、それぞれの状態を識別でき、既存ジョブの進行が待機表示で隠れないこと。
  - 追加投入や通知の到着順序によって、ジョブ状態・進捗・合算値が古い状態へ巻き戻らないこと。待機表示の解消を契機とした重複投入を行わないこと。
  - 実際にVRAM不足で未投入のジョブに対する安全ガード、待機表示・回復後の投入は維持する。
- **Acceptance criteria（2026-10-26レビュー後の現行AC）**:
  - [ ] AC-1: Given 同一セッションの通常生成中に追加投入し、その追加ジョブのComfyUI上流への投入が確認でき、他にVRAM待機中の未投入ジョブがない, When アプリが当該状態を受信・表示する, Then 投入済みジョブを「VRAM解放待ち」と表示せず、確認できたキュー待ち・実行中・終了の状態に対応する表示となること。
  - [ ] AC-2: Given 同じ通常生成グループに投入済みジョブと実際のVRAM不足による未投入の待機ジョブがある, When 進行状態を表示する, Then 投入済みジョブの進行と未投入ジョブのVRAM待機を区別でき、グループ全体が未投入であるかのように表示されないこと。
  - [ ] AC-3: Given 通常生成中に追加投入が受け付けられ、進行通知と待機・回復通知が順序を前後して到着する, When 状態を反映する, Then 古い通知でジョブ状態・進捗・合算値が巻き戻らず、同一グループ内の対象ジョブを重複なく集計し、投入済みジョブを再送しないこと。取消・解除・状態未確認による母数変更は現行仕様に従い、単なる母数減少を不具合とは扱わないこと。Studioの独立batchは合算しないこと。
  - [ ] AC-4: Given 上流未投入ジョブがあり、空きVRAMが設定された安全基準値を下回っている, When 投入判定を行い、その後安全基準を満たす状態へ回復する, Then 不足中は当該ジョブを未投入のまま待機表示し、安全確認後に投入へ進み、投入後は当該ジョブのVRAM待機表示が解消されること。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: 全体進捗プログレスバーの母数計算・追加投入マージ・ライフサイクル不整合の修正
- **旧Surface**:
  - アイドル状態で生成開始した際に対象プリセットのバッチ数の総和が母数になり、完全に完了する前に追加投入すると母数に加算、完全に全ジョブ完了後であれば新たに最初の母数計算になるはずだが、追加投入でも母数が減ったり（1/1化）、完了状態で投入したのに前回の完了済みジョブが引き継がれて追加投入のようになってしまう。
- **旧Root Cause（当時の説明・現行原因として未確認）**:
  - 全件完了時（`execution_complete` / `updateBatchJobStatus`）に `activeBatch` がクリアされず残存し、`useGenerateAction` でアイドル状態や全件完了状態を問わず無条件に `existingActiveBatch` としてマージされているため、完了後の新規投入で前回ジョブが合算される。
  - ComfyUIのジョブ切り替わり時に発行される WebSocket `status` により `fetchQueue` が先行実行された際、ComfyUIキューが一時的に空になったタイミングで `anyUnfinishedInQueue === false` と誤判定され、進行中であるべき `activeBatch` が `null` に破棄される。
  - `activeBatch` が `null` になるとUI側（`DesktopLayout` / `MobileLayout`）が `1/1 枚目` としてフォールバック表示し、その状態で追加投入すると新規投入分のみで再初期化される。
  - `useGenerateAction` の投入ループ内でローカル配列 `currentBatch` によるストア状態の上書きが発生し、投入待機中にWebSocketが更新した進行ステータスが古いスナップショットで上書きされる。
- **旧Requirement**:
  - 全ジョブが完了したアイドル状態での新規生成投入時は、前回の完了済みジョブを引き継がず、新規投入分のバッチ数のみを母数として開始すること。
  - 生成実行中・待機中に追加投入（Generate Batch）した場合は、現在進行中のバッチに新規ジョブが正しく合算され、母数が正しく増加・維持されること。
  - `fetchQueue` や WebSocket イベントの到着順序差によって `activeBatch` が進行中に誤って `null` に破棄されないようにすること。
  - バッチ投入ループ中および完了処理において、WebSocketによる最新のジョブ進行状態（generating / completed / failed）が失われないこと。
- **旧Acceptance criteria（履歴・適用終了）**:
  - 旧AC-1: 全ジョブが完了したアイドル状態から新規に生成を開始した場合、前回の完了済みジョブが除外され、今回投入した対象プリセットのバッチ数合計を母数 `m`（`全体進捗: 1/m 枚目`）として初期化されること。
  - 旧AC-2: 生成実行中に追加投入（キュー追加）を行った場合、既存の未完了ジョブおよび実行中ジョブと新規ジョブが正常に結合され、全体進捗の母数 `m` が合算値として即座に更新・反映されること（母数の減少や `1/1` 化が発生しないこと）。
  - 旧AC-3: ジョブ実行中・切り替わり時に ComfyUI から WebSocket `status` を受信して `fetchQueue` が実行されても、クライアント側の未完了バッチが誤って `null` に破棄されないこと。
  - 旧AC-4: 投入ループ処理（`queuePrompt` 実行中）に先行ジョブの状態遷移（`generating` / `completed`）が発生しても、ループ終了時のストア更新によってそれらの状態が巻き戻されないこと。
