### REQ-389: BaseHTTPMiddleware の応答遅延への寄与を計測する

- **Type**: spike
- **Status**: new
- **Priority**: P3
- **Surface**: backend/app/middleware/request_logging.py（`RequestLoggingMiddleware`。`BaseHTTPMiddleware` を継承）, backend/app/main.py（ミドルウェア登録）。計測のみで製品コードは変更しない。
- **起点**: REQ-387（commit fca9965）の後続課題。REQ-387 は `BaseHTTPMiddleware` の置換を「寄与度が未計測」として対象外とした（設計 §4-7）。
- **根拠資料**: `docs/design/REQ-387.md` §4-7（対象外）と §6（性能閾値）、`docs/logs/REQ-387/qa-code-report-r2.md`（AC-3 の実測: イベントループ最大遅延 21.0ms、preview 応答 10.0ms。第 1 段階の参考値であり、基準値ではない）。`docs/logs/` は gitignore 対象のローカル資料。
- **5 Whys / Root Cause**:
  1. なぜ調査が必要か: 全リクエストが `BaseHTTPMiddleware` を経由する。この方式は、リクエストごとのタスク生成とストリーム中継のため、応答の遅延や長時間応答への影響が知られている。REQ-387 後の応答遅延にどの程度寄与するか不明である。
  2. なぜ不明か: REQ-387 は遅延の主因（snapshot の全件同期読込）の除去に集中し、ミドルウェアの寄与は計測せずに対象外とした。
  3. なぜ現状の仕組みで不十分か: 寄与が未計測のままだと、置換が必要か不要かを判断できず、不要な改修か、見逃した遅延要因のどちらかが残る。
  4. なぜ spike とするか: 置換は全 API に影響する変更であり、判断材料なしに着手すべきでない。まず現状とノイズを測って判断基準を作り、その基準で比較して結論を出す。
  5. 根本原因: ミドルウェアの寄与度を測る手段と、置換の要否を決める基準が未定義である。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 変更なし。
  - **Interaction (インタラクション)**:
    - 間接的に、全 API の応答遅延が利用者の操作感に与える影響を判定する。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. 第 1 段階（現状計測）**:
    - ミドルウェア有効の現行構成で、対象 API の p50 / p95 / p99 / 最大と、同一構成どうし（A/A）のノイズ幅を測る。あわせて体感上の目安（例: 操作応答が 100ms を超えると遅いと感じる）を決めて記録する。
  - **2. 判断基準の確定**:
    - 第 1 段階の結果をもとに、置換の要否の判断基準を確定し、設計文書へ記録してから第 2 段階に進む。基準は第 2 段階の結果を見て変更しない。
    - 基準は「ノイズ幅の 2 倍以上の差があり、かつ体感の目安に影響する」のように、ノイズ幅に対する倍率と体感の目安（絶対値 ms）を組み合わせた形にする。割合だけ、または絶対値だけの基準にしない（基準値が小さいと割合だけでは過敏になるため）。
  - **3. 第 2 段階（比較）**:
    - 3 構成を同条件で比較して判定する。(1) 現行（`BaseHTTPMiddleware` 版の `RequestLoggingMiddleware` あり）、(2) ミドルウェアなし、(3) 同じログ出力と `X-Request-ID` 付与を行う純粋な ASGI ミドルウェア版。
    - (1) と (3) の差を `BaseHTTPMiddleware` 方式の負担、(2) と (3) の差をログ出力の負担として区別して記録する。
  - **4. 結果の記録**:
    - 計測条件、結果表、基準、結論、再現手順を設計文書へ残す。製品コードは変更しない。純粋 ASGI 版は一時的な計測用であり、製品コードにも成果物にも残さない。
- **Acceptance criteria**:
  - 第 1 段階（現状計測）
  - [ ] AC-1: Given 終端 job 1000 件を含む DB（REQ-387 AC-3 と同じ構成）で、同一マシン・同一コミットの現行構成のバックエンド, When `GET /api/generation/state`（キャッシュヒット時）と軽量な GET API 2 本以上を、各 1000 リクエスト（逐次、および並行度 16）で実行する, Then API・並行度ごとの p50 / p95 / p99 / 最大を ms の小数 1 桁で記録し、各測定を 5 回繰り返して中央値を採ること。
  - [ ] AC-2: Given AC-1 と同じ条件, When 現行構成どうし（A/A）を同じ手順で 2 組測り比較する, Then API・並行度ごとに p95 の差をノイズ幅として ms で記録すること。
  - [ ] AC-3: Given 生成実行中でプレビューフレームを 30 枚受信している状態の現行構成, When 10ms 周期 tick のイベントループ最大遅延、`GET /api/generation/preview/{job_id}` の応答時間（最初のバイトまで、および完了まで）、画像バイナリ応答の完了時間を、AC-1・AC-2 と同じ要領（5 回の中央値、A/A）で測る, Then 各指標の値とノイズ幅を記録すること。
  - [ ] AC-4: Given AC-1〜AC-3 の結果, When 体感上の目安を決める, Then 操作の種類（軽量 GET 応答、プレビュー表示、画像表示）ごとに、遅いと感じる応答時間の目安（ms）とその根拠が記録されていること。
  - 判断基準の確定
  - [ ] AC-5: Given 第 1 段階（AC-1〜AC-4）の結果, When 判断基準を確定する, Then ノイズ幅に対する倍率と AC-4 の体感の目安を組み合わせた基準（絶対値だけ、割合だけの基準は不可）が `docs/design/REQ-389.md` に記録され、記録の日時が第 2 段階の計測開始より前であること。
  - [ ] AC-6: Given 確定した基準, When 第 2 段階の判定を行い完了する, Then 判定後の設計文書の基準の記載が確定時点と同一であり、第 2 段階の結果を見た変更がないこと。
  - 第 2 段階（比較と判定）
  - [ ] AC-7: Given AC-1・AC-3 と同じ条件（DB、リクエスト数、並行度、5 回の中央値、プレビュー 30 枚受信状態）, When (1) 現行、(2) ミドルウェアなし、(3) 同じログ出力と `X-Request-ID` 付与を行う純粋な ASGI ミドルウェア版の 3 構成で同じ指標を測る, Then 構成・API・並行度・指標ごとの値を記録すること。
  - [ ] AC-8: Given AC-7 の結果, When 構成間の差を算出する, Then (1) と (3) の差を「`BaseHTTPMiddleware` 方式の負担」、(2) と (3) の差を「ログ出力の負担」として区別し、API・並行度・指標ごとに記録すること。
  - [ ] AC-9: Given AC-5 の確定基準と AC-8 の (1) と (3) の差, When 基準を適用する, Then 各指標が基準を満たしたか否かと、満たす指標が 1 つ以上あれば「置換が必要」、なければ「置換は不要」の二値の結論が記録されること。
  - 成果物と製品コードへの影響
  - [ ] AC-10: Given spike の完了, When 成果物 `docs/design/REQ-389.md` を確認する, Then 計測環境（OS、Python、uvicorn、starlette のバージョン、DB 構成）、再現手順（実行コマンド、入力、プレビュー受信状態の作り方）、結果表、ノイズ幅、体感の目安、基準、結論が記載されていること。
  - [ ] AC-11: Given spike の完了, When `git diff` で `backend/app` と `frontend/src` を確認する, Then 差分がなく、純粋 ASGI 版も無効構成も恒久的な製品コード変更として残っていないこと。
  - [ ] AC-12: Given 結論が「置換が必要」, When spike を完了する, Then 置換の PBI は本 PBI の外で別途起票されること（本 PBI では置換を実施しない）。
- **Inferred points**:
  - 「軽量な GET API 2 本以上」の具体的な選定は、10/24 のインシデントで遅延が観測された軽量マスタ API から設計時に決める。
  - プレビューフレーム 30 枚受信状態の再現手順は設計時に決め、AC-10 の成果物に記録する。
  - 計測は利用者端末のローカルホストで行う。WS（`/api/ws`）経路は `BaseHTTPMiddleware` の対象外（HTTP のみ）と想定するため、本 spike の計測対象に含めない。この想定が誤りなら第 2 段階の AC に追加する。
  - 無効構成と純粋 ASGI 版の作り方（環境変数での切替、アプリ生成時の差替えなど）は spike 側の判断とする。差替えが一時的で製品コードに残っていないことは、`git diff` で確認する（AC-11）。
  - AC-9 の基準の適用対象は、置換による改善幅にあたる (1) と (3) の差とする。(2) と (3) の差は、ログ出力の負担を把握するための記録であり、結論の判定には使わない。
  - REQ-387 の実測値（ループ遅延 21.0ms、preview 10.0ms）は第 1 段階の参考値であり、第 1 段階の計測結果が基準の根拠となる。
