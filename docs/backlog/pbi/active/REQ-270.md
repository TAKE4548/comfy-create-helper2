### REQ-270: BaseModelマルチバリアント対応とDBスキーマ拡張（Phase 2）

- **Type**: enhancement
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**:
  - BaseModel（Anima, Illustrious, SDXL, Pony 等）の違いによって同一キャラクターのカードが乱立しライブラリが肥大化している。
  - 構想設計書に基づき、1つの論理カード内に複数のBaseModel向けバリアント（LoRAファイル、強度、トリガーワード、プロンプトタグ定義）を内包できるデータモデルおよび編集UIを構築したい。
  - バリアントテーブルにおいて、兄弟関係・互換関係にあるモデル（例: Illustrious と NoobAI）で共通のバリアントを相互利用・共有できるようにしたい。最初から多対多（1つのバリアントが複数のBaseModelをカバー）または継承・フォールバックができる構造とし、並び替えや他機能への影響・リスクが最小となる形態を採用したい。
  - 既存のTagSetおよびLoRAデータを壊さずに安全に自動移行したい。
- **Root Cause**:
  - **Information Design (Entity-Variant Conflation & Library Proliferation)**:
    - 1枚のカードが特定のBaseModel実装（物理ファイル名や固有構文）と密結合しており、「キャラクター/アセットという論理概念」と「BaseModel別の物理実装」が分離されていない。
    - モデルごとに別カードを作成する必要があるため、同一キャラクターのカードが乱立し、ライブラリの肥大化とシリーズ管理の複雑化を招いている。
    - さらに、アーキテクチャ的に互換性のあるモデル（例: IllustriousとNoobAI）であっても、別々のBaseModelとして管理されている場合に設定を二重登録せざるを得ない冗長性が生じている。
- **Requirement**:
  - **論理カードエンティティとモデル別バリアントの分離（データモデル）**:
    - `tag_sets` および `loras` テーブルを「論理カード（表示名、カテゴリ、説明、共通サムネイル、並び順）」として位置付けること。
    - モデル別バリアントテーブル（`tag_set_variants`, `lora_variants`）を新設し、1つの論理カードに対してBaseModelごとの個別プロファイル（LoRAファイルパス、推奨強度最小/最大/デフォルト値、トリガーワード、モデル依存構文タグ等）を保持できる構造へ移行すること。
    - タグセットのサブセット（衣装・表情差分等）はバリアント配下の階層（`tag_subsets`）として管理できる構造とすること。
    - タグセットにおいては、特定BaseModelに依存しない「共通デフォルトバリアント（全モデル共通）」の保持を許容すること。
  - **BaseModelとバリアントの多対多・互換共有（共通設定の組）**:
    - 1つのバリアント定義（LoRAファイルパス、強度、トリガーワード、タグ等）を、複数のBaseModelに対して共通の定義として紐付け・再利用できるリレーショナル設計（例: 中間テーブルによる多対多マッピング等）を採用すること。
    - これにより、Illustrious系とNoobAI系などの互換モデル間で、同一のLoRAファイルやプロンプト設定を二重登録することなく、1つのバリアントで共有可能とすること。
    - カードの並び順（`sort_order`）は論理カード単位でカテゴリ内にスコープされているため、バリアントの多対多共有がソート順やD&D操作に悪影響を与えないこと。
  - **既存データの自動マイグレーション**:
    - DBマイグレーションスクリプトを作成し、既存のすべてのTagSetおよびLoRAデータを欠落や破損なく、自動的に対応するバリアントレコード（共通デフォルトまたは紐づくBaseModelバリアント）へ移行すること。
    - 既存の関連テーブルや外部キー参照の整合性を100%保護すること。
  - **カード管理UIのバリアント対応**:
    - カード編集モーダル内に「モデル別バリアント」管理インターフェースを新設し、BaseModelごとの設定値をタブまたはアコーディオンで個別に確認・編集・保存できるようにすること。
    - 各バリアント設定において、対応するBaseModelを複数チェック選択（例: [x] Illustrious, [x] NoobAI）して共通共有できるようにすること。
    - 未登録のBaseModelに対して「モデル設定を追加」操作により即座に新規バリアントを追加・設定できること。
    - カード一覧のフッターに対応しているBaseModelバッジを表示し、どのモデルに対応済みであるかを視覚的に識別可能とすること。
  - **BaseModelフィルタのバリアント連携**:
    - 管理画面のBaseModelフィルタ適用時、対象モデルのバリアント（または対象モデルが共有紐付けされているバリアント）を内包する論理カードを絞り込み表示し、論理カードの並び順を崩さないこと。
- **Acceptance criteria**:
  - [ ] AC-1: `tag_set_variants` および `lora_variants` テーブルが新設され、1つの論理カードに対して複数のバリアントが登録・永続化できること。
  - [ ] AC-2: 1つのバリアント定義に対して複数のBaseModel（例: IllustriousとNoobAIの組）を関連付けて共有でき、互換モデル間で重複レコードを作成せずに設定を共有できること。
  - [ ] AC-3: DBマイグレーション実行時に、既存のすべてのTagSetおよびLoRAデータが適切なバリアントレコードへとデータ欠落なく自動移行されること。
  - [ ] AC-4: タグセットにおいて、バリアント配下に複数のサブセット（`tag_subsets`）が保持・編集可能であること。
  - [ ] AC-5: カード詳細・編集画面において、各BaseModelバリアントの設定（LoRAファイルパス、推奨強度、トリガーワード、構文タグ）が個別に編集・保存できること。
  - [ ] AC-6: カード詳細・編集画面において、バリアントがカバーするBaseModelを複数選択でき、新規BaseModelバリアントの追加および不要なバリアントの削除が行えること。
  - [ ] AC-7: カード一覧において、各カードに対応済みのBaseModelバッジ（共有モデル含む）が表示され、視覚的に対応モデルが把握できること。
  - [ ] AC-8: BaseModelフィルタ適用時、対象BaseModelをカバーするバリアントを有するカードのみが絞り込まれ、カード固有の論理的な並び順（`sort_order`）が維持されること。
  - [ ] AC-9: バリアント追加・変更後も、Phase 1で導入されたカテゴリセクションおよびセクション内D&D並び替え機能が正常に動作し続けること。
