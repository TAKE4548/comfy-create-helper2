### REQ-367: 共通Modal：ダイアログ内フォーカス時のEscape閉じ不具合の修正、ネストModalのEscape/Tabフォーカス制御、およびバックドロップ全面被覆の保証

- **Type**: bug
- **Status**: ready
- **Priority**: P2
- **Surface**: frontend/src/components/common/Modal.tsx（共通Modal）、およびそれを利用する全画面のダイアログ（Settings の各管理・編集モーダル、MappingMasterEditModal 内の WorkflowNodePicker ネスト、GeneratePage の名前変更ダイアログ等）、BaseModelSection のように親が `space-y-*` を持つ配置箇所
- **Reference**:
  - docs/design/REQ-365-verification-report.md（D-1）、REQ-365-verification-report-r3.md（D-R3-1、ネストEscの実測）、REQ-365-verification-report-r4.md（入れ子Modal Tabトラップを許容トレードオフとして計上除外）
  - docs/specs/SPEC_COMMON.md §1-3 / §1-4（共通Modalのfocus管理・Escape/backdrop制御、ネスト例外の記述）
  - docs/specs/SPEC_SETTINGS.md（カスタム型マスタ節のネスト例外の記述）
  - docs/design/REQ-365-test-plan.md（AC-9 / RT-5b：Escape検証は本PBI（旧D-1）へ送り）
  - docs/backlog/pbi/active/REQ-302.md（AC-3 が Esc でモーダルが閉じることを前提とするため、本PBIを先行させる）
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: キーボード利用者が、ダイアログ内（ボタン・入力欄など）にフォーカスがある通常の状態で Escape を押してもダイアログを閉じられず、マウスで「閉じる」ボタンを押す以外に退出手段がないため（実ブラウザで確認済み、閉じるボタンは正常動作）。
  2. なぜその課題が発生するか: ダイアログ内でのキー入力が、ダイアログ外（ウィンドウ全体）の Escape 監視へ到達しない経路になっているため。HEAD 時点から存在する既存不具合で、REQ-365 の変更行が原因ではない。
  3. なぜ現状の仕組みで不十分か: 既存の自動テストが、フォーカス中の要素ではなくウィンドウへ直接キーイベントを送って検証しており、実際のキーボード操作では閉じない状態を検出できない（偽陽性）。また、ネスト（MappingMasterEditModal 内の WorkflowNodePicker）は外側の Escape 無効化という個別回避で成立しており、ピッカー内にフォーカスがあるときの Escape は何も閉じない。ネスト時の Tab/Shift+Tab 移動が最前面ダイアログに閉じる保証もない。さらに、親が `space-y-*` のとき共通Modalのバックドロップが上端24pxずれて背景が操作可能になった事例（D-R3-1）が、回帰防止なしで残る。
  4. なぜこのアプローチを採用するか: 全画面で共通のダイアログ契約（Escapeで閉じる、最前面のみが応答する、Tabは最前面内を循環する、バックドロップは常に全面を覆う）を共通Modal側の単一箇所で保証すれば、個別画面ごとの回避策が不要になり、後続のモーダル改修（REQ-302 など）の前提が安定するため。
  5. 根本原因: 共通Modalのキーボード契約（Escape・フォーカストラップ・ネスト時の最前面制御）と、バックドロップ全面被覆の不変条件が、実キー操作・実レイアウトを用いた自動検証で担保されていなかったこと。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 該当なし（表示内容・情報構造の変更はない）。
  - **Interaction (インタラクション)**:
    - ダイアログ内フォーカス時の Escape による閉じる操作。
    - ネスト時に最前面のダイアログのみが Escape / Tab / Shift+Tab に応答し、閉じた後は開いた元の要素へフォーカスが戻る。
    - ポップオーバー・メニュー・IME変換中など、ダイアログ内のサブ要素が Escape を処理している間はダイアログを閉じない。
  - **Visual (視覚デザイン)**:
    - バックドロップが親の余白クラスに関係なく viewport 全面を覆い、上端などに未ディム帯や操作可能な背景を残さない。
- **Requirement**:
  - **1. Escape で閉じる（フォーカス位置非依存）**:
    - Escape での閉じる操作が有効に設定された共通Modalは、ダイアログ内のどの要素にフォーカスがあっても、実キーボード操作の Escape で閉じる。Escape が無効に設定されたダイアログは閉じない。バックドロップ操作・閉じるボタンの既存動作は維持する。
  - **2. サブ要素の Escape 優先**:
    - ダイアログ内でポップオーバー・ドロップダウンメニュー・IME変換中の入力など、サブ要素が Escape を自身で処理する場合は、そのサブ要素のみが反応し、ダイアログは閉じない。サブ要素が Escape を消費しなかった場合に限りダイアログが閉じる。
  - **3. ネストModalの最前面制御（Escape）**:
    - 共通Modalの中に共通Modalを開く場合（例: MappingMasterEditModal 内の WorkflowNodePicker）、Escape は最前面（最後に開いた）ダイアログのみを閉じ、外側は閉じない。次の Escape で外側が閉じる。フォーカスが内側ダイアログのどこにあっても同じ。
  - **4. ネストModalのフォーカス制御（Tab）**:
    - ネスト中は Tab / Shift+Tab のフォーカス移動が最前面ダイアログ内のみを循環し、外側ダイアログや背面ページの要素へ移らない。内側が閉じた後、フォーカスは内側を開いた要素（外側ダイアログ内）へ戻り、以後は外側ダイアログ内で循環する。
  - **5. バックドロップ全面被覆の保証**:
    - 共通Modalのバックドロップは、親要素の余白系クラス（例: `space-y-*`）の有無にかかわらず viewport 全面（位置0,0・幅・高さとも viewport と一致）を覆い、背景要素をクリック不可にする。
  - **6. 検証要件**:
    - Escape・Tab の検証は、フォーカスされた要素に対する実キー操作（ブラウザ実行またはそれと等価なユーザー操作シミュレーション）で行い、ウィンドウへの直接イベント送出のみで合格としない。バックドロップの被覆は実レイアウトを持つブラウザ実行で検証する。
- **Acceptance criteria**:
  - [ ] AC-1: Given Escape での閉じる操作が有効な共通Modal（例: カスタム型マスタ管理ダイアログ、GeneratePage の名前変更ダイアログ）が開いていて、フォーカスがダイアログ内のボタンまたは入力欄にある, When 実キーボード操作で Escape を押す, Then ダイアログが閉じ（`role="dialog"` の数が 0）、フォーカスがダイアログを開いた要素へ戻ること。
  - [ ] AC-2: Given Escape での閉じる操作が無効に設定された共通Modalが開いている, When フォーカスがダイアログ内にある状態で Escape を押す, Then ダイアログは開いたままであること。また、Escape の有効/無効にかかわらず、閉じるボタン押下では従来どおり閉じ、バックドロップ押下は従来の設定（バックドロップで閉じるダイアログのみ）どおりに動作すること。
  - [ ] AC-3: Given ダイアログ内でポップオーバー、ドロップダウンメニュー、または IME 変換中の入力欄が Escape を自身で処理する状態になっている, When Escape を押す, Then そのサブ要素のみが閉じる/変換取消となりダイアログは開いたままであり、サブ要素が無い状態でもう一度 Escape を押すとダイアログが閉じること。
  - [ ] AC-4: Given MappingMasterEditModal の中で WorkflowNodePicker が開いている（`role="dialog"` が2件）, When フォーカスが WorkflowNodePicker 内のどの要素にある状態でも Escape を押す, Then WorkflowNodePicker のみが閉じ（`role="dialog"` が1件）MappingMasterEditModal は開いたままで、続けてフォーカスが MappingMasterEditModal 内にある状態で Escape を押すと MappingMasterEditModal も閉じること。
  - [ ] AC-5: Given MappingMasterEditModal の中で WorkflowNodePicker が開いている, When Tab を連続して押し、また Shift+Tab を連続して押す, Then フォーカスは WorkflowNodePicker 内のフォーカス可能要素のみを循環し（最後の要素から Tab で最初の要素へ、最初の要素から Shift+Tab で最後の要素へ）、MappingMasterEditModal 内および背面ページの要素にはフォーカスが移らないこと。
  - [ ] AC-6: Given AC-5 の状態から WorkflowNodePicker を閉じた（Escape・閉じるボタン・選択確定のいずれか）, When 閉じた直後およびその後 Tab / Shift+Tab を押す, Then 閉じた直後のフォーカスは WorkflowNodePicker を開いた要素にあり（その要素が存在しない/フォーカス不能な場合は MappingMasterEditModal 内の最初のフォーカス可能要素にあり）、以後の Tab / Shift+Tab は MappingMasterEditModal 内のみを循環して背面ページの要素へ移らないこと。
  - [ ] AC-7: Given 共通Modalが1件だけ開いている, When Tab / Shift+Tab を連続して押す, Then フォーカスがダイアログ外の要素へ移らず、ダイアログ内のフォーカス可能要素を循環すること（単一ダイアログの既存挙動を維持する非回帰）。
  - [ ] AC-8: Given 親要素が `space-y-*` などの余白クラスを持つ配置箇所（例: BaseModelSection のモデルマスタ管理・作成編集・マッピング追加の各モーダル）で共通Modalを開く, When 375x667 および 1280x900 の viewport で表示する, Then バックドロップの矩形が viewport 全面（位置0,0、幅・高さとも viewport と一致）となり、viewport 上端付近（例: y=6）の点で背景要素ではなくバックドロップ/ダイアログが操作対象になる（背景がクリックできない）こと。
  - [ ] AC-9: Given 本PBIの AC-1〜AC-8 に対応する自動テスト, When テストスイートを実行する, Then Escape・Tab の検証がフォーカスされた要素に対する実キー操作（ブラウザ実行またはユーザー操作シミュレーション）で行われ、AC-8 の検証が実レイアウトを持つブラウザ実行で行われ、修正前の実装に対して AC-1・AC-4・AC-5・AC-8 の各テストが失敗する（回帰検出力がある）こと。
- **Inferred points**:
  - 利用画面の範囲: 本PBIは共通Modalを使う全ダイアログに共通契約として適用する。`.modal-backdrop` を直接使うレガシーモーダル（SPEC_COMMON §1-4 のレガシー一覧）は対象外であり、対象に含める場合は別途判断する。
  - 単一ダイアログのTab循環（AC-7）が現状どこまで満たされているかは未確認（BAはコード非参照）。既に満たされていれば非回帰、満たされていなければ本PBIの修正範囲に含まれる。
  - 仕様の更新: SPEC_COMMON のネスト例外記述（外側は Escape を無視して内側のみ閉じる）を「最前面のみが Escape / Tab に応答し、閉じた後は開いた元要素へフォーカスが戻る」という契約へ更新する。SPEC_SETTINGS のカスタム型マスタ節および REQ-365 テスト計画（AC-9 / RT-5b の「別PBI」注記）も整合させる。SPEC_COMMON の「ネスト表示しない」原則と WorkflowNodePicker 例外は維持する。
  - 外側ダイアログの Escape 無効化という既存の個別回避（REQ-365 の WorkflowNodePicker 向け措置）は、AC-4 の挙動が共通Modal側で満たされれば不要になる可能性がある。撤去するか残すかは設計判断とし、AC は結果のみを規定する。
  - テスト規約: テスト名に `[REQ-367/AC-n]` を付与し、ファイル名・パスにチケット番号を含めない（SPEC-TESTING v2.1 / REQ-356）。実キー操作の検証は frontend/e2e/ に置く。
  - 実施順序: REQ-302 の AC-3（Escape でモーダルが閉じる）は本PBIの修正を前提とするため、REQ-302 より先に実施する。REQ-302 の AC-4（ネストモーダルの重なり順序）とも整合を取る。
  - ポップオーバー等のサブ要素が Escape を処理する対象は、現在ダイアログ内に存在するもの（メニュー、候補リスト、IME変換）を想定する。個別の列挙は設計フェーズで確定する。
  - REQ-365 r4 検証レポートの「入れ子 Modal の Tab トラップ」は、当時ユーザー決定により不具合計数から除外された許容トレードオフであり、恒久的な設計方針ではない。本PBIはユーザー承認（Q1）によりこれを解消対象に含める（先行判断を置き換える）。
  - 自動テストの実装（実キー操作のE2E/単体テスト）は本PBIの範囲に含む（AC-9）。
  - ネスト時のバックドロップ押下: 内側のバックドロップが viewport 全面を覆う（AC-8）ため、押下の対象は最前面ダイアログのバックドロップのみとなり、閉じる対象は最前面のみ（Escape と同じ規則）と解する。個別AC化は不要と判断したが、異議があれば追加する。
  - 範囲外（本PBIでは扱わない）: スクリーンリーダー読み上げの詳細、3段以上のネスト、サードパーティ部品が独自に Escape を握る場合の個別対応。サブ要素（AC-3）が Escape を消費しない場合はダイアログが閉じる。
  - AC-8 の 375x667 / 1280x900 は REQ-365 検証で用いた代表 viewport であり、固定条件ではなく代表例。
