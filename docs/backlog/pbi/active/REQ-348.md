### REQ-348: Settingsスマート置換の未設定ステージ候補追加とステージ別識別情報の保持

- **Type**: feature
- **Status**: ready
- **Priority**: P2（既存仮置きを維持）
- **Current step**: none
- **Surface**: Settingsのスマート置換における未設定の有効role×stage候補、選択・確定・再表示。通常の対応付け画面は既存動作維持と保存整合性の確認対象とする。
- **Operational need**: スマート置換時に既存の対応付けだけでなく、必要な未設定工程のロールを追加し、同一masterの異なるstageを混同せず保存する。
- **UX Classification**: Information Design / Interaction
- **現状確認（2026-10-26、コード読取）**:
  - 通常の対応付けはAdaptiveWorkflowWiring/buildWiringStageGroupsでstage別の有効variantと未設定slotを表示し、master_idとvariant_idを保持して選択・保存する経路がある。stage masterを参照するため固定3工程ではない。これらの保存後再表示や実画面操作は未検証。
  - スマート置換のdiff-analyzeはwf.mappingsだけからrole_migrationsを作成し、画面も既存行だけを編集する。未設定role×stageを新たに追加する候補がない。
  - スマート置換の確定payloadはmaster_id/node_idのみで、通常対応付けで使うvariant_idを引き継がない。stageごとのidentity保持は残件である。
- **Requirement**:
  - 既存マスタと対象workflowで有効なrole×stageをスマート置換の追加候補に含め、未設定の組合せもstage名付きで識別・選択できるようにする。ユーザー定義stageを固定のMain/Rough/Detailから除外しない。
  - 新規候補を選択した場合も既存行を再割当した場合も、masterとstage/variantの対応を保持して確定し、保存・再表示後に別stageへ混同されないようにする。同じmasterの異なるstageをmaster_idだけで上書きしない。
  - 不要な任意role×stageを追加することを強制しない。新規候補を選ばず未設定のまま確定できる範囲と、既存の必須割当制約を区別し、既存制約を一律解除しない。
  - 通常の対応付け画面のstage別表示・未設定候補・variant付き保存・不要slotの未設定保存を維持し、スマート置換との保存/再表示の整合を確認する。
  - stage順序変更・クローン・権限・新たな未設定警告・推定アルゴリズム全面刷新は含めない。表示はREQ-301で見直した現行デザイン要求と整合させる。
- **Acceptance criteria（2026-10-26レビュー後の現行AC）**:
  - [ ] AC-1: Given Main/Rough/Detailが有効でRough/Stepsが未設定であり有効なマスタvariantがある, When スマート置換の追加候補を開く, Then Rough/Stepsをstage名付きで選択でき、既存のMain/Stepsと区別できること。
  - [ ] AC-2: Given 未設定のRough/Stepsと割当可能ノード, When スマート置換で追加・確定して保存内容を再取得し画面を再表示する, Then 選択したmaster・variant/stage・nodeの組合せが保持され、通常の対応付け画面でも同じ工程に表示されること。
  - [ ] AC-3: Given 同じmasterのMain/StepsとRough/Stepsを異なるノードへ割当済み, When スマート置換で片方のノードを変更して確定・再表示する, Then 両方のvariant/stageが保持され、変更しなかったstageの対応付けが欠落・上書きされないこと。
  - [ ] AC-4: Given ユーザー定義の第四stageが対象workflowで有効で対応する有効variantがある, When スマート置換の未設定候補から選択し保存・再表示する, Then 第四stageも識別・追加でき、通常の対応付け画面でも当該stageを確認・編集できること。
  - [ ] AC-5: Given 不要な任意role×stageを未設定として扱えるworkflow, When その候補を追加せず確定し通常の対応付けも保存・再表示する, Then 未設定が保持され、既存設定を意図せず削除せず、既存の必須割当制約と他stageの独立保存が維持されること。
- **設計・検証への引継ぎ**:
  - 有効条件・variant identity・legacyのvariantなしmapping・同名stageとrole・API入出力・置換/復旧の保存契約を確認する。分析とFE確定の型を含む変更範囲を明示し、identityをタイトルやsuffixから推測補完しない。
  - AC-1〜5の追加/既存再割当/再表示/任意未設定と、通常の対応付けの既存ケースを新規候補で検証する。部分的に実装経路があることや過去の完了記録を今回の受入PASSにしない。
  - API契約・型の変更はREQ-248/391のOpenAPI方針と、表示変更はREQ-301と整合させる。新機能の範囲拡大が必要なら再レビューする。
- **Reference docs**: docs/specs/SPEC_SETTINGS.md（Workflow/Mapping）、docs/specs/SPEC_GENERATE.md、REQ-336、REQ-343、REQ-301

### 旧REQ-348: Settingsのスマート置換と対応付けを複数ステージへ対応させる

- **Type**: feature
- **Status**: ready
- **Priority**: P2（仮置き）
- **Surface**: Settingsのスマート置換・ワークフロー対応付け
- **Operational need**: 生成ページと同じ複数工程構成を設定ページでも追加し保存する。
- **5 Whys / 業務上の課題整理**（ユーザー報告からの要約。実装原因の断定ではない）:
  1. 必要な工程のロールを追加・対応付けできない。
  2. スマート置換候補が既存設定に限られ対応付けで工程が欠ける。
  3. 設定済み候補だけでは未設定工程を追加できない。
  4. 有効なロールと工程の組み合わせを選べば構成を完成できる。
  5. 画面間で編集可能な多段構成の範囲が揃っていないことが課題である。
- **UX Classification**: Information Design / Interaction
- **Requirement**:
  - 未設定でも有効ロール×対象ステージをスマート置換で選択し追加可能にする。
  - 対応付けで対象ワークフローの全有効ステージを編集・個別保存可能にする。
- **旧Acceptance criteria（履歴・適用終了）**:
  - 旧AC-1: Given Main/Rough/Detailが有効でRough/Steps未設定, When Settingsのスマート置換追加候補を開く, Then Rough/Stepsをステージ名付きで選択できること。
  - 旧AC-2: Given 未設定Rough/Stepsと候補ノード, When スマート置換で追加し保存して再表示する, Then そのステージとノードの組み合わせが保持されること。
  - 旧AC-3: Given Main/Rough/Detailとユーザー定義の第四ステージがワークフローに存在する, When Settings対応付けを開く, Then 4ステージ全てを編集できること。
  - 旧AC-4: Given Main/StepsとRough/Steps, When 各々別ノードへ対応付けて保存し再表示する, Then ステージ別の対応付けが保持されること。
  - 旧AC-5: Given 特定ステージのロールが不要, When その組み合わせを未設定のまま保存する, Then 保存でき未設定を保持すること。
