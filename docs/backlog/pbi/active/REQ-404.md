### REQ-404: プリセット作成で id が返らないとき作成が繰り返されないようにする

- **Type**: bug
- **Status**: frontmatter の `status` を参照（状態の正本）。
- **Priority**: P2（実運用での発生は未確認。仮置き）
- **Surface**: 生成画面のプリセット同期（`usePresetStoreSync`）と、プリセットの作成・一覧の API 応答に対する画面の振る舞い。
- **利用者ニーズ**: プリセットの作成がうまくいかない場合でも、サーバーに不要なプリセットが増え続けたり画面が使えなくなったりせず、失敗に気づいて対処できるようにしたい。
- **課題の整理（観測）**: REQ-309-T3 のテストで、プリセット一覧 API の mock が空配列を返したとき、プリセット同期が作成要求を繰り返し、`sets=[]` のままになった。作成 API が id を返さない、または作成後も一覧が空のまま、という状態で起こる。これはテストでの観測であり、実運用でこの状態になるかは未確認。
- **5 Whys**:
  1. なぜ起票するか: 一覧が空のままだと作成が繰り返され、プリセットのない状態から抜けられないため。
  2. なぜ作成が繰り返されるか: 「プリセットが 0 件なら作成する」という同期が、作成結果の確認（id の取得、一覧への反映）を前提にしており、確認できない場合の止め方が定まっていないため（推定。実装は調査していない）。
  3. なぜ失敗に気づけないか: 作成が成功したか失敗したかを利用者に示す契約が、仕様書にないため（SPEC_GENERATE §2-6 に記述なし）。
  4. なぜ今まで表面化しなかったか: 通常は作成 API が id を返し一覧にも現れるため（推定）。テストの mock で初めて観測された。
  5. 根本原因: プリセット作成が期待どおりに完了しなかったときの終了条件・利用者への通知・復帰手段が定義されていない。
- **UX Classification**: Information Design（作成失敗を利用者に知らせる表示）と Interaction（再試行の操作）。Visual（見た目の刷新）は含めない。
- **Requirement**: プリセット作成で id が得られない、または一覧が空のままのとき、自動での作成要求を繰り返さず、失敗を利用者に示し、生成画面を使える状態に保ち、利用者の操作で再試行できること。

## 範囲

- 対象: 生成画面のプリセット同期が行う自動作成の終了条件、失敗の通知、画面の可用性、再試行手段。
- 対象外: 作成 API やプリセット一覧 API の応答形式の変更。複数端末間の競合解決（既存の 409 競合モーダル）の変更。プリセットタブの一括クローズ（REQ-402）。

## Acceptance Criteria

- [ ] AC-1: 作成 API が id を返さないとき自動で作成を繰り返さない
  - Given 生成画面でプリセットが 0 件の状態で、作成 API が成功応答を返すが id を含まない
  - When 生成画面を表示して同期が完了または停止するまで待つ
  - Then 自動で送信される作成要求は同じ条件で最大 1 回であり、それ以降は利用者の操作なしに送信されないこと
- [ ] AC-2: 作成後も一覧が空のままのとき自動で作成を繰り返さない
  - Given 生成画面でプリセットが 0 件で、作成 API は id を返すが、その後の一覧取得が空配列を返し続ける
  - When 生成画面を表示して同期が完了または停止するまで待つ
  - Then 自動で送信される作成要求は同じ条件で最大 1 回であり、それ以降は利用者の操作なしに送信されないこと
- [ ] AC-3: 作成要求がエラーで失敗したときも自動で繰り返さない
  - Given 生成画面でプリセットが 0 件で、作成 API がエラー応答または通信断で失敗する
  - When 生成画面を表示して同期が完了または停止するまで待つ
  - Then 自動で送信される作成要求は同じ条件で最大 1 回であり、それ以降は利用者の操作なしに送信されないこと
- [ ] AC-4: 作成が完了しなかったことを利用者に示す
  - Given AC-1 から AC-3 のいずれかの状態になった
  - When 同期が停止する
  - Then 画面上にプリセットを作成または取得できなかったことを示すメッセージが表示され、作成に成功したと誤解させる表示（プリセットタブが存在するかのような表示）が出ないこと
- [ ] AC-5: 失敗の後も生成画面を使える
  - Given AC-4 のメッセージが表示されている
  - When 利用者がプロンプトとパラメータを編集し、ほかの画面へ移動する
  - Then 画面が応答し続け、入力した内容が編集欄に表示され、ほかの画面へ移動できること
- [ ] AC-6: 利用者の操作で作成を再試行できる
  - Given AC-4 のメッセージが表示されている
  - When 利用者が再試行の操作を行う
  - Then 作成が 1 回だけ試行され、成功して id が得られ一覧にも現れた場合は通常の状態に戻り、プリセットが 1 つだけ表示されること
- [ ] AC-7: 再試行も失敗した場合は同じ案内を維持する
  - Given AC-4 のメッセージが表示されている
  - When 利用者が再試行の操作を行い、再び作成が完了しない
  - Then 失敗のメッセージが維持され、利用者の操作ごとに送信される作成要求が 1 回であること
- [ ] AC-8: 後から一覧にプリセットが現れたら重複して作成しない
  - Given AC-4 のメッセージが表示されている
  - When その後の一覧取得でプリセットが 1 件以上返る
  - Then 追加の作成要求が送信されず、返ったプリセットが表示され、失敗のメッセージが消えること
- [ ] AC-9: 正常時の作成は従来どおり
  - Given 生成画面でプリセットが 0 件で、作成 API が id を返し、一覧にその 1 件が現れる
  - When 生成画面を表示する
  - Then 作成要求が 1 回送信され、プリセットが 1 つだけ表示されて失敗のメッセージが出ないこと
- [ ] AC-10: 既存のプリセットがある場合は作成しない
  - Given 生成画面で一覧が 1 件以上のプリセットを返す
  - When 生成画面を表示する
  - Then 自動の作成要求が送信されず、既存のプリセットがタブに表示されること

## Inferred points

<inferred_points>
- 実運用で作成 API が id を返さない、または作成後の一覧が空のままになる条件があるかは未確認。要確認事項: (a) サーバーが id を返さない応答を返す経路があるか、(b) 一覧の反映が遅れる（結果整合）経路があるか、(c) 実運用で発生しないテスト専用の状態なら、本 PBI の優先度と範囲をどうするか。
- 「自動の作成要求は最大 1 回」は、無限の繰り返しを防ぐ検証可能な上限として BA が置いた値。数回の自動再試行を許すか、再試行の間隔を設けるかは要確認（設計で具体化し、AC-1 から AC-3 の上限値を合わせて更新する）。
- 失敗のメッセージの文言、表示位置、再試行の操作の見た目は設計で具体化する。AC は表示の有無と再試行できることを求める。
- 失敗状態（`sets=[]` 相当）で「生成」の実行を許すかは未確認。AC-5 は編集と画面遷移の可用性だけを求め、生成実行の可否は要確認とする（許さない場合は、その理由を利用者に示すことが望ましい）。
- 作成 API が「id を返さない成功応答」を返した場合、サーバー側にプリセットが作られている可能性がある。AC-8 は一覧にその後現れたものを採用する考え方だが、孤立したプリセットの扱いは範囲外とし、要確認とする。
- 画面の再読込や再訪時に、同期の「最大 1 回」の計数をどう扱うか（再読込でリセットされるか）は要確認。
- 要件取りまとめ時点では実装コードは未調査。上記の原因は推定で、設計で確認する。
</inferred_points>
