- **起点**: REQ-394のQAトリアージでユーザーが別PBI化を選択（2026-10-25）。根拠は`docs/logs/REQ-394/qa2/walkthrough.md`（s8 RT1）、`docs/logs/verification/a58d778c4e72425f868ee2eb005f5b72.record.json`、`docs/logs/REQ-394/qa-triage-2.json`。過去のローカル記録として扱う。
- **過去の観測記録**:
  - FE全体のシャッフルでseed 1は6 files/11 tests、seed 2は6 files/15 testsが失敗し、和集合が上記7ファイルと記録されている。
  - `connectionSlice.test.ts`と`jobQueueSlice.test.ts`は同じseedの単独実行でも失敗したと記録される。他5ファイルがすべてファイル内順序依存と確定したものではない。
  - 通常順序、REQ-394でnode化した43ファイル、および範囲を限定したシャッフルの成功は当時の記録であり、現在候補のPASSではない。
- **現状確認（2026-10-26）**:
  - 7ファイルは現在も存在し、既定jsdom構成の対象である。共通setupはjest-domのimportで、個別ファイルにそれぞれ初期化/復元処理がある。
  - TagChipにはdescribe内の共有vi.fn、SpeechBubbleEditorModal/CreateProjectModalにはclearAllMocksを使うbeforeEach、useGeneratePageStateには共有mock storeと個別復元処理がある。connectionSlice/jobQueueSliceはdescribeごとにlocalStorage・WebSocket・mock・storeの初期化内容が異なり、部分的setStateも存在する。
  - これらは調査候補となる構造の確認であり、漏洩や失敗の原因を確定したものではない。cleanupが見当たらないことだけで自動cleanupの不在を断定しない。今回はテスト収集・通常/シャッフル実行・再現・原因確定を行っていない。
- **Root Cause（仮説・未確定）**: mock実装/once応答、store、DOM、storage、QueryClient、WebSocket購読、timer、未完了非同期処理等の初期化・後始末不足が考えられる。各ファイルで実行順と状態の受渡しを調べ、ファイル内依存・全体実行時のみの問題・負荷によるタイミング問題を区別する。
- **関連・境界**: REQ-394は完了記録を持つ。REQ-399は実行資源/並列度の安定化を扱い、本件へ統合しない。worker削減や順序固定で本件の失敗を隠さない。7件外の新規失敗や製品不具合が出た場合は影響と扱いをレビューし、黙って対象を広げない。
- **UX Classification**: Information Design（テストの独立性と原因/証拠の追跡）。製品の表示・操作の変更は要求しない。
- **Requirement**:
  - 各7ファイルを単独でseed 1・2・3、FE全体もseed 1・2・3でシャッフルし、全必須ケースが順序に依存せず成功するようにする。seed 3を設計判断で省略しない。追加seedは原因調査に応じ設計で決める。
  - ファイルごとに原因と修正境界を定め、状態を再現可能に初期化・復元する。既存assertionや期待値を緩和せず、skip・削除・固定順序・retry・安易なtimeout延長で解決しない。実装内部の関数置換を増やして成功を作らない。
  - 既存ケースの安定IDと意味上の検証内容を保持する。必要な回帰ケースの追加は許容し、追加分を識別する。通常順序でのFE全体も成功すること。
  - CLI・依存版・pool/isolate/worker・shuffleの対象（ファイル順/テスト順）・seed・環境を固定して前後比較し、意図した並べ替えが有効なことを確認する。製品/実サービス/実DBへの副作用を起こさない。

- **観測事実**:
  - FE 全体を `vitest --sequence.shuffle` で実行した結果（seed 1: 6 files / 11 tests、seed 2: 6 files / 15 tests が FAIL）。2 回の失敗ファイルの和集合が上記 7 ファイル。

- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: FE の既存テストがテスト順に依存しており、シャッフル実行で FAIL する。
  2. なぜその課題が発生するか: 各テストが、前のテストが残した状態（モジュールやストアの状態、DOM、モックなど）に依存しており、テスト間で状態が分離されていない。
  3. なぜ現状の仕組みで不十分か: 通常の順序では常に PASS するため、順序依存が検出されない。順序に依存するテストは、並列化や環境変更（REQ-394 のような実行環境の変更）を行う際に検証の妨げになる。
  4. なぜこのアプローチを採用するか: 順序依存を解消すれば、FE 全体のシャッフル実行が検証手段として使えるようになり、将来の実行環境変更の検証が確実になる。
  5. 根本原因（仮説・未確定）: 対象ファイルで、テスト間の状態のリセットが不足している。原因の確定はファイルごとに設計で行う。
