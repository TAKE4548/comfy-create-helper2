### REQ-392: pytest マーカー（REQ-xxx / AC-N）を登録済みの単一 case マーカーへ移行して PytestUnknownMarkWarning を解消する

- **Type**: chore
- **Status**: ready
- **Priority**: P3
- **Surface**: `backend/pytest.ini`、`backend/tests/conftest.py`、旧マーカー使用テスト、`scripts/verify_test_naming.py`と関連検証、`.agents/context.md`のテスト規約。製品コードは対象外。
- **起点**: REQ-387の後続課題。過去の根拠は`docs/logs/REQ-387/qa-code-report-r2.md`（軽微2、gitignore対象のローカル資料）。
- **方式の決定**: 2026-10-25のユーザー承認済み方針を維持し、REQ・ACを別名のマーカーで登録する方式から、登録済みの単一`case`マーカーへ移行する。例は`@pytest.mark.case("[REQ-xxx/AC-y]", layer="integration")`。引数の最終形と複数AC指定は後続設計で確定する。
- **現状確認（2026-10-26）**:
  - Python ASTによる静的確認では、旧`getattr(pytest.mark, ...)`は7ファイル・111呼出し。内訳はREQ-335が41、REQ-366が1、REQ-386が4、REQ-387が9、ACマーカーが56。これはデコレータやモジュール変数内の呼出し数であり、テスト収集件数・警告件数ではない。
  - 対象は`backend/tests/governance/test_ui_invariants.py`と`backend/tests/integration/legacy/`の`test_generation_api.py`、`test_generation_integration.py`、`test_generation_jobs_migration.py`、`test_generation_repository.py`、`test_generation_schema.py`、`test_generation_service.py`。モジュール単位の`pytestmark`と、同一テストへの複数AC指定も存在する。
  - `backend/pytest.ini`にマーカー登録はなく、`backend/tests/conftest.py`に`case`の登録・収集時検証はない。`verify_test_naming.py`のPython抽出は関数名/docstringを読み、caseメタデータを読み取る処理はない。
  - `.agents/context.md`は旧テスト名規約の説明を保持している。REQ-387の既存設計・テスト計画には`-k req387`による選択がある。全実行経路の`-m`運用有無は後続設計で調査する。
  - 725件収集・111警告は2026-10-25の過去記録。今回はpytest収集・テスト・mypy・命名検証を実行しておらず、現在値や成功を示すものではない。
- **Root Cause**: 未登録のREQ/AC別マーカーが警告を生み、対応関係のメタデータ・検証スクリプト・選択運用が一貫していない。
- **UX Classification**: Information Design（検証出力と追跡情報）、Interaction（開発者のケース選択操作）。利用者向け画面の変更はない。
- **Requirement**:
  - 既存REQ/AC別マーカーを登録済み`case`へ移行し、旧マーカー由来の`PytestUnknownMarkWarning`を解消する。警告の抑制や番号別の大量登録では解決しない。
  - REQ・ACの組、layer、パラメータ展開後の安定したケースIDを追跡可能にする。モジュール/クラスからの継承と複数AC指定も扱い、機械的な直積で誤った対応を作らない。
  - 書式・layerの不正と、参照先REQ/ACが存在しない未知タグをそれぞれ拒否する。実在する新規REQ/ACはマーカー名の追加登録を不要とする。参照元はプロジェクトのactive/archive PBI等から設計で定め、過去ACの履歴と現行ACを区別して既存完了テストの追跡を保つ。
  - `verify_test_naming.py`でcaseメタデータを対応証拠として読み取り、既存のファイル名・docstring規約を維持する。ただしdocstringやコメントだけを明示メタデータの代替として受入証拠にしない。
  - `.agents/context.md`を現行方式へ更新し、既存の名前選択を維持する。旧マーカー選択の運用があれば移行先と同一ケース集合を示す。全体共有ルールの変更や、全FEテストの移行は本件へ含めない。

- [ ] AC-8: Given 更新後の`.agents/context.md`, When 規約と実コマンドを照合する, Then caseの書式・layer・複数AC・新規PBI追加・未知タグ拒否・ケース選択例が実装と一致し、コメント/docstringだけを受入メタデータとして扱わないこと。変更した管理対象テキストがUTF-8（BOMなし）・LFであること。

- **設計・検証への引継ぎ**:

  - テスト基盤・収集/選択・検証処理を変更するため、低リスク扱いせず、現行規約のfreshな全スイートbaselineと各Gateを適用する。
  - 共有定義やインストール済み共有スクリプトは本件の編集対象ではない。プロジェクトの命名規約と共有メタデータ規約の衝突は設計で明示し、黙って片方を撤回しない。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: backend/pytest.ini, backend/tests/conftest.py, backend/tests（マーカー使用 7 ファイル）, scripts/verify_test_naming.py, .agents/context.md（テスト規約の記載）
- **起点**: REQ-387（commit fca9965）の後続課題。tester-reviewer が受入レポートの軽微 2 として記録した（ゲートには影響しない）。
- **根拠資料**: `docs/logs/REQ-387/qa-code-report-r2.md`（軽微 2）。`docs/logs/` は gitignore 対象のローカル資料。実測: `backend` で `python -m pytest --collect-only` を実行すると 725 件の収集に対して `PytestUnknownMarkWarning` が 111 件出る。内訳は `REQ-335`（41 件）、`AC-1`〜`AC-8`、`REQ-387`（9 件）、`REQ-386`（4 件）、`REQ-366`（1 件）。マーカーは `@getattr(pytest.mark, "REQ-335")` の形式で、7 ファイル・約 110 行に使われている。
- **登録方式の決定（2026-10-25、ユーザー承認）**: 規約変更（B）を採用する。既存の `@getattr(pytest.mark, "REQ-xxx")` / `@getattr(pytest.mark, "AC-n")` を、`backend/pytest.ini` に登録した単一マーカー `case`（例: `@pytest.mark.case("[REQ-xxx/AC-y]", layer="unit|integration|e2e|scenario")`）へ移行する。マーカー名・引数の最終形は設計で確定してよい。
- **背景**: 共有ルール `rules/testing.md` に「AC 対応は明示的なテストフレームワークのメタデータ（例 `@case('[REQ-xxx/AC-y]', layer=...)`）と安定したケース ID で示す。AC タグのコメントだけでは証拠にならない」が追加された。現行の `REQ-xxx` と `AC-n` は別々のマーカーで、両者の対応を結べないため、この規約に合わない。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: 全テストの実行・収集のたびに警告が約 110 件出て、本当に注意すべき警告が埋もれる。
  2. なぜ発生するか: テストが PBI のトレーサビリティ用に `REQ-xxx` / `AC-N` 名のマーカーを付けているが、`backend/pytest.ini` に `markers` が登録されていない。
  3. なぜ現状の仕組みで不十分か: マーカー名は PBI ごとに増える（REQ-の番号と AC の番号）。個別登録では PBI を追加するたびに ini の更新を忘れ、警告が再発する。また REQ と AC が別マーカーのため、どの AC がどの REQ に属するかをテスト単位で結べない。
  4. なぜ chore とするか: テストの結果や製品コードを変えず、マーカーの形式と登録の規約を整えるだけで済む。
  5. 根本原因: マーカーの命名規約はあるが、登録の規約（誰がいつ登録するか）と、REQ・AC の対応を 1 つのメタデータで示す規約が定義されていない。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - テスト実行出力の情報設計の改善（警告の雑音を減らす）。テストのトレーサビリティ情報を単一のメタデータにまとめる。利用者向けの表示は変更しない。
  - **Interaction (インタラクション)**:
    - 開発者の操作（テスト実行）への影響は出力の変化と、マーカーによる選択方法の変更（変わる場合）。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. 警告の解消**:
    - 既存のマーカーによる `PytestUnknownMarkWarning` を 0 件にする。
  - **2. 単一 case マーカーへの移行**:
    - `backend/tests` の既存の `@getattr(pytest.mark, "REQ-...")` / `@getattr(pytest.mark, "AC-...")` をすべて、`backend/pytest.ini` に登録した単一の `case` マーカー（REQ と AC の組と layer を保持）へ移行する。
  - **3. 再発防止**:
    - 将来の新しい PBI 番号・AC 番号は `case` マーカーの値として書くだけで、`pytest.ini` への追記なしに警告なく使えるようにする。値の形式（`[REQ-n/AC-n]`）や layer の許容値が不正な場合は、検出されて失敗するようにする。
  - **4. 検証スクリプトの追従**:
    - `scripts/verify_test_naming.py`（REQ-356 の命名規約。docstring の `[REQ-xxx/AC-n]` を読む）が、`case` マーカーの値も対応の証拠として読めるようにする。REQ-356 の既存規約は変更しない。
  - **5. 規約の更新**:
    - `.agents/context.md` のテスト規約を新方式に更新し、マーカーによる選択方法が変わる場合の代替手段を記載する。
- **旧Acceptance criteria（履歴・適用終了）**:
