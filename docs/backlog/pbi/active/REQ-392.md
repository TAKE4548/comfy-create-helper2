### REQ-392: pytest マーカー（REQ-xxx / AC-N）を登録済みの単一 case マーカーへ移行して PytestUnknownMarkWarning を解消する

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: backend/pytest.ini, backend/tests/conftest.py, backend/tests（マーカー使用 7 ファイル）, scripts/verify_test_naming.py, .agents/context.md（テスト規約の記載）
- **起点**: REQ-387（commit fca9965）の後続課題。tester-reviewer が受入レポートの軽微 2 として記録した（ゲートには影響しない）。
- **根拠資料**: `docs/logs/REQ-387/qa-code-report-r2.md`（軽微 2）。`docs/logs/` は gitignore 対象のローカル資料。実測: `backend` で `python -m pytest --collect-only` を実行すると 725 件の収集に対して `PytestUnknownMarkWarning` が 111 件出る。内訳は `REQ-335`（41 件）、`AC-1`〜`AC-8`、`REQ-387`（9 件）、`REQ-386`（4 件）、`REQ-366`（1 件）。マーカーは `@getattr(pytest.mark, "REQ-335")` の形式で、7 ファイル・約 110 行に使われている。
- **登録方式の決定（2026-10-25、ユーザー承認）**: 規約変更（B）を採用する。既存の `@getattr(pytest.mark, "REQ-xxx")` / `@getattr(pytest.mark, "AC-n")` を、`backend/pytest.ini` に登録した単一マーカー `case`（例: `@pytest.mark.case("[REQ-xxx/AC-y]", layer="unit|integration|e2e|scenario")`）へ移行する。マーカー名・引数の最終形は設計で確定してよい。
- **背景**: 共有ルール `rules/testing.md` に「AC 対応は明示的なテストフレームワークのメタデータ（例 `@case('[REQ-xxx/AC-y]', layer=...)`）と安定したケース ID で示す。AC タグのコメントだけでは証拠にならない」が追加された。現行の `REQ-xxx` と `AC-n` は別々のマーカーで、両者の対応を結べないため、この規約に合わない。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: 全テストの実行・収集のたびに警告が約 110 件出て、本当に注意すべき警告が埋もれる。
  2. なぜ発生するか: テストが PBI のトレーサビリティ用に `REQ-xxx` / `AC-N` 名のマーカーを付けているが、`backend/pytest.ini` に `markers` が登録されていない。
  3. なぜ現状の仕組みで不十分か: マーカー名は PBI ごとに増える（REQ-の番号と AC の番号）。個別登録では PBI を追加するたびに ini の更新を忘れ、警告が再発する。また REQ と AC が別マーカーのため、どの AC がどの REQ に属するかをテスト単位で結べない。
  4. なぜ chore とするか: テストの結果や製品コードを変えず、マーカーの形式と登録の規約を整えるだけで済む。
  5. 根本原因: マーカーの命名規約はあるが、登録の規約（誰がいつ登録するか）と、REQ・AC の対応を 1 つのメタデータで示す規約が定義されていない。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - テスト実行出力の情報設計の改善（警告の雑音を減らす）。テストのトレーサビリティ情報を単一のメタデータにまとめる。利用者向けの表示は変更しない。
  - **Interaction (インタラクション)**:
    - 開発者の操作（テスト実行）への影響は出力の変化と、マーカーによる選択方法の変更（変わる場合）。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. 警告の解消**:
    - 既存のマーカーによる `PytestUnknownMarkWarning` を 0 件にする。
  - **2. 単一 case マーカーへの移行**:
    - `backend/tests` の既存の `@getattr(pytest.mark, "REQ-...")` / `@getattr(pytest.mark, "AC-...")` をすべて、`backend/pytest.ini` に登録した単一の `case` マーカー（REQ と AC の組と layer を保持）へ移行する。
  - **3. 再発防止**:
    - 将来の新しい PBI 番号・AC 番号は `case` マーカーの値として書くだけで、`pytest.ini` への追記なしに警告なく使えるようにする。値の形式（`[REQ-n/AC-n]`）や layer の許容値が不正な場合は、検出されて失敗するようにする。
  - **4. 検証スクリプトの追従**:
    - `scripts/verify_test_naming.py`（REQ-356 の命名規約。docstring の `[REQ-xxx/AC-n]` を読む）が、`case` マーカーの値も対応の証拠として読めるようにする。REQ-356 の既存規約は変更しない。
  - **5. 規約の更新**:
    - `.agents/context.md` のテスト規約を新方式に更新し、マーカーによる選択方法が変わる場合の代替手段を記載する。
- **Acceptance criteria**:
  - [ ] AC-1: Given `backend` で全テストを収集する（`python -m pytest --collect-only`）, When 出力の warnings summary を確認する, Then `PytestUnknownMarkWarning` が 0 件で、収集件数が変更前と同じであること。変更前の件数は着手時に実測して `docs/design/REQ-392.md` に記録する（前回記録は 725 件）。
  - [ ] AC-2: Given `python -m pytest -W error::pytest.PytestUnknownMarkWarning` を実行する, When 全テストを収集・実行する, Then 警告由来のエラーがなく、成功・失敗・スキップの件数が変更前と同一であること。
  - [ ] AC-3: Given 移行後の `backend/tests`, When `@getattr(pytest.mark, "REQ-` と `@getattr(pytest.mark, "AC-` を検索する, Then どちらも 0 件であり、変更前に REQ マーカーまたは AC マーカーを持っていたテストの集合が、すべて `case` マーカーを持つこと。
  - [ ] AC-4: Given `case` マーカーの値が `[REQ-\d+/AC-\d+]` の形式でないテスト、または layer が許容値（`unit`/`integration`/`e2e`/`scenario`。最終形は設計で確定）の外のテスト（一時テスト）, When 収集または実行する, Then 不正が検出され失敗すること。正しい値（例: 実在しない `[REQ-999/AC-99]` と許容値の layer）の一時テストは、`pytest.ini` や `conftest.py` への追記なしに警告 0 件で収集されること。
  - [ ] AC-5: Given 変更前後, When `-k req387` など既存のケース名での選択を、変更前に実行して記録した選択条件のすべてについて実行する, Then 選択されるテスト ID の集合が変更前と同一であること。
  - [ ] AC-6: Given 変更後, When `scripts/verify_test_naming.py --strict` と `mypy backend` を実行する, Then どちらも変更前と同じ結果（エラー 0 件）であること。さらに、`case` マーカーに `[REQ-n/AC-n]` を持つテストを対応の証拠として読み取り、値の形式が不正なものを `--strict` で報告すること。REQ-356 の docstring 規約による判定結果は変更前と同一であること。
  - [ ] AC-7: Given 変更前のリポジトリ（`backend/pytest.ini`、テスト実行用のスクリプト・設定、CI 設定、`.agents/context.md`、`docs/`）, When `-m "REQ-..."` や `-m "AC-..."` によるマーカー選択運用の有無を調べる, Then 運用の有無と調べた範囲が `docs/design/REQ-392.md` の調査節に記録されていること。
  - [ ] AC-8: Given 変更後の `.agents/context.md`, When テスト規約を確認する, Then `case` マーカーの書式・layer の許容値・新しい PBI 追加時の書き方が記載され、`-m` による選択方法が変わる場合は代替手段（`-k` またはケース値でのフィルタ）の実行例が記載されていること。
- **Inferred points**:
  - 件数（111 件、725 件収集）は 2026-10-25 に `backend` で `--collect-only` を実行した実測値である。着手時に再測定が必要。
  - 登録方式は規約変更（B）で確定した（ユーザー承認済み）。動的登録（A）は、REQ と AC が別マーカーのため対応を結べず、`rules/testing.md` の規約に合わないため採用しない。
  - 本 PBI は、テストの合否やテスト名の `[REQ-xxx/AC-n]` プレフィックス規約（REQ-356）を変更しない。ただし `scripts/verify_test_naming.py` を変更する際に REQ-356 規約と矛盾しないことは設計で確認する（監査 F-006 は受容リスクとして扱う）。
  - 1 つのテストが複数の REQ・AC に対応する場合の `case` マーカーの書き方（複数指定の可否）は設計で確定する。
