### REQ-378: モバイルUI共通規約のSPEC_COMMON反映（スクロール・固定操作・アクション配置・複数選択ほか）

- **Type**: chore（ドキュメントのみ。Task Cardの change_kind は doc とする想定）
- **Status**: ready
- **Priority**: P2
- **Surface**: docs/specs/SPEC_COMMON.md（§1-3、§1-4、§2-4、§5 ほか）。アプリケーションコードは変更しない
- **Reference**:
  - docs/design/mobile-ui-redesign/mobile-common-ui-redesign-proposal.md（COMMON-01〜11、§3 共通コンポーネント影響表、§5 決定フロー、C-AC-01〜13）
  - docs/design/mobile-ui-redesign/mobile-history-generate-selection-design-draft.md（§4 共通の複数選択パターン）
  - docs/specs/SPEC_COMMON.md、SPEC_GENERATE.md、SPEC_HISTORY.md、SPEC_LORAS.md、SPEC_TAGS.md
  - 後続: REQ-371〜REQ-377（各画面のPBI）
- **5 Whys / Root Cause**:
  1. なぜ必要か: モバイルUI改修（REQ-371〜377）が複数画面に共通の規則（入れ子スクロールの回避、固定操作、Close/Cancel左・Edit/Save右、複数選択の上下分離など）を前提にしているため。
  2. なぜその課題が発生するか: 共通規則が提案書にしか存在せず、現行の SPEC_COMMON（例：§5-2は上部ツールバー、§1-3は44px）と一部が食い違う。
  3. なぜ現状の仕組みで不十分か: 規則を各PBIが個別に解釈・仕様化すると、画面間で不整合が生じ、共通化の判断（共有部品を変えるか）も画面ごとにばらつく。
  4. なぜこのアプローチを採用するか: Spec-Firstの方針に従い、画面横断の規則を先に確定仕様へ反映し、画面固有の仕様は各PBIの完了時に更新する。ユーザーが提案の方向性を採用した（2026-10-18）。
  5. 根本原因: 画面横断のUI規則を保持する確定仕様の置き場と、承認済み／未承認の区別がないこと。
- **UX Classification**:
  - **Information Design (情報設計)**: 共通規則を仕様書の一節にまとめ、適用画面と導入状況を示す。
  - **Interaction (インタラクション)**: 該当なし（仕様記述のみ）。
  - **Visual (視覚デザイン)**: 該当なし。
- **Requirement**:
  - **1. 共通規約の節を新設する**: COMMON-02〜11 を、モバイル（幅767px以下）に適用する採用済み規則として SPEC_COMMON に記載する。各規則に適用画面と適用するPBIを併記する。
  - **2. 既存記述との整合**: SPEC_COMMON の既存記述（§1-3 操作対象44px、§1-4 共通モーダルとレガシーモーダル、§2-4 ボトムナビ、§5 複数選択UI）と食い違う箇所を、改訂または明示的な例外として解消する。
  - **3. 画面固有値を共通化しない**: 提案書の寸法・数値（Generateのタブ42px、LoRA／Tag Setカード320px・2/2/1行、チップ3px/8px、下部余白72px、ナビ54px等）は共通トークンにせず、各画面のPBIで扱う。
  - **4. 共有部品の判断を区別する**: `TagChipEditor`／`ImageCarousel`／`MultiSelectToolbar`／`TagSetFormFields` 等の共有部品の変更は、承認済みの規則とは別の「未承認事項」として列挙し、既成事実として記載しない。
  - **5. 実装との区別**: 未実装の挙動を現状として書かない。導入前の規則はその旨（導入前／導入済み）を明記する。
- **Acceptance criteria**:
  - [ ] AC-1: Given 本PBIの完了後の SPEC_COMMON, When モバイルUI共通規約の節を確認する, Then スクロール、固定操作、アクション配置（左＝Close/Cancel、右＝Edit/Save）、シート／画像、操作領域、表示階層、情報階層（行数制限時は全文確認の経路を保持）、入口の一貫性、ジェスチャー、複数選択の各規則が、規則ID・適用画面・適用PBIとともに記載されていること。
  - [ ] AC-2: Given SPEC_COMMON §5（複数選択UI）, When 本PBIの後に確認する, Then モバイルの「上部＝×＋選択件数＋補助選択操作、下部＝画面固有の一括操作ドック」のパターンが記載され、デスクトップの既存パターンとの適用範囲の違いが明記され、SPEC_HISTORY／SPEC_GENERATEの記述と矛盾しないこと。
  - [ ] AC-3: Given 各規則, When 導入状況を確認する, Then 各規則に「導入前」または「導入済み」が記載され、導入前の規則が現状の挙動として記述されていないこと。
  - [ ] AC-4: Given 提案書の画面固有値（42px、320px、2/2/1行、3px/8px、72px、54px等）, When SPEC_COMMON を確認する, Then いずれも共通トークンとして記載されておらず、各画面のPBIの範囲であることが明記されていること。
  - [ ] AC-5: Given 共有部品の変更候補, When SPEC_COMMON を確認する, Then `TagChipEditor` のチップ密度、`ImageCarousel` の中央配置、`MultiSelectToolbar` の統合、`TagSetFormFields` のスクロール仕様が「未承認事項」として列挙され、各項目に判断が必要な内容と影響画面が記載されていること。
  - [ ] AC-6: Given SPEC_COMMON の既存記述（§1-3、§1-4、§2-4、§5）, When 新しい節と照合する, Then 食い違いが残らず、残す場合は例外としての理由と適用範囲が記載されており、照合結果の一覧がレビュー記録に残ること。
  - [ ] AC-7: Given 変更した仕様書, When リポジトリ既定のドキュメント検証（リンク検証、UI不変条件チェック）を実行する, Then 失敗がなく、新設した節のリンクと参照が解決すること。
  - [ ] AC-8: Given アプリケーションのコード、テスト、API仕様, When 本PBIの差分を確認する, Then ドキュメント以外の変更が含まれないこと。
