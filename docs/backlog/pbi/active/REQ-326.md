### REQ-326: Prompt Surgeon: ComfyUI 通信クライアント共通フック (useComfyClient) の統合

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-03 (Task 2.1) に基づき、現在 GeneratePage 側の Store/WebSocket と LoRA Studio 側コンポーネント内の raw `fetch` で分散している ComfyUI (Port 8188) への通信・直接ジョブ投入ロジックを、共通フック `useComfyClient` / 共通 API 層へと統合する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: ComfyUI (8188) への通信ロジックが画面ごとに二重実装されており、接続エラー時やオフライン時のハンドリングにばらつきがあるため。
  2. なぜ二重実装されたのか: LoRA Studio (REQ-319) 実装時に、既存の Store/WebSocket 経由の実装から切り離して手早く独立動作させるためにローカルな `fetch` を使用したため。
  3. なぜ共通化するのか: 接続状態の監視、キュー投入、エラー通知（ECONNREFUSED や未起動警告）を一元化し、クライアント DX とユーザー体験を統一するため。
  4. 根本原因: ComfyUI クライアント通信の共通フック/サービス層が存在しなかったため。
- **UX Classification**:
  - **Interaction (インタラクション設計)**:
    - ComfyUI 未起動時の一貫したエラー通知と再試行案内
    - 単一フック `useComfyClient` によるシンプルなキュー投入インターフェース

#### Acceptance Criteria (AC)

- [ ] **AC-1**: Given ComfyUI サーバー（Port 8188）との直接通信を行う必要のあるコンポーネントにおいて、When 共通カスタムフック `useComfyClient` を利用したとき、Then 接続状態の確認、プロンプト・ワークフローのキュー投入、キュー状態取得が統一されたインターフェースで実行できること。
- [ ] **AC-2**: Given ComfyUI サーバーが未起動または接続拒否（ECONNREFUSED）となったとき、When キュー投入または接続確認を試行したとき、Then 各画面（GeneratePage, LoRA Studio）で一貫したエラーハンドリングおよび通知が行われること。
- [ ] **AC-3**: Given LoRA Studio のストレステスト生成およびテスト生成コンポーネントにおいて、When `useComfyClient` を経由してジョブを投入したとき、Then raw `fetch` による重複コードが排除され、従来と同様に正常にテスト生成が開始されること。
- [ ] **AC-4**: Given リファクタリング後において、When `npm run typecheck` および `npm test` を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
