### REQ-326: Studioストレステストの生成投入・エラー処理を共通Generation経路へ統合

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: Studioの学習後評価から開くストレステスト（`BenchmarkGrid`）の生成投入とエラー表示。
- **現在の実装確認（2026-10-26、コード読取）**:
  - Generateの`useGenerateAction`とStudio Step 1の`useStudioGeneration`は、共通storeの`submitGenerationBatch`から`generationApi.submitBatch`（`/api/generation/batches`）を使用する。通信結果不明時は共通処理でrequest IDによる受付照合を行う。
  - `DatasetStudioPage/index.tsx`の学習後評価から実際に表示される`BenchmarkGrid.tsx`では、`handleRunStressTest`が`comfyApi.queuePrompt`をループ呼出しする。これは`/api/comfy/prompt`の旧proxy経由であり、Generation batch受付を経由しない。
  - ストレステストのエラーは汎用requestの例外をローカルbannerへ表示し、共通Generationの型付きエラー・結果未確認時の照合と異なる。
  - ブラウザーから8188への直接fetchが残るという旧説明は現状に合わない。問題はバックエンド経由の二つの投入・エラー処理経路が残ること。
- **Requirement**:
  - ストレステストの生成投入を既存の共通Generation受付へ統合し、Studio project・request・batchとの対応を保持する。
  - 接続失敗、受付失敗、通信結果不明を既存Generationの意味に従って扱い、結果不明を確定失敗や生成完了と誤表示しない。結果不明時は共通の受付照合を使い、無条件の再送をしない。
  - 通常生成のgroupやStudio Step 1の独立batchへストレステストを誤合算しない。
  - `useComfyClient`という新フックの導入は要求しない。既存共通層の再利用方法は設計で決定する。
- **UX Classification**: Interaction（生成投入と失敗・結果未確認時の一貫した通知）。画面の通知形式そのものの完全統一は要求しない。

#### Acceptance Criteria（2026-10-26レビュー後の現行AC）

- [ ] **AC-1**: Given 保存済みStudioプロジェクトのストレステストで有効な生成入力がある, When 利用者が実行する, Then 既存の共通Generation batch受付を経由して投入され、request・batch・jobと当該projectの対応が保持され、`BenchmarkGrid`から旧`comfyApi.queuePrompt`経由の投入が行われないこと。
- [ ] **AC-2**: Given ストレステストの受付または上流処理で接続障害・確定失敗・応答不明が生じる, When 結果を処理する, Then 共通Generationのエラーと状態の区別に従い利用者に通知され、応答不明時はrequest IDによる共通照合を使い、確認できない受付や生成を成功・完了扱いせず、無条件のPOST再送をしないこと。
- [ ] **AC-3**: Given 通常生成またはStudio Step 1のbatchが存在する, When ストレステストを投入し進捗・終了状態が通知される, Then ストレステストは自身のStudio project・batchに対応して追跡され、他のgroup・batchへ誤合算されず、重複投入や既存ジョブ状態の巻き戻りがないこと。
- [ ] **AC-4**: Given 共通経路への統合後, When Generate、Studio Step 1、ストレステストをそれぞれ実行し、失敗・結果未確認も確認する, Then 既存の生成投入・進捗・通知とストレステストの4軸×3強度の要求対応が維持されること。プロンプト作成と評価アルゴリズムの全面刷新は本PBIに含めない。

- **設計時の確認事項**:
  - 現行`BenchmarkGrid`には簡易graph送信と、受付後に固定のPASS/WARN・画像URLを設定する処理もある。共通受付が要求する有効なworkflow/metadataとの対応と、受付成功を生成完了と誤認させない状態遷移を設計で確認する。今回、その処理の実動作や評価精度を検証したものではない。必要な変更が評価機能全体へ広がる場合は、範囲を明示して再レビューする。
  - backendの旧proxy route削除や他利用箇所の全面移行は本PBIの必須範囲ではない。
  - REQ-259のVRAM待機表示不整合の修正は本PBIに含めない。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: Prompt Surgeon: ComfyUI 通信クライアント共通フック (useComfyClient) の統合

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-03 (Task 2.1) に基づき、現在 GeneratePage 側の Store/WebSocket と LoRA Studio 側コンポーネント内の raw `fetch` で分散している ComfyUI (Port 8188) への通信・直接ジョブ投入ロジックを、共通フック `useComfyClient` / 共通 API 層へと統合する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: ComfyUI (8188) への通信ロジックが画面ごとに二重実装されており、接続エラー時やオフライン時のハンドリングにばらつきがあるため。
  2. なぜ二重実装されたのか: LoRA Studio (REQ-319) 実装時に、既存の Store/WebSocket 経由の実装から切り離して手早く独立動作させるためにローカルな `fetch` を使用したため。
  3. なぜ共通化するのか: 接続状態の監視、キュー投入、エラー通知（ECONNREFUSED や未起動警告）を一元化し、クライアント DX とユーザー体験を統一するため。
  4. 根本原因: ComfyUI クライアント通信の共通フック/サービス層が存在しなかったため。
- **UX Classification**:
  - **Interaction (インタラクション設計)**:
    - ComfyUI 未起動時の一貫したエラー通知と再試行案内
    - 単一フック `useComfyClient` によるシンプルなキュー投入インターフェース

#### 旧Acceptance Criteria（履歴・適用終了）

- **旧AC-1**: Given ComfyUI サーバー（Port 8188）との直接通信を行う必要のあるコンポーネントにおいて、When 共通カスタムフック `useComfyClient` を利用したとき、Then 接続状態の確認、プロンプト・ワークフローのキュー投入、キュー状態取得が統一されたインターフェースで実行できること。
- **旧AC-2**: Given ComfyUI サーバーが未起動または接続拒否（ECONNREFUSED）となったとき、When キュー投入または接続確認を試行したとき、Then 各画面（GeneratePage, LoRA Studio）で一貫したエラーハンドリングおよび通知が行われること。
- **旧AC-3**: Given LoRA Studio のストレステスト生成およびテスト生成コンポーネントにおいて、When `useComfyClient` を経由してジョブを投入したとき、Then raw `fetch` による重複コードが排除され、従来と同様に正常にテスト生成が開始されること。
- **旧AC-4**: Given リファクタリング後において、When `npm run typecheck` および `npm test` を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
