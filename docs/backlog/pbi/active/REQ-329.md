### REQ-329: 公開API契約を維持したバックエンドのルーター登録整理

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P3（低優先度の保守改善）
- **Surface**: バックエンドのエントリポイントにあるルーターimport・登録処理。API本体や公開契約を変更せず、関連する登録を機能・責務のまとまりごとに整理し、保守時の見通しを改善する。
- **現状確認（2026-10-26、コード読取）**:
  - `backend/app/main.py`には32件の`app.include_router`が並ぶ。ドメイン別の登録集約は未実施。
  - API本体はすでに`routers/`配下の機能別モジュールへ分離され、dataset・benchmark・trainingも個別prefix/tagを持つ。API実装自体がエントリポイントへ混在している状況ではない。
  - 本PBIの効果は登録・importの整理であり、今回、不具合解消や性能改善の必要性を示す根拠は得ていない。
- **UX Classification**: Information Design（開発保守時の登録構造・責務の把握）。Swagger UIのタグ体系変更は対象外。
- **Requirement**:
  - 登録対象・グループの責務と登録箇所が追える構造とし、エントリポイントのimport・登録を整理する。単なる行数削減を達成基準としない。
  - APIのURL・HTTPメソッド・リクエスト/レスポンススキーマ・既存OpenAPIタグ・operationIdを維持する。既存APIの追加・削除や仕様変更を伴わない。
  - WebSocket、静的配信・SPA fallback、health/config、middleware・例外処理・lifespanを含む既存動作を維持する。登録順序によるルート解決や依存関係を変えない。
  - ドメイン別の登録モジュール・サブルーター等の具体方式は後続設計で決める。API本体のディレクトリ再編やOpenAPIタグ改変を必須としない。

#### Acceptance Criteria（2026-10-26レビュー後の現行AC）

- [ ] **AC-1**: Given エントリポイントが個別ルーターを直接登録している現状, When 登録構造を整理する, Then エントリポイントのimport・登録が責務のまとまりで整理され、各グループの登録対象と責務を追跡でき、登録漏れ・重複がないこと。削減行数だけをもって達成としないこと。
- [ ] **AC-2**: Given 整理前後の同一設定・環境, When 全APIのルート一覧と生成OpenAPIを比較する, Then URL・HTTPメソッド・リクエスト/レスポンススキーマ・既存tags・operationIdを含む公開契約が維持され、エンドポイントの追加・削除がないこと。意図しないOpenAPI差分を除外・更新して通過扱いしないこと。
- [ ] **AC-3**: Given 整理後のアプリ, When 代表API・WebSocket・静的配信/SPA fallback・health/configと起動終了処理を検証する, Then 既存のルート解決・依存関係・middleware・例外処理・lifespanの動作が維持されること。

- **設計・検証への引継ぎ**:
  - 整理前の全ルート・OpenAPIを比較基準として保存し、既存のWorkflow/Mappingに限定した契約テストだけを全API不変の証拠として使わない。
  - 正常/失敗/競合パス、登録順序、WebSocketと静的mountを含む比較方法と、型チェック・バックエンド全テストの具体コマンドを設計・テスト計画で定める。受入検証は適用される現行の検証プロファイルに従う。
  - 公開契約変更が必要になった場合は本PBI内で黙って変更せず、範囲と影響を提示して再レビューする。
- **References**: `backend/app/main.py`、`backend/app/routers/`、`backend/tests/governance/test_openapi_contract.py`、`docs/specs/SPEC_SUMMARY.md`（OpenAPI SSoT）
- **Review record（2026-10-26）**: 現状確認後、ユーザーが「それで残そう」と判断。低優先度で内部登録整理に限定し、旧要求のタグ整理とOpenAPI完全不変の矛盾を解消した。既存readyを維持する。今回の作業はPBI更新であり、新規監査・設計承認・実装開始・受入完了を示さない。コード変更・テスト実行は行っていない。
- **Design doc**: none

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: Prompt Surgeon: backend/app/main.py ルーターのドメイン階層別集約

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P3
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-05 (Task 3.2) に基づき、現在 `backend/app/main.py` にフラットに 27 個以上 include されている APIRouter 群を、ドメイン別サブルーター（例: `routers/lora_studio/`, `routers/settings/` 等）へと階層的に集約する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: `main.py` に 27 個以上のルーターがフラットに並んでおり、エントリポイントの凝集度が下がり全体構造が把握しづらいため。
  2. なぜフラットに並んだのか: 機能追加のたびに `main.py` へ `app.include_router` を 1 行ずつ追記していったため。
  3. なぜサブルーター化するのか: ドメインごとにルーティングと OpenAPI タグ体系を整理し、保守性と見通しを改善するため。
  4. 根本原因: ドメイン単位のサブルーター集約設計が行われていなかったため。
- **UX Classification**:
  - **Information Design / API Documentation**:
    - OpenAPI (Swagger UI) ドキュメント上のタグ体系の整理
    - ルーティング定義の可読性とドメイン境界の明確化

#### 旧Acceptance Criteria（履歴・適用終了）

- **旧AC-1**: Given 27 個以上のルーターがフラットに include されている `main.py` において、When 関連するドメイン（例: LoRA Studio 関連のデータセット・学習・評価、設定関連等）がサブルーターに集約された場合、Then `main.py` 内の `app.include_router` 行数が大幅に削減され、責務ごとに整理されること。
- **旧AC-2**: Given ドメイン別サブルーターへの集約後において、When 各 API エンドポイントのパスプレフィックス（URL）および HTTP メソッドを検証したとき、Then 既存のすべてのエンドポイントの URL 構造および OpenAPI スキーマが一切変更されず、完全な後方互換性が維持されること。
- **旧AC-3**: Given リファクタリング後において、When `mypy backend` および `pytest`（バックエンド全テスト）を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
