### REQ-384: 共有タグチップ（TagChipEditor／TagChip）のチップ密度・編集操作の方針決定と適用範囲（Generate限定／共有）の確定

- **Type**: feature
- **Status**: new
- **Priority**: P3
- **Surface**: 共有部品 `TagChipEditor`／`TagChip`（docs/specs/SPEC_COMMON.md §3）と、その利用画面。Generateのプロンプト、Tag Setの作成・編集（`TagSetFormFields` 経由）、LoRA（トリガーワードセットのタグ入力）、Studio（`MatrixGenerationStep`）。主対象はモバイル（幅767px以下）。
- **Reference**:
  - docs/specs/SPEC_COMMON.md（§1-6-5 共有部品に関する未承認事項の「`TagChipEditor`／`TagChip` のチップ密度」行、§1-6-2 MUI-06／MUI-10、§1-3 モバイル操作対象44px、§1-5-3 Hit-Slop、§3 TagChipEditor）
  - docs/design/REQ-378.md（Q4: チップ密度の判断は専任PBIが担う、と決定済み）
  - docs/design/mobile-ui-redesign/mobile-generate-redesign-proposal.md（§5 比較用Proposal値、§9.2〜9.3 共通タグチップの決定フロー、AC-10・AC-11）
  - docs/design/mobile-ui-redesign/mobile-lora-tagset-redesign-proposal.md（共通チップの密度・挙動を変更する場合は横断評価と別途承認）
  - docs/backlog/pbi/active/REQ-371.md（AC-6: 共有部品に及ぶ修正時のTag Set画面の同等動作）
  - docs/backlog/pbi/active/REQ-373.md、REQ-377.md（いずれもチップ密度の変更を非対象と明記）
  - docs/specs/SPEC_GENERATE.md（プロンプト欄）／docs/specs/SPEC_TAGS.md（§2、§3）／docs/specs/SPEC_LORAS.md（§5）
- **5 Whys / Root Cause**:
  1. なぜ新設が必要か: モバイルのタグ編集では、チップの寸法（Padding・Gap）が大きく、1画面に見えるタグ数が限られ、編集面積を圧迫するという指摘があり、モバイル改修提案がチップ密度を縮める案（上下3px・左右8px、内部Gap 5px、エディタ内6px）を比較用に示した。
  2. なぜその課題が発生するか: `TagChipEditor`／`TagChip` はGenerate以外（Tag Set、LoRA、Studio）でも使われる共有部品であり、Generateだけの見た目変更を確定仕様にすると他画面と不整合になる。一方、全利用箇所で一律に変えると各画面の操作性（誤タップ、44px有効タップ領域）に影響が及ぶ。
  3. なぜ現状の仕組みで不十分か: REQ-373（Generate）とREQ-377（LoRA／Tag Set）はどちらもチップ密度を非対象とし、REQ-378はSPEC_COMMON 1-6-5に「未承認事項（担当: 専任PBI・未起票）」として残しただけで、誰も判断していない。判断する場がなければ、各画面PBIの中で暗黙に変わるか、永久に未決のまま残る。
  4. なぜこのアプローチを採用するか: 密度・編集操作の判断をひとつの専任PBIに集約し、全利用箇所の影響調査、比較、ユーザーの明示的な採否、仕様への反映を一括で行う。「無根拠なGenerate限定の例外を作らない」という既存方針（REQ-371、モバイルGenerate提案AC-10）を守りつつ、Generate限定にする場合も理由と他画面への非影響を記録できる。
  5. 根本原因: 共有部品の見た目・操作の方針を決める責任主体と承認手順が、画面別の改修PBIの外に存在せず、判断が未実施のまま残っていること。
- **UX Classification**:
  - **Information Design (情報設計)**: 密度の向上で一度に確認できるタグ数と、長文・多数タグ時の可読性（折返し・省略されない重要情報）を、画面ごとに評価する。
  - **Interaction (インタラクション)**: 寸法を縮める場合のタップ領域（MUI-06）、サブメニュー編集・ドラッグ・削除・入力（SPEC_COMMON §3-5）の操作維持、編集操作を変更する場合のタップによる代替経路（MUI-10）。
  - **Visual (視覚デザイン)**: チップのPadding・内部Gap・エディタ内のPadding／Gapの採否と、利用画面間の見た目の一貫性。
- **Requirement**:
  - **1. 利用箇所の棚卸し**: `TagChipEditor`／`TagChip` を使う全画面を列挙し、画面ごとに現行のチップ寸法と編集操作を記録する。確認できない箇所は「未確認」として明示する。
  - **2. 比較と判断**: 同一条件（同じ寸法・同じ幅360px）で、最低でもGenerateとTag Set作成・編集を比較する。選択肢は「A: 共有部品として全利用箇所で変更」「B: Generate限定の例外（バリアント）」「C: 変更しない」とし、提案書の値（上下3px・左右8px／Gap 5px／エディタ内6px）は比較用の候補であり、採否はユーザーが明示的に決める。
  - **3. 有効タップ領域との両立**: 採用する寸法でも、チップ内の各操作（サブメニューを開く、有効／無効、削除、ドラッグ）の有効タップ領域は SPEC_COMMON §1-3 の44×44px以上を維持する。外形を小さくする場合は §1-5-3 のHit-Slopで満たす。満たせない操作は、MUI-06の補足に従い理由と影響を記録してユーザーの判断を得る例外として扱う。
  - **4. 編集操作**: 編集操作（SPEC_COMMON §3-5 の表）を変えるかどうかを判断に含める。変える場合は、ジェスチャー専用の操作にせず、タップによる代替経路を残す。
  - **5. 仕様への反映**: 完了時に、SPEC_COMMON §1-6-5 の当該行の担当欄を本PBIのIDに更新し、状態を判断結果に合わせて更新する。採用した場合は §3 のチップ規則を更新する。
  - **6. 非対象**: `TagChipInput`／`TagChipViewer` の視覚の統一（SPEC_COMMON 1-6-5「その他の共有部品」の行）、タグデータ構造・プロンプト文字列の生成規則・API、デスクトップ（幅768px以上。判断で変更対象に含める場合を除く）、チップと固定生成バーの重なり（REQ-371）。
- **Acceptance criteria**:
  - [ ] AC-1: Given `TagChipEditor`／`TagChip` を使う画面（Generateのプロンプト、Tag Setの作成・編集、LoRA、Studio `MatrixGenerationStep`、および設計時に確認できた他の画面）, When 設計書を確認する, Then 全利用画面が一覧化され、画面ごとに現行のチップ寸法（Padding・内部Gap）と編集操作が記録され、確認できなかった画面は「未確認」と明記されていること。
  - [ ] AC-2: Given 幅360pxのモバイル表示, When 現行の寸法と候補寸法（上下3px・左右8px／Gap 5px／エディタ内6px）を、Generateの一画面とTag Set作成・編集の一画面で同一条件で比較する, Then 設計書に画面ごとの比較結果（同じタグ数での表示行数、折返し、長文タグの表示）が記録されること。
  - [ ] AC-3: Given AC-1とAC-2の記録, When ユーザーに提示する, Then ユーザーが「A: 全利用箇所で変更」「B: Generate限定」「C: 変更しない」のいずれかと採用する寸法・編集操作の変更有無を明示的に回答し、その回答・日付・理由が設計書に記録されていること。回答前は候補寸法をSPEC_COMMONや本番の仕様として採用しないこと。
  - [ ] AC-4: Given 採否がAまたはB, When 幅360pxで各チップ内の操作（サブメニューを開く、有効／無効の切替、削除、ドラッグ）の有効タップ領域を実画面の測定で確認する, Then いずれも44×44px以上であるか、満たさない操作は理由と影響を含む例外として設計書に記録され、ユーザーの承認を得ていること。
  - [ ] AC-5: Given 採否がA, When 全利用画面を表示する, Then 全画面でチップ寸法が同一の採用値になること。
  - [ ] AC-6: Given 採否がB, When Generate以外の全利用画面を表示する, Then それらのチップ寸法・操作が本PBI前から変化せず、Generateだけを別寸法とする理由が設計書に記録されていること。
  - [ ] AC-7: Given 採否がC, When 全利用画面を表示する, Then チップの寸法・操作が本PBI前から変化せず、見送りの理由が設計書に記録されていること。
  - [ ] AC-8: Given 採否がAまたはBで寸法が変わった画面, When SPEC_COMMON §3-5 の表の各操作（クリックでのサブメニュー表示、サブメニュー内のタグ名編集・有効／無効・強度スライダー、×での削除、ドラッグ&ドロップ、ダブルクリックのインライン編集、Delete／Backspace、Space、Ctrl+D、新規タグ入力のカンマ・Enter・Tab・ペースト）と折返し表示を実行する, Then 各操作が、本PBI前と同じ結果（表に記載の動作）になること。ただしユーザーが採否で明示的に変更を承認した操作は、承認後の動作と同じ結果になること。
  - [ ] AC-9: Given 採否で編集操作の変更を含む, When 変更した操作を確認する, Then ジェスチャーのみで実行できる操作がなく、タップによる代替経路があり、REQ-373の横スワイプによるセクション切替・縦スクロール・ドラッグと競合しないこと。編集操作の変更を含まない場合、この基準は対象外であると設計書に記録されていること。
  - [ ] AC-10: Given 幅768px以上の表示（ユーザーが採否でデスクトップを変更対象に含めると明示した場合を除く。明示がない場合、本ACは必ず適用される）, When 本PBIの変更後に全利用画面のチップを表示・操作する, Then チップの寸法と操作結果が本PBI前から変化しないこと。デスクトップを変更対象に含めた場合は、その範囲以外が変化しないこと。
  - [ ] AC-11: Given REQ-371の受け入れ条件（AC-1〜AC-4: チップが固定生成バーの前面に出ない、バー上のタップをバーが受け取る、ドラッグ中・サブメニュー表示中も隠れない）, When 本PBIの変更後に同じ手順を実行する, Then 同じ結果になること。
  - [ ] AC-12: Given 本PBIの完了時, When SPEC_COMMON §1-6-5 の「`TagChipEditor`／`TagChip` のチップ密度」行を確認する, Then 担当欄が「専任PBI(未起票・ID未定。起票後に更新)」から REQ-384 に更新され、状態欄が判断結果（承認済み／Generate限定の例外として承認済み／見送り）と整合していること。
  - [ ] AC-13: Given 採否がAまたはB, When SPEC_COMMON §3 を確認する, Then 採用したチップの寸法規則・バリアントの条件・変更した編集操作が §3 に記載され、SPEC_GENERATE・SPEC_TAGS・SPEC_LORAS の該当記述と矛盾しないこと。採否がCの場合は、§3 に変更がなく、見送りの結果が §1-6-5 に記録されていること。
  - [ ] AC-14: Given タグデータ（`TagChip` の構造）、ComfyUIへ送信されるプロンプト文字列（`chipsToString` の出力）、API, When 本PBIの変更後にGenerate・Tag Set・LoRA・Studioで同じタグ入力を保存・生成する, Then 保存される値と送信されるプロンプト文字列が、本PBI前と同一であること。
- **Inferred points**:
  - 本PBIは「判断（棚卸し・比較・ユーザーの採否・仕様反映）」を主目的とする。A・Bの場合のみ実装を伴う。採否の前に実装方式を固定しない。
  - 寸法（3px・8px・5px・6px）は提案書の比較用の値であり、共通トークンではなく、採用値は設計と比較結果で確定する（SPEC_COMMON 1-6-4）。
  - 主対象はモバイル（幅767px以下）と仮定する。デスクトップを変更対象に含めるかは判断事項（AC-10。ユーザーが明示しない限りデスクトップは不変）。
  - Studio（`MatrixGenerationStep`）とLoRAの利用状況は、仕様書での記載が限られる。利用実態は設計時に確認し、確認できなければ「未確認」とする（AC-1）。BAはコードを調査していない。
  - REQ-373（Generateのセクション切替）・REQ-377（LoRA／Tag Setの詳細・編集シート）とは独立して判断できるが、実装の着手順は設計で決める。両PBIはチップ密度を変更しないため、両PBIの回帰条件とは矛盾しない。
  - `TagChipInput`／`TagChipViewer` の統一は、SPEC_COMMON 1-6-5 の別の行（その他の共有部品）であり、本PBIに含めない。含める場合は別途ユーザーの判断を要する。
  - REQ-378の設計Q4は、起票後にREQ-378設計書とSPEC_COMMON 1-6-5の担当欄のIDを更新するとしている。本PBIの起票時にそのIDの暫定反映を行うか、完了時（AC-12）のみとするかは、コーディネーターの運用判断とする。
  - テスト規約: テスト名に `[REQ-384/AC-n]` を付与し、ファイル名・パスにチケット番号を含めない。
  - ID採番: `pbi_manager.py create` は本ワークツリーでは REQ-380 を返したが、メイン側で REQ-380〜REQ-383 が既に使用されているため、衝突を避けて空き番号の REQ-384 を使用した（当初の仮番号から再採番）。
  - 監査記録（2026-10-19、ローカルモデル qwen/qwen3.5-9b、requirement、`--context-length 32768`）: 初版（AC-1〜AC-13）は ISSUES_FOUND（有効な指摘8件）。うちAC-8（「従来どおり」の基準不明）とAC-10（検証対象の曖昧さ・デスクトップ条件）は妥当と判断して本文を修正し、AC-14（データ・API不変）を分離した。残りの指摘（SPEC_COMMON・REQ-371の抜粋が入力に含まれないという指摘など）は、入力パッケージに該当抜粋を含めていたため対象外と判断した。修正後の再監査は3回実行したがいずれも完了しなかった（出力形式不正、LM Studio HTTP 400、出力トークン上限）。再監査は AUDIT_ERROR（INCONCLUSIVE）であり、修正版は監査未完了である。各実行後にモデルのアンロードを確認した。監査はPASSではない。
