### REQ-390: SPEC の Generation snapshot 周辺の文言を精緻化する

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: docs/specs/SPEC_GENERATE.md, docs/specs/SPEC_COMMON.md（文書のみ。コード変更なし）
- **起点**: REQ-387（commit fca9965）の後続課題。REQ-387 の AC-5（SPEC_GENERATE の改訂）は PASS だったが、doc-reviewer が軽微指摘（n1、n3、m3、m4）を後続課題として残した。
- **根拠資料**: `docs/logs/REQ-387/qa-doc-report-r2.md` §3（n1 / n3 / m3 / m4）、`docs/design/REQ-387.md` §8-4、§8-7。`docs/logs/` は gitignore 対象のローカル資料。以下の行番号は commit fca9965 時点のもの。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: REQ-387 後の SPEC に、字面どおりに読むと成り立たない文、定義のない用語、SSoT 内で定義されない参照、未更新の周辺文書が残る。
  2. なぜ発生するか: REQ-387 の rework では、承認済みの是正対象（m1 / m2 / m5 と 503 契約の 1 文）に範囲を絞った。他の指摘は AC-5 の PASS を妨げないため対象外とした。
  3. なぜ現状の仕組みで不十分か: 後続の設計・実装・レビューが、字面と意図のずれ（n1）、「型付き」の解釈（n3）、1000 件方針の根拠（m3）、SPEC_COMMON の「全 snapshot data」（m4）を個別に解釈することになり、誤読の余地がある。
  4. なぜ chore とするか: 振る舞いを変えず、既存の意図を明文化するだけである。
  5. 根本原因: SSoT が REQ-ID の参照や抽象表現に依存し、定義を本文内に持っていない。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 仕様文書の情報設計の改善（定義の自己完結、周辺文書との整合）。利用者向けの表示は変更しない。
  - **Interaction (インタラクション)**:
    - 変更なし。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. n1: 配信窓の補足の保証範囲**（SPEC_GENERATE L204）:
    - 「窓に含まれる batch は単位ごとに欠けず含まれる」が、条件 5（released 直近 10 件）だけで窓に入った batch には字面上成立しない。保証の対象を、条件 2〜4 で窓に入った batch と現在の `normal_group_id` の group に限定して書く。
  - **2. n3: 「型付きの 503」の定義**（SPEC_GENERATE L206）:
    - 「型付き」が何を指すか（エラー応答の形式）を本文内で定義する。
  - **3. m3: 1000 件方針の定義**（SPEC_GENERATE L209）:
    - 「REQ-333 の 1000 件方針」を、REQ-ID を引かなくても読めるよう保持対象・上限・整理順序・非終端の扱いとして本文内で定義する。
  - **4. m4: SPEC_COMMON の更新**（SPEC_COMMON L549）:
    - 「全 snapshot data」を、SPEC_GENERATE の配信窓と整合する表現にする。
  - **5. 既存文言の不変**:
    - 上記以外の既存文言を変更しない。
- **Acceptance criteria**:
  - [ ] AC-1: Given SPEC_GENERATE.md の「配信窓の補足」, When 改訂後を確認する, Then 「単位ごとに欠けず含まれる」保証の対象が、窓条件 2（非終端を含む batch）・3（現在の `normal_group_id`）・4（直近 20 batch）で窓に入った batch / group に限定されていること。条件 5 だけで窓に入った released job の batch は兄弟 job が欠けることがある旨が明記されていること。「解除済み直近 10 件の表示は全件時と同じ」という既存の保証は維持されていること。
  - [ ] AC-2: Given SPEC_GENERATE.md の非機能制約の行, When 改訂後を確認する, Then 「型付きの 503」が、`ErrorEnvelope` 形式の HTTP 503 であること、エラーコード `generation_state_unavailable`、`outcome` の値 `unconfirmed` として本文内で定義または参照されていること。値は `GET /api/generation/state` の実装の応答と一致すること。
  - [ ] AC-3: Given SPEC_GENERATE.md の保持方針の行, When 改訂後を確認する, Then REQ-333 を参照しなくても、(a) 終端状態（succeeded / failed / cancelled）の保持上限が 1000 件であること、(b) 超過時は古いものから整理すること、(c) 非終端 job は整理しないこと、(d) released 記録の上限が実装の定数と一致する値で記載されていること、が読み取れること。「REQ-333」の参照は由来として残してよい。配線の有無（REQ-388）に左右されない方針の記述であること。
  - [ ] AC-4: Given SPEC_COMMON.md の Generation snapshot / event の記述, When 改訂後を確認する, Then 「全 snapshot data」が配信窓（SPEC_GENERATE）の範囲の状態を指すと読める表現に改まり、SPEC_GENERATE の該当節への参照があること。version・epoch・revision、FE の採用規則（同一 epoch で新しい revision のみ採用、epoch 切替時は全体置換）、SYSTEM_STATS と VRAM_RECOVERED の記述は不変であること。
  - [ ] AC-5: Given 改訂前後の SPEC_GENERATE.md と SPEC_COMMON.md, When 行単位で差分を取る, Then 変更が AC-1〜AC-4 の 4 箇所に限られ、これ以外の行（SPEC_GENERATE の snapshot を全状態で扱う行 L197、配信窓の 5 条件 L198〜L203、窓外 job の扱い L205、ログ抑制 L207、SQLite 接続設定 L208、N / F の行、Studio batch の行、解除済み直近 10 件の行）は一字一句変わらず、他のファイルに差分がないこと。REQ-387 の AC-5 の (1)〜(6) が引き続き明記されていること。
  - [ ] AC-6: Given 改訂後の 2 ファイル, When 文字コードを確認する, Then UTF-8（BOM なし）・LF で、末尾が改行で終わっていること。
- **Inferred points**:
  - AC-3(d) の released の上限値は、現行実装の定数（1000 件）に一致させる前提である。REQ-388 が released の扱いを変える場合は、値を合わせて確認する。
  - 「型付き」の定義は、現行の実装の応答（エラーコード、outcome）に合わせる。openapi.yaml への追記は REQ-391 で扱う。
  - n1 の修正は、REQ-387 の設計 §8-4（承認済みの是正方針は「窓内の batch・group」への限定）と矛盾しない。条件 5 だけで窓に入った batch の扱いを明確にするものである。
