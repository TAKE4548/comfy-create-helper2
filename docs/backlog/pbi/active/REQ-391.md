### REQ-391: GET /api/generation/stateの503契約をルート宣言・正本OpenAPI JSONへ反映する

- **Type**: chore
- **Status**: ready
- **Priority**: P3
- **Surface**: `backend/app/routers/generation.py`のルート宣言、正本`backend/openapi.json`、関連契約テスト。`docs/openapi.yaml`はREQ-248による廃止までの移行順序に応じて同期する。
- **起点・根拠**: REQ-387（commit fca9965）の後続課題。`docs/design/REQ-387.md` §8-7、`docs/logs/REQ-387/qa-doc-report-r2.md` §2-5・n2、`docs/logs/REQ-387/qa-code-report-r2.md`（軽微4）。logsはgitignore対象のローカル資料であり、今回の新規検証結果ではない。
- **現状確認（2026-10-26）**:
  - `get_generation_state`はsnapshot取得・検証の例外時にHTTP 503、`ErrorEnvelope`形式、`detail.code=generation_state_unavailable`、`detail.outcome=unconfirmed`を返す。
  - ルート宣言は`response_model=StateSnapshot`のみで503の宣言がなく、保存済みJSON/YAMLの当該responsesも200のみである。コードと保存物の読取確認であり、今回`app.openapi()`や失敗経路のテストは実行していない。
  - 旧AC-2の「YAML以外の差分なし」は、旧AC-5の実装由来OpenAPIへの503追加と両立しない。REQ-248は正本JSONへの一本化・YAML廃止へ見直し済みである。
- **Root Cause**: 実行時の例外応答がルートのOpenAPI宣言へ反映されず、保存済み契約にも記載されていない。同期自動化そのものはREQ-248の責務とする。
- **UX Classification**: Information Design（API契約の整合）。利用者向けの操作・表示は変更しない。
- **Requirement**:
  - `GET /api/generation/state`のルート宣言にHTTP 503と`ErrorEnvelope`を追加し、`app.openapi()`と正本`backend/openapi.json`の当該応答を一致させる。descriptionは状態取得の失敗を示す。
  - 200の`StateSnapshot`と実行時の正常・失敗動作、他APIの契約を維持する。変更は当該503宣言・保存物への反映・必要な参照先schema・検証に限定し、無関係な既存の契約ずれを一括修正しない。
  - REQ-248より先に実施しYAMLが現行の参照先として残る場合は、当該503と必要な参照先schemaをYAMLにも同期する。REQ-248でYAML廃止済みならJSONのみを対象とし、YAMLを再導入しない。設計時に採用順序と対象を明記する。
  - OpenAPI保存物の全体出力・同期チェック・FE型生成の自動化はREQ-248、「型付き503」の仕様本文の精緻化はREQ-390で扱う。本件を理由に通信制御や生成処理を変更しない。

- [ ] AC-3: Given 状態取得が失敗する条件（例: `app_settings`の読込失敗）, When `GET /api/generation/state`を呼ぶ, Then HTTP 503の本文が宣言した`ErrorEnvelope`に適合し、`detail.code=generation_state_unavailable`、`detail.outcome=unconfirmed`で部分的な状態を含まないことを実行テストで示すこと。サービス未初期化等の別の失敗経路に同一codeを強制しないこと。

- **設計・検証への引継ぎ**:
  - 既存JSON/YAMLには当該応答以外の差異があるため、全再生成による無関係な変更を混ぜない。必要なErrorEnvelopeとその参照先schemaの追加を「components差分禁止」で妨げない。
  - `backend/tests/integration/legacy/test_generation_api.py`に状態取得失敗の既存テストがある。既存証拠を今回再実行したものと扱わず、宣言との整合と実際の失敗注入境界を後続設計で確認する。
  - ルート宣言・公開API契約・関連テストを扱うため、実装時は適用されるコード検証規約と全スイートfallbackに従う。文書読取や保存物の構文検証だけで受入PASSにしない。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: openapi の GET /api/generation/state に 503（ErrorEnvelope）を追記する

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: docs/openapi.yaml（`GET /api/generation/state` の responses）。必要に応じて frontend/src/api/types.ts への影響確認のみ。
- **起点**: REQ-387（commit fca9965）の後続課題。openapi の `/api/generation/state` に 200 しか記載がなく、503（`ErrorEnvelope`）が未記載であることは REQ-387 以前からの仕様と実装の乖離である。REQ-387 の設計 §8-7 が後続課題の候補として記録し、doc-reviewer の n2 も同じ指摘をした。
- **根拠資料**: `docs/logs/REQ-387/qa-doc-report-r2.md` §2-5・n2、`docs/logs/REQ-387/qa-code-report-r2.md`（軽微 4）、`docs/design/REQ-387.md` §8-7。`docs/logs/` は gitignore 対象のローカル資料。
- **関連 PBI**: REQ-248「OpenAPI スキーマ静的同期自動化と TypeScript 型安全性の静的検証（Contract Drift 防止）」（status: ready）。本件は、その PBI が自動検出しようとする契約ずれの具体例である。REQ-248 が実装されるまでは `docs/openapi.yaml` を手作業で保守している。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `GET /api/generation/state` は状態取得に失敗すると 503（`generation_state_unavailable`、`ErrorEnvelope` 形式）を返すが、openapi は 200 のみを定義しており、契約が実装を表していない。
  2. なぜ発生するか: openapi の他のエンドポイント（例: 履歴の残余取得）は 503 を `ErrorEnvelope` で記載しているのに、`/state` だけ記載が漏れた。
  3. なぜ現状の仕組みで不十分か: 契約に 503 がないと、クライアントや契約テストが 503 を想定外の応答として扱うおそれがある。
  4. なぜ追記とするか: 実装の応答は変えず、契約を実装に合わせるだけで済む。
  5. 根本原因: openapi と実装の同期が手動運用で、ずれを検出する仕組みがない（REQ-248 が扱う課題）。

    - 変更なし。
- **Requirement**:

  - **2. 既存契約の不変**:
