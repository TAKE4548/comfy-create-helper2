### REQ-391: openapi の GET /api/generation/state に 503（ErrorEnvelope）を追記する

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: docs/openapi.yaml（`GET /api/generation/state` の responses）。必要に応じて frontend/src/api/types.ts への影響確認のみ。
- **起点**: REQ-387（commit fca9965）の後続課題。openapi の `/api/generation/state` に 200 しか記載がなく、503（`ErrorEnvelope`）が未記載であることは REQ-387 以前からの仕様と実装の乖離である。REQ-387 の設計 §8-7 が後続課題の候補として記録し、doc-reviewer の n2 も同じ指摘をした。
- **根拠資料**: `docs/logs/REQ-387/qa-doc-report-r2.md` §2-5・n2、`docs/logs/REQ-387/qa-code-report-r2.md`（軽微 4）、`docs/design/REQ-387.md` §8-7。`docs/logs/` は gitignore 対象のローカル資料。
- **関連 PBI**: REQ-248「OpenAPI スキーマ静的同期自動化と TypeScript 型安全性の静的検証（Contract Drift 防止）」（status: ready）。本件は、その PBI が自動検出しようとする契約ずれの具体例である。REQ-248 が実装されるまでは `docs/openapi.yaml` を手作業で保守している。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `GET /api/generation/state` は状態取得に失敗すると 503（`generation_state_unavailable`、`ErrorEnvelope` 形式）を返すが、openapi は 200 のみを定義しており、契約が実装を表していない。
  2. なぜ発生するか: openapi の他のエンドポイント（例: 履歴の残余取得）は 503 を `ErrorEnvelope` で記載しているのに、`/state` だけ記載が漏れた。
  3. なぜ現状の仕組みで不十分か: 契約に 503 がないと、クライアントや契約テストが 503 を想定外の応答として扱うおそれがある。
  4. なぜ追記とするか: 実装の応答は変えず、契約を実装に合わせるだけで済む。
  5. 根本原因: openapi と実装の同期が手動運用で、ずれを検出する仕組みがない（REQ-248 が扱う課題）。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - API 契約文書の情報設計の是正。利用者向けの表示は変更しない。
  - **Interaction (インタラクション)**:
    - 変更なし。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. 503 の追記**:
    - `GET /api/generation/state` の responses に 503 を追加し、本文のスキーマを `ErrorEnvelope` とする。
  - **2. 既存契約の不変**:
    - 200 のスキーマ（`StateSnapshot`）と他のエンドポイントは変更しない。
- **Acceptance criteria**:
  - [ ] AC-1: Given `docs/openapi.yaml` の `GET /api/generation/state`, When 改訂後を確認する, Then responses に `'503'` があり、`content` の `application/json` の schema が `#/components/schemas/ErrorEnvelope` を参照し、description が状態取得の失敗（Generation state is unavailable）を示していること。
  - [ ] AC-2: Given 改訂前後の `docs/openapi.yaml`, When 差分を取る, Then 変更が `GET /api/generation/state` の responses への 503 の追加だけで、`'200'` の定義（`StateSnapshot`）、他のパス、`components` に差分がなく、他のファイルにも差分がないこと。
  - [ ] AC-3: Given 状態取得が失敗する条件（例: `app_settings` の読込失敗）, When `GET /api/generation/state` を呼ぶ, Then 応答が HTTP 503 で、本文が `ErrorEnvelope` のスキーマに適合し、`code` が `generation_state_unavailable`、`outcome` が `unconfirmed` で、部分的な状態を含まないこと（AC-1 の契約と実装の一致を、テストまたは OpenAPI スキーマ検証で示す）。
  - [ ] AC-4: Given 改訂後の `docs/openapi.yaml`, When YAML として読み込み、OpenAPI として検証する, Then 構文エラー・重複キー・未解決の `$ref` がなく、`npm run typecheck`（frontend）が 0 errors で通ること。
  - [ ] AC-5: Given 実装後の backend, When `app.openapi()` の出力を取得する, Then `/api/generation/state` の GET の responses に `'503'` が含まれ、その本文（`application/json`）のスキーマが `ErrorEnvelope` を参照していること。
  - [ ] AC-6: Given 改訂後の `docs/openapi.yaml`, When 文字コードを確認する, Then UTF-8（BOM なし）・LF のままであること。
- **Inferred points**:
  - AC-5 は、REQ-248 が未実装の現時点で検証できる形として、FastAPI のルート宣言から出力される `app.openapi()` に 503（`ErrorEnvelope`）が含まれることを確認する。ルート宣言側の変更が必要になる場合、それは実装の振る舞い変更ではなく宣言の追加に限る。
  - `docs/openapi.yaml` を `app.openapi()` から再生成したときに 503 の記載が保持されること（自動再生成後の保持）は、REQ-248 側の責務であり、本 PBI の受入条件には含めない。
  - 実装の応答（`generation_state_unavailable`、`outcome=unconfirmed`）は REQ-387 の受入レポートで確認された現行の挙動であり、本 PBI では変えない。
  - 「型付きの 503」の SPEC_GENERATE 側の定義は REQ-390 で扱う。
