### REQ-368: Settings直接アクセス（hashなし）時に保存済みタブへ復元されない不具合の修正

- **Type**: bug
- **Status**: ready
- **Priority**: P3
- **Surface**: frontend/src/pages/SettingsPage（useSettingsTab による初期タブ解決）
- **Reference**:
  - docs/design/REQ-365-verification-report.md（D-2）
  - docs/specs/SPEC_SETTINGS.md（タブの初期選択順: 有効なURL hash → 有効な prompt-surgeon-settings-active-tab → workflows）
  - REQ-365 AC-10（タブ切替の LocalStorage 同期。本PBIの非回帰対象）
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `/settings`（hash なし）を直接開く/ブックマークから開く/再読込すると、最後に使ったタブ（例: 翻訳）ではなく常に「ワークフロー・モデル」タブに戻り、毎回タブを選び直す手間が生じるため。
  2. なぜその課題が発生するか: 仕様上は保存済みタブへ復元されるはずの初期選択が、hash が無い場合に保存値ではなく既定値で解決されている（開発環境では確認済み、本番ビルドでの再現は未確認）。
  3. なぜ現状の仕組みで不十分か: REQ-365 の自動テストは保存値の書き込みと再マウント時の復元までを検証しているが、hash なしで実ブラウザを開いた際の復元は検証されていない。
  4. なぜこのアプローチを採用するか: 仕様（SPEC_SETTINGS）が既に初期選択順を定めているため、仕様どおりの動作を満たす最小修正に留め、実行環境（開発/本番）に依存しない再現テストで固定するため。
  5. 根本原因: hash が無い初期表示の解決経路で保存済みタブが参照されず、環境差（開発時の二重実行など）を含めて検証されていなかったこと（原因の特定は設計フェーズ。開発環境の StrictMode 起因はコード読解による推定）。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 該当なし。
  - **Interaction (インタラクション)**:
    - hash なしで Settings を開いたときに、前回選択タブへ復帰する。
  - **Visual (視覚デザイン)**:
    - 該当なし。
- **Requirement**:
  - **1. hash なし初期表示での保存済みタブ復元**:
    - 有効な URL hash が無く、保存済みの有効なタブ ID がある場合、Settings はそのタブを表示し、URL hash も保存済みタブに正規化する。
  - **2. 既存の優先順位の維持**:
    - 初期選択は「有効な URL hash → 有効な保存済みタブ ID → workflows」の順で解決する。有効な hash がある場合は hash を優先する。
  - **3. 実行環境非依存**:
    - 開発環境・本番ビルドのどちらでも同じ結果になる。本不具合が開発環境でのみ再現する場合も修正対象とする。
- **Acceptance criteria**:
  - [ ] AC-1: Given 保存済みタブ（prompt-surgeon-settings-active-tab）に有効な値（例: translation）があり URL に hash が無い, When `/settings` を新規に開く（直接アクセスまたは再読込）, Then 保存済みタブ（翻訳タブ）が選択表示され、URL hash が `#translation` に正規化されること。この正規化はブラウザ履歴エントリを追加せず（replace）、ブラウザの戻る操作で Settings を開く直前のページへ戻れること。
  - [ ] AC-2: Given 保存済みタブが translation で URL が `/settings#prompt`（有効な hash）, When Settings を開く, Then hash のタブ（プロンプト支援）が選択表示され、hash 優先の挙動が維持されること。
  - [ ] AC-3: Given 保存済みタブが未設定または無効な値で URL に hash が無い, When `/settings` を開く, Then 既定の workflows タブが選択表示され、URL hash が `#workflows` に正規化されること。
  - [ ] AC-4: Given Settings を表示している, When ユーザーがタブを切り替える, Then 保存済みタブの値が切替後のタブへ更新され、以後の hash なし再訪（AC-1）で復元されること（REQ-365 AC-10 の非回帰）。
  - [ ] AC-5: Given 開発サーバー実行と本番ビルド（preview）実行の両方, When AC-1 の操作を実ブラウザで行う, Then どちらの環境でも同一の結果（保存済みタブが表示される）になること。加えて、開発環境特有の初期化処理の二重実行（StrictMode 相当）を再現する自動テストで AC-1 が検証され、その自動テストが修正前の実装に対して失敗すること（本番ビルドで修正前も再現するかは問わず、再現した場合は優先度を P2 へ引き上げる）。
- **Inferred points**:
  - 優先度: P3。開発環境でのみ再現する場合は低影響として扱い、本番ビルドでも再現することが確認された場合は P2 へ引き上げる（AC-5 の実測で判定）。
  - 原因は開発環境の StrictMode 起因と推定されているが、BA はコード非参照のため確定していない。AC は原因に依存せず挙動のみを規定する。
  - 仕様変更は不要（SPEC_SETTINGS の初期選択順は既に定義済み）。仕様と実装の乖離の是正であり、仕様書の更新は原則発生しない。
  - テスト規約: テスト名に `[REQ-368/AC-n]` を付与し、ファイル名・パスにチケット番号を含めない。
  - 範囲外: 複数ブラウザタブ間の保存値同期（後に書いた値が保存される現行の localStorage 挙動を変更しない）、SSR（本アプリはクライアント描画のSPAを前提とし、サーバー側の hash 処理は対象外）。
  - REQ-367（共通Modal）とは独立しており、依存関係はない。
