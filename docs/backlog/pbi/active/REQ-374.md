### REQ-374: モバイルHistory：ヘッダー・フィルター・カード操作の整理

- **Type**: feature
- **Status**: ready
- **Priority**: P3
- **Surface**: モバイルHistory（幅767px以下）のスナップショット一覧・アルバム詳細のヘッダー、フィルター／ソート領域、画像カード
- **Reference**:
  - docs/design/mobile-ui-redesign/mobile-history-generate-selection-design-draft.md（§1〜§3、§6 AC-01〜AC-03、AC-10）
  - docs/design/mobile-ui-redesign/mobile-common-ui-redesign-proposal.md（COMMON-01 / 06）
  - docs/specs/SPEC_HISTORY.md（§2 機能一覧、§3 レイアウト）
  - 比較モック: `/history?ui=baseline` ／ `/history?ui=proposal`
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: モバイルHistoryはフィルター領域が高く、カード上の操作と日時が競合し、ヘッダーも窮屈で、画像一覧の面積が削られるため。
  2. なぜその課題が発生するか: PC向けの操作群（フィルター、セリフ一括変換、アルバム切替、カード操作）が、モバイルでも同じ密度で縦に積まれるため。
  3. なぜ現状の仕組みで不十分か: スナップショットとアルバム詳細でカード操作の位置が異なり、操作を学習しづらい。
  4. なぜこのアプローチを採用するか: 画像中心の情報設計を維持し、フィルターの折りたたみとカード操作の統一で画像面積を確保する方向を、ユーザーがモックで評価した。
  5. 根本原因: モバイルでの操作の優先順位（画像＞絞り込み＞管理操作）が画面構成に反映されていないこと。
- **UX Classification**:
  - **Information Design (情報設計)**: スナップショット／アルバム切替をヘッダーの中心に置く。セリフ一括変換はスナップショット側のフィルター・ソート列へ移す。
  - **Interaction (インタラクション)**: フィルターを折りたたみ可能にする。ソートは外側のアイコンで常時実行可能。カード操作は「⋯」メニューへ集約する。
  - **Visual (視覚デザイン)**: 日時と操作の重なりを解消する。2列グリッドを維持する。
- **Requirement**:
  - **1. ヘッダー整理**: スナップショット／アルバム切替を中心に置き、セリフ一括変換はスナップショットのフィルター・ソート列側へ移す。アルバム表示にはスナップショット用フィルターを出さない。
  - **2. フィルター折りたたみ**: 既存のWorkflow／LoRA／Tag Set条件を展開時に使える。ソートは展開状態に依存しない。
  - **3. カード操作の統一**: 右上に「⋯」、日時は左下。スナップショットとアルバム詳細で位置を揃える。音声関連操作・ダウンロード・削除は既存の機能・確認フローを呼び出す。
  - **4. プレビュー**: 画像タップのプレビューを継続し、モバイル画面内で画像が表示される。
  - **5. 非対象**: 複数選択UI（REQ-375）、PC表示、Baseline、API。
- **Acceptance criteria**:
  - [ ] AC-1: Given 幅767px以下のHistoryスナップショット一覧, When 画面を表示する, Then 画像カードが2列で表示され、各カードの日時と右上の「⋯」ボタンが重ならないこと。
  - [ ] AC-2: Given 幅767px以下のHistory, When ヘッダーを確認する, Then スナップショット／アルバムの切替が主要要素として表示され、「セリフ一括変換」がヘッダーでなくスナップショットのフィルター・ソート列側に配置されていること。
  - [ ] AC-3: Given フィルター領域を折りたたんだ状態と展開した状態, When ソート操作を行う, Then どちらの状態でもソートが実行でき、展開時はWorkflow／LoRA／Tag Setの絞り込み条件を従来どおり指定できて、AND結合の結果（0件時はEmpty Stateとフィルタ解除）が従来と同じであること。
  - [ ] AC-4: Given スナップショット一覧とアルバム詳細を繰り返し行き来する, When アルバムに切り替えて戻る操作を複数回行う, Then フィルターバー／ツールバーが重複して表示されず、アルバム表示にスナップショット用フィルターが表示されないこと。
  - [ ] AC-5: Given スナップショット一覧とアルバム詳細, When カードの「⋯」を開く, Then 両画面で「⋯」が同じ位置にあり、音声関連操作・ダウンロード・削除が従来と同じ処理と確認フロー（削除の確認を省略しない）を起動すること。
  - [ ] AC-6: Given 画像カード, When カードをタップする, Then 画像が表示された状態でプレビューが開き、枠だけが表示される状態にならないこと。
  - [ ] AC-7: Given 幅360px、セーフエリア、画面回転、拡大表示, When AC-1〜AC-6を実行する, Then レイアウトが崩れず、「⋯」を含む各操作の有効タップ領域が44×44px以上であること。
  - [ ] AC-8: Given 幅768px以上、Baseline、他ページ, When 操作する, Then 本PBI前から表示と挙動が変化しないこと。
- **Inferred points**:
  - 参考: REQ-378（モバイルUI共通規約のSPEC_COMMON反映）の規約と整合させる（先行着手は可能）。
  - 「選択モード」ボタンの扱い、長押し、選択バー・下部ドックはREQ-375で扱う。ただし本PBIの「⋯」メニューとREQ-375の選択モードが同じカード上で競合しないよう、設計時に操作領域を共同で確認する。
  - 現行仕様（SPEC_HISTORY §2）の「履歴検索・カード表示」は2:3の画像カードを定義している。モバイルでも2:3比率を維持するかを設計で確認する。
  - 音声関連操作（現行の機能名はSPEC_HISTORY／画面で確認）の具体名は設計フェーズで棚卸しする。
  - モックはDOM後処理とCSS上書きで実現しており、本番の実装方式として採用しない。
