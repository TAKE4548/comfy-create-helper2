### REQ-328: GPU／VRAM資源と併用条件に基づくワークロード共通管理

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: LoRA学習・画像生成・VLM/LLM推論のGPU／VRAM競合を共通管理する。学習中という理由だけで生成・推論を一律禁止せず、利用可能な資源と併用条件に基づき開始・待機・解放を判断する。
- **ユーザー判断（2026-10-26）**:
  - 共通管理の要求は継続し、学習中の一律禁止は見直す。
  - 空きVRAMと併用条件に応じた開始許可、不足・非互換条件での待機または制限、資源状態不明時の扱いの明確化、他の実行中処理を妨げない資源解放という見直し案を「OK」で承認した。
- **現状と課題**:
  - 現行の生成仕様には、バックエンドworkerの上流投入直前VRAM判定と、低VRAM時の未投入ジョブ待機がある。この仕組みの存在だけで、学習・推論を含む共通調停まで実装済みとは判断しない。
  - 個々の学習ガード・推論後アンロード等の現行実装と共通化範囲は設計で確認する。旧PBIの機種名・実装名・原因説明を現在の必須構成として固定しない。
- **UX Classification**: Interaction / Reliability（併用可能時の不要な制限の解消と、資源不足・競合理由の明示）。
- **Requirement**:
  - 学習・生成・推論の開始可否を、利用可能なGPU／VRAM資源、必要量・余裕量、同時実行中の処理との併用条件で判断する。条件を満たせば学習中でも併用を許可する。
  - 資源不足または併用不可の条件では新規開始を待機・制限し、資源不足なのか処理の組合せなのかを利用者に分かる理由として通知する。
  - 資源状態を取得できない場合は安全確認できない旨を表示し、開始可否・再確認方法を設計で明確化する。取得不能を十分な空き容量として扱わない。
  - 複数の開始要求が競合しても同じ空き資源を重複割当しない。終了・失敗・取消後は当該処理の管理状態を解放し、待機処理の開始条件を再判定する。
  - VLM/LLM等の資源解放は他の実行中処理を妨げない。処理の管理状態・予約の解放と、実際のモデルアンロード・物理VRAM回復を区別し、未確認の物理解放を成功と断定しない。
  - 現行の受付・上流投入境界、低VRAM時の必要なガードと取消範囲を維持する。REQ-259の投入後VRAM待機表示不整合は別件として扱う。

#### Acceptance Criteria（2026-10-26レビュー後の現行AC）

- [ ] **AC-1**: Given LoRA学習が実行中でも必要な空きVRAMと設計で定めた併用条件を満たしている, When 画像生成またはVLM/LLM推論の開始を判定する, Then 学習中という理由だけでは拒否せず、条件を満たす処理の開始を許可すること。
- [ ] **AC-2**: Given 資源不足または設計で定めた併用不可条件がある, When 新規処理の開始を判定する, Then 条件に応じて待機・制限され、実際の理由が利用者に表示され、既存の実行中処理を意図せず中断しないこと。資源状態が取得不能の場合は安全確認できない旨を表示し、設計で定めた開始可否・再確認の動作に従うこと。
- [ ] **AC-3**: Given 複数の開始要求が同時に到着し、すべてを併用するための資源はない, When 共通管理が割当を判定する, Then 同じ利用可能資源を重複して割り当てず、許可された処理と待機・制限された処理の状態が整合すること。
- [ ] **AC-4**: Given 共通管理下の処理が正常終了・失敗・取消のいずれかになる, When 終了処理を行う, Then 当該処理の管理状態・予約を解放して待機処理を再判定し、必要なモデル解放を他の実行中処理に影響しない条件で行うこと。解放失敗や物理VRAM回復が未確認の場合はその状態を保持・通知し、重複終了通知で過剰解放や重複開始を起こさないこと。

- **設計・検証への引継ぎ**:
  - 必要容量・余裕量、計測の鮮度、取得不能時の開始可否と再確認、併用不可の組合せは設計・テスト計画で具体化してレビューする。現在の空き量だけで将来のピーク使用量まで保証したとは扱わない。
  - 共通化するサービスと外部プロセスの境界、既存ガードとの二重判定、同時要求の原子性、終了・失敗・取消・解放失敗・再通知を検証する。ユーザーが許可していない実行中処理の停止や外部モデルの強制アンロードを導入しない。
  - WorkloadCoordinatorというサービス名やシングルトン・ロックAPIは必須要件とせず、実現方式を後続設計で定める。
- **References**: `docs/specs/SPEC_GENERATE.md` §5-4、`docs/specs/SPEC_COMMON.md` §7、`docs/specs/SPEC_DATASET_STUDIO.md`

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **旧タイトル**: Prompt Surgeon: WorkloadCoordinator によるローカルハードウェア/VRAM排他制御の集約

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-04 (Task 3.1) に基づき、現在複数箇所（`training_manager` の学習ガード、LM Studio の推論後アンロード、画像生成の WebSocket 監視等）に点在している GPU/VRAM ガード機構を、統一サービス `WorkloadCoordinator`（`backend/app/services/workload_coordinator.py`）に集約する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: LoRA 学習・VLM 推論・ComfyUI 生成が並行して動く構成において、各機能が個別にガードを設けており競合や OOM リスクがあるため。
  2. なぜ点在したのか: 機能追加ごとに局所的なガード（学習中フラグ、推論後アンロード）を独立して追加したため。
  3. なぜ集約するのか: 単一の調停サービスによって VRAM セーフティインターロックと排他ロックを一元管理するため。
  4. 根本原因: ローカル計算資源（RX 9070 XT + WSL2）の調停を一括して担うアーキテクチャ層が欠如していたため。
- **UX Classification**:
  - **Interaction / Reliability**:
    - リソース競合時の明確かつ親切なブロックメッセージ通知（「LoRA学習中のため生成できません」等）
    - 推論終了時・非常時の確実な VRAM 解放

#### 旧Acceptance Criteria（履歴・適用終了）

- **旧AC-1**: Given `WorkloadCoordinator` シングルトンサービスが存在するとき、When LoRA 学習中（`LORA_TRAINING` ワークロード実行中）に画像生成または重い VLM 推論リクエストが試行された場合、Then `can_start_workload` が `False` と適切なエラーメッセージを返し、新規リソース消費が確実にインターロックされること。
- **旧AC-2**: Given VLM/LLM 推論タスクが実行されるとき、When `WorkloadCoordinator` のセーフティインターロックを経由して実行された場合、Then 完了時に自動的または明示的にモデル解放（LM Studio アンロード等）がトリガーされ、GPU VRAM が速やかに解放されること。
- **旧AC-3**: Given 各バックエンドサービス（学習マネージャー、推論サービス等）において、When `WorkloadCoordinator.acquire_lock` / `release_lock` を用いた調停ロジックに移行したとき、Then 既存の単体テストが正常に動作し、競合回避ロジックが統合されていること。
- **旧AC-4**: Given リファクタリング後において、When `mypy backend` および `pytest`（バックエンドテスト）を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
