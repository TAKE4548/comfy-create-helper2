### REQ-328: Prompt Surgeon: WorkloadCoordinator によるローカルハードウェア/VRAM排他制御の集約

- **Type**: refactoring
- **Status**: ready
- **Current step**: none
- **Priority**: P2
- **Surface**: `tmp/refactoring_analysis_and_roadmap.html` の REF-04 (Task 3.1) に基づき、現在複数箇所（`training_manager` の学習ガード、LM Studio の推論後アンロード、画像生成の WebSocket 監視等）に点在している GPU/VRAM ガード機構を、統一サービス `WorkloadCoordinator`（`backend/app/services/workload_coordinator.py`）に集約する。
- **5 Whys / Root Cause**:
  1. なぜ変更が必要か: LoRA 学習・VLM 推論・ComfyUI 生成が並行して動く構成において、各機能が個別にガードを設けており競合や OOM リスクがあるため。
  2. なぜ点在したのか: 機能追加ごとに局所的なガード（学習中フラグ、推論後アンロード）を独立して追加したため。
  3. なぜ集約するのか: 単一の調停サービスによって VRAM セーフティインターロックと排他ロックを一元管理するため。
  4. 根本原因: ローカル計算資源（RX 9070 XT + WSL2）の調停を一括して担うアーキテクチャ層が欠如していたため。
- **UX Classification**:
  - **Interaction / Reliability**:
    - リソース競合時の明確かつ親切なブロックメッセージ通知（「LoRA学習中のため生成できません」等）
    - 推論終了時・非常時の確実な VRAM 解放

#### Acceptance Criteria (AC)

- [ ] **AC-1**: Given `WorkloadCoordinator` シングルトンサービスが存在するとき、When LoRA 学習中（`LORA_TRAINING` ワークロード実行中）に画像生成または重い VLM 推論リクエストが試行された場合、Then `can_start_workload` が `False` と適切なエラーメッセージを返し、新規リソース消費が確実にインターロックされること。
- [ ] **AC-2**: Given VLM/LLM 推論タスクが実行されるとき、When `WorkloadCoordinator` のセーフティインターロックを経由して実行された場合、Then 完了時に自動的または明示的にモデル解放（LM Studio アンロード等）がトリガーされ、GPU VRAM が速やかに解放されること。
- [ ] **AC-3**: Given 各バックエンドサービス（学習マネージャー、推論サービス等）において、When `WorkloadCoordinator.acquire_lock` / `release_lock` を用いた調停ロジックに移行したとき、Then 既存の単体テストが正常に動作し、競合回避ロジックが統合されていること。
- [ ] **AC-4**: Given リファクタリング後において、When `mypy backend` および `pytest`（バックエンドテスト）を実行したとき、Then 型エラー 0、テスト失敗 0 件で通過すること。
