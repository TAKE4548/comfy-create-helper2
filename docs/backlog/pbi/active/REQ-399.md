### REQ-399: scripts/run_full_suite.py の並列度制御によるCPU飽和防止とテスト安定化

- **Type**: chore
- **Status**: ready
- **Priority**: P3
- **Surface**: `scripts/run_full_suite.py`と必要な実行インフラ検証。FEの並列度を変更する場合に限り`frontend/vite.config.ts`等の設定と`docs/specs/SPEC_TEST_ARCHITECTURE.md` §8の該当規定・実績同期を含む。テストのassertion・製品コードは対象外。
- **リスク区分**: 固定Gate 2コマンドの実行基盤変更（高リスク）。現行V1 baselineとfreshな全スイートfallbackを適用する。
- **起点**: REQ-394のQAトリアージでユーザーが別PBI化を選択（2026-10-25）。根拠は`docs/logs/REQ-394/qa-triage-2.json`、`docs/logs/REQ-394/qa2/qa-evidence.md`、verificationの`9dddfa368f004001a6d8ae1da9aa407b.record.json`（FAIL）と`f063838a7837491d943ceff9ace67c5c.record.json`（再実行PASS）。いずれも過去のローカル記録として扱う。
- **現状確認（2026-10-26）**:
  - 現行`run_full_suite.py`はSUITESをforループ内で`subprocess.run`し、FE→BEの順次実行である。FE/BEを完全並行で起動しているという旧前提は現行コードと一致しない。
  - FEは`npm.cmd --prefix frontend test`（vitest run）、BEはvenv Pythonの`-m pytest -n auto`。一方が失敗しても次を実行し、いずれか失敗ならwrapperは1、両方成功なら0を返す。
  - FEはforks・isolate:trueでmaxForksは既定。SPEC §8.3も既定maxForksを規定し、変更時には状態リーク検証・複数回計測・同節改訂を要求する。BE/FE各スイート内の並列度とホスト負荷は現行の調査対象になる。
  - `.agents/verification.json`は本wrapperをGate 2固定コマンドとして使用する。コマンド入口と全件実行・失敗集約を維持する。
  - 遅延177msの失敗、同一候補の再実行成功、単独3回成功、CPU100%は過去PBIの記録であり、今回再計測していない。当時の候補・実行条件・負荷の時系列を後続設計で照合する。現行の原因を「BE/FE同時実行」と断定しない。
- **Root Cause（仮説・未確定）**: 各スイートのworker設定や外部負荷による資源競合が遅延テストの散発失敗へ寄与する可能性がある。現行候補の再現・負荷観測・設定比較で寄与を確認し、並列度の数式だけでCPU飽和防止を実証したと扱わない。
- **関連・境界**: REQ-394は完了記録を持つ。REQ-400はFEテストの順序依存解消を扱い、本件へ統合しない。順序依存や製品不具合が見つかった場合は原因を分け、本件の資源調整や再試行で隠さない。
- **UX Classification**: Information Design（実効worker・計測条件・終了結果の追跡）、Interaction（既存の実行入口と終了コードを維持）。製品画面の変更はない。
- **Requirement**:
  - FE→BEの順次実行を維持し、各スイート内のworkerとCPU負荷・メモリ・wall時間を調査して資源配分を明示する。BEの実効worker上限は`max(1, floor(論理コア数 * 0.75))`以下とし、旧版の別式との選択曖昧性をなくす。FEのworker上限と変更要否は比較計測を基に設計で確定する。
  - 論理コア数不明・1/少数コアでも0workerや過剰起動にしない安全なfallbackを定義する。既存CLI・終了コードと、一方が失敗しても両スイートを全件実行する失敗集約を維持する。自動リトライで失敗を成功に置換しない。
  - 個別テストの遅延150ms・preview300ms等の閾値、assertion、ケース、隔離・収集範囲を緩和・削除しない。内部ロジック置換・意図的遅延注入・skipによる安定化を行わない。
  - フルスイート5回連続成功とwrapper全体のwall150秒以内を維持する。現行順次実行での実現性を測り、達成困難なら黙って緩めず設計へ戻す。既存の各スイート性能予算と新しいwrapper予算を混同しない。

- **設計・検証への引継ぎ**:
  - 固定スイートが既に順次実行である点を起点に現行再現を調べる。過去の「同時実行でCPU100%が真因」という説明は未照合の履歴へ移し、現行の確定原因としない。
  - 基準環境の範囲と負荷の有効条件を事前に定め、無効判定を失敗後の都合で変更しない。5回の途中失敗・中断時の再検証手順も設計で定める。有限回の成功をあらゆる負荷での無失敗保証とは表現しない。

#### 旧要求の履歴（現行の実装指示・受入条件として適用しない）

- **Type**: chore
- **Status**: new
- **Priority**: P3
- **Surface**: `scripts/run_full_suite.py`（フルスイート実行インフラ）
- **リスク区分**: 検証インフラの変更（高リスク）。Gate 2 の固定コマンド `python scripts/run_full_suite.py` を変更するため、受け入れ検証は全スイートを再実行する。
- **起点**: REQ-394 の QA トリアージで、ユーザーが別 PBI 化を選択（2026-10-25）。
- **根拠資料**: `docs/logs/REQ-394/qa-triage-2.json`、`docs/logs/REQ-394/qa2/qa-evidence.md`、`docs/logs/verification/9dddfa368f004001a6d8ae1da9aa407b.record.json`（FAIL 記録）、`docs/logs/verification/f063838a7837491d943ceff9ace67c5c.record.json`（同一候補の再実行 PASS 記録）。
- **観測事実**:
  - `scripts/run_full_suite.py` の 1 回目で `event loop lag 177.0ms exceeds 150ms` により FAIL。同一候補の再実行は PASS。単独実行は 3 回とも PASS（各約 1.6 秒）。
  - BE（`pytest -n auto`）と FE（`vitest`）を完全並行で実行した際、CPU 使用率が 100% に張り付き、OS スケジューリングによってイベントループの tick（10ms 周期）すら遅延し、一時的な過負荷で 177ms まで待たされていた。
- **依存関係**: なし。個別テストのアサーション閾値（REQ-387 AC-3: 遅延 150ms、preview 300ms）は一切変更せず維持する。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: フルスイート（Gate 2）で、機能に問題がないのに当該テストが散発的に FAIL し、受け入れ検証の判定を保留にした。
  2. なぜその課題が発生するか: BE（`pytest -n auto`）と FE（`vitest`）の同時実行により CPU が完全飽和し、イベントループ tick の最大遅延が 150ms を超えたため。
  3. なぜ現状の仕組みで不十分か: `run_full_suite.py` がマシンの論理コア数や負荷を考慮せず、BE と FE それぞれで最大並列を実行して過負荷を引き起こしているため。
  4. なぜこのアプローチを採用するか: 個別テストの閾値を緩和したり危険な遅延注入を行ったりせず、テスト実行インフラ側で並列ワーカー数を適切に制御・配分することで、CPU 飽和（Starvation）を防ぎテストを根本的に安定化できる。
  5. 根本原因: `scripts/run_full_suite.py` における BE と FE の並行実行時のリソース割り当て・並列度制御の欠如。
- **UX Classification**:
  - **Information Design (情報設計)**: 変更なし。
  - **Interaction (インタラクション)**: 変更なし（`python scripts/run_full_suite.py` の実行引数・終了コードは維持）。
  - **Visual (視覚デザイン)**: 変更なし。
- **Requirement**:
  - **1. 並列ワーカー数・リソースの適切な制御**:
    - `scripts/run_full_suite.py` は、BE と FE の同時実行時において、CPU コア数の完全飽和を防ぐよう並列度（`pytest -n` のワーカー数やプロセス割り当て）を適切に制御する。
  - **2. 個別テスト検証能力の完全維持**:
    - 個別テストのアサーション閾値（遅延 150ms、preview 300ms 等）やテストケースを緩和・削除・変更しない。
  - **3. 全体実行時間の大幅悪化の防止**:
    - 並列度制御を適用しても、フルスイート全体の実行時間が許容範囲内（設計で定める基準時間内）に収まること。
- **旧Acceptance criteria**:
  - 旧AC-1: Given 改修後の `scripts/run_full_suite.py`（並列度制御適用）, When フルスイートを連続 5 回実行する, Then 起点となった遅延テスト `test_req387_ac3_event_loop_lag_and_preview_latency_with_1000_terminal_jobs` を含む全テストが 5 回とも PASS し、`event loop lag` による失敗および過負荷に起因する他テストの失敗が 0 件であること。
  - 旧AC-2: Given `scripts/run_full_suite.py` 実行時, When BE と FE が並行実行される, Then CPU の完全飽和を防ぐよう、BE `pytest -n` のワーカー数が論理コア数の 75% 以下（または `max(1, os.cpu_count() - 2)`）を上限とし、FE との極端な CPU 競合が回避されるよう制御されていること。
  - 旧AC-3: Given 変更前後, When テストコードを比較する, Then 個別テストのアサーション閾値（遅延 150ms、preview 300ms 等）の緩和・削除・変更が一切なく、REQ-387 AC-3 の検証能力が完全に維持されていること。
  - 旧AC-4: Given 変更後, When フルスイート全体の実行時間を計測する, Then 並列度制御を適用しても、フルスイート全体の実行時間が 150 秒以内に収まっていること。
- **Inferred points**:
  - コア数配分の具体的なアルゴリズム（例: 論理コア数の 50% を BE、残りを FE やシステム用に配分、あるいは `os.cpu_count() - 1` など）は設計で確定する。
  - 優先度 P3 の根拠: 機能影響はなく再実行で回避可能だが、CI や受け入れ検証のたびに判定を保留にする恐れがあるため。
