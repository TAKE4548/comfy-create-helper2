### REQ-388: prune_terminal を配線して終端 job の 1000 件保持を実現する

- **Type**: bug
- **Status**: new
- **Priority**: P2
- **Surface**: backend/app/services/generation_repository.py（`prune_terminal`）, backend/app/services/generation_service.py, backend/app/main.py（起動処理）, docs/specs/SPEC_GENERATE.md（保持方針の既存記述。文言の精緻化は REQ-390 で扱う）
- **起点**: REQ-387（commit fca9965）の後続課題。REQ-387 は「`prune_terminal` の未配線」を対象外とし後続課題と明記した（設計 §4-7、PBI Inferred points）。
- **根拠資料**: `docs/logs/REQ-387/qa-doc-report-r2.md`（m3: REQ-333 の 1000 件方針と `prune_terminal` 未配線の差が文書から読めない）、`docs/logs/REQ-387/qa-code-report-r2.md`、`docs/design/REQ-387.md` §4-7 / §8、`docs/design/REQ-333.md`（終端記録は既存 server metadata 1000 件の保持集合と同じ範囲で整理し、active は実行が終わるまで整理しない）。`docs/logs/` は gitignore 対象のローカル資料。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `generation_jobs` が生成を重ねるほど単調に増え、REQ-333 で承認済みの「終端 job は 1000 件まで保持」と実態が一致しない（10/24 実測で 874 行、うち metadata_json が約 23.7MB）。DB サイズ、バックアップ、DB 全体を走査する処理が生成回数に比例して重くなる。
  2. なぜ発生するか: 整理処理 `GenerationRepository.prune_terminal` は実装済みで、保持上限の定数（終端 1000 件）も持つが、アプリ本体（`backend/app`）のどこからも呼ばれていない。呼出しはテストだけである。
  3. なぜ現状の仕組みで不十分か: REQ-387 は snapshot の読出しを配信窓で有界化したが、DB の保持件数は不変とした（SPEC_GENERATE の保持方針行）。読出しが有界になっても、書込み側の増加は止まらない。
  4. なぜこのアプローチ（配線）を採用するか: 保持方針は REQ-333 で承認済みであり、新しい方針を作るのではなく既存方針を実際に働かせるだけで済む。
  5. 根本原因（Spec Gap と推定）: REQ-333 の要件が「保持集合を揃える整理機能」を求めた一方、それを「いつ・誰が呼ぶか」（契機）を受入条件にも SPEC_GENERATE にも定義しなかったため、機能の存在だけで受入が通り、配線が漏れた。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 変更なし。Job 管理の表示項目と配信窓（REQ-387 AC-1）は維持する。保持上限を超えた古い終端 job（保護対象を除く）は DB から消え、窓外 job と同じく job 単位照会で「見つからない」扱いになる。
  - **Interaction (インタラクション)**:
    - 整理の実行中も生成受付・取消・プレビュー・状態取得が即時に応答すること（REQ-387 で達成した応答性を悪化させない）。
  - **Visual (視覚デザイン)**:
    - 変更なし。
- **Requirement**:
  - **1. 終端 job の保持上限を実際に働かせる**:
    - 終端状態（succeeded / failed / cancelled）の job は、下記 5 の保護対象を除き最大 1000 件に保たれる。超過分は、保護対象を除いて古いものから削除される。非終端 job（queued / submitting / running / unconfirmed）は件数に関係なく削除しない。
  - **2. 整理の契機**:
    - バックエンド起動時に 1 回、および job が終端状態へ遷移した後に、保持上限超過（保護対象による超過を除く）が解消される。契機の頻度（毎遷移か間引きか）は設計に委ねるが、超過が長時間残らないこと。
  - **3. revision とキャッシュの整合**:
    - 整理で 1 件以上削除したときは revision を進め、snapshot キャッシュを無効化し、接続中の WS クライアントへ新 revision を配信する。削除が 0 件のときは revision を進めない。
  - **4. 応答性と失敗耐性**:
    - 整理はイベントループを占有しない。整理が失敗しても生成受付・取消・終端遷移を失敗させず、次の契機で再試行する。
  - **5. 整理対象から保護する job**:
    - 次の終端 job は整理で削除しない: (a) 現在の `normal_group_id` に属する job、(b) 非終端 job を 1 件以上含む batch に属する job。理由は、REQ-387 の配信窓（SPEC_GENERATE 配信窓の条件 2・3）の「batch / group は単位ごとに欠けず含まれる」と、進捗 N/F の算出を保つためである。
    - 保護対象が多く、終端 job が保持上限 1000 件を超える場合は、保護を優先して一時的に上限を超えてよい。このとき超過件数をログまたは記録で確認できること。保護対象でなくなった後の整理で上限に収まる。
- **Acceptance criteria**:
  - [ ] AC-1: Given 保護対象に該当する終端 job を含まない、終端 job 1500 件と非終端 job 3 件を含む `generation_jobs`, When バックエンドを起動して `GET /api/generation/state` が 200 を返せる状態から 10 秒経過する, Then 終端 job が 1000 件になり、削除された 500 件は `finished_at` の古い順（同値は `accepted_at`、さらに `job_id` の昇順）で、非終端 3 件はすべて残ること。
  - [ ] AC-2: Given 保護対象に該当する終端 job を含まず終端 job が 1000 件で保持されている, When 別の job が終端状態へ遷移して終端が 1001 件になる, Then その遷移から 10 秒以内に終端 job が 1000 件に戻り、削除されたのは（保護対象を除く）最古の 1 件だけであること。終端が 1000 件以下の間は削除が起きないこと。
  - [ ] AC-3: Given 非終端 job（queued / submitting / running / unconfirmed）が各 1 件、終端 job が 1200 件, When 整理が実行される, Then 非終端 4 件の status・prompt_id・outputs が整理前と同一のまま残ること。
  - [ ] AC-4: Given 整理で 1 件以上の job が削除される, When 整理が完了する, Then `generation_revision` が整理前より 1 以上大きくなり、直後の `GET /api/generation/state` は整理後の job 一覧（別の repository インスタンスから取得した snapshot と一致）を返し、接続中の WS クライアントが新しい revision の snapshot / event を受信すること。
  - [ ] AC-5: Given 終端 job が 1000 件以下で削除対象がない, When 整理が実行される, Then `generation_revision` は変化しない（整理を繰り返しても revision が増え続けない）こと。
  - [ ] AC-6: Given 整理で削除済みの job_id, When 取消・記録解除・`GET /api/generation/preview/{job_id}`・画像 availability を要求する, Then 応答は従来の「見つからない」結果（`job not found` 等の 404 相当）であり、5xx にならないこと。
  - [ ] AC-7: Given 終端 job 1000 件超（各 metadata 約 27KB）を含む DB, When 整理の実行中に `GET /api/generation/state` を並行して呼ぶ, Then 10ms 周期 tick で測るイベントループの最大遅延が 150ms 以下、state 応答の最大が 300ms 以下であること（REQ-387 AC-3 と同じ閾値）。
  - [ ] AC-8: Given 整理中に DB 例外（例: `database is locked`）が発生する, When 整理が失敗する, Then DB は整理前と同一（部分削除なし、revision 不変）で、失敗が WARNING 以上のログに 1 件記録され、その間の生成受付・取消・終端遷移は成功し、次の整理契機で整理が再試行されること。
  - [ ] AC-10: Given 終端 job 1200 件のうち、現在の `normal_group_id` に属する最古の終端 job と、非終端 job を含む batch に属する終端 job があり、いずれも `finished_at` が全体の最古側にある, When 整理が実行される, Then それらは削除されず、保護対象でない他の最古の終端 job から削除されて終端 job が 1000 件に収まること。
  - [ ] AC-11: Given 保護対象の終端 job が 1100 件ある, When 整理が実行される, Then 保護対象は 1 件も削除されず、保護対象でない終端 job はすべて削除され、保持上限 1000 件を超過した件数（100）がログまたは記録で確認でき、保護対象でなくなった後の整理で終端 job が 1000 件に収まること。
  - [ ] AC-9: Given released 記録が 1001 件（`released_at` が異なる）, When 整理が実行される, Then 従来の `prune_terminal` と同じく `released_at` が最古の 1 件が削除され released が 1000 件になること。既存の `prune_terminal` 単体テスト（1000 件上限、active 保護、冪等）は変更なしで通ること。
- **Inferred points**:
  - 「10 秒以内」は確定値である（人レビューで承認済み）。契機の頻度（間引き可）は設計に委ね、10 秒以内という観測可能な上限の範囲で決める。
  - 現行の `prune_terminal` は終端 job の全行（metadata_json を含む）を読み込んで並べ替えている。そのまま終端遷移ごとに同期呼出しすると REQ-387 が解消した問題（イベントループ占有）を再発させる恐れがあるため、AC-7 を置いた。どう実現するかは設計の判断とする。
  - 現在の `normal_group_id` に属する job と、非終端 job を含む batch の job は整理対象から保護する（人レビューでの決定。Requirement 5、AC-10・AC-11）。保護が上限 1000 件を超える場合は保護を優先して一時的に超過してよい。保護対象の判定方法と超過の記録形式は設計の判断とする。released 記録の整理（AC-9）はこの保護の対象外とする。
  - released 記録の上限（現行実装は 1000 件）を AC-9 に含めたのは、現行の `prune_terminal` の挙動を変えない前提による。SPEC_GENERATE にこの値は書かれていない（REQ-390 で精緻化する）。
  - REQ-390（SPEC 文言の精緻化）が保持方針を定義するため、本 PBI では SPEC_GENERATE の文言を変更しない。
