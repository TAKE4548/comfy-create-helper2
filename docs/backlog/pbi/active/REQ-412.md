### REQ-412: ヘッダーリソースモニタからのComfyUIメモリ解放アクション実行

- **Type**: feature
- **Status**: ready
- **Priority**: P2
- **Surface**: 共通ヘッダー（`PageHeader`）のリソースモニタ（`ResourceGaugeChips.tsx`、`ResourceHoverMonitor.tsx`）、デスクトップ用リソース詳細ホバーカード、モバイル用リソース詳細オーバーレイ、およびWeb Manager連携 ComfyUI メモリ解放アクション。
- **5 Whys / Root Cause**:
  1. なぜ新設・改修が必要か: 現在のUIではComfyUIのモデルアンロード・メモリ解放を行うために作業画面（Generateタブ等）を離れてSettingsタブのシステム欄まで移動する必要があり、作業の手間とコンテキストの中断が発生しているため。
  2. なぜその課題が発生するか: メモリ解放機能がSettings画面のサーバー管理（Web Manager連携）コンポーネント内にのみ実装されており、ヘッダーに常駐するリソース監視UIから直接操作する導線が存在しないため。
  3. なぜ現状の仕組みで不十分か: 画像生成やプロンプト調整中にヘッダーのリソースモニタでVRAM高負荷を検知した際、その場ですぐに解放したいという利用者の直感的な意思決定フローに対し、タブ遷移・画面復帰の手数（待ち時間や編集コンテキストの視覚的離脱）が運用のボトルネックになっているため。
  4. なぜこのアプローチを採用するか: リソース使用状況（CPU/RAM/GPU/VRAM）を詳細確認するリソースモニタの詳細メニュー（デスクトップのホバーカード、モバイルのタップオーバーレイ）内にメモリ解放アクションを配置することで、画面遷移を一切伴わずにVRAM逼迫の解消を行えるようにするため。
  5. 根本原因: システムリソースの「監視（ヘッダー）」と「制御・介入（Settings）」のUI導線が分離して配置されており、高負荷検知からアクション実行に至るユーザーの認知・操作ジャーニーに最適化されていなかったため。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - デスクトップのリソース詳細ホバーカード（幅250px）およびモバイルのリソース詳細オーバーレイ（幅240px）に、ComfyUIの「メモリ解放」ボタンを配置。
    - ボタンの活性・非活性状態（アイドル時のみ実行可能、生成中・キュー待機中・未接続・操作中は無効）を明確に表現し、非活性理由または現在の稼働ステータスをインライン表示またはツールチップで提示。
    - 要求受付後のフィードバック情報として、「解放要求を受け付けました。空き容量は監視値で確認してください」（物理VRAM解放完了を断定しない）を表示。
  - **Interaction (インタラクション)**:
    - デスクトップ環境では、ヘッダーリソースチップへのホバーでカードを展開し、hoverBridgeを通過してカード内の「メモリ解放」ボタンをクリック可能とする。
    - モバイル環境では、VRAMピルをタップしてオーバーレイを展開し、「メモリ解放」ボタンをタップ可能とする。
    - ボタン押下時に即時で二重送信防止（disabled化 + 処理中スピナー/ローディング表示）を適用。
    - 要求受付完了またはエラー発生時の結果フィードバックを提示し、外側クリックまたはホバー離脱による通常クローズ操作を阻害しない。
  - **Visual (視覚デザイン)**:
    - `SPEC_COMMON.md` §4-4-1（ヘッダー下端+6px、最大高さ制限と内部スクロール、`--z-header-menu: 60`）に準拠したレイアウト。
    - UI 6大不変条件（Hit-Slop 44x44px、ボタンテキストの `min-w-0`、文字サイズ規約）に適合したボタン設計。
    - 危険操作ではないため通常のアクションボタン（セカンダリ/プライマリ調）またはリフレッシュ系アイコン付きボタンとして調和したスタイル。
- **Requirement**:
  - **1. リソース詳細メニューへのメモリ解放ボタン配置**:
    - デスクトップ（640px以上）のホバー詳細カードおよびモバイル（640px未満）のタップ詳細オーバーレイの双方に、ComfyUIのメモリ解放を実行できるアクションボタンを配置する。
  - **2. 実行可否ガードと状態表示**:
    - ComfyUIが接続中でアイドル状態（実行中およびキュー待機中が0件）のときのみボタンを有効化する。
    - 生成中、キュー待機中、ComfyUI停止/未接続、または別のサーバー管理操作実行中はボタンを無効化（disabled）し、理由または状態を明示する。
  - **3. 二重送信防止とフィードバック表示**:
    - ボタン押下後は直ちにボタンを非活性化し、ローディング表示を行う。
    - 要求受付成功時は「解放要求を受け付けました。空き容量は監視値で確認してください」等の受付成功通知を表示する。物理的VRAM解放の完了を意味する表現は行わない。
    - タイムアウトや通信エラー時は「要求結果未確認」または失敗理由を表示する。
  - **4. 展開契約と末尾到達性の維持**:
    - ボタン追加後もメニュー全体のヘッダー展開契約（ヘッダー下端+6px、ビューポート超過時の内部スクロール）を維持し、すべての項目に到達・操作可能とする。
- **Acceptance criteria**:
  - [ ] AC-1 (デスクトップリソースホバーカードでのメモリ解放ボタン表示と配置):
    - **Given**: 画面幅640px以上のデスクトップ環境で任意の画面を表示している。
    - **When**: ヘッダーのリソースモニタチップにマウスホバーし、リソース詳細カード（`data-testid="resource-hover-card"`）を展開する。
    - **Then**: カード内に「ComfyUI メモリ解放」アクションボタンが表示され、ポインターをカード内に移動してもカードが閉じずにボタンを押下可能であること。
  - [ ] AC-2 (モバイルリソース詳細オーバーレイでのメモリ解放ボタン表示と配置):
    - **Given**: 画面幅640px未満のモバイル環境で任意の画面を表示している。
    - **When**: ヘッダーのVRAMピルをタップしてリソース詳細オーバーレイを展開する。
    - **Then**: 詳細オーバーレイ内に「ComfyUI メモリ解放」アクションボタンが表示され、タップ操作が可能であること。
  - [ ] AC-3 (アイドル時のメモリ解放実行と二重送信防止):
    - **Given**: ヘッダーのリソース詳細メニューを展開しており、ComfyUIが接続中かつアイドル状態（実行中0件、キュー待機中0件）である。
    - **When**: 「ComfyUI メモリ解放」ボタンをクリックまたはタップする。
    - **Then**: 解放要求が送信され、応答確認までの間ボタンが非活性化（disabled）されてローディング状態が表示され、二重送信が防止されること。
  - [ ] AC-4 (要求受付成功時のフィードバック表示):
    - **Given**: ヘッダーのリソース詳細メニューから解放要求を送信した。
    - **When**: サーバーから解放要求の受付成功応答を受信する。
    - **Then**: 「解放要求を受け付けました。空き容量は監視値で確認してください」と同等の受付成功フィードバックが表示され、物理VRAM解放完了を断定する表現を含まないこと。
  - [ ] AC-5 (非アイドル時・非接続時のボタン非活性ガード):
    - **Given**: ヘッダーのリソース詳細メニューを展開している。
    - **When**: ComfyUIでジョブ実行中、キュー待機中、ComfyUI未接続、または別のサーバー管理操作が実行中である。
    - **Then**: 「ComfyUI メモリ解放」ボタンが無効化（disabled）され、操作不可である理由または現在の稼働ステータスが表示されること。
  - [ ] AC-6 (通信エラー・タイムアウト時のエラーフィードバック):
    - **Given**: ヘッダーのリソース詳細メニューから解放要求を送信した。
    - **When**: サーバー通信切断、HTTPエラー、またはタイムアウトが発生する。
    - **Then**: 「要求結果未確認」またはエラー理由が表示され、要求が未完了であることがユーザーに通知されること。
  - [ ] AC-7 (ヘッダー展開契約および末尾到達性の維持):
    - **Given**: ヘッダーのリソース詳細メニューにメモリ解放ボタンが配置されている。
    - **When**: ビューポート高さが小さい状態やヘッダーが複数行に折り返された状態で詳細メニューを展開する。
    - **Then**: メインメニューの展開位置がヘッダー下端+6pxを維持し、高さ超過時は内部スクロール（`overflow-y: auto`）によりメモリ解放ボタンを含む全項目に到達・操作できること（SPEC_COMMON §4-4-1準拠）。
- **Inferred points**:
  - メモリ解放のバックエンド処理は、SettingsタブやWeb Manager Dashboardで使用されている既存のManager API（`POST /api/action {"action":"free-memory","service":"comfy"}`）と共通のインターフェースおよび状態ガードを再利用することを想定。
  - メニュー内でのフィードバック表示（インラインメッセージまたは共通トースト通知）により、ホバーが外れてカードが閉じた後でもユーザーが解放受付の結果を確認できるようにすることが望ましい。
