### REQ-335: ComfyUI停止後の未確認ジョブが待機表示のまま残留し解除できない

- **Type**: bug
- **Status**: new
- **Priority**: P2
- **Surface**: frontend/src/store/slices/jobQueueSlice.ts, frontend/src/components/JobManagementModal.tsx, backend/app/services/generation_service.py, backend/app/services/generation_repository.py
- **Incident report**: [調査報告](../../../incident_report.md)
- **User decision**: 2026-10-10、調査承認・バックログ登録のみ。設計・実装には着手しない。残留3件はユーザー指定の暫定解除を別途行う。
- **5 Whys / Root Cause**:
  1. 生成が進んでいないジョブが待機表示のまま残り、実状態を判断できない。
  2. ComfyUI接続エラーによる投入結果不明のジョブをFEが待機中へ投影する。
  3. BEの取消判定では未確認を終了済みと扱い、状態が変わらない。
  4. prompt_id未取得のジョブは上流照合できず、DBではactiveとして再起動後も保持される。
  5. 未確認を区別する既存仕様の実装不整合と、未確認記録を手動解除する操作契約の不足がある。
- **UX Classification**:
  - **Information Design (情報設計)**:
    - 待機中・実行中・状態未確認を表示、件数、進捗で区別する。
  - **Interaction (インタラクション)**:
    - 未確認への取消結果を明示し、手動解除の意味と対象を設計で定義する。
  - **Visual (視覚デザイン)**:
    - 未確認を待機中と同じラベルで表示しない。
- **Requirement**:
  - **1. 未確認状態の表示・取消判定の修正（Type A）**:
    - REQ-333.md:103に沿い、未確認を状態未確認として表示する。
    - SPEC_COMMON.md:318、SPEC_GENERATE.md:174に沿い、未確認を確認済み終了として扱わない。
  - **2. 未確認記録の解除（仕様補足）**:
    - 利用者判断で解除する恒久操作のライフサイクル、保持、normal group終了条件を設計で定義し、成功・失敗・上流取消確認と区別する。
  - **3. 新規生成の継続・二重投入防止**:
    - 結果不明を理由に自動再送せず、無関係な生成や保存済み結果に影響させない。
- **Acceptance criteria**:
  - [ ] AC-1: Given 上流キューが空でprompt_id=null/status=unconfirmedのジョブ, When FEが同期する, Then 待機中と区別した状態未確認を表示し、待機件数・進捗に矛盾がない。
  - [ ] AC-2: Given 未確認ジョブ, When 単件または一括取消する, Then 確認済み終了を意味するalready_terminalとして処理せず、確認できた範囲と未確認を明示する。
  - [ ] AC-3: Given 利用者が未確認記録の解除を確定した場合, When 解除を反映しBEを再起動する, Then 対象は待機キューへ復活せず、上流取消の確認とは区別した解除記録が残る。
  - [ ] AC-4: Given 未確認ジョブが存在する場合, When 新しい生成を追加する, Then 新規生成が完了でき、二重投入や無関係なジョブの取消を起こさない。
  - [ ] AC-5: Given 後から上流識別情報が判明した場合, When 照合する, Then 承認された保持・解除仕様に従い結果を扱う。
- **Inferred points**:
  - 主分類Type Aは表示・取消判定の既存仕様逸脱。恒久解除操作の具体的な状態・APIは未決定。
  - ComfyUI自体が停止した根因は対象外で未確定。
  - 上記ACはバックログ要求であり、設計・実装・検証完了を表さない。
- **Design doc**: 未作成（開発開始の承認待ち）。
