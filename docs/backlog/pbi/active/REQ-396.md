- **現状確認（2026-10-26）**:
  - `frontend/e2e`の現行specは7件。アプリを開くのは`generateMobileGallery.spec.ts`、`headerHoverCard.spec.ts`、`headerMenuRoutes.spec.ts`、`stickyHeader.spec.ts`、`settingsResponsive.spec.ts`の5件である。
  - `headerMenuOverlay.spec.ts`は専用HTMLハーネスを開く。`serverManager.spec.ts`は`tests/support/server_manager_sandbox.py`で起動したManagerサンドボックスを開く。両者を単にファイル名で除外せず、アプリWSの発生有無と許可する通信先・理由を設計で確認する。
  - `routeWebSocket`の定義は`generateMobileGallery.spec.ts`の1箇所だけで、捕捉URLを記録する。既存の確認ケースは捕捉が1件以上あることとpathnameだけを確認しており、中継しないことの独立した証拠にはならない。他4件では共通WS遮断を確認できない。
  - Viteの`/api` proxyは`127.0.0.1:8000`へ`ws: true`で中継する。`scripts/run_e2e.py`はViteの起動/終了とworker=2を管理し、Playwright設定自体にwebServerはない。本件では並列度・実行基盤を無関係に変更しない。
  - `settingsResponsive.spec.ts`にもManagerサンドボックスの利用と別originのアプリ起動があり、単一のgotoだけを調べて適用済みとしない。`headerMenuOverlay.spec.ts`には条件付きskipがあるため、設計でケースID・条件・承認済み除外を整理する。
  - コード読取のみ。今回はE2E収集/実行、実バックエンドの稼働確認・停止、通信観測、退行注入は行っていない。2026-10-25のPASS/失敗記述は過去記録であり、現在の結果ではない。
- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `frontend/e2e` の spec は HTTP の `/api/*` だけを `page.route` でスタブし、WebSocket `/api/ws` を遮断していない（REQ-395 で直した `generateMobileGallery.spec.ts` を除く）。
  2. なぜその課題が発生するか: `page.route` は WebSocket を捕捉しない。Vite proxy（`ws: true`）が `/api/ws` を稼働中の実バックエンド（:8000）へ中継する。
  3. なぜ現状の仕組みで不十分か: 現時点では他の spec はバックエンド稼働中でも PASS する（2026-10-25 の Gate 3 全体実行で失敗は REQ-395 の 4 件だけ）。ただしアプリが WS の内容により強く依存すると、同じ環境依存の失敗が起きる。さらに REQ-395 の Red Team RT2 で、遮断の定義に中継（`connectToServer()`）を足しても、REQ-395 で追加した遮断確認ケースが PASS のままで、退行を検出できないことがわかった（検出したのは既存の [REQ-372] の 4 件だけで、他の spec には同様の検出手段がない）。
  4. なぜこのアプローチを採用するか: HTTP と WS のスタブを共通ヘルパーにまとめ、各 spec がそれを使うようにすれば、遮断漏れを構造的に防げる。遮断が実バックエンドへの中継に変わった場合に失敗する確認を持たせれば、バックエンドの稼働有無や個別specの画面期待値に頼らず退行を検出できる。捕捉URLの記録だけで遮断成立と判定しない。
  5. 根本原因: E2E spec のネットワーク隔離が spec ごとの個別実装に任されており、隔離が保たれていることを確認する手段も（1 ファイルの副次的な失敗を除いて）存在しない。

- **Requirement**:
  - **1. 共通の WS 遮断**:
    - `/api/ws` を `page.routeWebSocket` で遮断する共通ヘルパーを `frontend/e2e/` 配下に置き、アプリを読み込む全specから使う。各ケースの画面読込前に登録し、別origin・追加page/context・再接続も設計で調査して漏れを防ぐ。個別specが独自に`/api/ws`を扱う定義を持たない。ViteのHMR等の別WSと対象のアプリWSを区別する。
  - **2. 中継への退行の検出**:
    - 遮断が実バックエンドへの中継に変わった場合に、バックエンドの稼働有無に依存せず検出して失敗する確認を持つ。確認をどこに置くか（共通ヘルパー側か、各 spec 側か）は設計で決める。
  - **3. HTTP スタブの集約（設計で採否を決める）**:
    - HTTP の `/api/*` スタブも共通ヘルパーへ集約するか、WS 遮断だけを共通化するかは設計で決める（既存ケースのアサーション・件数は変えない）。
  - **4. 対処が必要な場合の警告（REQ-398から目的を引継ぎ）**:
    - 共通WS隔離の未適用・実バックエンドへの中継・隔離確認の不成立など、本PBIの隔離契約に反する状態を検出した場合に警告を出す。バックエンドのポートが開いていることだけを警告条件としない。
    - 警告には対象spec、対象通信path（例: `/api/ws`）、検出した異常と確認すべき設定を含め、stderrまたはテスト失敗レポートで実行者が確認できるようにする。認証情報や受信した実データは出力しない。
    - 警告はAC-6の退行検出を補助する診断であり、隔離違反のFAILを警告のみへ弱めない。バックエンド停止による接続失敗と、遮断が適用されたことを混同しない。
    - 隔離が正常ならバックエンド稼働中・停止中のいずれでも当該警告を出さない。警告の追加によって本来不要な実バックエンド接続、プロセス停止、DB操作を行わない。

- **5 Whys / Root Cause**:
  1. なぜ改修が必要か: `frontend/e2e` の spec は HTTP の `/api/*` だけを `page.route` でスタブし、WebSocket `/api/ws` を遮断していない（REQ-395 で直した `generateMobileGallery.spec.ts` を除く）。
  2. なぜその課題が発生するか: `page.route` は WebSocket を捕捉しない。Vite proxy（`ws: true`）が `/api/ws` を稼働中の実バックエンド（:8000）へ中継する。
  3. なぜ現状の仕組みで不十分か: 現時点では他の spec はバックエンド稼働中でも PASS する（2026-10-25 の Gate 3 全体実行で失敗は REQ-395 の 4 件だけ）。ただしアプリが WS の内容により強く依存すると、同じ環境依存の失敗が起きる。さらに REQ-395 の Red Team RT2 で、遮断の定義に中継（`connectToServer()`）を足しても、REQ-395 で追加した遮断確認ケースが PASS のままで、退行を検出できないことがわかった（検出したのは既存の [REQ-372] の 4 件だけで、他の spec には同様の検出手段がない）。
  4. なぜこのアプローチを採用するか: HTTP と WS のスタブを共通ヘルパーにまとめ、各 spec がそれを使うようにすれば、遮断漏れを構造的に防げる。遮断が実バックエンドへの中継に変わった場合に失敗する確認を持たせれば、バックエンドの稼働有無や個別 spec の内容に頼らず退行を検出できる。
  5. 根本原因: E2E spec のネットワーク隔離が spec ごとの個別実装に任されており、隔離が保たれていることを確認する手段も（1 ファイルの副次的な失敗を除いて）存在しない。
