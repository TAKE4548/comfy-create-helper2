## 3. 実装要件 (Implementation Logic)
以下の各 Acceptance Criteria および Red Teaming シナリオを検証する Vitest 自動テストケースを実装する：

1. **AC-1 テスト (新規作成時の前プリセット保護)**:
   - Preset A（ID: 101, prompt: "A orig"）アクティブ時に `createPresetMutation.mutate({ name: "B", paramValues: { prompt: "B new" } })` を実行。
   - `newPreset` 返却後、Preset A の `paramValues` が汚染されず、直後にも Preset A への `update` が呼ばれないことを検証。
2. **AC-2 テスト (タブ切替時の未保存変更フラッシュ保存)**:
   - Preset A を編集後、デバウンス時間満了前に Preset B へタブ切替（`handleSelectPresetTab(102)`）。
   - `workflowPresetsApi.update` が Preset A の編集パラメータで同期的に呼ばれ、変更が脱落しないことを検証。
3. **AC-3 テスト (他端末更新プリセット切替時の最新反映)**:
   - Preset B が他端末で更新された後、Preset B にタブ切り替えを行った際、最新のパラメータがロードされることを検証。
4. **AC-4 テスト (未編集プリセットの定期ポーリング再同期)**:
   - 未編集の Preset A に対してバックグラウンドポーリングで新データを受信した際、インメモリ値で破棄されず正しく更新されることを検証。
5. **AC-5 テスト (非アクティブプリセット更新時のパラメータ保護)**:
   - `updatePresetMutation` にて非アクティブなプリセット ID の更新を行った際、アクティブプリセットのパラメータが誤送信されないことを検証。
6. **Red Teaming テスト (高速連続切替 & 境界値)**:
   - A編集 → B切替 → C切替 と連続操作した際に、A の変更が確実にフラッシュされ、レースコンディションが発生しないことを検証。
