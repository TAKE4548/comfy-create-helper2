2026-10-14追加指示による承認済み手戻り。有効チェック変更/ID入力/保存時に全slotのhydrateと全候補scoreを再計算する遅延を測定・解消する。無効state/raw ID/未知state/legacy identity/REQ-359安定性は保持。チェック操作でHTTPを発生させず、保存1クリックはPUT1件だけ。初期化effectがsaving phaseをeditingへ戻さない。保存完了または失敗まで操作を二重発火できないようにする。

## Impacted Files

- frontend/src/hooks/useMasterMappingRows.ts
- frontend/src/components/RescanModal.tsx
- frontend/src/components/UploadWorkflowModal.tsx

- frontend/src/components/__tests__/WorkflowModalMultiStage.test.tsx
- frontend/src/utils/workflowNodeUtils.ts（初回採点の正規化・stage集合・bigram集合の重複処理だけを削減。スコア/順位規則を変更しない）
- frontend/src/utils/__tests__/workflowNodeUtils.test.ts（既存の全境界assertを回帰実行）

型や純粋helperのcontract確認のためworkflowMappingState.tsを読取可。workflowNodeUtils.tsは上記Impacted Filesの私有計算部分だけを編集可。その他sourceは編集しない。

API境界確認のためfrontend/src/api/client.ts、api/domains/workflows.ts、そこから参照するtransport/types contractを読取可。既存modal suiteの全体mockを不用意に変更せず、実update serializer/fetchを使う境界caseを追加する。全APIの実通信回数は隔離ブラウザで別途確認する。

候補scoreはworkflow/master/stage定義の変更時だけ算出し、slot enabled/選択値/phaseでは再計算しない。hookのdefinitions/hydrated state/rowsをmemo化し、状態復元は一度だけ実行する。候補rankの呼出回数、保存遅延中のdisabledボタン、実serializerのHTTP回数を境界testで確認。大きなfixtureで操作所要時間を修正前後測定し、CPUとnetworkを区別して報告する。

Verification Command (frontend cwd): `npx vitest run src/hooks/__tests__/useMasterMappingRows.test.ts src/components/__tests__/WorkflowModalMultiStage.test.tsx`
Typecheck: `npm run typecheck`

初回の全候補採点も別測定する。32 masters×9 stages/200 nodes、登録stage名の重複288件から9件へのdedup、title/stage正規化とcurrent bigramの事前計算で冗長な反復を避ける。mutable graphに対する永続cacheは導入せず、同じ入力のscore/tier/順序は保つ。benchmark: `.tmp/req358-browser-verify/rank-bench.cjs`。
