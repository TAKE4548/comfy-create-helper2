# REQ-333-T5: BE生成管理・normal group・scope状態機械

## Purpose and Ownership

注入RepositoryPort/GenerationPort/clockを使う常駐service。normal未終了集合が空→次受付で新group、Studioは毎batch独立。キャンセルは確認済みだけcancelled、failedは通知と終了数。VRAM既存get_vram_status入力/10秒通知をworkerへ移し数値維持。低VRAM時は既存の上流POST前ゲートを保持し、同じ警告は10秒間隔で通知（10秒ごとにポーリングする意味ではない）。queue空だけで完了にしない。

## Hermetic Contract

以下は承認対象の新contract。scopeとproject、上流client IDと利用者sessionは別。clientから完了状態を送らない。
受付はDB commit後202。上流POST結果不明はunconfirmed、自動再送なし。BE再起動完全復元を追加しない。
通常Nはcancelled除外、F=succeeded+failed。Studio各batch独立。別scope待機優先、他session待機はfilter ONだけ。
snapshotはepoch/revisionでatomic置換、eventも同じ形の全状態dataを使い部分mergeを避ける。SYSTEM_STATS/VRAM_RECOVEREDのtype/data・2.5秒周期保持。
既存30local/1000server metadata、Snapshot独立、Studio750ms/draft競合、画像aspectを保持。
カード外ファイルや公開contract変更が必要なら設計へ差し戻す。

### Cancellation Compatibility Contract (D7)

一括scopeはall|normal、mode=single|queued|allとは別軸。既定scope=allを維持。singleは選択job_id/prompt_id一方だけ、scopeを選択させずallのみ。表示filterは対象決定へ使わない。
all scope: queuedは全BE受付済み未投入＋全上流pendingをglobal clear:true、running保持。mode allは同clear後global interrupt、Studio/全session/legacyを含む。per-job loopへ縮小しない。
normal scope: 全sessionのDB job.scope=normalかつcutoff前commit済み未投入、またはDB prompt_idに正に対応付いた上流normal pendingだけ対象。削除はdelete:[確定ID群]、clear:true禁止、Studio/unknown legacyは触らない。推測client_id/表示行/残数からnormalを判定しない。
accept/dispatch/cancelを同じBE lockで直列化。normal allはID削除後に最新queueを再取得し、running又は上流pendingにStudio/unknownが1件でもある、queue照合不能、対象normalがrunningと確認不能ならinterruptを送らない。upstream_interrupt=skipped、messageで「Studio/未分類を保護するため通常実行中を維持」等の理由、正常終了前ならnot_cancelledを返す。全取消完了と表示しない。normal queuedはrunningに関係なく上記確定待機取消を行う。
最新queueが全件known normal、対象running一致、lock保持の場合だけnormal-running interruptを試行可能。直前一致検査を行うが、上流はexpected IDを受けず、外部legacy投入/上流自律切替/遅延到達とのTOCTOUを原子的に防げない。Studio保護の絶対保証と称さず、競合・timeoutはunconfirmedで明示、自動再送しない。既知保護対象がある場合は常に見送るという保守条件を優先。
未投入はlock下の取消commit、上流投入済みは正常ack＋queue/history/terminal照合で確認。queue不在/旧HTTP200 status:errorだけを証拠にしない。成功/失敗先行は終端を優先。normal Nはconfirmed cancelledのみ除外し重複減算なし、操作のfailed/unconfirmed/skippedをjob失敗へ変換しない。cutoff後の新BE受付は次集合、上流global clearは実行時集合、分散atomicではない。
Studio batch F=成功+失敗、取消非加算、12成功+8取消は12/20停止。cancelled終端でrunning flags解除、Step移動/auto-advanceなし。confirmed cancelに失敗トーストなし。running履歴cleanupは取消確認後best effort、先行完了履歴/保存Snapshotを消さずcleanup失敗で取消を戻さない。

AC-36/FC15–19: default all、normal指定ID削除、Studio/unknown running/pending barrier interrupt0、known-normal限定試行、skipped非完了、scope/結果型parityを局所検査する。

### Upstream history/event contract

`GenerationPort.history(prompt_id)` はT6 bridgeの追加DTOではなく、Comfy標準mapping `{prompt_id:{outputs:{node_id:{images:[{filename,subfolder,type}]}},status:{completed,status_str,messages}}}` を受ける。serviceは既知prompt_idだけを照合する。成功は `completed=true` とsuccess status/evidenceの両方、失敗は `execution_error` またはstatus errorを要する。queue不在だけではterminal化しない。`execution_interrupted` は既知cancel操作に結び付く場合だけ取消として扱う。

history画像は `filename/subfolder/type` を保持し、`/api/comfy/view` と `/api/comfy/thumbnail` の既存query（filename/subfolder/type）をURL encodeして構成する。`t=prompt_id` metadata keyは保持し、`node_id/index` はImageView DTO項目のみでURL queryへ追加しない。Comfy historyに出力画像があることだけでは原画存在を確定しないため、初期availabilityはunknown。`execution_success` event時はhistoryを取得しoutputsを保存してからterminal snapshotをpublishする。progress/preview eventは既知prompt_idへ対応づけ、payloadにIDがない形式は現在の上流runningを検証できた場合だけ関連づける。executed image event単独でterminalにしない。

T10 lifespanはbridge.start(service.on_event, service.on_preview)をwireし、shutdownはbridge.stop後service.stopを呼ぶ。on_eventはknown prompt_idのexecution_start/executing/progressをrepositoryへ反映し、初回running時刻とnode progressを更新してsnapshotをpublishする。node titleは凍結graphの`_meta.title`/`class_type`から取り、現在のformを参照しない。IDのないeventは検証済みcurrent upstream runningが一意の場合だけ結び付ける。on_previewはpreview frame bytesを永続化せず、状態revisionを更新してHTTP preview URL cacheが更新されるようにする。`_snapshot`はbridge.get_upstream_state()のlive http_ready/ws_connected/failure_sinceをrepository stateへoverlayして返し、DBへ永続化しない。GET/publishは同じservice snapshotを使い、T10でhealthを二重合成しない。probe failureのfirst failure timestampはHTTP成功まで維持する。raw binaryはGenerationSnapshotへ含めない。

## Local Verification

### 待機取消の確認と対象なし操作

標準Comfyの待機delete/clearはexecution_interrupted履歴を作らない。
待機取消は正常ACK＋直前pendingでの対象確認＋正常な操作後queueでrunning/pending双方から消失＋正常history照会で先行成功/失敗なしを組み合わせて確認する。
queue不在だけ、ACKだけ、照会失敗、pendingからrunningへの競合は未確認のまま保持。
single/queued global/normalの3経路とlegacyで同条件。実行中interruptは既存terminal証拠を必要とし、この補正を流用しない。
historyの成功/失敗は取消より優先、対象不明/再投入推定はしない。分散原子保証は追加しない。
空queueを操作前後に正常確認でき、global clear→interruptの正常ACKが得られたall操作は「対象なし確認済み」とする。照会不能なら未確認。
操作前が待機だけの場合も、その全対象が既述条件で取消/先行終端確認済み、実行中対象なし、正常ACKと操作後空queueを確認できれば中断対象なしの効果を確認済みとする。
試験はdeleteで履歴を捏造せず空historyとする。ACKerror/timeout、操作後running、history503、先行成功、重複取消、空allを含む。

wire revision具体化: Serviceの合成snapshot（DB job状態＋live上流状態）が変わった時だけ単調revisionを進める。
同じ内容のGETでは増加せず、repositoryの保存revision/transactionは変更しない。epochはService寿命のnamespace。
HTTP/WS healthやfailure_sinceの変化もjobが0件でもpublishする。同revisionで異なる状態を送らない。
202受付はcommit根拠を返し、後続snapshot read失敗で取り消さない。lookupはwire snapshotに依存させない。

VRAM待機取消の具体化: `async cancel_unsubmitted(job_id:str)->CancelResult` を追加する。
同じaccept/dispatch/cancel lock内で、管理jobのstatus=queuedかつprompt_id=NULLの場合だけpendingから除外しcancelled保存。
上流投入済み/実行中はnot_cancelled、既存terminalはalready_terminal。上流queue/delete/interruptを一切呼ばない。
存在しないIDはrejected（routeは既存404規約に対応）。確定取消後にsnapshotをpublishし、重複取消は二重減算しない。
これは旧VRAM wait abortの「将来未投入だけ停止」をBE受付後でも維持するguard。他request/Studioを巻き込まない。
T10の単件cancel endpointのonly_unsubmitted=true query時のみ使用し、通常単件/一括modeは変更しない。

3/8→3/7、4/8、Studio13/20と別batch不変、N=0、VRAM待機取消、global queued/allはStudio/他session/legacyを含む。同request replay同IDsでsubmit重複なし、terminal replay不再送、snapshot dict callback、started_at初回running固定、legacy prompt single pending/running route、upstream live HTTP/WS health overlayとHTTP失敗timestampの維持/成功resetを検証する。
