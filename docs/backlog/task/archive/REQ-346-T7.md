# REQ-346-T7: 実ブラウザでの展開アクション契約検証（ヘッダー下・末尾到達・resize・将来アクション） (AC-1〜6, AC-8)

## 設計改訂（2026-10-16・実ブラウザ所見 R1〜R3。着手済みの spec／ハーネスを下記に沿って修正する）
最初の実行で 8 件が失敗した。人間決定により契約と検証を次のとおり改訂した（設計 `docs/design/REQ-346.md` §4 HEO-2／HEO-3、改訂履歴 R1〜R3）。**前提: T11（純関数）・T12（`HeaderDropdown`）・T13（`PageHeader` の `data-page-header-root`）・T14（`ResourceHoverMonitor` の `hoverBridge`）が完了していること**。未完了なら AC-1 系が失敗するのは実装側の未完了であり、本カードで検証を弱めない。
- **R1（全パネルの上端＝ヘッダー下端＋6px）**: 以前の「パネル上端 ≥ トリガー下端」は不十分。**パネル上端がヘッダー下端＋6px（±1px のサブピクセル）であること、かつトリガー下端以上であること**を A1〜A4・future の全アクション×全幅で判定する。ヘッダー下端の基準は `[data-page-header-root]` 要素の bbox.bottom（ハーネスでは `harness-header` の bbox と一致するが、契約の目印そのものを使う）。モバイル（375／639）ではヘッダー下端が約118（`actions` 折り返し 2 行目を含む）で、ピルのパネルもそこまで下がる。
- **R2（AC-3）**: workflow パネルは 4 項目で `scrollHeight == clientHeight`（約225）のため、**「あふれていること」を assert しない**。workflow は「`maxHeight` 内に収まる（`panel.bottom <= h - 8 + 0.5`）」と「最後の項目に到達できる（`reachLast`）」のみ判定する。**あふれ（`scrollHeight > clientHeight`）と「末尾までスクロールして到達」の判定は高い `future`（40項目）アクションのみ**で行う。高さ 280 では workflow がヘッダー基準の `maxHeight`（約216）を超えて内部スクロールになる場合もあり、いずれの場合も `reachLast` は成立すること。
- **R3（ケバブ）**: 768px 未満のケバブはボタンが 44px のヒットスロップを持つ。R1 により `p.y >= t.bottom`（t はボタン bbox）は構造的に満たされる。弱めずそのまま判定する。
- **resize 追従（AC-6）**: 各 resize 後に `expect.poll` で「パネル上端＝ヘッダー下端＋6px（±1px）」も判定する（1280→375 でヘッダー高さが約50→118へ変わる）。

共通ヘルパー（spec 内ローカル）: `openHarness(page, w, h)`（`stubApi`＋`setViewportSize`＋`goto('/e2e/fixtures/header-menu-harness.html')`＋`harness-header` 可視待ち）、`headerBottom(page)`（`harness-header` の bbox.bottom）、`reachLast(page, a)`（`panel.evaluate(el => { el.scrollTop = el.scrollHeight })` → `last` の bbox が `0 <= y` かつ `y+height <= viewportHeight` → `last.click({ trial: true })`（受信可能性）→ `elementFromPoint` が `last` 自身か子）、`layoutSnapshot(page)`（`harness-header` の高さ、`harness-main`/`harness-root`/`documentElement` の `scrollHeight`）。`maxWidth` を超える幅の `pill` は `test.skip`。

テスト（すべて `[REQ-346/AC-n] …` 命名、`for (const a of ACTIONS)`／`for (const v of VIEWPORTS)` でループ）:
1. `AC-1`: 各アクション×各幅（高さ通常）: 開く→ `panel.bbox.bottom > headerBottom`、**`Math.abs(panel.bbox.y - (headerBottom + 6)) <= 1`（ヘッダーに重ならない）**、`panel.bbox.y >= trigger.bbox.bottom`。`headerBottom` は `[data-page-header-root]` の bbox.bottom。
2. `AC-1`（押し広げ無し）: 開く前後で `layoutSnapshot` の各値（ヘッダー高さ・各 `scrollHeight`）の差が 1px 以内（サブピクセル丸めのみ許容。押し広げは数px以上の差として検出される）。
3. `AC-2`: ヘッダー下端より下にある `click` 項目をクリック→ `__events` に期待イベント（`event: null` は閉鎖確認）。クリック前に項目 bbox.y > headerBottom を assert。
4. `AC-3`: 高さ `SHORT_H`(360) と Red Team 高さ 280 で、`future` と `workflow` について `maxHeight` により `panel.bbox.bottom <= h - 8 + 0.5` と `reachLast` が成立。**`panel.scrollHeight > panel.clientHeight` を assert するのは `future` のみ**（R2。`workflow` はあふれの有無を assert しない）。
5. `AC-4`: トリガー再押下で panel が非表示（`count() === 0`）。外側クリック（`harness-main` 上）でも閉じる。
6. `AC-5`: 各幅で panel bbox が `x >= 0` かつ `x+width <= viewportWidth`（8px 余白を許容）、panel 左上+(10,10) の `elementFromPoint` が panel 内（`harness-tabs` z10／`harness-progress` z40 に隠されない＝重なり順の実測）、`reachLast` 成立。
7. `AC-6`（resize while open）: (a) 1280×800 で `workflow` を開く→ `setViewportSize({width:375,height:360})`→ `expect.poll` で `reachLast` 成立**かつパネル上端＝ヘッダー下端＋6px（±1px）**。(b) 375×667 の `pill` → 600×400 でも開いたまま到達可、→ 800×400 で閉じる（640px 境界）。(c) `future` で 1280×800→768×1024→375×360 を連続変更。
8. `AC-8`: `future`（40項目）で上記 1–6 が通ること（ループに含まれる）。末尾 `future-item-39` が画面内でクリック可。
9. Red Team（AC対象外・非ブロッキングの情報採取ではなく**合否判定する**）: 幅 320×667 で全アクションの panel が左右 `>= 0` に収まる、高さ 280 で `reachLast` 成立、連続トグル10回後にパネルが1つ以下（`[data-header-menu-panel]` の数）、別アクションを開くと前のアクションが閉じる。
10. A4（hover 型）のハーネス上の重なり順確認のみ（A4 の AC-1〜6 個別の完全マトリクスは T10 が実ルートで判定。ここで重複実装しない）: 幅 >= 640（640／768／1024／1280）で `resource-hover-monitor` に hover→ `resource-hover-card` の bbox.bottom > headerBottom **かつ `|card.y - (headerBottom + 6)| <= 1`**、viewport 内、パネル左上+(10,10) と中心の `elementFromPoint` が card 内（`harness-tabs` z10／`harness-progress` z40 に隠されない）。幅 639 ではカードが可視にならず、`[data-header-menu-bridge]` も 0 件（カード非描画時はブリッジを出さない）。
