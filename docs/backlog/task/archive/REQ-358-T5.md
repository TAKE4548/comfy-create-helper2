## Implementation Logic

本Taskの製品変更はtypes.tsだけ。追加fieldをoptionalにして既存読込fixture/作成・更新payloadを保持する。
workflowsApi.create/updateはunknownをJSON.stringifyしgetはrequest<Workflow>を返す既存透過経路。
APIドメイン/core/requestの変更やworkflow POST/PUT/GET通信caseは本Taskの対象に追加しない。
mappingApi.test.ts内に独立したdescribe('REQ-358/API_TYPES')を追加し、API呼出しやfetchを使わず型契約を確認する。
既存suiteのtransport mockやcaseは変更しない。

許可する検証（AC-19/26/31の型境界の部分証拠）:
- Workflowの追加fieldなし旧fixture、WorkflowCreate旧payload、WorkflowUpdate={}が型適合する。
- 上記型のmapping_slot_statesがRecord<string,boolean>|undefinedで、{'v:1':false,'m:2':true}を受け入れる。
- master読込/作成/更新の既存型でdefault_enabledがboolean|undefined、falseを受け入れ、省略可能である。
- expectTypeOfで対象追加fieldの厳密型を照合し、必要なら@ts-expect-error付きのnull/不正型例をコンパイラで検証する。
- 旧読込の呼出側の互換形として(master.default_enabled ?? true)と(workflow.mapping_slot_states ?? {})を型付きfixtureで確認する。
  これは型と既定形の証拠であり、実際のhydrate既定はT7、サーバ既定はT2/T3/T4で検証する。
