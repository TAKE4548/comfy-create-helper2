# REQ-309-T3

## Scope and AC
`frontend/src/pages/GeneratePage.tsx` が静的 import している 10 種のモーダル/パネルを `LazyModalHost`（T1）経由に置換し、初期 `/` の Generate chunk から外す。対象 AC: AC-1、AC-3、AC-4。Desktop/Mobile レイアウト（`DesktopLayout`/`MobileLayout`）は **遅延化しない**（設計書の代替案 D 参照。レイアウト内の `GenerateModalsOverlay` は T4）。API・store・hook は変更しない。
**AC 分担**: AC-2（警告）は T2 の route 分割と本カードの縮小が寄与し、判定は T5 `buildGuard`。AC-5/AC-6 の画面遷移は T2/T5、overlay の 4 モーダルは T4、SSoT は T6。本カードは History/Settings 側のコードに触れないため、AC-5/AC-6 への影響は T2/T5 の全 route 検証で確認する。

## 変更規則
loader はモジュールレベル定数（例: `const loadJobManagementModal = () => import('../components/JobManagementModal').then((m) => ({ default: m.JobManagementModal }))`）。`LazyModalHost`（`mode`/`isOpen`/`load`/`modalProps`/`onClose`/`label`）で次のとおり置換する。**現行の mount 寿命を保つ**ことが要件。
| モーダル | mode | isOpen に渡す式 | 現行 |
|---|---|---|---|
| AddSnapshotToAlbumModal | latch | `isSaveModalOpen`（modalProps にも `isOpen` を含める） | 常時 mount |
| HistoryModalPreview | latch | `isModalPreviewOpen` | 常時 mount |
| JobManagementModal | latch | `isJobModalOpen` | 常時 mount |
| ProfileBulkEditModal | latch | `isBulkEditOpen` | 常時 mount |
| PresetConflictModal | latch | `!!state.conflictData` | 常時 mount |
| RescanModal | while-open | `rescanOpen && !!workflow` | 条件 render |
| UploadWorkflowModal | while-open | `uploadModalOpen && !!uploadedJson` | 条件 render |
| WorkflowManageModal | while-open | `!!workflowManageMode && !!selectedWorkflowId` | 条件 render |
| SceneGeneratorModal | while-open | `isSceneGeneratorOpen && !!selectedWorkflowId`（modalProps の `isOpen: true`） | 条件 render |
| PresetManagerPanel | while-open | 外側の overlay `div`（`data-testid="preset-manager-overlay"`/`-modal`、背面クリック閉じ）は **静的に残し**、内側のパネルだけをホストで包む。ホストは overlay の内側なので `isOpen={true}`、`onClose` は `() => setIsPresetManagerOpen(false)` | 条件 render |
`label` は各モーダルの利用者向け名称（例: 'ジョブ管理'、'履歴プレビュー'、'プリセット管理'）。LoRA 設定のインライン modal・一括削除確認ダイアログは静的のまま。`GeneratePage.tsx` に上記 10 モジュールへの静的 import を残さない。props の並び・値・コールバックは現行のまま渡す。

### 共通前提（isolation-safe。`mountFreshGeneratePage` に必須。attempt 2 の 2 件失敗の根本原因）
**preset 一覧を固定する**。`vi.mock('api/client')` の `workflowPresetsApi.list` は既定で `[]` だが、このファイル先頭側の `[REQ-186/AC-1,2]` が `mockResolvedValue(presetsData)` を設定し、`vi.resetModules()` 後もこの mock 実体は引き継がれる（factory 結果が再生成されない。全体実行では Alpha/Beta が見えることを実測）。そのため **全体実行では一覧が非空、`-t` 単独では `[]`** になり挙動が分岐する。`[]` だと `usePresetStoreSync.ts:410-413` が `handleCreatePreset('Set 1')` を呼び続け（`create` mock は `{}` を返すので一覧が増えず `isCreatePending` が戻るたびに再発火）、(a) `usePresetStoreSync.ts:256` の `setSets(mappedSets)` が `sets` を `[]` に置換して Generate に checked セットが無くなり（`useGenerateAction.ts:313-316` で「生成対象のセットが選択されていません」を出して `submitBatch` 未呼出）、(b) 再 render が 250 commit/回で指数的に増えて jsdom が 30 秒超ブロックし `findByRole('dialog')` が 5 秒で時間切れになる。アプリ側の不具合ではない（`usePresetStoreSync` は未変更で lazy 化と無関係。実 API は id 付き preset を返す）。
`mountFreshGeneratePage` の `qc.setDefaultOptions(...)` の直後に次を追加（`LS_KEYS` は import 済み）:
```tsx
const presetFixture = [{ id: 101, workflow_id: 1, name: 'Set 1', param_values: {} }];
vi.mocked(freshApi.workflowPresetsApi.list).mockResolvedValue(presetFixture as never);
localStorage.removeItem('prompt-surgeon-checked-presets-1');           // usePresetStoreSync.ts:127
localStorage.removeItem(`${LS_KEYS.ACTIVE_SET_PREFIX}1`);              // usePresetStoreSync.ts:261
qc.setQueryData(['workflow-presets', 1], presetFixture);
```
preset は **1 件**（2 件だと `items[0]` が active でない set になり得る）。`freshApi` は `mountFreshGeneratePage` 内の `import('../../../api/client')` の結果（既存変数）。他の期待値・タイムアウト・手順は変えない。診断のヒント: REQ-309 の 6 ケースは単独でも各 1 秒前後で終わる。1 ケースが 5 秒超なら render storm（`workflow-presets` の invalidate ループ）を疑い、タイムアウトを延ばさず fixture を確認する。

### while-loading の閉じ方（`modal-open-close-while-loading`）

### act と gate（4. の原因）
コードからは原因を確定できない（未確認）。観測事実: T1 の `await act(async () => { deferred.resolve(...) })`（`LazyBoundary.test.tsx:200`）は成功し、本ファイルの gate 解放は後続で `importOriginal()`（vitest の実モジュール読込）を待つ点だけが異なる。React 18.3 + RTL 14 の `act` は外部の読込完了を待たない設計のため、gate 解放を `act` に包む利点は無い。確定パターンは上記「gate 解放」（素の `release()` + `findBy*`/`waitFor`）。`findBy*`/`waitFor` は RTL の asyncWrapper が act 環境を外して待つ。
既存ケースで modal を同期 `getBy*` する箇所（`[REQ-112/AC-5]` `[REQ-186/AC-1..3]` `[REQ-363/AC-4]` のプリセット管理ほか）は `findBy*`/`waitFor` に直す（期待値そのものは変えない）。
