# REQ-394-T5: 遅いテスト上位の待ち要因（AC-1）

## 実行境界

- 役割は engineer / dev-task。FE のコマンドは `cd frontend` してから実行する。`PYTHONDONTWRITEBYTECODE=1`。
- 所有ファイルは上記 4 つだけ。**製品コード（`frontend/src/utils/queryCachePersister.ts` を含む）は変更しない。** `vite.config.ts`、`setup.ts` も変更しない。
- 前提: T4 が完了していること（`queryCachePersister.test.ts` の 1 行目に docblock が入っている）。コーディネーターが設計承認を確認し、exact-ID で in-progress へ遷移済みであること。状態更新・QA・commit は担当外。
- UI 制約: 該当なし（テストのみ）。
- **禁止**: アサーションの削除・緩和、`it.skip`/`it.only`/`it.todo` の追加、テスト件数の増減、期待値を実装から逆算して書き換えること。

## 計測済みの上位（8 並列、`fe-exp-E13-top.txt`）

| テスト | 時間 | 第一候補の原因 |
| --- | --- | --- |
| `residualHistoryRestore.test.tsx` 「caps pagination at 20 pages/200 items…」 | 5.5s | 20 ページ × 10 件の再描画（描画コスト）。`waitFor(..., { timeout: 15000 })` は上限であり待ちではない |
| `queryCachePersister.test.ts` 「rejects expired clients…」 | 4.0s | `persistClient` の書込みデバウンス 1000ms を実タイマーで 4 回待つ |
| `queryCachePersister.test.ts` 「round trips only after transaction completion…」 | 2.0s | 同上（2 回） |
| `apiCacheStorage.test.tsx` 「[REQ-332/AC-2] updates workflows with an exact 4 MiB…」 | 2.0s | 大きい payload の直列化/IndexedDB、およびデバウンス |
| `queryCacheRecovery.test.tsx` 「AC16/17…」ほか約 1.0s が複数 | 2.0s / 1.0s | デバウンス 1000ms |

製品側の根拠（参照のみ。`frontend/src/utils/queryCachePersister.ts` 付近）:

```ts
const batch = { client: copy, waiters: [resolve], timer: undefined as unknown as ReturnType<typeof setTimeout> }
batch.timer = setTimeout(() => { void flush() }, 1000)   // persistClient は 1000ms 後に flush される
```

同ファイルの既存テストが使っている fake timers の型（そのまま踏襲する）:

```ts
vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })
...
await vi.advanceTimersByTimeAsync(999)   // まだ flush されない
await vi.advanceTimersByTimeAsync(1)     // flush される
```

## 手順

1. 各対象テストの待ち要因を、計測（`--reporter=verbose` と `performance.now()` による一時的な区間計測。コミットしない）で次のいずれかに分類する: (a) 実タイマー待ち（デバウンス・setTimeout）、(b) IndexedDB（fake-indexeddb）の非同期、(c) React の描画/再描画コスト、(d) `waitFor` のポーリング（既定 50ms 間隔）、(e) その他。分類と根拠（秒）を `docs/logs/REQ-394/fe-slow-tests-analysis.md` に書く（git 管理外）。
2. (a) が原因で、fake timers に置き換えてもアサーションが同一のまま成立する場合に限り、`vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })` と `advanceTimersByTimeAsync` に揃える。`afterEach` で `vi.useRealTimers()` に戻す（既存ファイルの `afterEach(() => { ... })` に既にあれば流用する）。fake-indexeddb の内部スケジューリング（`setImmediate`）を巻き込まないよう、`toFake` は上の 2 つに限定する。
3. (b)(c)(d) が原因なら変更しない。理由を分析ファイルに記録する（描画コストは製品側の再描画量の問題であり、本 PBI の範囲外。フォローアップ候補として報告）。
4. 変更前後で同じ負荷条件で対象 4 ファイルを `--reporter=json` で比較する。
