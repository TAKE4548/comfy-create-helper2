## Required contracts

- ManagerActionResultへ後方互換のoptional outcome?: 'accepted' | 'unconfirmed'を追加する。拒否bodyのrequest_sent/code/errorはunknownから厳密にvalidateし、未送信と確認できないbodyを確定拒否へ推測しない。
- ManagerActionNameへfree-memoryを追加。systemManagerApi.freeMemory(): Promise<ManagerActionResult>はaction='free-memory',service='comfy'を固定し既存POST :8899/api/actionを使用する。既存actionメソッドと旧start/stop/restartの挙動を維持する。
- comfyの追加状態型: execution_state?: 'idle'|'executing'|'queued'|'unknown'、queue_running?: number|null、queue_pending?: number|null、execution_error?: string。欠落した旧応答はunknown扱い。不正な追加fieldをidleへ推測しない。新応答は非負整数のcountとstateを整合検証する。
- free-memoryの200/status=ok/outcome=acceptedを受付成功とする。409/503かつ有効body request_sent=falseは確定拒否としてerror文字列を表示する。通常actionの既存503/504/ネットワーク失敗未確認規約を維持する。free-memoryの504/status=timeoutまたは通信結果不明もManagerActionOutcomeUnknownError。自動再送しない。
- ServiceConnectionCardのComfyUI行へメモリ解放を置く。Manager available、comfy.status==='LISTEN'、execution_state==='idle'、countが共に0、busy false時だけ有効。停止/生成中/キュー待機/状態不明の理由を隣接表示する。disabled button titleだけで説明しない。
- busyRefを同期setして連打を防止し、他サービスaction_in_progressにも従う。要求送信中は『解放要求を送信中』、成功は『解放要求を受け付けました。空き容量は監視値で確認してください』。POST成功は物理完了・解放量ではない。
- 成否後に既存refetchでManager状態を再取得する。成功後はQueryClientのsettings-vram queryもinvalidateする。stop/restart確認、ログ、URL読み取り専用、8899 host/Origin境界は維持する。
- VRAMは接続中の既存SYSTEM_STATS（2.5秒）を優先する。systemWsConnected=falseなら古いstore値を最新として優先せず、表示中のVramGuardSectionでsettings-vram queryを2.5秒pollする。retry=false、background pollなし。Backend monitor2.5秒と合わせ正常時最大5秒で取得値へ追従する。
- query取得失敗やmonitor値不明は『VRAM情報を更新できません』を表示する。直前値を残すなら最新でない旨を示す。WS回復/次取得で解除する。既存dirtyRef/draftRef/保存規約を維持し、pollが未保存閾値とenabledを上書きしない。
- UI分類: Forms & Controls + Shell。操作域44×44px、relative Hit-Slopを使う場合は隣接領域へ重ねない。touch-manipulation、flex-wrap、長い理由break-words、11px以上の個別文字サイズ。重要な状態をtruncateしない。新modal・生vh・global font floorを追加しない。

## Response and recovery boundaries

ブラウザーUIはSettings/Managerの両方とも8899の既存/api/actionを使い、Managerが常にJSONを返す。ComfyUIネイティブ/freeだけが空本文HTTP200を返し得る。Managerはこのnative応答を{status:ok,action:free-memory,outcome:accepted}のJSONへ包む。外部localツールのloopback8188直接利用は別consumerで、Managerのguardを経由しない。通常のLANブラウザー/スマートフォンへ8188接続を要求しない。

UIは応答直後に『解放要求を受け付けました。空き容量は監視値で確認してください』というacknowledgementを表示する。『完了』『解放成功』とは表示しない。解放後にも古い/高いVRAM測定値が残り得るため、数値は監視で取得した測定値として表示し、低下を検出して完了を宣言する永続的なcompletion detectorは追加しない。応答後はfresh GET statusが既知idleかつcounts0/0と確認できる場合だけ再有効化する。unknownはdisabledのまま、後続GETで既知idleへ回復した場合だけ解除する。古いidle cacheでunknownを上書きして操作可能にしない。

同一タブはクリック直後のbusyRef/isActionPending、別タブはManager共通_active_action lockで排他する。先行actionの実行中に別タブactionが到達した場合はHTTP409、code=ACTION_BUSY、request_sent=falseを必ず返す。キューイングしない。試験では異なる2clientから同時要求し、2件目409/ACTION_BUSYとnative POST1件をassertする。

自動再送禁止は操作POSTだけ。background status/VRAM GET pollとWS再接続は継続し、操作POSTを再生しない。WS切断時はGET statusとVRAM refreshだけ行う。実ComfyUIの/free処理とGET /queueの間は外部clientの新規投入に対して非原子的であり、完全な外部排他は保証しない。
