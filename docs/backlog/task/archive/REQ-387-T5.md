# REQ-387-T5: 実 bridge/service/repository/router 統合シナリオ

## 実行境界

- 役割は engineer / dev-task。所有ファイルはテスト1本だけ。プロダクションコードは変更しない。閾値を満たせない場合はコードを直さず、計測値を添えて ESCALATE_TO_DESIGN で返す。
- 前提: REQ-387-T2 / T3 が done であること。本 Card は coordinator により exact-ID で in-progress 済みであること。
- 上流は既存の `LocalUpstream`（httpx.MockTransport）と、既存テストと同じ実 WebSocket サーバ（`websocket_serve`）で切る。service/repository/bridge の内部メソッドを monkeypatch しない。
- テスト名は `test_req387_acN_<内容>`、docstring 1行目は `[REQ-387/AC-n] ...`。

## 既存の土台（同ファイル）

- `_integration_app(tmp_path, upstream, *, bridge_url=..., start_bridge=False) -> (app, service, bridge, sessions)`: tmp file SQLite + 実 `GenerationRepository` + 実 `ComfyGenerationBridge` + 実 `GenerationService` + `generation_api_router`/`ws_api_router`。
- 実 WS 上流の起動例は `test_real_bridge_service_repository_router_accepts_and_completes_without_browser`（`websocket_serve(upstream_ws, "127.0.0.1", 0)` → `bridge_url=f"http://127.0.0.1:{ws_port}"`、`start_bridge=True`）を参照する。
- プレビューフレームの wire 形式（bridge `_handle_binary_message`）: `struct.pack(">II", 1, 2) + png_bytes`（event_type=1、image_type=2 → image/png）。bridge は `GET /queue` の running が1件のときだけ、その prompt_id へ紐付ける。

## シナリオ準備

1. `sessions()` で `GenerationJob` を直接 INSERT する。
   - 終端 succeeded 1000件（batch 3件単位、metadata_json 各約27KB。`{"workflow_id":1,"param_values":{"__prompt_surgeon_metadata_v1": json.dumps({"version":1,"fields":[...]}), "pad": "x"*26000},...}`）
   - accepted_at は過去の時刻を順に割り当てる。
   - `AppSetting(key="generation_revision", value="1")` を投入する。
2. lifespan 内で `POST /api/generation/batches`（`_batch()`）を受け付け、worker の投入で `prompt-1` が付くまで待つ（既存 `_eventually_state` を使う）。
3. `upstream.running = [[0, "prompt-1", {}, {}, []]]` にして running を確定させる（既存テストの running 行形式に合わせる）。

## テスト

- `test_req387_ac3_event_loop_lag_and_preview_latency_with_1000_terminal_jobs`:
  - 10ms 間隔で `loop.time()` の実遅れを記録する tick タスクを起動する。
  - その間に、実 WS からプレビューフレームを30枚（間隔 30ms）送る。
  - 並行して `GET /api/generation/state`、`GET /api/generation/preview/{job_id}`、`GET /api/generation/upstream-queue` を各10回呼ぶ。
  - 判定: tick の最大遅れ ≤ 150ms、preview 応答の最大 ≤ 300ms かつ 200 + `image/png`、`/state` の jobs 件数 ≤ 1 + 20 batch × 3。
- `test_req387_ac2_preview_frames_do_not_reload_generation_jobs`:
  - engine に `before_cursor_execute` リスナー（`sessions.kw["bind"]`）を付け、プレビュー30フレームの区間で `generation_jobs` を FROM に含む SELECT の回数を数える。
  - 判定: フレーム数に比例して増えない（区間の revision 変化回数 + 2 以下）。
- `test_req387_ac4_cancel_returns_within_budget_while_previews_stream`:
  - フレーム送信中に `POST /api/generation/cancel` を呼ぶ。対象は単件（running の job_id）、次に一括 normal。
  - 応答時間 ≤ 2秒、HTTP 200、結果の outcome が既存 cancel テストと同じ種別集合に入ることを確認する。
