## Implementation Logic

- [ ] useIsRestoring=false、非空persist baseline、有効初回generationSnapshotを待つ。persist baselineなしは要求をskipしcomplete。tab/filter/viewport独立、1document reload epochで1logical sync。QueryClient単位の共有epoch実行記録を持ち、route再mountでも自動再開しない。既存cache初期化で復元を消去しない。
- [ ] 最新両query/store/Mからknown生成、examined初回[]。T8 residualHistoryを逐次呼ぶ。items/rejectedをexaminedへ追加、has_more継続。最大20page/200検査、容量不足/上限はpartialで終了。
- [ ] Snapshot/generationSnapshot初回の過去出力を未確認で追加しない。live executedはT3のmissing保護を経由。query/allstore/batchを最新stateへ追加mergeし、selectedImg/selectedIds/modalへ同期から書かない。
- [ ] presentをcontroller.adoptしてからT9merge。missing rejectedをsame-origin/view URLに組み立てadoptしてpage lock。unknown新規は追加保留。adoptがpending/既存missingを上書きしない契約。
- [ ] 複数page受信順をpriorAddedIdentitiesへ蓄積。race到着のCは再比較し1件。ownは確定sessionのみ、Dにない画像だけ追加。
- [ ] focus/visibilityのfetchHistoryはchecking中に開始しない。同期完了後の既存明示更新は別でT3のmissing filter維持。residualの結果をhistory-fetched全件eventへ変換しない。
- [ ] errorは既存/適用済みpageを保持。自動retry/fallbackなし。明示retryだけ新同期、unknown再検査可能。空page+has_more/不正responseで停止。
- [ ] `has_more=true` のpageに、現時点のall/own display identitiesへ新たに追加できるidentityが1件もない場合（全件がknown/examined、unknown/missing、または200枠満杯で除外）、pageを処理後に追加POSTをせず `partial` で停止する。unit testで初回応答の新規identityをexaminedへ記録した後の明示retryが1回のPOSTで止まること、および20-page cycle後にknown Bだけが返った場合もretryが1回で止まることを検証する。
- [ ] API pageが現在の表示済みidentityを異なる`t`付きview_urlで再返却してもidentityで重複排除し、既存表示URL・順序・選択を保持する。live cache更新がpage待機中に届いた場合も、同じidentityは1行だけ残る。unit testでcanonical same-origin URLに対して確認する。
- [ ] StrictMode reconnectは同owner/同世代Promise共有。真unmountは同一turn reconnect猶予後abort/失効、late store/query書込0。復元未完了unmountは要求0。
- [ ] unitは実QueryClient+persist復元barrierでstart順、0fullGET/0置換event、multi-page、Mlate race、unknown/fail/nullsession、StrictMode、leave、selection保持を確認。
