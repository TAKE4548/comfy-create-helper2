# REQ-432-T4: VRAM ガード仕様の SSoT 改訂

## 1. 概要と目的
現行 SPEC_GENERATE.md L478 は「空きVRAMが安全基準値を下回る場合、受付済みrequestを維持して上流投入を保留する」とだけ定め、自セッション（ComfyUI）残留の扱いを規定していない（Type B 仕様欠落、実機計測で確定）。REQ-432 の設計決定（自セッション残留をガード判定から除外、自動 /free は不採用、primary LUID 限定、判定直前の新規取得、保留理由の区別）を SSoT に反映する。

## 2. ターゲット識別
- `docs/specs/SPEC_GENERATE.md`
  - L274（`SYSTEM_STATS` と `VRAM_RECOVERED` の型・意味維持の記述）
  - §2-10 リソース監視のバックエンド配信基盤（L280-L283）
  - §5-4 生成前他プロセスVRAM競合防止と待機通知（L474-L486）
- `docs/specs/SPEC_SETTINGS.md` L113（VRAMガードのメーター記述）

## 4. 改訂内容

### 4.1 SPEC_GENERATE §5-4 の 1（L476-L478 を改訂・追記）
- 判定値: worker は上流投入の直前に、判定のたびに新規取得した値で判定する（2.5 秒周期の監視キャッシュ値は使わない）。保留中の再評価は 1 ジョブあたり 1.0 秒間隔とし、再評価のたびに新規取得する。
- 自セッション残留: ComfyUI `/system_stats` の torch 予約量（`torch_vram_total`）を自セッション残留とみなし、判定用空き = （ComfyUI が報告するデバイス空き − torch 予約内の未使用量）+ torch 予約量（0 以上、総量以下）とする。自セッション残留だけを理由に保留しない。ComfyUI は保持モデルを次の実行時に自ら退避・回収するためである。同じ ComfyUI を他クライアントが使う場合、その保持分も同じ扱いとなる。
- 自動 /free: 生成完了後に Backend が ComfyUI `/free` を自動実行することはしない（モデル再ロード待ちを毎回招き、Windows 側計測の反映遅延も解消しないため）。手動の「メモリ解放」（SPEC_SETTINGS §3、REQ-380/REQ-412）は従来どおり。
- フォールバック: ComfyUI の値が取得できない（timeout 1.0 秒、接続失敗、不正値）場合は、ホスト空き VRAM（primary アダプタ）で従来どおり判定する。双方とも取得不能なら保留しない（従来どおり）。
- 既定値の記述: 現行 L478 の「デフォルト4.0GB」は実装の既定（`resource_monitor` 初期値 6.0GB）と食い違う。実装値を確認して、正しい既定値へ修正する（確認結果を完了報告に記載する）。

### 4.2 SPEC_GENERATE §5-4 の 2（L479-L480）
- 保留理由: `external`（自セッション残留を除いても不足 = 他プロセス等の占有）と `unattributed`（ComfyUI の値が取得できず、占有元を判別できない）を区別する。自セッション残留は保留理由にならない。
- 表示: `external` は従来の「VRAM解放待ち（他プロセスの終了待機中）」（モバイルのバナーは「VRAM解放待ち（待機中）」）。`unattributed` はデスクトップで「VRAM解放待ち（占有元を判別できません）」、モバイルのバナーで「VRAM解放待ち（占有元未確認）」。10 秒トーストは `unattributed` のとき「占有元を判別できません」とする。待機表示の「空き」は判定用空き（`vram_guard_free_gb`、欠落時は `vram_free_gb`）を表示する。

### 4.3 SPEC_GENERATE §5-4 の 5（L486）と L274
- `SYSTEM_STATS` に任意フィールド `vram_guard_free_gb`、`vram_own_residual_gb`、`vram_hold_reason`（`external`/`unattributed`/null）、`vram_measure_source`（`comfyui`/`host`/null）を追加する。既存フィールドの型と 2.5 秒周期は維持する。`vram_safe` の意味は「判定用空き ≥ 安全基準値」に改訂する（REQ-432）。`vram_free_gb` は物理空き（primary アダプタ）のまま。`VRAM_RECOVERED` の形式と発火条件（`vram_safe` が false から true）は維持する。
- L274 は「既存の型を維持し、REQ-432 で追加フィールドと `vram_safe` の意味改訂を行った」旨が読み取れるように調整する（Generation snapshot 周期へ統合しない点は維持）。

### 4.4 SPEC_GENERATE §2-10（L283）
- Windows の VRAM 使用量は、PDH `\GPU Adapter Memory(*)\Dedicated Usage` のうち DXGI で選んだ primary LUID のアダプタだけを合算する（同一 LUID の複数 phys は合算）。primary LUID が未解決、または一致するインスタンスが無い場合は全アダプタを合算する（安全側）。ヘッダー表示の VRAM 使用量も同じ基準とする。
- 既知の制約: ComfyUI を WSL2 で動かす場合、Windows 側計測では ComfyUI が `vmwp.exe` として見え、`/free` 後の反映が約 12 秒遅れる（2026-11-16 計測、`docs/logs/REQ-432/vram-measurement.md`）。

### 4.5 SPEC_SETTINGS L113
- VRAMガードのメーターは物理空き（`GET /api/settings/vram` の `vram_free_gb`、primary アダプタ）を表示する。生成ガードの判定は自セッション残留を除外した判定用空きで行うため、メーターが閾値未満（赤）でも生成が保留されない場合がある旨を注記し、SPEC_GENERATE §5-4 を参照させる。
