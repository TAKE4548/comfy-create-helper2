# REQ-333-T4: 生成記録repositoryとmetadata互換保存

## Purpose and Ownership

受付全件をtransaction保存、terminal状態とoutputs保存後にrevisionを発行。同request同hashは同IDs、異hash409。PromptMetadataの旧APIを維持し受付worker用保存関数を再利用。upstream prompt_id初回確定時はfrozen workflow_id/param_values/applied_assetsを使って必ずPromptMetadataを同一repository transactionで追加する。任意の`param_values.__prompt_surgeon_metadata_v1`が文字列JSONかつversion=1なら、既存recordをコピーしqueued_at（確認済みprompt_id初回記録時のUTC ISO時刻）とprompt_idを加え、更新recordを同じparam_values予約キーへ文字列JSONで戻してから追加する。markerがない/不正でもmetadata rowは必ず作り、param_valuesはそのまま保存する。prompt_id記録とmetadataの片方だけがcommitされないようにする。terminal job記録の保持集合を既存metadata1000件へ揃え、activeは実行中保護、graphはterminal解放。

## Hermetic Contract

snapshot()はread-only。DB read/serialize失敗は503、FEは前回のvalid状態を保持して同期失敗表示、部分payloadは適用しない。受付transaction未commitならrollbackして202なし。commit済みなら後続snapshot取得/通知失敗で受付を拒否扱いに戻さず、commitしたjob IDs/epoch/revisionから202を返す。request lookupを受付根拠とし、state取得失敗でmutationを再送しない。

以下は承認対象の新contract。scopeとproject、上流client IDと利用者sessionは別。clientから完了状態を送らない。
受付はDB commit後202。上流POST結果不明はunconfirmed、自動再送なし。BE再起動完全復元を追加しない。
通常Nはcancelled除外、F=succeeded+failed。Studio各batch独立。別scope待機優先、他session待機はfilter ONだけ。
snapshotはepoch/revisionでatomic置換、eventも同じ形の全状態dataを使い部分mergeを避ける。SYSTEM_STATS/VRAM_RECOVEREDのtype/data・2.5秒周期保持。
既存30local/1000server metadata、Snapshot独立、Studio750ms/draft競合、画像aspectを保持。
カード外ファイルや公開contract変更が必要なら設計へ差し戻す。

```python
from typing import Any, Literal, Protocol
from pydantic import BaseModel
Scope = Literal['normal','studio']
JobStatus = Literal['queued','submitting','running','succeeded','failed','cancelled','unconfirmed']
class BatchItem(BaseModel):
    graph: dict[str, Any]
    workflow_id: int | None = None
    param_values: dict[str, Any]
    applied_assets: dict[str, Any] | None = None
    set_name: str | None = None
class BatchRequest(BaseModel):
    request_id: str
    session_id: str
    scope: Scope
    project_id: int | None = None
    items: list[BatchItem]
class GenerationPort(Protocol):
    async def submit(self, graph: dict[str, Any]) -> dict[str, Any]: ...
    async def queue(self) -> dict[str, Any]: ...
    async def history(self, prompt_id: str | None = None) -> dict[str, Any]: ...
    async def interrupt(self, prompt_id: str) -> None: ...
    async def clear_queue(self) -> dict[str, Any]: ...
    async def delete_queue(self, prompt_ids: list[str]) -> dict[str, Any]: ...
    async def interrupt_all(self) -> dict[str, Any]: ...
    async def delete_history(self, prompt_ids: list[str]) -> None: ...
class RepositoryPort(Protocol):
    def accept_batch(self, payload: BatchRequest) -> dict[str, Any]: ...
    def snapshot(self) -> dict[str, Any]: ...
    def transition(self, job_id: str, status: JobStatus, **fields: Any) -> dict[str, Any]: ...
# UUID、空items禁止、studio project必須をvalidatorで検査。
```

実装具体化: `GenerationRepository(session_factory: Callable[[], Session], epoch: str | None = None)`。
Sessionの生成/closeを各操作で行い、専用SQLite fixtureを注入できる。epoch省略はinstanceごとのUUID。
accept_batch応答はBatchAcceptedのmodel_dump相当のみ: batch_id,job_ids,epoch,revision。
同request同canonical payload hashは既存batch/job IDsを返し、異payloadはHTTPException409。
payload hashはBatchRequest.model_dump(mode='json')をsort_keys=TrueのJSONからSHA256。
通常groupは未終了normalのgroupを継承、全終端後は新UUID。Studioはnormal_group_id=NULL。
snapshotはT2 StateSnapshotのmodel_dump(mode='json')と同一: version1,epoch,revision,normal_group_id,jobs,batches,upstream。
jobsはmanagedのみ、graph/metadata内容はwireへ出さない。timestampsはUTC ISO、JSON列からnode/outputs/failureを復元。
repository単体upstreamはhttp_ready=False,ws_connected=False,failure_since=None（serviceが現況を合成）。
find_requestはRequestLookup相当batch_id/job_idsのみ、不存在None。snapshotを呼ばず独立照会する。
transitionはjob_idの既存行を更新し、StateSnapshot.jobsの該当JobView dictを返す。
fieldsはprompt_id,started_at,finished_at,node,outputs,failure,cancel_requestedを対応列へ保存。未指定値は保持。
terminal状態は成功/失敗/取消。二重terminalは変更なし、先行terminalを優先。graph_jsonはterminalでNULLにする。
revisionは既存AppSettingの専用key generation_revisionでmutationと同transaction増分、rollbackでは増分しない。
現在normal_group_idはAppSettingの専用key generation_normal_group_idでも保持し、完了groupを次受付まで表示する。
PromptMetadata互換helperはflushまで、commitは呼出元transactionが所有。保持整理は既存1000件を継承する。
prompt_idを初回記録するtransitionは同一DB session/transaction内で必ずprompt metadata helperを呼ぶ。対象キーは`metadata_json`直下ではなく`metadata_json['param_values']['__prompt_surgeon_metadata_v1']`。その値が文字列JSONでversion=1の時だけrecord全項目を保ったcopyへqueued_at/prompt_idを追加し、同じparam_values予約キーへJSON文字列として戻す。PromptMetadataCreateのprompt_id/workflow_id/param_values/applied_assetsは既存fieldへ写し、queued_atは予約record内だけに置く（DB列追加なし、既存created_atは変更しない）。queued_atには確認済みprompt_id初回記録時のUTC ISO時刻を使う。marker不在/malformed/version不一致ならrecordを推測・再構成せず、frozen param_valuesを不変で保存するが、PromptMetadata row自体は省略しない。再同一prompt_id遷移はmetadataを重複作成せず、保存済みmetadataの再送をFEへ要求しない。transaction失敗時はprompt_idとPromptMetadataの両方をrollbackし、成功publishを返さない。上流受付済みならserviceはjobをunconfirmedとして照合し、自動再送しない。
retentionは独立した「terminal job 1000件」上限でmetadata保持を追い越さない。既存metadataの1000件保持規則を正本として同期し、active jobsは保持対象として保護する。
