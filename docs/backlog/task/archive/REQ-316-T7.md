### API操作・応答の根拠
- prompt POST `/api/prompt-metadata` → 200、`{"status":"ok","prompt_id":prompt_id}`。GET `/api/prompt-metadata/{prompt_id}` → 200で `prompt_id/workflow_id/param_values/applied_assets/created_at`（`backend/app/routers/prompt_metadata.py:16-28,32-55,87-121`）。
- snapshot POST `/api/snapshots` → **201・SnapshotSummary**（`backend/app/routers/snapshots.py:73-87`）。`id/workflow_id/params/image_path/thumbnail_path/created_at/source_snapshot_id` が返る。POST応答にloras/tag_setsを要求しない。
- snapshot GET `/api/snapshots/{id}` → **200・SnapshotRead**（同:40-69）。上記に `loras:[]/tag_sets:[]` が加わり `params` はJSON辞書。`created_at` は非空の保存時刻であり完了時刻としてassertしない。
- POST bodyは `{"workflow_id": workflow_id, "params": source_params}` のみでよい。`image_path` とalbum/関連/source IDを省略する。`backend/app/schemas/snapshot.py:37-46` と `backend/app/services/snapshot_service.py:110-167` により、画像ダウンロード/ローカル画像読取/thumbnail生成を通らない。
- source prompt削除のAPIはない。**fixtureのテストDBだけ**で `models.PromptMetadata` をfilter-delete/commitし、GETが404になることを確認する。workflowを削除してはならない（snapshot FKのCASCADEと検証目的が異なる）。

### 記録fixtureとassertion
`record_text = json.dumps(record, ensure_ascii=False)` を一度だけ作り、予約キーの**文字列**として送る。最小妥当recordには設計契約どおりversion=1、workflow_id/name、completeness、fields、parameters、assets、queued_atを置く。
fieldsは名前/roleが異なる2欄以上＋negative＋記録済み空欄。各CapturedFieldの `mapping_id/node_id/role/param_name/input_type/display_name/class_type/recorded/value/status/value_kind` を含め、1欄に `"日本語(重み:1.2)\r\n" * 200 + "末尾-REQ316"` を用いる。parametersに実seed、false、0、null、配列/辞書、LoRA stackのmodel/clip別値を入れる。assetsはunknown origin例を含める。関連キーには別JSON文字列を置く。
1. 既存promptテスト追加: POST/GETで `param_values == source_params`、予約値の型がstr・元record_textと完全一致、decode後record等値。通常Quality/seed/複合JSON値・applied_assetsも等値。原文字列が二重JSON化/切り詰めされない。
2. 新snapshot独立テスト: source prompt POST→GETで取得したparamsをsnapshot POSTに渡す→snapshot GETを照合→source prompt削除→source GET 404→snapshot再GETを再照合。最後にテストDBのSnapshot.paramsもdecodeして独立保持を確認する。
3. 旧flat paramsと{}は同じfixtureでPOST/GET等値を各1ケース追加。未知の通常JSON値をAPIが落とさない。1000件pruningの仕様変更/大量fixture追加はしない。
