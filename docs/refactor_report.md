# リファクタリング・テスト充足性・仕様整合性 監査レポート

本レポートは、リポジトリの主要なソースコード（状態管理、カスタムフック、コンポーネント、APIクライアント）に対して実施した、**「通常のリファクタリング（AIコンテキスト効率含む）」「テストの充足性」「仕様書（`docs/specs/`）との整合性」**の統合監査結果をまとめたものです。

---

## 1. 監査の総評

全体として、フロントエンドのコードベースは機能ごとに分離されていますが、以下の重大な課題が検出されました。

1. **テストコードの形骸化・未実装**: 
   - `useComfyWebSocket` などのコアフックでテストがスキップされている、あるいは `useAuditAction` や `useGeneratePageState` のような主要な状態遷移ロジックに対するテストコードが一切存在しません。
2. **AIコンテキスト効率（AI-Efficiency）の低下**:
   - `getInitialParams` のような巨大なオブジェクト解析ロジックが1つの関数に集中しており、AIエージェントがコンテキストを読み取る際のトークン浪費と推論ミスの原因（Cognitive Load）となっています。
3. **仕様との不整合（SpecMismatch）**:
   - `useAuditAction` にて、仕様上は複数の監査タイプ（`interference`, `vocabulary`, `physical`）に対応するべき箇所が、実装では `['interference']` に固定されているなど、一部の仕様要件が反映されていません。

---

## 2. ターゲット別の監査詳細

### 2.1 状態管理: `useGenerationStore.ts`
- **リファクタ指摘 (High)**:
  - `ComfyHistoryItem` インターフェースの `prompt` プロパティが、タプル構造を持つ複雑なインライン定義になっており、AIコンテキストのパースエラーや推論ミスを招きやすい。
  - `reconcileState` や `initialize` などのアクションに、非同期の順次フェッチ、WebSocket の初期化、タイマー破棄などの副作用と状態更新が混在しており、Cognitive Load が非常に高い。
- **テスト充足性**:
  - テストはある程度カバーされているものの、非同期処理の競合状態や WebSocket イベント発生時の状態伝播の検証が不十分。

### 2.2 通信フック: `useComfyWebSocket.ts`
- **テスト充足性 (High)**:
  - **現状のテストがスキップ（Skip）されています。** WebSocket 接続の成功・切断、および進捗イベント（`progress`）、完了イベント（`executed` 等）、エラー（`execution_error`）に伴う状態更新のテストが皆無です。
  - バイナリ画像受信処理（Blob/ArrayBuffer）や URL 生成ロジックの検証がありません。
- **仕様整合性 (Medium)**:
  - スマホでの画像プレビュー時の長押し操作について、共通フック側でタッチイベントの制御やマルチ選択（Long Press）との競合回避ロジックがなく、UX仕様に影響する懸念があります。

### 2.3 マッピング処理: `useMasterMappingRows.ts`
- **テスト充足性 (High)**:
  - 仕様書（AC-1）に定義されている、警告ステータス `class_type_mismatch` 時の挙動がテストされていません。
  - `initFromScan` で、定義外のステータスの警告が渡された際の例外・無視挙動のテストが不足しています。

### 2.4 生成ページ・アクション: `useGenerateAction.ts` & `useWorkflowParams.ts` & `useAuditAction.ts`
- **リファクタ指摘 (High)**:
  - `getInitialParams` （`useWorkflowParams.ts`）が約60行の巨大な関数になっており、LoRAスタックのパラメータ抽出と一般パラメータの抽出が混在して複雑化しています。
  - `useGenerateAction.ts` 内で `JSON.parse(JSON.stringify(...))` を用いたディープコピーが行われており、パフォーマンス上非効率です。
- **テスト充足性 (High)**:
  - `useWorkflowParams.ts` のテストでは、基本型（Int, String）しか検証されておらず、**最重要要件である `lora_stack` 入力タイプのパース処理のテストが欠落しています。**
  - **`useAuditAction.ts`（LLMによるプロンプト監査実行フック）に対するユニットテストが1つも存在しません。**
- **仕様整合性 (Medium)**:
  - 仕様上、プロンプト監査は `interference`, `vocabulary`, `physical` の3種を選択・実行できる必要がありますが、実装は `['interference']` 固定となっています。

### 2.5 ページ状態管理: `useGeneratePageState.ts`
- **テスト充足性 (High)**:
  - ページ全体を司るこのフックに対するテストが全くありません。ドラッグ＆ドロップ、複数選択（Ctrl+Click/Shift+Click）、リセット処理などが未テストです。

### 2.6 タグエディタ: `TagChipEditor` (`index.tsx` & `useChipParser.ts`)
- **テスト充足性 (High)**:
  - `@dnd-kit` を使用したドラッグ＆ドロップによるタグの並び替え機能のテストが欠落しています。
  - `parseToChips` での一時的なID生成に `Math.random()` が使用されており、衝突の可能性やテストの決定性を損なう構造になっています。

### 2.7 API クライアント: `client.ts`
- **テスト充足性 (High)**:
  - **APIクライアントモジュール全体のユニットテストが存在しません。** エラーハンドリングやクエリパラメータの組み立て（`snapshotsApi.list()` 等）の妥当性が未検証です。

## 3. High 優先度の指摘事項とPBI化

以下の項目は、システムの品質向上およびAIエージェントの開発生産性の観点から「High」に分類され、優先的にバックログへの追加（PBI作成）が必要です。

| 対象モジュール | 指摘カテゴリ | 課題概要 | 対策 |
| :--- | :--- | :--- | :--- |
| `useComfyWebSocket.ts` | テスト充足性 | テストがスキップされ、主要なWebSocketイベント処理が未テスト | `ws-mock` 等を導入し接続・イベント処理のテストを完備する |
| `useWorkflowParams.ts` | テスト充足性 | 最重要要件である `lora_stack` パースのテストが不足 | 各種 `lora_stack` パターンのテストケースを追加 |
| `useAuditAction.ts` | テスト充足性・仕様整合 | テストコードが存在せず、また監査タイプが仕様と乖離 | ユニットテストの実装と、3つの監査タイプのマルチ選択対応 |
| `useGeneratePageState.ts`| テスト充足性 | ページ状態フック全体のテストが未実装 | 状態遷移とイベントハンドラの統合/ユニットテストを作成 |
| `TagChipEditor/index.tsx` | テスト充足性 | ドラッグ＆ドロップによる並び替えのテストが未実装 | `@testing-library/user-event` を用いた並び替えテストの追加 |
| `client.ts` | テスト充足性 | APIクライアント全体のテストが未実装 | fetchモックを使用した各APIメソッドのテスト作成 |

---

## 4. 総括と推奨するアクション

1. **テストのカバレッジ向上**: 
   特にカスタムフック層におけるビジネスロジックのテストが手薄です。不具合の混入を防ぐため、新規機能の開発前にこれらのフックテストの修復・新規作成を優先的に行うべきです。
2. **関数のリファクタリングと型定義の厳密化**:
   AIエージェントによる開発時、巨大な関数（例: `getInitialParams`）や複雑なインライン型（例: `prompt: ...`）はハルシネーションを多発させます。これらを小さく分割することで、人にとってもAIにとっても理解しやすいコードになります。
