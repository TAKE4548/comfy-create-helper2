# バックエンド監査および OpenAPI/フロントエンド整合性 監査レポート

本レポートは、バックエンド（FastAPI）の主要なソースコード（モデル、ルーター）に対して実施した、**「通常のリファクタリング」「テストの充足性」「OpenAPIとフロントエンド（FE）定義の整合性」**の統合監査結果をまとめたものです。

---

## 1. 監査の総評

バックエンドコードおよびAPIスキーマとFEの整合性を検証した結果、以下の主要な課題が検出されました。

1. **ルーター層（routers/）へのロジック集中**:
   - `snapshots.py` や `workflows.py` などのルーターハンドラ内に、複雑なデータベースのフィルタリング/結合クエリ、ファイルシステムへの画像保存、関連データ（Lora/TagSet）の一括生成・削除などのビジネスロジックが混在しています。これらは保守性を下げるため、サービス層（Service Layer）への分離が必要です。
2. **例外系・境界値テストの欠落**:
   - `snapshots.py` や `loras.py` において、存在しないID（404 Not Found）や不正な値の送信（422 Validation Error）といったエラーハンドリングが適切に実装されているにもかかわらず、対応するテストが `backend/tests/` 内に定義されておらず、異常系の振る舞いが未検証です。
3. **データ構造の暗黙的シリアライズ**:
   - `models.py` において `expected_class_types` や `param_values` など、JSON配列・オブジェクトをDBに文字列型として保存しているフィールドにおいて、Pydanticによる厳密な型定義・バリデーションが不足しており、AIがAPIやDBスキーマの意図を誤解する原因となっています。
4. **OpenAPI / FE 整合性**:
   - 現状の `openapi.json` と `frontend/src/api/client.ts` および `types.ts` を比較した結果、主要なエンドポイント定義に致命的なパスの齟齬は見つかりませんでしたが、FE側の `client.ts` の一部引数の型ヒントが緩く（例: `data: unknown`）、バックエンドが期待するPydanticの入力スキーマを十分に強制できていない箇所が多数あり、開発時における型安全性の強化が推奨されます。

## 2. ターゲット別の監査詳細

### 2.1 データモデル: `models.py` & `schemas/`
- **リファクタ指摘 (Medium)**:
  - `expected_class_types` や `param_values` などのフィールドが `Text` (JSON文字列) としてDBに格納されているが、スキーマ上でのバリデーション定義が不足しており、データ構造がブラックボックス化している。
- **テスト充足性 (High)**:
  - `SnapshotCreate` 等で `workflow_id` に不正なデータ型（浮動小数点数や数値に変換できない文字列）が渡された場合の、Pydantic側での `ValidationError` 発生テストが存在しない。
  - `Lora` の `recommended_strength_min` などの浮動小数点型に対して、無効な値（文字列など）のバリデーションテストが不足している。

### 2.2 スナップショット管理: `routers/snapshots.py`
- **リファクタ指摘 (High)**:
  - `create_snapshot` 関数において、画像のダウンロード、ディスク保存、データベース書き込み、関連エンティティ（Lora/TagSet/Album）の一括処理が同一のハンドラに集中しており、結合度が高すぎる。
- **テスト充足性 (High)**:
  - 存在しない `lora_ids` や `tag_set_ids` を PATCH リクエストに含めて送信した場合に、期待される `HTTP 400 Bad Request` が正しく返されることを確認するテストが存在しない。
  - 画像書き込み時にディスクフルなどで書き込みが失敗した際のエラーハンドリング（HTTP 500）のテストケースがない。

### 2.3 LoRA管理: `routers/loras.py`
- **テスト充足性 (High)**:
  - `update_lora` や `delete_lora` のエンドポイントに対して、存在しない LoRA ID を指定してリクエストした際の `HTTP 404 Not Found` 例外発生のテストが定義されていない。
  - `reorder` エンドポイントにおいて、空の配列や重複するID、存在しないIDが送信された際の挙動（バリデーション挙動）のテストが欠落している。

### 2.4 ワークフロー管理: `routers/workflows.py`
- **テスト充足性 (High)**:
  - `copy_workflow` ハンドラにおいて、関連する `mappings` や `presets` が空のワークフローをコピーした際の挙動がテストされていない。
  - `update_workflow` において、他のワークフロー名と重複する名前で更新しようとした際の `HTTP 409 Conflict` の検証テストがない。

## 3. High 優先度の指摘事項とPBI化

以下の項目を High 優先の課題として定義し、バックログへの追加を実施します。

| 対象モジュール | 指摘カテゴリ | 課題概要 | 対策 |
| :--- | :--- | :--- | :--- |
| `snapshots.py` / `loras.py` | テスト充足性 | 存在しないID送信時の例外エラー（400/404）が未テスト | `TestClient` を使用し、無効ID送信時のレスポンス検証テストを追加 |
| `snapshots.py` | リファクタリング | ルーター層へのビジネスロジック・ファイル保存処理の集中 | 処理をサービスレイヤー（Service class）へ移譲・カプセル化 |
| `workflows.py` | テスト充足性 | コピー元のマッピング空状態や名称重複（409エラー）のテストが未実装 | エッジケースおよび競合エラーレスポンスのテストケースを追加 |
| `loras.py` | テスト充足性 | `reorder` エンドポイントにおける境界値・無効値の検証欠如 | 空配列や無効ID送信時のバリデーション挙動のテストを追加 |

---

## 4. 総括と推奨するアクション

1. **エラーハンドリングテストの網羅**:
   バックエンドが正しく例外を送出していることはコード上確認できますが、回帰テストが不足しているため、今後の改修時に予期せぬ不具合がすり抜ける懸念があります。特に `HTTP 404` や `HTTP 400` を返す検証テストの追加を最優先とします。
2. **ルーターのリファクタ（サービス層の導入）**:
   特に `snapshots.py` の画像処理・トランザクション処理は肥大化しており、コード変更時の影響範囲が大きいです。これらを Service クラスとして切り出すことで、テストの容易性（Mock化）およびAIエージェントの理解しやすさ（AI-Efficiency）が大幅に向上します。
