# REQ-408 詳細設計書: モバイル: ボトムシートのスワイプダウンによる閉じるジェスチャー操作

## 1. アーキテクチャ概要と背景

### 1.1 現状の課題と原因分析 (5 Whys)
1. **なぜ新設・改修が必要か**: モバイル表示時のボトムシートを閉じる際、明示的な閉じるボタンや背景タップに頼っており、片手操作時の操作導線が遠く不便であるため。
2. **なぜその課題が発生するか**: ボトムシートの閉じるボタンやキャンセルボタンが親指の届きにくい位置にある場合、持ち替えが必要となり、シートを素早く片手で閉じる直感的なジェスチャー操作が提供されていないため。
3. **なぜ現状の仕組みで不十分か**: ボトムシート上部にシートハンドル（`modal-sheet-handle`）等の視覚要素が存在するものの、ドラッグやスワイプダウンによる閉じるジェスチャーが実装されておらず、視覚的アフォーダンスと実際の振る舞いに乖離があるため。
4. **なぜこのアプローチを採用するか**: ボトムシートのハンドル部や上端領域からのスワイプダウン（下方向へのドラッグ／フリック）でシートをスムーズに閉じられるようにすることで、ネイティブアプリ同等の片手操作性と素早い情報確認・離脱を実現できるため。
5. **根本原因**: モバイル向けモーダルをボトムシートUIへ移行した際、外観（下部固定・角丸・ハンドル表示）のみが先行し、ボトムシートの物理メタファーに沿ったタッチジェスチャー（スワイプダウンによる閉じる）のインタラクション設計と内部縦スクロールとの競合回避機構が未導入であったため。

### 1.2 解決方針と受入基準 (AC-1〜AC-5)
共通モーダルコンポーネント（`frontend/src/components/common/Modal.tsx`）を拡張し、モバイル表示時（画面幅768px未満）に下方向タッチスワイプ／ドラッグによる閉じるジェスチャー操作を提供する。
- **スワイプダウン閉じるジェスチャー ([REQ-408/AC-1])**: モバイル表示時（幅768px未満）、シート上部ハンドルやコンテンツ上端からの下方向ドラッグ量が規定閾値（80px以上）に達するか、下向きフリック速度が一定以上（速度 > 0.5px/ms かつ移動量 > 30px）の場合に閉じるコールバック（`onClose`）を発行する。
- **閾値未満のスナップ復帰 ([REQ-408/AC-2])**: 移動量が閾値未満で指が離れた場合は、`onClose` を発行せず元の表示位置（translateY: 0）に滑らかにスナップ復帰する。
- **内部縦スクロールとの調停 ([REQ-408/AC-3])**: ボトムシート内にスクロール可能なコンテンツが存在し、`scrollTop > 0` の状態では、コンテンツのスクロール（上方向へのスクロール戻し）を最優先とし、シートのドラッグ／クローズ処理は起動しない。`scrollTop === 0`（最上部）に達している状態からのみスワイプダウン操作を有効とする。
- **既存閉じる導線の完全維持・MUI-10準拠 ([REQ-408/AC-4])**: 既存のヘッダー閉じるボタン、フッターのキャンセルボタン、バックドロップクリック、および Esc キーによる閉じる経路を損なわず完全維持する。
- **デスクトップ表示の非破壊 ([REQ-408/AC-5])**: 画面幅768px以上のデスクトップ表示（中央ダイアログモーダル）では、下方向ドラッグ操作によるモーダル閉鎖を無効化し、既存の操作性と配置を維持する。

### 1.3 UI 6大ハード不変条件および MUI-10 ガイドラインとの整合
- **UI 不変条件 3 (Mobile Modals)**: モバイル表示時のボトムシート配置（`items-end`、`rounded-t-2xl`、`modal-sheet-handle`）および `overscroll-contain` を維持し、スワイプ操作中もビューポート突き破りを発生させない。
- **UI 不変条件 4 (Strict Input Guard)**: シートハンドルには適切なタッチ領域を確保し、誤タップや意図しないピンチズームを防ぐ `touch-action: pan-y`（またはハンドル上 `touch-none`）を考慮する。
- **MUI-10 (ジェスチャー保護)**: スワイプ操作でのみ閉じられる孤立UIを厳禁とし、明示的なタップ操作（ボタン、バックドロップ）およびキーボード操作（Esc）の代替経路を100%維持する。

## 2. インタラクション・状態遷移設計

### 2.1 タッチジェスチャー検知と状態遷移
`Modal.tsx` のダイアログコンテナ（`dialogRef`）において、以下のタッチイベントライフサイクルを管理する：

```
[Touch Start]
    |
    v
画面幅 < 768px かつ !disableSwipeToClose ?
    |-- No --> 通常のタッチ/スクロール処理（ドラッグ無効）
    |-- Yes
         |
         v
    タッチ開始要素の scrollTop === 0 か？ (最上位までスクロール済み)
         |-- No (scrollTop > 0) --> canDrag = false（内部スクロールを優先）
         |-- Yes --> canDrag = true, startY / startX / startTime を記録, isDragging = true
              |
              v
[Touch Move]
    canDrag === true ?
         |-- No --> 処理なし（ブラウザ標準スクロール）
         |-- Yes --> deltaY = currentY - startY
                     deltaX = currentX - startX
                     横スクロール優勢 (|deltaX| > |deltaY|) ?
                         |-- Yes --> canDrag = false (水平ジェスチャー優先)
                         |-- No  --> translateY = Math.max(0, deltaY) (上方向は0クランプ)
                                     transform: translateY(${translateY}px) を適用
              |
              v
[Touch End]
    canDrag === true ?
         |-- Yes --> elapsed = Date.now() - startTime
                     velocity = translateY / elapsed
                     translateY >= 80px || (velocity > 0.5 && translateY > 30px) ?
                         |-- Yes --> onClose() 発火 [REQ-408/AC-1]
                         |-- No  --> translateY = 0 へスナップ復帰アニメーション [REQ-408/AC-2]
         |-- No  --> 状態リセットのみ
```

### 2.2 縦スクロール（scrollTop）との調停アルゴリズム
- **最上部判定 (`isAtTop`)**:
  タッチイベントの `target` から `dialogRef.current` までの祖先チェーンを走査し、いずれかの要素で `scrollTop > 0` が検出された場合、内部コンテンツが下方向にスクロール中であると判定する。
  この場合、`canDragRef.current = false` としてスワイプダウン操作の開始を抑制し、標準のコンテンツスクロールに委ねる。
- **上方向ドラッグのクランプ**:
  `scrollTop === 0` の状態であっても、ユーザーが上方向に引っ張った場合（`deltaY < 0`）は、`Math.max(0, deltaY)` により `translateY` を `0` に固定する。これにより、シートが上部に突き破る不自然な挙動を完全に防止する。

### 2.3 閾値・速度判定とスナップ復帰 / アニメーション
- **定数設計**:
  - `SWIPE_THRESHOLD = 80` (px): シートを下方向に80px以上引き下げた場合に閉じる。
  - `FLICK_VELOCITY = 0.5` (px/ms): 素早い下向きフリックを検知する速度閾値。
  - `FLICK_MIN_DISTANCE = 30` (px): フリック誤判定を防ぐための最小移動量。
- **トランジション制御**:
  - ドラッグ中 (`isDragging === true`): 指の動きに遅延なく追従させるため、`transition: 'none'` とする。
  - ドラッグ終了後 (`isDragging === false`): スナップ復帰時、`transition: 'transform 0.2s cubic-bezier(0.25, 1, 0.5, 1)'` を付与してスムーズに原点復帰させる。

### 2.4 デスクトップ非破壊・アクセシビリティ維持
- **画面幅判定**:
  `typeof window !== 'undefined' && window.innerWidth >= 768` の場合、`handleTouchStart` は即時リターンし、一切のドラッグ追従を行わない。
- **マウス操作非干渉**:
  ドラッグ検知はタッチイベント（`onTouchStart`, `onTouchMove`, `onTouchEnd`, `onTouchCancel`）に限定し、マウスイベント（`onMouseDown` 等）にはバインドしない。これによりデスクトップ上でのテキスト選択やクリック操作に一切干渉しない。
- **オプトアウト機構 (`disableSwipeToClose`)**:
  入力フォームなど未保存データの誤破棄を防ぎたいモーダルに対応するため、`ModalProps` に `disableSwipeToClose?: boolean` を追加する。`disableSwipeToClose: true` の場合はモバイル表示であってもスワイプ閉じる操作が無効化される。

## 7. トレードオフ・リスク開示・維持契約

### 7.1 トレードオフ
- **マウスドラッグによるデスクトップ閉じる操作の非対応**:
  - メリット: デスクトップ環境における文字選択、スクロールバードラッグ、フォーム入力操作との偶発的な競合を完全に排除し、安全性を最大化できる。
  - デメリット: デスクトップのタッチスクリーン端末（Surface等）で幅768px以上の場合はドラッグで閉じられないが、デスクトップ中央モーダルの標準UX（閉じるボタン/Esc/バックドロップ）で十分に代替可能である。
- **上方向ドラッグの0クランプ**:
  - メリット: シートが上部セーフエリアや画面外へ突き抜けるレイアウト破損を確実に防止できる。
  - デメリット: iOS特有のゴムバンド（ラバーバンド）抵抗感はないが、ウェブビューでの安定性と実装のシンプルさを優先する。

### 7.2 リスクと対策
- **子要素内の横スワイプ（カルーセル等）との競合リスク**:
  - 対策: `touchMove` 判定時に `Math.abs(deltaX) > Math.abs(deltaY)` の場合はドラッグフラグを直ちに解除し、横方向操作を優先する。
- **入力中モーダルでの意図しない閉じるリスク**:
  - 対策: `disableSwipeToClose` プロパティを提供し、フォーム入力や未保存変更を持つモーダルでオプトアウト可能とする。

### 7.3 維持契約 (Invariants)
- UI 6大不変条件（特に Invariant 3: Mobile Modals, Invariant 4: Strict Input Guard）に完全準拠する。
- 全受入基準（AC-1 〜 AC-5）が常にPASSし、既存の30件の `Modal.test.tsx` テストを1件もリグレッションさせない。
