## 2. 現状調査 (As-Is) と対象アクション列挙

調査範囲は `PageHeader` の全呼出元（Generate Desktop/Mobile, LoRAs, Tags, History, LoRA Studio, Settings）と、ヘッダー右クラスタ（`ResourceHoverMonitor`, `HeaderKebabMenu`）に限定した（R-AR-4）。

### 2-1. クリップ原因（コード確認済み・実ブラウザ未確認）

`PageHeader.tsx:83` の `actions` スロット外枠は `overflow-x-auto`。CSS仕様上、`overflow-x` が `visible` 以外のとき `overflow-y` の `visible` は `auto` に計算されるため、このスロット内に置かれた `position: absolute` の展開メニューは外枠（高さ約 `min-h-[50px]`）の内側で切り詰められ、枠内スクロールになる。これは「展開メニューが極端に短い」というユーザー報告と整合する。`WorkflowActionsMenu`（`absolute left-0 top-full ... z-50`）はこのスロット内にある。

右クラスタ（`ml-auto ... shrink-0`）は `overflow-*` を持たないため、`HeaderKebabMenu` / `ResourceHoverMonitor` の展開は現状ヘッダー高さでは切り詰められていない。

### 2-2. 対象アクション一覧（共通ヘッダー内の展開アクション全数）

| ID | アクション（トリガー） | 実装 | 配置 | 現状のクリップ | 本設計での扱い |
|---|---|---|---|---|---|
| A1 | ワークフロー設定（`#workflow-actions-btn`, `aria-expanded`） | `WorkflowActionsMenu.tsx` | Generate の `PageHeader actions` スロット。Desktop（768px以上, `DesktopLayout.tsx:732`）と Mobile（768px未満, `MobileLayout.tsx:352`）の2マウント | **あり**（2-1。`overflow-x-auto` 外枠で切り詰め） | 共通プリミティブへ移行（必須） |

**実ブラウザ所見による追補（2026-10-16）**: (1) モバイル（768px 未満）では `PageHeader` は `flex-wrap` で `actions` が 2 行目に折り返す。ピル／ケバブ／A4 は 1 行目の右クラスタにあるため、トリガー下端基準では A3 のパネルが 2 行目（actions 行）に重なって開く（実測: ヘッダー下端 118 に対しパネル上端 約71）。(2) ケバブのトリガーは 768px 未満で `w-11 h-11 -m-2`（44px のヒットスロップ）を持ち、`anchorRef` のラッパー（`relative inline-flex`）の矩形はボタンより上下 8px 小さい。ラッパー基準で `+6px` を置くとボタン下端より約 2px 上にパネルが出る。(3) `PageHeader` に `children`／`subtitle` スロットがあるが、本番ページで `children` を渡している箇所は無い（grep 確認）。ヘッダー下端は `PageHeader` ルート要素の下端と定義する。

トリガー種別: A1・A2・A3・将来アクション(F) は **click 型**（トリガー押下で開閉）、A4 は **hover 型**（ポインター滞在で表示）。両型とも同一プリミティブ `HeaderDropdown`（開閉状態は呼出側が持つ制御型）を使い、型固有の規律は HEO-6（click）／HEO-9（hover）で分ける。

## 4. 共通契約（Header Expand Action Overlay Contract: HEO）

共通ヘッダーの展開アクションは、以下の全項目を満たす。契約は観測可能な振る舞いとして定義し、実装は共通プリミティブ `HeaderDropdown` に集約する。

| # | 契約 | 実現方法 | 関連AC |
|---|---|---|---|

### 5-2. 新規モジュール（シグネチャ）

```ts
// frontend/src/components/common/header/headerMenuPlacement.ts （純関数・DOM非依存）
export const HEADER_MENU_GAP_PX = 6
export const HEADER_MENU_EDGE_MARGIN_PX = 8
export const HEADER_MENU_MIN_HEIGHT_PX = 96
export const PAGE_HEADER_ROOT_SELECTOR = '[data-page-header-root]'   // 追加(R1): PageHeader ルートの目印
export interface RectLike { top: number; bottom: number; left: number; right: number }
export type HeaderMenuAlign = 'start' | 'end'
export interface HeaderMenuPlacementInput {
  anchor: RectLike              // ラッパー rect（水平基準・画面外判定）。bottom は呼出側が子要素分を含めて計測済み（triggerBottom）
  headerBottom?: number         // 追加(R1): PageHeader ルートの bottom（ビューポート座標）。未指定／非有限なら無視
  panelWidth: number            // measured offsetWidth (px)
  viewport: { width: number; height: number }  // visualViewport ?? window.inner*
  align: HeaderMenuAlign
}
export interface HeaderMenuPlacement { top: number; left: number; maxHeight: number; shouldClose: boolean }
export function computeHeaderMenuPlacement(input: HeaderMenuPlacementInput): HeaderMenuPlacement
```

// frontend/src/components/common/header/HeaderDropdown.tsx
// 制御型・トリガー非依存: open/onClose は呼出側が持つ。click 型(A1-A3,F)も hover 型(A4)も同じプリミティブを使う。

// panel attrs: data-header-menu-panel="" data-placement="below-anchor"（値は既存テスト互換のため据え置き。意味は「ヘッダー／トリガーの下」）

`HeaderDropdown` 内部（非 export）の計測手順（毎回の `measure()`）:

```ts
const anchorEl = anchorRef.current;  const panel = panelRef.current
const header = anchorEl.closest(PAGE_HEADER_ROOT_SELECTOR)             // 毎回引き直す（再親子付け・複数ヘッダー対応）
const r = anchorEl.getBoundingClientRect()
let bottom = r.bottom                                                    // triggerBottom: 直接子要素のはみ出し（ヒットスロップ）を含める
for (const c of Array.from(anchorEl.children)) bottom = Math.max(bottom, c.getBoundingClientRect().bottom)
const anchor = { top: r.top, bottom, left: r.left, right: r.right }      // 水平・top は常にラッパー（子要素で水平／top を広げない）
const p = computeHeaderMenuPlacement({ anchor, headerBottom: header?.getBoundingClientRect().bottom, panelWidth: panel.offsetWidth, align, viewport })
const bridge = hoverBridge && panel.offsetWidth > 0
  ? { left: anchor.left, top: anchor.bottom, width: Math.max(0, anchor.right - anchor.left), height: Math.max(0, p.top - anchor.bottom) + 1 }
  : null
```

純関数の確定アルゴリズム（境界は厳密不等号。jsdomのゼロrectを「画面外」とみなさないため）:

```
refBottom  = isFinite(headerBottom) ? max(anchor.bottom, headerBottom) : anchor.bottom   // R1
top        = refBottom + GAP
maxHeight  = max(0, viewport.height - top - EDGE)
offscreen  = anchor.bottom < 0 || anchor.top > viewport.height || anchor.right < 0 || anchor.left > viewport.width
shouldClose= offscreen || maxHeight < MIN_HEIGHT
width      = min(panelWidth, viewport.width - 2*EDGE)  // 下限0
rawLeft    = align==='end' ? anchor.right - width : anchor.left
left       = clamp(rawLeft, EDGE, max(EDGE, viewport.width - width - EDGE))
```

## 7. サポート対象ビューポート（既存サポート範囲に基づく）

本リポジトリに「最小サポート幅」の明文は無く、SPEC_COMMON §2-2〜2-4・§1-4 のブレークポイントと既存E2E（`settingsResponsive.spec.ts`: 375, 767, 768, 1279, 1280）が基準となる。

| 区分 | 範囲（仕様） | 本PBIの検証幅×高さ |
|---|---|---|
| mobile | 768px未満（ボトムナビ54px+safe-area） | **375×667**（既存E2E基準）、**767×900**（境界上限）、**639/640**（A3/A4のsm境界） |
| tablet | 768–1023px（左レール56px） | **768×1024**、**1023×768** |
| desktop | 1024px以上（サイドバー） | **1024×768**、**1280×800** |
| 高さ境界 | 範囲外の明文なし | 通常 667/800 に加え、メニュー内スクロールを強制する **短い高さ 360**（全幅で実施） |
| Red Team（範囲外・AC対象外） | — | 幅 **320**（左右クランプ確認）、高さ **280**（メニュー内スクロール）。合否はクランプ・到達性のみ確認し、サポート範囲の拡張とはみなさない |

resize 検証（AC-6。R4 で改訂）: **ハーネス（T7。レイアウトを切り替えない）**は従来どおり、開いたまま 1280×800 → 375×667 → 375×360、および 375×667 → 600×400 を実行し、最後の項目へ引き続き到達できること。**実ルート Generate（T8）**は 768px でレイアウトが入れ替わりメニューが閉じる（正常）ため、(i)**同一レイアウト内**: Desktop 1280×800 → 1024×768、Mobile 700×900 → 375×667（→ 375×360）を開いたまま実行し、メニューが開いたまま・上端＝ヘッダー下端＋6px・最後の項目が押下可であること、(ii)**境界跨ぎ**: 1280×800 → 375×360（および逆方向）でメニューが閉じ（`[role="menu"]` 0 件）、新サイズで開き直すと最後の項目が押下可であることを判定する。**R1 追加**: 各 resize 後に「パネル上端＝ヘッダー下端＋6px（±1px）」も保たれること（1280→375 でヘッダー高さが約 50→118 に変わる＝`ResizeObserver`／resize 追従の実測）。

R1 による閉鎖閾値の影響: 閉鎖条件は `viewport.height < headerBottom + 6 + 96 + 8`。モバイルの折り返しヘッダー（約118）では高さ 228px 未満で開けない（トリガー基準なら約 190px 未満）。範囲外の Red Team 高さ 280 は 148px の `maxHeight` が残るため成立する。

A4（hover 型・640px以上のみ表示）の検証幅×高さ: **640×800, 768×1024, 1024×768, 1280×800**（幅は §7 の承認済み値のうち ≥640 のもの）。639×667 では「カードを表示しない（A3 が担う）」ことのみ確認する。短い高さ検証は、実測した**ヘッダー下端**（R1。以前はトリガー下端）から `maxHeight = 100px`（`shouldClose` 閾値 96px を超える）となる高さ（`h = ceil(headerBottom + 6 + 100 + 8)`、Settings の 1 行ヘッダーで約165前後）で行い、カード内スクロールによる最終行(CPU/GPU)到達を確認する。resize while open（AC-6）: 1280×800 でホバー中に 800×400、1024×768 に変更しても到達可、639 以下へ縮めるとカードは非表示（孤立しない）。

### 8-2. A4（hover 型）への AC-1〜6 適用性

PBI の AC-4 は「展開ボタンを再度押す」、AC-2 は「設定項目を押す」を前提とするが、A4 はボタンも操作項目も持たない情報カードである。適用できない文言は**捏造で合格にせず**、読み替えと代替検証を明示し、人間レビューで承認を得る（§10-1）。

| AC | A4 での適用 | 検証内容 |
|---|---|---|
| AC-1 | そのまま適用 | ホバーで開いたカード下端がヘッダー下端より下。ヘッダー高さ・各 `scrollHeight` を押し広げない。カードは `body` 直下 `position: fixed` |
| AC-2 | **読み替え**（押下可能な項目なし） | 「カード内へポインターを移動しても閉じない（ホバー継続）」。トリガー→隙間(ブリッジ。**R1: 1 行ヘッダーで約20px、折り返しヘッダーで約80〜90px**)→カードへの実ポインター移動後もカードが表示され続ける。カード内の行（CPU/GPU）が表示される |
| AC-3 | そのまま適用 | `maxHeight` 超過時にカード内スクロールで最終行(CPU/GPU)が画面内に到達（スクロールにはカード上へのポインター滞在が必要＝ホバー継続が前提） |
| AC-4 | **読み替え**（再押下トグルなし） | click トグルは追加しない。「ポインターがトリガー・ブリッジ・カードの外へ出ると閉じる」「外側 `pointerdown` で閉じる」で検証 |
| AC-5 | そのまま適用（≥640px） | 640/768/1024/1280 幅で画面内に収まり、プリセットタブバー(z10)・進捗ライン(z40)・固定ナビに隠れない（`elementFromPoint`） |
| AC-6 | そのまま適用（≥640px） | ホバー中の resize/高さ変更で再計測され最終行に到達可。639px 以下ではカード非表示（孤立しない） |
| AC-8 | 該当（将来 hover 型） | HEO-9 は将来の hover 型アクションにも適用義務（SPEC_COMMON §4-4-1 に記載）。検証例は A4 自体。合成 hover フィクスチャは追加しない |
