# REQ-154 詳細設計書: 生成キュー投入・進捗管理・Abort制御の不具合修正

## 1. 概要 (Overview)
本設計書は、生成画面（GeneratePage）におけるバッチ投入、中断（Abort）、追加投入、進捗カウント、およびキュー残数表示の動作不良（REQ-154）に対する包括的な改修設計を定義します。

---

## 2. 影響分析・対象範囲 (Scope & SSoT Impact)

### 影響を受けるフロントエンドファイル
1. **`frontend/src/store/useGenerationStore.ts`** (MODIFY):
   - `cancelJob`: 対象ジョブが `currentPromptId` または `queueRunning` に該当する場合、確実に `POST /interrupt` を発行するよう条件を修正。
   - `activeBatch` / `updateBatchJobStatus`: バッチ追加投入に対応した状態更新とマージをサポート。
2. **`frontend/src/pages/GeneratePage/hooks/useGenerateAction.ts`** (MODIFY):
   - `handleGenerate`: `AbortController` を生成・登録し、単体連続投入中の中断要求でループを停止するよう改修。
   - `handleGenerateSets`: 既存の `activeBatch`（未完了ジョブ）を破棄せず、新規投入ジョブとマージして `setActiveBatch` を更新し、母数 `m` を正しく合算・維持。
3. **`frontend/src/pages/GeneratePage/hooks/useGeneratePageState.ts`** (MODIFY):
   - `totalQueueCount`: ComfyUI の `/queue` に加え、クライアント側の未完了・送信中バッチジョブ（`isBatchSubmitting` / 未登録 `pending`）を加味してリアルタイムに算出。

   - ステータスバーの全体進捗テキスト表示（`全体進捗: X/Y 枚目`）において、完了数ではなく現在生成中のインデックス（1-indexed）を表示するよう計算ロジックを修正。

   - `frontend/src/store/__tests/useGenerationStore.test.ts`
   - `frontend/src/pages/GeneratePage/hooks/__tests__/useGenerateAction.test.ts`

## 3. 詳細設計 (Detailed Design)

### 3.1 Abort制御・キュー削除の全面改修 (`useGenerationStore.ts`)

#### 課題とComfyUI APIの責務分離
ComfyUIのAPI仕様において、ジョブのキャンセルは状態に応じて命令が異なります：
1. **実行中（Running）ジョブの中断**: `POST /interrupt`
2. **キュー待機中（Pending）ジョブの削除**: `POST /queue` (body: `{"delete": [prompt_id]}`) またはクリア `{"clear": true}`
3. **履歴（History）の削除**: `POST /history` (body: `{"delete": [prompt_id]}`)

現在、以下の重大な不備があります：
- **`cancelGeneration`（一括中断）の不備**: `POST /interrupt` のみを発行しており、ComfyUIの待機キュー（`queuePending`）に残っているジョブを削除（`POST /queue`）していない。そのため、1枚目を中断してもComfyUIが待機中の2枚目・3枚目を続けて実行してしまい、Abortが効かない・遅い最大の原因となっている。
- **`cancelJob(promptId)`（個別ジョブのキャンセル）の不備**: `queueRunning` ポーリング結果のみで判定しているため、実行中ジョブなのに待機中と誤判定して `POST /queue (delete)` を送ってしまい、ComfyUI側で無視される。また、実行中ジョブを中断した際に後続の自セッション待機ジョブをどう扱うかの制御が不十分。

#### 改修方針

##### ① `cancelGeneration` / `cancelAllJobs`（一括中断の実行順序制御）
> [!IMPORTANT]
> **実行順序の厳密な制御（待機キュー削除 ⇒ 実行中ジョブ中断）**:
> もし先に `POST /interrupt` を呼ぶと、ComfyUI が現在のジョブを中断した瞬間に待機キュー（`queuePending`）から次のジョブを取り出して実行を開始してしまい、後続の `POST /queue (delete)` が間に合わず次のジョブが走り出してしまうレースコンディションが発生します。
> したがって、必ず **「① 待機キュージョブ削除 (`POST /queue`)」⇒「② 実行中ジョブ中断 (`POST /interrupt`)」** の順序で実行します。

```typescript
cancelGeneration: async () => {
  // 0. クライアント側の投入ループを即座に遮断
  get().abortSubmission()
  if (!comfyUrl) return
  const activeUrl = resolveComfyUrl(comfyUrl)
  try {
    const filterJob = (job: any) => !get().filterOwnSession || job[3]?.client_id === get().clientId
    const pendingIds = get().queuePending.filter(filterJob).map((j) => j[1])
    const runningIds = get().queueRunning.map((j) => j[1])
    const allIds = [...runningIds, ...pendingIds]

    // 1. 【最優先】待機キュージョブを ComfyUI 側キューから削除（次のジョブが走り出すのを防止）
    if (pendingIds.length > 0) {
      await fetch(`${activeUrl}/queue`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ delete: pendingIds } as ComfyQueueDeletePayload),
      })
    }

    // 2. 実行中ジョブの割り込み中断
    await fetch(`${activeUrl}/interrupt`, { method: 'POST' })

    // 3. 履歴削除
    if (allIds.length > 0) {
      await fetch(`${activeUrl}/history`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ delete: allIds } as ComfyHistoryDeletePayload),
      })
    }

    // 4. ステートリセット
    set({
      activeBatch: null,
      isGenerating: false,
      currentPromptId: null,
      activeClientId: null,
      generationStartTime: null,
      currentNode: null,
      nodeProgress: null,
      currentWorkflow: null,
    })
    localStorage.removeItem(LS_KEYS.CURRENT_PROMPT_ID)
    await get().fetchQueue()
  } catch (e) {
    console.error('Failed to cancel generation:', e)
  }
}
```

##### ② `cancelJob(promptId)`（個別ジョブの確実な分岐）
- `promptId === get().currentPromptId || get().queueRunning.some((j) => j[1] === promptId)` の場合は **`POST /interrupt`**。
- それ以外（待機キュー内）の場合は **`POST /queue { delete: [promptId] }`**。
- 該当ジョブの履歴削除 `POST /history { delete: [promptId] }`。
- `activeBatch` 内で該当ジョブを `failed` に更新し、残りのジョブ状況に応じてステートを整合。

### 3.2 `handleGenerate` への AbortController 導入 (`useGenerateAction.ts`)
#### 課題
単体生成のループ中に中断を行っても、`handleGenerate` 内に AbortController がないためループが止まらない。

#### 改修方針
```typescript
const handleGenerate = async () => {
  if (!workflow) return
  const activeBypassNodeIds = Array.from(
    new Set(
      bypassProfiles
        .filter((p) => p.is_enabled)
        .flatMap((p) => p.bypassed_node_ids)
    )
  )

  const syncedParamValues = applyParamSync(currentParamValues)

  const abortController = new AbortController()
  setSubmissionAbortController?.(abortController)
  setIsBatchSubmitting?.(true)

  try {
    for (let i = 0; i < currentBatchSize; i++) {
      if (abortController.signal.aborted) break

      let wfJson = JSON.parse(JSON.stringify(workflow.json_body)) as Record<string, unknown>
      injectParams(wfJson, syncedParamValues, currentSeedMode, currentSeed, i)
      if (activeBypassNodeIds.length > 0) {
        wfJson = applyBypass(wfJson, activeBypassNodeIds, comfyObjectInfo)
      }
      await queuePrompt(wfJson, { paramValues: syncedParamValues, appliedAssets }, { signal: abortController.signal })
    }
  } finally {
    setIsBatchSubmitting?.(false)
  }
}
```

### 3.3 追加投入時のバッチ配列マージ (`useGenerateAction.ts`)
#### 課題
`handleGenerateSets` 開始時に既存の `activeBatch` が上書きされ、生成中の母数 `m` がリセットされる。

#### 改修方針
- 実行中の `activeBatch` が存在する場合、未完了（`pending` または `generating`）のジョブおよび既存の全ジョブを保持し、新規ジョブを末尾に追加して配列を拡張する。
- 既存のバッチがある場合は `[...existingActiveBatch, ...newJobs]` としてマージし、母数 `m`（`activeBatch.length`）を合計値とする。

```typescript
const existingBatch = activeBatch || []
const newBatchJobs: BatchJob[] = []
checkedSets.forEach((setItem) => {
  for (let i = 0; i < setItem.batchSize; i++) {
    newBatchJobs.push({
      promptId: `pending-${setItem.name}-${i}-${Date.now()}`,
      setName: setItem.name,
      status: 'pending'
    })
  }
})

const initialBatch = [...existingBatch, ...newBatchJobs]
setActiveBatch(initialBatch)
```

### 3.4 キュー残数カウントのリアルタイム化 (`useGeneratePageState.ts`)
#### 課題
ComfyUIの `/queue` ポーリング値のみを参照しているため、クライアントが投入中・検証中（`isBatchSubmitting` / `pending`）のジョブが除外され「Queue: 0」と表示される。

#### 改修方針
`totalQueueCount` を以下のように計算：
```typescript
const totalQueueCount = useMemo(() => {
  const filterJob = (job: any) => !store.filterOwnSession || job[3]?.client_id === clientId
  const comfyRunningCount = store.queueRunning.filter(filterJob).length
  const comfyPendingCount = store.queuePending.filter(filterJob).length
  const comfyTotal = comfyRunningCount + comfyPendingCount

  // クライアント側で投入中・未登録の pending ジョブ数（promptId が pending- で始まるもの）
  const localPendingCount = store.activeBatch
    ? store.activeBatch.filter((j) => j.status === 'pending' && j.promptId.startsWith('pending-')).length
    : 0

  return comfyTotal + localPendingCount
}, [store.queueRunning, store.queuePending, store.filterOwnSession, clientId, store.activeBatch])
```

### 3.5 全体進捗表示の助数詞「枚目」補正 (`DesktopLayout.tsx`, `MobileLayout.tsx`)
#### 課題
現在 `<span>全体進捗: {finished}/{total} 枚目</span>` となっており、1枚目生成中に `0/m 枚目` と表示されてしまう。

#### 改修方針
```typescript
const finished = activeBatch ? activeBatch.filter((j: any) => j.status === 'completed' || j.status === 'failed').length : 0
const total = activeBatch ? activeBatch.length : 1
const hasGenerating = activeBatch ? activeBatch.some((j: any) => j.status === 'generating') : isGeneratingHere
// 生成中は finished + 1、全件完了または生成待機中は適切に clamp
const currentItemNumber = hasGenerating ? Math.min(total, finished + 1) : Math.min(total, finished)
```
表示:
```tsx
<span>全体進捗: {currentItemNumber}/{total} 枚目</span>
```
これにより、1枚目生成中は `1/5 枚目`、2枚目生成中は `2/5 枚目`、全完了時は `5/5 枚目` と正しく表示される。

## 4. 非機能要件・安全性
- バッチ投入の中断時、`localStorage` のメタデータやプロンプトマッピングの整合性を破壊しない。
- 他クライアントとのセッション分離（`filterOwnSession`）が維持されること。
