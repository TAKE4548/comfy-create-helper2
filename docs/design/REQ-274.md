# REQ-274: Windows環境におけるWeb Managerポーリングによるバックエンド(WinError 64)クラッシュの防止 詳細設計書

## 1. 背景と根本原因分析 (Root Cause Analysis)

### 1-1. 発生現象
Windows環境下で Web Manager を起動した状態、または Web Manager からバックエンド（ポート8000）を起動した際、バックエンドログに以下の致命的例外が出力され、通信受付が停止（またはプロセスごとクラッシュ）する。

```text
ERROR:    Accept failed on a socket
OSError: [WinError 64] 指定されたネットワーク名は利用できません。
```

### 1-2. メカニズムの解明
1. **Windows Python 3.8+ のイベントループ仕様**:
   Windows環境の標準 `asyncio` は、I/O完了ポート (IOCP) を利用する `ProactorEventLoop` がデフォルトとなっている。
2. **AcceptEx の動作と即時切断**:
   `ProactorEventLoop` はリスナーソケットの接続受付に Win32 API の `AcceptEx`（オーバーラップI/O）を使用している。
3. **Web Manager のポーリング切断特性**:
   Web Manager のサーバーステータス取得エンジン（`tools/server-manager/server_status.py`）は、2秒おきに `socket.create_connection(('127.0.0.1', 8000))` を実行し、即座にコンテキストマネージャを抜けて `socket.close()` を呼ぶ。
   この時、ソケットのグレースフルシャットダウン（`shutdown(SHUT_RDWR)`）が行われずに急激にクローズされると、Windows TCPスタックは TCP RST パケットを送信するか、未完了のオーバーラップ操作をキャンセルする。
4. **ProactorEventLoop の致命的なソケット破棄バグ**:
   `asyncio.proactor_events.BaseProactorEventLoop._start_serving` の内部ループでは、`f.result()` 時にクライアントの切断に起因する `OSError`（WinError 64, 1236, 10054 等）が発生すると、例外ハンドラがリスナーソケット自身に対して `sock.close()` を呼び出してしまう（Python 標準ライブラリ既知の挙動）。
   リスナーソケットが破棄されるため、以降ポート 8000 へのあらゆる接続が `ConnectionRefused` となり、バックエンドが応答不能となる。

## 2. アーキテクチャ設計方針 (Multi-Layer Defense Architecture)

本改修では、単一箇所の対策に依存せず、**「原因側（Web Manager切断）の無害化」** と **「受付側（バックエンド）の二重防御（Selector化 ＋ Proactor例外防壁）」** を組み合わせた多層防御を構築する。

```mermaid
flowchart TD
    subgraph ClientSide["Web Manager (クライアント側)"]
        SS["server_status.py / server-manager.ps1"]
        SS -->|1. socket.connect| TCP["TCP Handshake"]
        SS -->|2. s.shutdown(SHUT_RDWR)| FIN["Graceful FIN (No RST)"]
        SS -->|3. s.close()| CL["Clean Disconnect"]
    end

    subgraph BackendRun["起動レイヤー (run_server.bat)"]
        BAT["run_server.bat"] -->|--loop asyncio:SelectorEventLoop| UV_CLI["Uvicorn CLI"]
        UV_CLI --> SEL_LOOP["SelectorEventLoop 起動<br/>(WinError 64 構造的非発生)"]
    end

    subgraph BackendApp["バックエンドアプリケーション (app.main)"]
        INIT["app.main 読込"]
        INIT --> DEF_MOD["app.utils.windows_loop_defense"]
        DEF_MOD -->|Policy 登録| POL["WindowsSelectorEventLoopPolicy"]
        DEF_MOD -->|直接実行 python -m uvicorn 防護| PATCH["ProactorEventLoop._start_serving パッチ<br/>(WinError 64 検知時に sock.close() を防止し accept 再試行)"]
    end
```

### 2-1. レイヤー1: Web Manager の TCP ヘルスチェックのグレースフル化
- `tools/server-manager/server_status.py` の `check_port_listening()`:
  - 接続確立後、`s.close()` の直前に `s.shutdown(socket.SHUT_RDWR)` を呼び出す。
  - これにより TCP 4-way ハンドシェイク（FIN/ACK）が正しく完了し、RST パケットの発生を防止する。
  - 例外発生時も確実にクローズされるよう `try ... finally` ガードを適用。
- `tools/server-manager/server-manager.ps1` の `Test-PortOpen`:
  - `TcpClient` を使用するフォールバック処理において、接続成功時に `$tcp.Client.Shutdown([System.Net.Sockets.SocketShutdown]::Both)` を実行してから `$tcp.Close()` を行う。

### 2-2. レイヤー2: Uvicorn 起動オプションの SelectorEventLoop 指定
- `backend/run_server.bat`:
  - 引数に `--loop` が含まれていない場合、デフォルトで `--loop asyncio:SelectorEventLoop` を追加して起動する。
  - `SelectorEventLoop` は Win32 IOCP / `AcceptEx` を使用せず、標準の `select()` システムコールでポーリングするため、ポートスキャンや切断による `[WinError 64]` が構造上絶対に発生しない。

### 2-3. レイヤー3: バックエンド側の ProactorEventLoop 自律例外防護
- 直接実行（`python -m uvicorn app.main:app` 等）で `--loop` が明示されない場合、Uvicorn は初期ループとして `ProactorEventLoop` を生成した上で `app.main` をインポートする。
- このケースに対応するため、`backend/app/utils/windows_loop_defense.py` を新設し、`backend/app/main.py` の最上部で実行する。
- **防護ロジック**:
  1. `sys.platform == "win32"` の場合、`asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())` を適用。
  2. `asyncio.proactor_events.BaseProactorEventLoop._start_serving` をラップ。
  3. `loop(f)` 内で `OSError` が発生した際、`winerror in (64, 1236, 10053, 10054)`（一時的切断エラー）であれば、警告ログを出力した上で `sock.close()` をスキップし、新規に `self._proactor.accept(sock)` を再発行してリスナーを健全に維持する。

## 4. トレードオフとリスク開示 (Trade-off Disclosure)

1. **`SelectorEventLoop` のサブプロセス制限**:
   - Windows において `SelectorEventLoop` は `asyncio.create_subprocess_exec` などの非同期サブプロセス実行をネイティブサポートしない（制限事項）。
   - Prompt Surgeon のバックエンドは、外部プロセス起動を `subprocess.run` / `Popen`（同期またはスレッドプール）で行っており、`asyncio` サブプロセス API に依存していないため実用上の影響はない。
2. **Proactor モンキーパッチの局所性**:
   - Python 内部の未公開メソッド `_start_serving` をラップするため、将来の Python メジャーバージョンアップで内部構造が変更される可能性がある。
   - そのため、パッチ適用時は `try ... except` で安全にフォールバックさせ、かつ `run_server.bat` 側では公式引数 `--loop asyncio:SelectorEventLoop` を第一防壁とすることで耐障害性を高める。
