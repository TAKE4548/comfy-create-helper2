# REQ-437 設計書: プリセット一括削除時の孤立 `workflow_preset_values` 残存による新規作成 `IntegrityError` 修正

## 1. 概要と根本原因

`POST /api/workflow-presets` 実行時に `sqlite3.IntegrityError: UNIQUE constraint failed: workflow_preset_values.preset_id, workflow_preset_values.variant_id, workflow_preset_values.sub_key` が発生し HTTP 500 となる不具合（P1）を修正する。

### 根本原因（3要因の複合）
1. **ORM カスケード迂回**: `backend/app/routers/presets.py:230-237` の `bulk_delete_presets` が `db.query(models.WorkflowPreset).filter(...).delete(synchronize_session=False)` でバルク SQL `DELETE` を直接実行するため、`WorkflowPreset.values` の ORM `cascade="all, delete-orphan"` が発火しない。
2. **SQLite 外部キー制約の未有効化**: `backend/app/database.py:9-22` の `configure_sqlite_pragmas` が `PRAGMA foreign_keys=ON` を設定していないため、DDL 上の `FOREIGN KEY(preset_id) REFERENCES workflow_presets(id) ON DELETE CASCADE` が SQLite 側で無効化されている。
3. **最大 ID の再利用衝突**: `workflow_presets.id` は SQLite の `AUTOINCREMENT` なし `INTEGER PRIMARY KEY` であるため、最大 ID のプリセットを一括削除すると次回 `create_preset` で同一 ID が再利用され、残存していた孤立 `workflow_preset_values` 行と `uq_workflow_preset_values_preset_variant_sub_key` が衝突する。

## 2. `PRAGMA foreign_keys=ON` 影響評価（Requirement 3）と設計判断

### 2.1 現状調査の事実根拠
実 DB（`db/prompt_surgeon.db`）に対する読み取り専用 `PRAGMA foreign_key_check` およびコードベース精査により、以下を確認した。

1. **実 DB の既存 FK 違反**:
   - `workflow_preset_values -> workflow_presets`: **1,872 件**（26 プリセット分。本件の直接原因）
   - `dataset_projects -> workflows`: **4 件**（ワークフロー削除後に残存した孤立プロジェクト）
   - `workflow_preset_values -> mapping_variants`: **0 件**
2. **他テーブル・ルーターの未対応箇所**:
   - `DatasetProject.workflow_id`（`backend/app/models.py:715`）は `ForeignKey("workflows.id")` に `ondelete` 指定がなく、`Workflow` 側にも `dataset_projects` リレーションシップがない。`PRAGMA foreign_keys=ON` を有効化すると、`DELETE /api/workflows/{workflow_id}`（`workflows.py:371-377`）が既存の `DatasetProject` 参照時に `IntegrityError` で失敗する。また、実 DB の孤立 4 件に対して `PUT /api/dataset/projects/{project_id}` 等で更新を行うと `FOREIGN KEY constraint failed` が発生する。
   - `LoraTrainingJob.project_id`（`backend/app/models.py:750`）も `ForeignKey("dataset_projects.id")` に `ondelete` がなく、`DatasetProject` 側のカスケード定義もないため、`DELETE /api/dataset/projects/{project_id}` が失敗するようになる。
3. **マイグレーションおよびテストへの影響**:
   - `step_034_mapping_variants_phase5_constraints`（`backend/app/migrations/steps.py:1150-1201`）等は `DROP TABLE` + `ALTER TABLE ... RENAME` によるテーブル再構築を行っており、`PRAGMA foreign_keys=ON` 下では参照中テーブルの `DROP TABLE` 失敗や意図しないカスケード削除を引き起こす恐れがある。
   - 既存テスト（例: `backend/tests/integration/services/test_ref_image_gc.py:90-95` の `_loc_preset_value`）には親レコードなしで `workflow_preset_values` を直接挿入するフィクスチャが存在する。

### 2.2 設計判断とトレードオフ
- **判断 A（採用）**: `REQ-437` では `backend/app/database.py` の `configure_sqlite_pragmas` は変更せず（`PRAGMA foreign_keys=ON` のグローバル有効化は見送り）、以下により本不具合を確実かつ安全に解消する。
  1. `bulk_delete_presets` で子テーブル `workflow_preset_values` を同一トランザクション内で明示的に先行削除する。
  2. 起動時マイグレーション `step_037_cleanup_orphaned_workflow_preset_values` により既存の孤立 `workflow_preset_values` 行を冪等に除去する。
  - **トレードオフ**: 他テーブルの将来的な bulk SQL 削除で同様の FK 不整合が起きる可能性は残るが、`DatasetProject` 等のデータ損失や既存機能・マイグレーションの回帰リスクをゼロに抑えられる。グローバル `PRAGMA foreign_keys=ON` 化は、`DatasetProject` / `LoraTrainingJob` の `ondelete` ポリシー確定・孤立 4 件の救済方針決定・マイグレーションガードを伴う別 PBI として分離推奨する。
- **判断 B（`bulk_delete_presets` の実装方式）**: ORM ループ（対象を取得し 1 件ずつ `db.delete(preset)`）ではなく、**子テーブル明示バルク削除 + 親テーブルバルク削除**を採用する。
  - **理由**: 対象 N 件に対して ORM ループは N+1 回の `SELECT` と個別 `DELETE` を発行するが、明示バルク削除は単一トランザクション内で定数回（2 回）の SQL `DELETE` で完了し、パフォーマンスを維持したまま `WorkflowPresetValue` の孤立を完全に防止できる。なお `WorkflowPreset` の子テーブルは `workflow_preset_values` のみであることを `backend/app/models.py` で確認済みである。

## 3. 詳細設計

### 3.1 一括削除ルート修正（`backend/app/routers/presets.py`）
`bulk_delete_presets`（L230-237）を以下の手順に修正する。
1. `payload.ids` が空リストの場合は DB 操作を行わず 204 を返す（既存仕様維持）。
2. `target_ids = list(dict.fromkeys(payload.ids))` で重複を除去する。
3. 同一セッション・同一トランザクション内で先に `models.WorkflowPresetValue`（`preset_id.in_(target_ids)`）を `delete(synchronize_session=False)` で削除し、続けて `models.WorkflowPreset`（`id.in_(target_ids)`）を `delete(synchronize_session=False)` で削除する。
4. `db.commit()` により原子的に確定する。存在しない ID が含まれていても例外を送出せず静かにスキップする（既存仕様維持）。

※単件削除 `delete_preset`（L240-246）は `db.delete(preset)` を使用しており、`WorkflowPreset.values` の `cascade="all, delete-orphan"`（`passive_deletes` 未設定）により子行も連動削除されるため変更不要。

### 3.2 起動時クリーンアップマイグレーション（`backend/app/migrations/steps.py`）
`step_037_cleanup_orphaned_workflow_preset_values(conn: Connection, inspector: Inspector) -> None` を追加し、`ALL_MIGRATION_STEPS` 末尾へ登録する。
1. `table_names = set(inspector.get_table_names())` を取得する。
2. `"workflow_preset_values" in table_names and "workflow_presets" in table_names` の場合のみ実行する（未作成テーブルへの安全ガード）。
3. 以下の SQL を実行する（`NOT EXISTS` により親が存在しない行のみ削除）:
   ```sql
   DELETE FROM workflow_preset_values
   WHERE NOT EXISTS (
       SELECT 1 FROM workflow_presets wp
       WHERE wp.id = workflow_preset_values.preset_id
   )
   ```
4. `res.rowcount` から削除件数を取得し、`logger.info(f"Migrated: Step 037 cleaned up {deleted_count} orphaned workflow_preset_values rows.")` を記録する。
5. 有効な `workflow_presets` に紐づく `workflow_preset_values` は保持され、再実行時は `deleted_count == 0` となり完全に冪等である。

## 4. Seam Map (`[W-DD-SEAM]`)

1. **Integrated (real code)**:
   - FastAPI ルーター `backend/app/routers/presets.py`（`bulk_delete_presets`, `create_preset`, `list_presets`, `update_preset`, `delete_preset`）
   - SQLAlchemy ORM モデル `WorkflowPreset`, `WorkflowPresetValue`, `Workflow`, `MappingVariant`
   - マイグレーションランナー `MigrationRunner` / `run_migrations` / `step_037_cleanup_orphaned_workflow_preset_values`
   - インメモリ SQLite 永続化（API テストは `conftest.py` の `db_session` SAVEPOINT 分離、マイグレーションテストは独立 `sqlite:///:memory:` エンジン）
2. **Severed (external I/O only)**:
   - ComfyUI 外部 HTTP 通信（`http://localhost:8188/queue`, `http://127.0.0.1:8188/queue` を `respx` トランスポート層でモック）
   - 本番ディスク DB（`db/prompt_surgeon.db` には一切アクセス・書換を行わない）
3. **Mock Level**:
   - トランスポート境界（`respx`）のみ。内部ビジネスロジック・ORM・マイグレーション関数へのモンキーパッチは禁止する。
4. **PBT Decision**:
   - 不要。パーサ・DSL・数式や広大な組合せ入力空間を持たず、整数 ID リストによるバルク削除と決定論的 SQL `NOT EXISTS` クリーンアップのみを対象とするため、境界値・異常系を含む明示的統合ケースで網羅する。
5. **Fault Injection**:
   - `bulk_delete_presets` に対する境界・異常入力（空配列 `ids: []`、存在しない ID のみ、実在 ID と非実在 ID の混在、重複 ID）および、`step_037` の前提テーブル欠損時の非破壊スキップ・再実行冪等性をテストする。
