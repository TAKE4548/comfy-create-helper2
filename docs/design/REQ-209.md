# REQ-209: ワークフローパラメータ解析・注入（LoRAスタック/バイパス）ロジックの共通化と二重実装排除 詳細設計書

## 1. 概要 (Overview)

本設計は、ComfyUIワークフローJSONのパラメータ解析および注入ロジックが `useWorkflowParams.ts` と `useGenerateAction.ts` に二重実装されている問題を解消し、純粋関数モジュール `workflowParamInjector.ts` にロジックを一元化（SSoT化）するものである。
また、`bypassUtils.ts` における複数連続ノードバイパス時の接続リンク解決を推移的・トポロジカルに安全解決するアルゴリズムへと刷新し、スキーマ未定義時の安全フォールバックおよび循環参照防止機構を強化する。

## 3. 詳細実装仕様 (Implementation Details)

### 3.1 ワークフローパラメータ解析・注入モジュール (`frontend/src/utils/workflowParamInjector.ts`)

#### 1) 型定義
```typescript
export interface WorkflowNode {
  inputs?: Record<string, any>
  class_type?: string
  [key: string]: any
}

export interface SeedInjectionOptions {
  seedMode: 'random' | 'fixed'
  seed: number
  index?: number
}

export interface InjectWorkflowParamsOptions {
  workflow: Workflow
  paramValues: Record<string, string>
  seedOptions?: SeedInjectionOptions
  cloneJson?: boolean
}
```

#### 2) パラメータ抽出関数
- `extractGeneralParam(node: WorkflowNode | null | undefined, paramName: string): string`
  - `node.inputs[paramName]` または `node.inputs['value']` から文字列として抽出。
- `extractLoraStackParams(node: WorkflowNode | null | undefined, role: string): Record<string, string>`
  - `num_loras` / `lora_count` またはキー名（`lora_${i}_name`, `lora_name_${i}`）の最大インデックスからスロット数を検出し、スロット 1〜N の名称・ウェイト・モデル強度・CLIP強度を正規化抽出。
- `getInitialParams(workflow: Workflow): Record<string, string>`
  - `workflow.mappings` を走査し、`lora_stack` または一般パラメータの初期値を抽出し辞書化。

#### 3) パラメータ注入関数
- `injectLoraStackParams(inputs: Record<string, any>, role: string, paramValues: Record<string, string>, classType?: string): void`
  - `easy loraStack` 判定（`num_loras` / `lora_1_name` / `class_type === 'easy loraStack'`）。
  - `easy loraStack` の場合:
    - `inputs.num_loras = loraCount`
    - スロット 1〜loraCount に `lora_${i}_name`, `lora_${i}_strength`, `lora_${i}_model_strength`, `lora_${i}_clip_strength` をセット。
    - スロット (loraCount + 1)〜10 の既存定義を `None` / `1.0` に初期化。
    - 標準キー（`lora_count`, `lora_name_${i}` 等）を完全削除。
  - 標準 `loraStack` の場合:
    - `inputs.lora_count = loraCount`
    - スロット 1〜loraCount に `lora_name_${i}`, `lora_wt_${i}`, `model_str_${i}`, `clip_str_${i}` をセット。
    - スロット番号 > loraCount の余剰キーを完全削除。
    - easy loraStackキー（`num_loras`, `lora_${i}_name` 等）を完全削除。
- `injectGeneralParam(inputs: Record<string, any>, paramName: string, inputType: string | null | undefined, rawValue: string | undefined): void`
  - `int` (`parseInt`), `float` (`parseFloat`), `boolean` (`=== 'true' || === '1'`), `string` への型変換とセット。
- `injectWorkflowParams(options: InjectWorkflowParamsOptions): Record<string, any>`
  - `workflow.json_body` のディープクローンを作成（`cloneJson !== false` 時）。
  - デフォルトパラメータと入力 `paramValues` をマージ。
  - 各マッピングに対して `injectLoraStackParams` または `injectGeneralParam` を適用。
  - `seedOptions` が渡された場合は `Sampler_Seed` ノードに対してシード値を注入（random: 0〜2^32-1, fixed: seed + index）。
  - パラメータ注入済みのワークフローJSONオブジェクトを返却。

### 3.3 バイパスユーティリティの安全性向上 (`frontend/src/utils/bypassUtils.ts`)

#### 1) 推移的リンク解決アルゴリズム (Transitive Link Resolution)
- バイパス対象リスト `bypassedNodeIds` のうち、`comfyObjectInfo` にスキーマが存在するノードのみを `validBypassSet` として抽出（スキーマ不在時は警告を出力してバイパス対象から除外）。
- 各バイパス対象ノードの output slot → input slot の対応関係を `computeOutputToInputMapping` で事前計算。
- ワークフロー内の全ノードの inputs を走査し、接続先が `validBypassSet` に含まれる場合、循環参照防止用 `visited: Set<string>` を用いて非バイパスノードに到達するまでリンクを推移的に追跡（Transitive Walk）。
- 型不一致やリンク終端が不正な場合は安全に該当 input スロットを削除（切断）。
- 全ノードのリンク解決完了後、`validBypassSet` に含まれるノードを一括削除。
- 入力される `bypassedNodeIds` の順序に一切依存せず、複数直列ノードや分岐ノードのバイパスが決定論的に成立することを保証。
