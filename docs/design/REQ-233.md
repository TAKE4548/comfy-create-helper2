# REQ-233 詳細設計書: server-manager ポート開放待ちタイムアウトのconfig化とリトライ機構の導入

## 1. 背景と課題

`tools/server-manager/` において、WSL2 上の ComfyUI、Windows 上の FastAPI バックエンド、React フロントエンドの一括起動およびライフサイクル管理が行われている。

現状の実装では以下の問題が存在する：
1. **ComfyUI 起動待ち時間の不足とハードコード**:
   `tools/server-manager/server-manager.ps1` 内で定義された `Wait-For-Port` およびその呼び出し箇所（計8箇所）において、待機タイムアウト時間として固定値 `10` 秒がハードコードされている。
   WSL2 上の ComfyUI は PyTorch、CUDA/ROCm ランタイムの初期化、多数のカスタムノード読み込みを伴うため、初回起動時やキャッシュ未生成時にはポート `8188` の開放までに 15〜30 秒以上を要することが頻繁に発生する。
2. **リトライ耐性の欠落**:
   ポート未開放のまま 10 秒が経過すると即座に待機処理が終了し、マネージャー上は起動失敗（`STOPPED`）と判定されてしまう。プロセス自体は WSL2 側で起動処理を継続している場合でも、マネージャーとの同期が破綻する。
3. **設定の外部化不足**:
   マシンスペックや利用するカスタムノード数によって ComfyUI の起動時間は大きく変動するが、待機時間やリトライ回数が `config.json` から調整できない。

## 2. アーキテクチャと設計方針

### 2.1 設定スキーマ設計 (`config.json`)
各サービス個別（`wsl`, `backend`, `frontend`）の待機パラメータと、全体共通のデフォルト設定（`port_wait`）をサポートする。

```json
{
    "wsl": {
        "port": 8188,
        "wait_timeout_sec": 30,
        "retry_count": 3,
        "retry_interval_sec": 2
    },
    "backend": {
        "port": 8000,
        "wait_timeout_sec": 15,
        "retry_count": 2,
        "retry_interval_sec": 1
    },
    "frontend": {
        "port": 5173,
        "wait_timeout_sec": 15,
        "retry_count": 2,
        "retry_interval_sec": 1
    },
    "port_wait": {
        "default_timeout_sec": 15,
        "default_retry_count": 2,
        "default_retry_interval_sec": 1
    }
}
```

#### 設定フォールバックルール (後方互換性保証):
1. サービス個別設定 (`$cfg.$serviceKey.wait_timeout_sec`) が存在し 0 より大きい場合 ➔ その値を採用
2. 全体設定 (`$cfg.port_wait.default_timeout_sec`) が存在し 0 より大きい場合 ➔ その値を採用
3. いずれも未定義または不正値の場合 ➔ 既定値（WSL/Comfy: 30秒, その他: 15秒）を採用
※ `retry_count` および `retry_interval_sec` も同様の階層で解決する（デフォルト: retry_count=3 for WSL / 2 for others, retry_interval_sec=2 for WSL / 1 for others）。

#### 2) リトライ対応 `Wait-For-Port`:
```powershell
function Wait-For-Port (
    [int]$port,
    [int]$timeoutSec = 15,
    [int]$retryCount = 0,
    [int]$retryIntervalSec = 1,
    [string]$serviceName = ""
) {
    $totalAttempts = $retryCount + 1
    for ($attempt = 1; $attempt -le $totalAttempts; $attempt++) {
        $elapsed = 0
        while ($elapsed -lt $timeoutSec) {
            if (Test-PortOpen $port) { return $true }
            Start-Sleep -Seconds 1
            $elapsed++
        }
        if (Test-PortOpen $port) { return $true }

        if ($attempt -lt $totalAttempts) {
            Write-Host "  [WAIT] $serviceName (Port $port) not open after ${timeoutSec}s. Retrying ($attempt/$retryCount) in ${retryIntervalSec}s..." -ForegroundColor DarkYellow
            Start-Sleep -Seconds $retryIntervalSec
        }
    }
    Write-Host "  [WARN] $serviceName (Port $port) failed to open after $totalAttempts attempt(s) (timeout: ${timeoutSec}s)." -ForegroundColor Red
    return $false
}
```

#### 3) サービス連携ヘルパー `Wait-For-Service`:
サービス識別子（`"wsl"`, `"backend"`, `"frontend"`）を受け取り、ポート番号・表示名・待機設定を自動解決して `Wait-For-Port` を呼び出す。

#### 4) 呼び出し箇所の更新:
- `Start-AllServices`: 各サービスの起動後、ハードコード `10` を廃止し `Wait-For-Service` を順次呼び出し。
- `Restart-ServiceByName`: サービス再起動後の待機処理を `Wait-For-Service` に統一。
- メインディスパッチ (`Action == "start"`): 単体起動後の待機処理を `Wait-For-Service` に統一。

## 4. トレードオフとリスク分析 (Trade-off Disclosure)

1. **最大待機時間とエラー検知のトレードオフ**:
   - タイムアウト30秒 × リトライ3回とすると、起動に完全に失敗した場合（例: Python起動時クラッシュ）に最大約100秒待機することになる。
   - **対策**: ポートが正常に開いた瞬間に即座にループを抜けて `$true` を返すため、正常系では1秒の無駄もなく完了する。異常系での待機時間が気になるユーザーは `config.json` で数値を縮小可能。
2. **Web Manager (`server_api.py`) との互換性**:
   - `server_api.py` は `server-manager.ps1` を `-Action start` でサブプロセス呼び出しし、完了後に最新ステータスを取得する。
   - 待機時間が延びても HTTP リクエストハンドラーはブロックされて完了を待つため、APIクライアント側のタイムアウト（ブラウザのfetch）を考慮する必要があるが、ブラウザ標準fetchのタイムアウトは数分間あるため問題ない。
