## 2. 設計時の計測結果

読み取りと実行のみ。ソースは変更していない。FE の「適用後」は scratch ディレクトリ上のコピー（`node_modules` を junction で共有）に変更を当てて測った。BE の「適用後」は `-o testpaths=...` と、`INTERVAL` を縮める pytest プラグイン（scratch、リポジトリ外）で模擬した。計測時 CPU 負荷は 10〜73%（Antigravity・LM Studio・ブラウザ常駐）で、インシデント時の 15% より高い。以下の数値は負荷込みの実測であり、負荷が上がると悪化する。

読み取れること。

- WS テストが各約 2.8 秒かかるのは、`ResourceMonitorService._run` が lifespan 開始直後に 1 回送信（まだ接続クライアントなし）してから `asyncio.sleep(INTERVAL=2.5)` し、2 回目の送信でようやく受信するため。`INTERVAL` はクラス属性で、`self.INTERVAL` を毎周期読むため monkeypatch できる。
- ルート収集の遅さは db/（約 13,600 ファイル）などの走査。`-n auto` は各ワーカーで収集するため全体を約 10 秒押し上げる。
- `tests/unit` の 8 件超の 0.5〜0.6 秒テストは `ThreadingHTTPServer.serve_forever()` の既定 `poll_interval=0.5` で `shutdown()` が最大 0.5 秒ブロックされるのが原因（`tests/unit/test_server_status.py`、`test_server_manager_timeout.py`。ファイル合計 7.7s と 7.8s）。インシデントの「Hypothesis 再帰 4.36s」はこの待ちが 8 例分積み上がったもので、`max_examples=8` は既に明示済み。
- `test_prune_disk_cache_if_needed`（4,001 ファイル作成）は 3.4s。定数 `_DISK_CACHE_MAX_FILES` / `_DISK_CACHE_TARGET_FILES` は呼出時に読まれるため縮小して同じ論理を検証できる。
- FuguMT の実トークナイザ読込は並列時 1.1s、逐次 3.1s。モデル不在なら自動でスキップされる条件付きテストで、実トークナイザの検証が価値なので**変更しない**（マーカーで除外すると収集件数が変わり、実モデル検証が Gate 2 から消える）。

判定ルール。

- 計測は CPU 負荷（計測前後の `LoadPercentage` 平均）60% 以下のものだけを有効とする。超過時は再計測し、無効計測を PASS 根拠にしない。
- 予算超過は黙って予算を緩めない。tester は FAIL 区分で報告し、設計へ戻す（予算改訂は人間レビュー事項）。
- Duration 内訳（environment / collect / tests など）はテスト実行ログとともに `docs/logs/REQ-394/final-*` に残す（AC-1）。

## 4. FE 設計

1. **node 環境化の選定手順**（DOM 依存判定）。静的 grep は偽陰性が出るため、実行で判定する。(a) 対象は `.test.ts`（`.test.tsx` は描画のため jsdom のまま）。(b) 候補 95 件に `--environment node` を CLI で当てて実行し、全件 PASS のファイルのみ採用（43 件）。(c) 採用ファイルのうち DOM 名を含む 4 件（`headerMenuPlacement`、`usePromptClipboardStore`、`browserStorageUsage`、`queryCachePersister`）は本文を読み、`window`/`navigator` をスタブしているだけか、`jsdom` が実挙動の根拠かを確認する。実 DOM を根拠にしていれば jsdom に残す。
2. **機構は docblock**。vitest 1.6.1 は `@vitest-environment` を正規表現でファイル内容から検出し、`environmentMatchGlobs` より優先する（`cli-api` の `groupFilesByEnv` で確認）。`environmentMatchGlobs` は 43 パスの列挙が `vite.config.ts` に集中し、将来の vitest 更新で非推奨・廃止される。docblock はテストと同居し、記載漏れは安全側（jsdom）に倒れる。
3. **常設カナリア**。`queryHelpers.test.ts`（node）に `typeof document === 'undefined'`、`storeHelpers.test.ts`（jsdom 既定）に `typeof document === 'object'` を 1 件ずつ追加する。docblock の効きと既定環境の維持を恒久的に検知する（FE +2 件）。
4. **isolate の扱い**。`isolate:false` は §2.1 の E7 で状態リークによりハングしたため採用しない。`vite.config.ts` に `isolate: true` を明示し、不採用の根拠を 3 行のコメントで残す（T6）。pool/maxForks は既定のまま。
5. **遅いテスト**（T5）。対象は `queryCachePersister`、`apiCacheStorage`、`queryCacheRecovery`、`residualHistoryRestore`。待ち要因を計測で分類して記録する。実タイマー（デバウンス 1000ms など）が原因なら、既存テストが使っている `vi.useFakeTimers({ toFake: ['setTimeout','clearTimeout'] })` + `advanceTimersByTimeAsync` に揃える。アサーションの削除・緩和、テスト件数の増減、製品コードの変更は禁止。
6. 失敗時の戻し方: T4 の docblock を外すだけで元に戻る（機械的）。T6 は設定 1 ブロック。

## 5. BE 設計

1. **testpaths（AC-3）**。ルート `pytest.ini` に `testpaths = backend/tests tests` を追加。`backend/tests` と `tests` の順序はどちらでも収集に成功することを確認済み（`be-collect-testpaths-trial.txt`）。`backend/pytest.ini` の `testpaths = tests` は変更しない。Gate 1 の `pytest backend/tests/unit` は祖先の `backend/pytest.ini` を使うため影響を受けない。
2. **既存ガード `test_pytest_collection.py` への影響**。コピーした ini に testpaths が入ると、`docs/logs/...` の重複コピーを置く既存の挙動テストは、`tests/` だけが走査されて常に通る形骸化が起きる。そこで挙動テストは `.` を明示して `norecursedirs` を引き続き検証する。AC-3 用に新規 3 件を追加する（testpaths の宣言 1 件、tmp 内で `db/`・`docs/`・`frontend/` に同名 `test_dup.py` を置いた無引数収集が testpaths あり=成功／なし=衝突の対照 2 件）。BE 774 → 777。
3. **WS（AC-4）**。`ResourceMonitorService.INTERVAL` を 0.05 に縮める。内部ロジックの差し替えではなく待ち時間の定数であり、PBI が示す方針どおり（Seam Map §6）。`test_ws.py` はモジュール autouse fixture、`test_vram_guard.py` は当該テスト内の `patch.object`。アサーションは一切変えない。恒久ガードとして、`SYSTEM_STATS` 受信までの経過が 2.0 秒未満であることを検証する（本番 2.5 秒に戻れば失敗する）。
4. **その他の固定待ち**（T3）。`serve_forever(poll_interval=0.01)`、`_prune_disk_cache_if_needed` は定数を 40/36 に縮め 41 ファイルで同じ論理（超過 → 目標数まで削除）を検証。本番定数 4000/3600 は別アサーションで固定する。FuguMT は据え置き（§2.2）。`tests/support/server_manager_sandbox.py` はサブプロセス用の共有ヘルパーで影響が未証明のため変更しない。
5. **収集件数**: マーカーでの除外はしない。BE 777 = 774 + 新規 3。ノードID の差分は新規 3 件のみであることを `be-collect-baseline-ids.txt` と突き合わせる。

## 6. Seam Map

- Integrated（実コード）: BE は FastAPI app（lifespan）、`ResourceMonitorService`、WS ルーター、`ConnectionManager`、SQLAlchemy。FE は vitest + React Testing Library + Zustand + React Query（製品コードをそのまま実行）。
- Severed（外部 I/O のみ）: BE は ComfyUI/LM Studio への HTTP（respx、既存 conftest）、GPU 統計 `_get_gpu_stats`（既存どおり AsyncMock）、ディスクは `tempfile`/`tmp_path`。FE は fetch/WebSocket（既存 networkGuard/MockWebSocketController）。
- Mock Level: 内部ビジネスロジックのパッチは行わない。許容するのは(1)待ち時間定数 `INTERVAL`、(2)キャッシュ閾値定数、(3)`poll_interval` 引数、(4)FE の fake timers。いずれも検証内容を変えず時間だけを縮める。
- PBT: 対象外（パーサ・DSL・数式ではない）。既存の Hypothesis（`max_examples=8`）は変更しない。
- Fault Injection: 外部連携は追加しない。代わりに設定回帰の Red Team を設ける（テスト計画 §4）。

## 7. リスクとトレードオフ

**リスク分類: high**（`docs/design/REQ-394-test-plan.md` §3）。vitest/pytest 設定は検証コマンドの入力（argv 相当の収集範囲、環境、共有フィクスチャ）を変える。`.agents/verification.json` の Gate 2 は `scripts/run_full_suite.py` で、これが `npm test` と `pytest -n auto` を呼ぶ。したがって V1 Baseline（Gate 1 静的、Gate 2 フィルタ無しの全件、Gate 3）をフレッシュに全実行する。V2 には移行しない。ローカル実行、キャッシュ再利用、engineer の自己確認は PASS 根拠にしない。

| 論点 | 採用 | 不採用 | 理由 |
| --- | --- | --- | --- |
| FE 環境切替 | docblock | `environmentMatchGlobs` | §4-2。集中管理の利点より将来互換と同居性を優先 |
| FE 並列度/pool | 既定のまま | maxForks=6/8、threads、vm 系 | 有意差なし（§2.1）。vm 系は非互換 |
| isolate | true を明示 | false | 状態リークでハング（E7）。再試行は状態リーク検証付きの別 PBI |
| WS 待ち | `INTERVAL` 縮小 | 接続直後送信フィクスチャ | 製品コード変更が不要。接続時送信は製品仕様変更になる |
| 重いテスト | 定数縮小・poll 短縮 | `slow` マーカーで既定除外 | 除外は収集件数を変え、実検証が Gate 2 から消える |
| pytest.ini の追跡 | T7 で `root_files` に追加（承認済み・実施） | 未追加のまま | 下記 |
| 予算 | 余裕込みの絶対値 | 旧実績 ~38s/~30s | 旧値は条件不明で再現不能 |

追跡漏れ: `.agents/verification.json` の identity は `input_dirs`（backend/frontend/scripts/tests/docs/tools/server-manager）と `root_files`（README.md、.gitignore、.gitattributes）で候補のハッシュを取る。ルートの `pytest.ini` はどちらにも含まれず、変更しても候補同一性が変わらない。AC-3 の中核がこのファイルなので、T7 で `root_files` に `pytest.ini` を追加する。これは検証契約そのものの変更（verification の高リスク範囲）であり、コーディネーター／人間レビューの明示承認がない限り実行しない。承認されなければ T7 を外し、tester が `pytest.ini` を手動で候補に含めたことをレポートに記録する。T7 を外す場合は T9 の depends_on からも外す。

その他のトレードオフ。

- 到達見込み: FE は約 15〜20% 短縮にとどまる（134s → 約 112s）。38s には届かない。プロセス単位の jsdom 初期化コストが残るため。残りの手段（happy-dom への切替、projects 分割）は挙動差のリスクがあり本 PBI では扱わない。フォローアップ PBI の候補として報告する。
- 負荷依存: 計測は常駐アプリの影響で ±20% ぶれる。予算に余裕を含め、有効計測条件（負荷 60% 以下）を設けた。
- `tests/unit` 単独実行は `app` を import できず失敗する（ルート実行は `backend/tests/conftest.py` の sys.path 追加に依存）。既存挙動で本 PBI の対象外。testpaths の順序に依存しないことは確認済み。
