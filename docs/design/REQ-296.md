# REQ-296 設計: セリフ一括生成の応答とVRAM解放

## 実現性と境界

AC-1〜5はバックエンドの局所変更で実現可能。既存の2系統参照選定、吹き出し変換、UIフロー、通常の `POST /api/llm-prompts/speech-draft` に使う `call_vlm` は維持する。シーン一括生成専用の呼び出し関数を追加し、画像説明を求める既存 user 指示をこの経路から外す。元の22:11のVLM返答本文は保存されておらず、その回の文面は確定できない。

## 契約と処理順

1. 参照選定後、使用するモデルキーを確定する。LM Studio REST API の `GET /api/v1/models` から同キーの `loaded_instances` を確認する。1件ならその `id` を保持し、0件なら `POST /api/v1/models/load` にモデルキーを渡し、返却された `instance_id` を保持する。モデルのコールドスタートは4秒を超えるため、loadだけに独立した**最大120秒の有界待機**（HTTP応答待ちと処理全体の期限）を設け、list/unloadの短いタイムアウトと分離する。load応答のReadTimeout等で結果が不明なときは同じloadを再送せず、`GET /api/v1/models` を最大20秒・1秒間隔で再照会する。元の一覧で未ロードだったモデルキーに対し単一の有効なIDを確認できた場合だけ、そのIDを回収して以降の推論・`finally`の解放へ渡す。複数件・キー不一致・ID欠落・回収期限内に見つからない場合は曖昧な対象のアンロードを避け、制御されたエラーにする。
2. 同じシーン生成タスクを system と user に指定し、user の画像とテキストを一緒に送る。`POST /v1/chat/completions` の `model` フィールドへ手順1で取得した **instance_id** を渡し、解放対象と推論対象を一致させる。`response_format: {type: "json_schema", json_schema: {name, strict: true, schema}}` を付ける。スキーマは `scene_interpretation: string` と1件以上の `items` を必須とし、各 item に `role: main|sub|se`, `speaker: string`, `text: string`, `position: top_right|center_right|center|top_left|bottom_left` を必須とする。`additionalProperties: false` を指定する。ReadTimeout後の一覧に出たIDにはreadinessフィールドがなく、実機では直後にHTTP 400 `{"error":"Model is unloaded."}` を返す状態を確認した。この完全一致エラーが初めて発生した場合に限り、同一ID・同一要求を総計最大90秒まで再試行する。各後続要求のtimeoutは最大60秒（残りdeadlineでcap）とする。厳密な準備待ちHTTP 400またはreadiness開始後のReadTimeoutの後は、残り時間内で1秒間隔に同一IDを再試行する。loadは再送せず、IDを切り替えず、他のHTTP 400やこのエラー前の通信失敗は再試行せず固定コードへ分類する。期限内にreadyにならなければ安全な `LM_STUDIO_INSTANCE_NOT_READY` 失敗にする。既存のマークダウン・`<think>` 除去パーサーは互換性のため保持する。
3. `choices[0].finish_reason` と `message.content` の型・空文字を検査する。`length` 等の途中終了、空本文、非JSON、スキーマ不一致を別の安全なコードで分類する。JSON Schema は生成制約として使い、サーバー側でも型・必須項目・列挙値・非空 items を検証する。失敗時も生のモデル本文、プロンプト、画像データ、LM Studio のエラー本文をログやAPI応答へ載せない。
4. 正常・推論失敗・キャンセルの各経路で、保持した `instance_id` に対し `POST /api/v1/models/unload` を実行する。URLは現在の `settings.llm_base_url` の `/v1` を REST 用 `/api/v1` に変換する。HTTP成功だけでは足りず、応答JSONの `instance_id` が一致し、再取得した `GET /api/v1/models` の対象 `loaded_instances` からそのIDが消えた時のみ `vram_unloaded=true` とする。unload HTTP失敗時も一覧を確認し、正確な対象IDの不在を確認できれば解放済みとして扱う。存在・一覧不明・ID不一致はFalse。失敗時は1回再試行し、成功と報告しない。推論の元エラーはアンロード失敗で上書きせず、両方を安全な分類コードで診断する。
5. JSON API と NDJSON stream の双方で同じエラー分類を返す。入力不正の404との混同、例外文字列の露出、非JSONを500にする経路を修正する。正常応答の `vram_unloaded` と stream の `vram_unload_failed` は検証結果のみで決める。

`vram_unloaded` は対象VLMインスタンスがモデル一覧から消えたことを表す。GPU総使用量が0であることや他モデルの解放を意味しない。LM Studioの現在の`loaded_instances` entryには`id`と`config`だけがあり、readiness状態はない。

## LM Studio の一次資料

- [Structured Output](https://lmstudio.ai/docs/developer/openai-compat/structured-output): Chat Completions に `json_schema` を指定し、返答を `choices[0].message.content` で受ける。一部モデルは非対応。
- [Chat Completions](https://lmstudio.ai/docs/developer/openai-compat/chat-completions): リクエストの `model` はモデル識別子。資料は任意の別名インスタンスIDの扱いを明記していない。下記の局所プローブでこの環境の基本経路を確認した。
- [List your models](https://lmstudio.ai/docs/developer/rest/list): `GET /api/v1/models` の `key` と `loaded_instances[].id`。
- [Load a model](https://lmstudio.ai/docs/developer/rest/load): `POST /api/v1/models/load` の応答 `instance_id`。
- [Unload a model](https://lmstudio.ai/docs/developer/rest/unload): `POST /api/v1/models/unload` の必須本文 `instance_id` と応答 `instance_id`。

## 依存と影響

上流はモデル設定キー、REQ-291の2系統参照、JPEG画像入力。下流は `convert_items_to_bubbles`、JSON/streamルーター、`vram_unloaded`、ComfyUIのVRAM競合回避。`call_vlm` は旧画像説明APIでも使用中なので共通関数の戻り型変更は避ける。並行シーン生成で同一インスタンスを互いにアンロードしないよう、取得から検証までモデル単位の排他を設ける。これは同一バックエンドプロセス内を対象とし、外部LM Studio利用者や複数ワーカーとの共有は運用制約として明記する。

## 別名instance IDの局所実現性

2026-09-29の対象LM Studioで、モデルキー `qwen3.5-9b-claude-4.6-highiq-instruct-heretic-uncensored` を別名ID `req296-instance-probe` としてロードした。`POST /v1/chat/completions` に `model=req296-instance-probe`、入力 `Reply with exactly OK.`、`max_tokens=2` を送り、HTTP 200、`finish_reason=stop`、本文 `OK` を得た。そのIDを `/api/v1/models/unload` で解放した後、`GET /api/v1/models` のロード済みインスタンスは0件だった。これにより**この環境での別名IDを使うテキスト推論と解放**は確認済み。画像入力、`response_format.json_schema`、本番のセリフ生成スキーマを同時に使う経路は未検証で、Gate 3の完了条件とする。

## Gate 3で見つかったコールドスタート障害

2026-09-30のGate 3では、未ロードのモデルをシーン生成が取得する際、`POST /api/v1/models/load` にlist/unloadと共通の4秒タイムアウトが適用され、`ReadTimeout` になった。LM Studio側のロードはその後完了したため、HTTP応答のタイムアウトだけではロード失敗と判断できない。上記の120秒待機と状態再照会で、この遅い正常ロードと「応答を受け損ねたがロードは完了した」経路を扱う。再照会で単一IDを回収できない場合は解放成功を報告しない。さらにlistにはreadiness fieldがないため、ReadTimeout回収IDへ要求したChat Completionsが厳密に `{"error":"Model is unloaded."}` と返った後の同一ID/同一要求retryを90秒に制限する。後続request timeoutは最大60秒（残りdeadlineでcap）とし、準備待ちHTTP 400またはreadiness開始後のReadTimeout後は1秒間隔で再試行する。HTTP400またはReadTimeoutが期限を超える場合は制御された失敗にする。外部利用者が同じモデルを同時ロードした場合はIDの所有者を完全には証明できないため、共有LM Studio上での同時ロードを運用上の制約とする。

## 設計レビューの判断点

既存ロード済みモデルもシーン生成後に解放する。REQ-291の「推論直後に全量返却」を優先するためであり、同じLM Studioを他の利用者が共有する場合はその利用を中断しうる。複数インスタンスまたはモデルキー不一致では推測でアンロードしない。モデルの構造化出力非対応は明確な失敗とし、無制約JSONへ自動で切り替えない。

局所プローブでは別名instance IDの指定が成功した。ほかのLM Studio設定・バージョンでID指定が拒否された場合は制御エラーにする。本番の画像と構造化JSONを組み合わせた呼び出しをGate 3で確かめる。モデルキーへ戻して別インスタンスを推論・解放する誤対応は避ける。

## BA監査の記録

`local_model_adapter.py ba-audit` は終了コード0だったが、モデルへの `target_content` が空と報告された。`--unload-after ba-audit docs/design/REQ-296.md` でも、モデルは参照ファイル本文が渡されていないと報告し、要求内容を評価しなかった。traceは `Action=ba-audit | Model=qwen3.5-9b-claude-4.6-highiq-thinking-heretic-uncensored | Domain=reasoning | Params=9.0B | Quant=Q6_K`。したがって外部BA判定は **INCONCLUSIVE**。この設計で補った境界条件は `finish_reason=length/content_filter`、choices欠落、200の偽成功、インスタンスID不一致、ロード状態残存、推論エラーと解放エラーの重複、同時要求。監査後の `unload` は終了コード0で、LM Studioのモデル一覧にロード済みインスタンスがないことを確認した。
