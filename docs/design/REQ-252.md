# REQ-252: 生成履歴サムネイル表示におけるイベントループブロッキング解消と多重ロード最適化 詳細設計書

## 1. 背景と課題

REQ-245（モバイル・弱Wi-Fi最適化）導入後、ホストPC（ローカル環境）において生成履歴ストリップの表示時に「画面が十数秒フリーズする」「ジョブキューの進行監視やポーリングが止まる」という重大な性能劣化が確認された（[docs/incident_report.md](../incident_report.md) 参照）。

### 特定された構造的ボトルネック
1. **メインイベントループの同期ブロッキング (FastAPI)**:
   `backend/app/routers/comfy.py` の `get_comfy_thumbnail` (`async def`) 内で、Pillow による画像デコード・縮小・WebPエンコードが同期的に実行されている。CPU負荷の高い画像変換処理により、FastAPIのシングルスレッドイベントループが1画像あたり 900ms〜1300ms 完全に停止する。
2. **横スクロールコンテナにおけるネイティブ `loading="lazy"` の機能不全**:
   Chromium/WebKit などのブラウザネイティブ `loading="lazy"` は縦スクロールを基準に判定するため、横スクロールコンテナ（`overflow-x: auto`）内の要素は画面外であってもマウント時に全件一括リクエストされる。履歴に20枚以上ある場合、マウント直後に数十件のリクエストが殺到する。
3. **インメモリ限定キャッシュによるコールドスタート常態化**:
   キャッシュがプロセス内メモリ（`OrderedDict` 最大500件）のみで永続化されておらず、サーバー再起動や開発時のホットリロードのたびに全消失し、初回アクセス時に常に最悪ケースの全件再変換が発生する。
4. **多段オーバーヘッドとコスト逆転**:
   ComfyUI 出力ディレクトリへのローカルI/O直読ではなく、HTTP `/view` を介して毎回数MBのPNGを取得しているため、ローカル環境では直接読み込み（数ミリ秒）に対して数十倍の遅延が発生している。

---

## 2. アーキテクチャ設計方針

本設計では、バックエンド・フロントエンド双方の構造的ボトルネックを解消し、ローカル環境およびモバイル環境の双方向で超低遅延な表示を実現する。

```mermaid
flowchart TD
    subgraph Frontend["Frontend (GeneratePage)"]
        A[GeneratePage Mount] --> B[LazyThumbnail]
        B -- "In Viewport (IO)" --> C[Request /api/comfy/thumbnail]
        B -- "Offscreen" --> D[Placeholder / No Network Request]
    end

    subgraph Backend["Backend (FastAPI)"]
        C --> E{In-Memory LRU Cache?}
        E -- "Hit (<1ms)" --> F[Return WebP Response]
        E -- "Miss" --> G{Disk Cache Exists? (db/thumbnails)}
        G -- "Hit (<1ms)" --> H[Read File via asyncio.to_thread]
        H --> I[Populate In-Memory LRU]
        I --> F
        G -- "Miss" --> J[Fetch ComfyUI /view via HTTP]
        J --> K[asyncio.to_thread: Pillow Decode & WebP Convert]
        K --> L[asyncio.to_thread: Write Disk Cache]
        L --> I
    end
```

## 3. 詳細仕様

### 3-1. バックエンド: ワーカースレッド委譲とディスクキャッシュ永続化 (`routers/comfy.py`)

#### (1) Pillow 同期変換処理の切り出しと `asyncio.to_thread` 化
FastAPI のイベントループを解放するため、同期的な画像処理を独立した関数に切り出し、ワーカースレッドプールで実行する。

```python
def _convert_to_webp_thumbnail(image_bytes: bytes, size: int, quality: int) -> bytes:
    """CPU-bound Pillow conversion executed in worker thread."""
    image = Image.open(io.BytesIO(image_bytes))
    if image.mode not in ("RGB", "RGBA"):
        image = image.convert("RGBA")
    image.thumbnail((size, size))
    buf = io.BytesIO()
    image.save(buf, format="WEBP", quality=quality)
    return buf.getvalue()
```

エンドポイント内での呼び出し:
```python
webp_bytes = await asyncio.to_thread(_convert_to_webp_thumbnail, resp.content, size, quality)
```

#### (2) ディスクキャッシュ層の導入と ComfyUI 元画像生存確認 (HEAD リクエスト)
- 保存ディレクトリ: `Path(settings.snapshot_path).parent / "thumbnails"`（デフォルト: `../db/thumbnails`）
- ディレクトリ自動生成: サーバー起動時または初回書き込み時に `mkdir(parents=True, exist_ok=True)`。
- キャッシュファイル命名規則: `hashlib.sha256(cache_key.encode("utf-8")).hexdigest() + ".webp"`
- **多層キャッシュ参照と ComfyUI 実体生存確認**:
  1. キャッシュヒット判定（L1 メモリキャッシュ または L2 ディスクキャッシュ）
  2. キャッシュヒット時、ComfyUI `/view` へ軽量な **HEAD リクエスト（約 20ms）** を送信し、元画像がまだ実在するかを検証する。
     - **元画像が存在 (200)**: キャッシュから WebP を即座に返却（重い Pillow 再変換は完全にスキップ）。
     - **元画像が削除済み (404)**: ディスクおよびメモリキャッシュから当該エントリを自動削除（パージ）し、HTTP 404 を返却。
  3. キャッシュミス時:
     - ComfyUI から元画像を取得 (`client.get`)。404 なら 404 を返却。
     - `asyncio.to_thread` で WebP 変換（サムネイル用に高速な補間アルゴリズムを使用）。
     - ディスクへ書き込み (`await asyncio.to_thread(path.write_bytes, webp_bytes)`)。
     - メモリキャッシュに格納後返却。

#### (3) ディスクキャッシュの容量・件数上限管理（LRU自動プルーニング）
- **上限件数**: `_DISK_CACHE_MAX_FILES = 4000`（1枚約25KB換算で約100MB目処）。
- **バッチ削除**: ファイル数が 4,000 件を超えた場合、最終更新日時（mtime）が古い順にソートし、約10%（400件）を削除して 3,600 件まで縮小する（ファイル書き込みごとの過剰な走査を防ぐバッチプルーニング）。
- **非同期実行**: ファイル走査および削除処理はすべて `asyncio.to_thread` で実行し、イベントループを一切ブロックしない。

### 3-2. フロントエンド: 横スクロール対応遅延ロード (`LazyThumbnail.tsx`) と 404 履歴自動消去

#### (1) `LazyThumbnail` コンポーネントの新設
ブラウザのネイティブ `loading="lazy"` が横スクロールコンテナ内で機能しない問題を解消するため、スクロールコンテナの `Ref` を `root` として監視する `IntersectionObserver` コンポーネントを導入する。

```typescript
// frontend/src/components/LazyThumbnail.tsx
export interface LazyThumbnailProps {
  src: string
  alt: string
  containerRef?: React.RefObject<HTMLElement | null>
  className?: string
  style?: React.CSSProperties
  rootMargin?: string
  onError?: () => void
}
```

- **表示判定および 404 ハンドリング**:
  - `containerRef.current` を `IntersectionObserver` の `root` に指定。
  - `rootMargin: '0px 150px 0px 150px'` を指定し、スクロール手前約150pxで先行ロード。
  - 交差前（`!isVisible`）は軽量なプレースホルダー `div`（アスペクト比・背景色のみ）を描画。
  - 交差検知時（`isVisible = true`）に初めて `src` を設定。
  - **404 欠損検知**: `<img>` の `onError` を捕捉し、`onError` コールバックを親に通知。親（`DesktopLayout` / `MobileLayout`）は当該画像を履歴一覧から自動除外し、UIから即座にフェードアウト・消去する。

- **表示判定ロジック**:
  - `containerRef.current` を `IntersectionObserver` の `root` に指定（指定なしまたは未設定時は viewport を root とする）。
  - `rootMargin: '0px 150px 0px 150px'` を指定し、スクロール手前約150pxで先行ロードしてチラつきを防止。
  - 交差前（`!isVisible`）は軽量なプレースホルダー `div`（アスペクト比・背景色のみ）を描画し、`<img>` タグの `src` を空にしてブラウザ通信の発行を完全に阻止する。
  - 交差検知時（`isVisible = true`）に初めて `toThumbnailUrl(src)` を `<img>` に設定し、オブザーバーの監視を解除（1回のみ発火）。

#### (2) `DesktopLayout.tsx` および `MobileLayout.tsx` への適用
- 履歴ストリップの画像要素を `<LazyThumbnail>` に差し替え。
- `containerRef` に `gallery.scrollContainerRef` を渡す。
- 初期表示時は画面内に見える 4〜6 枚程度のみ通信が発生し、20枚あっても画面外の14枚以上は通信が発生しない。

## 5. リスクとトレードオフ (Trade-off Disclosure)

1. **ディスク容量の消費**:
   - ディスクキャッシュを保存するため、生成画像数に比例して `db/thumbnails` のディスク使用量が増加する（WebP 256px は1枚あたり約 15〜30KB。10,000枚で約 200MB 程度）。
   - **対策**: スナップショット画像（数MB）に比べて極めて軽量であり、現段階での実害は極小。将来的なクリーンアップは別要件として整理可能。
2. **初回の画像交差検知オーバーヘッド**:
   - `IntersectionObserver` のリスナーが増加するが、1コンテナあたり数十個程度であり、画面外の通信ブロックによるネットワーク帯域・コネクション枠保護のメリットが圧倒的に上回る。
