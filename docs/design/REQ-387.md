## 2. 現状と根本原因（要約）

`GenerationRepository.snapshot()` は `generation_jobs` を無条件に全件取得する（現DB 874行。`metadata_json` が約23.7MBあり、各行で prompt 抜粋のため2段の `json.loads` を行う）。1回あたり約370msかかり、async 経路からイベントループ上で同期実行される。呼出頻度は次のとおり。

- worker: 0.2秒周期（pending/VRAM待機時は毎周期）。
- reconcile: 2.5秒毎に3回。
- プレビュー: 1フレームごとに3回（`asyncio.Lock` 保持下）。
- HTTP: `/state`、`/preview/{job_id}`、`/images/{job_id}/availability` の各リクエスト。

この結果、BE全体が停止する。WS配信も毎回約917KBある。REQ-333 で設計した終端job 1000件の保持（`prune_terminal`）は配線されていないが、仮に配線しても snapshot は最大1000件の終端jobを含むので、主因は解消しない。DB保持と snapshot 配信窓を分けて定義していないことが仕様上の欠落である。

## 4. アーキテクチャ

### 4-1. snapshot 配信窓（T2: repository）

`snapshot()` が返す `jobs` を、次の和集合の **job全件** に限定する（重複なし、並びは従来どおり `accepted_at ASC, item_index ASC`）。

1. 非終端job: `status IN ('queued','submitting','running','unconfirmed')`
2. 非終端jobを1件以上含む batch の全job
3. 現在の `normal_group_id`（app_settings `_NORMAL_GROUP_KEY`。空なら対象なし）に属する全job
4. 直近 `K = _SNAPSHOT_RECENT_BATCHES = 20` 個の batch（`MAX(accepted_at)` の降順）の全job
5. session ごとに直近10件の released job（`json_extract(release_json,'$.released_at') DESC, job_id DESC` の順位 ≤ `_SNAPSHOT_RELEASED_PER_SESSION = 10`）

`batches` には、窓に含まれるjobの batch だけを入れる（従来と同じ導出）。

N/F が保たれる根拠:

- FE の `selectedJobs` は「現在の normal_group 全job」または「指定 Studio batch 全job」でフィルタする。条件 2〜4 により、group と batch は単位ごと欠けずに入る。
- Studio の進捗を表示している batch は、非終端jobを含むか直近20 batch に入っている。現DBの batch サイズは最頻値3、最大25。
- unconfirmed は条件1で全件入る。
- `selectReleasedJobs(sessionFilter, 10)` の結果は、条件5（session毎の上位10）の部分集合になる。

### 4-2. snapshot キャッシュ（T2）

- `snapshot()` は最初に、軽量クエリで `(revision, normal_group_id)` を読む。キーが前回と同じならキャッシュした結果の `copy.deepcopy` を返し、`generation_jobs` は読まない。
- revision は repository の全書込み（`accept_batch` / `transition` / `release_unconfirmed` / `annotate_late_identity` / `prune_terminal`）で `_increment_revision` により単調増加する。このため、別インスタンスや別接続のコミット後もキーの変化で必ず無効化される。
- `threading.Lock` でキャッシュ参照・更新を保護する。
- prompt 抜粋のメモ: `(job_id, prompt_id) → excerpt` を最大 4096 件保持する。窓クエリでは `metadata_json` を `defer` し、メモにないjobだけ `metadata_json` を一括取得する。抜粋が変わり得る契機は prompt_id の初回確定だけ（`_persist_frozen_prompt_metadata`）なので、キーに prompt_id を含めれば十分である。

### 4-3. job単位照会（T2 + T3）

- repository に `get_job(job_id) -> dict | None` と `find_job_by_prompt(prompt_id) -> dict | None` を追加する。主キー/unique索引で1行だけ読み、`_job_view` 互換の dict を返す。
- service の `_find_job(state, job_id)` を instance method にする。state 内にあればそれを返し、なければ `repository.get_job` にフォールバックする（窓外の終端job・released に対する cancel/release/late-identity の判定を従来どおり保つ）。
- prompt_id で探す `cancel_queued` と `_cancel_single` も、新設 `_find_job_by_prompt(state, prompt_id)` で同様にフォールバックする。
- `RepositoryPort`（Protocol）に2メソッドを追加し、テスト用 `MemoryRepository` にも実装する。
- router の `/preview/{job_id}` と `/images/{job_id}/availability` は `service.find_job(job_id)`（公開ラッパー）を使う。窓外の過去jobの availability も従来どおり返せる。

### 4-4. プレビューと worker の再読込削減（T3）

- `on_preview`: `_snapshot()` は1回だけにする。`_advance_wire_revision` は state を引数で受ける形にし、再読込を避ける。publish 用の `_publish_snapshot` は呼ぶ（キャッシュヒットにより DB の jobs 読込は発生しない）。
- worker の 0.2秒周期の `_snapshot()` は維持するが、4-2 のキャッシュヒットで revision 1行の読込だけになる。

### 4-5. reconcile 失敗ログ抑制（T3）

- `_run_worker` の reconcile 例外は、失敗状態へ遷移した初回だけ `logger.warning(..., exc_info=True)` で記録する。
- 連続失敗の回数 n で判定する（時刻に依存せず決定的にテストできる）。n ∈ {24, 48, 96, 192}、および n > 192 で (n − 192) が 240 の倍数のときだけ `logger.warning("... still failing (%d consecutive)")` を exc_info なしで記録し、それ以外は `logger.debug` にする（2.5秒周期換算で約1分・2分・4分・8分、以降10分毎）。
- 成功に戻った時点で `logger.info("Generation reconciliation recovered after n failures")` を1回記録し、カウンタを戻す。

### 4-6. SQLite 接続設定とログ（T4）

- `database.py`: SQLite URL の場合だけ、`event.listens_for(engine, "connect")` で `PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`、`PRAGMA synchronous=NORMAL` を設定する。`:memory:` では journal_mode は `memory` のままでよい。
- `logging_config.py`: `logging.getLogger("httpx").setLevel(logging.WARNING)` と `httpcore` も同様に追加する。

### 4-7. 対象外（明示）

- `prune_terminal` の配線: 主因ではないため本PBIでは扱わず、後続課題として記録する。
- `BaseHTTPMiddleware` の置換: 寄与度が未計測。本PBIでは触れない。
- 同期DB呼出の `asyncio.to_thread` 移行: 窓とキャッシュで1回あたり数msに収まるため見送る（トレードオフ参照）。
- FE変更なし。

## 5. Seam Map

1. **Integrated (real code)**: `GenerationRepository` + SQLAlchemy + SQLite（`:memory:` または tmp file）、`GenerationService`、`ComfyGenerationBridge`、FastAPI router（`generation_api_router`）、`ws_manager`。
2. **Severed (external I/O only)**: ComfyUI HTTP は `httpx.MockTransport`（既存 `LocalUpstream`）で切る。プレビューフレームは bridge の `on_preview` コールバック入口から投入する。DB は sandbox の SQLite。
3. **Mock Level**: repository/service の内部関数を monkeypatch しない。計測用の呼出カウントは SQLAlchemy の `before_cursor_execute` イベント（DB transport 境界）で取る。
4. **PBT Decision**: 窓の選定（集合演算）は入力空間が広いため、既存 Hypothesis を用いて PBT を必須とする。性質: 任意の job 集合について、窓で求めた N/F・unconfirmed 一覧・released 上位10（全session/各session）が全件 snapshot から求めた値と一致する。
5. **Fault Injection**: ComfyUI `/queue` の ConnectError 連続（ログ抑制と回復）、snapshot 例外時の 503 維持、窓外 job_id への cancel/release/preview/availability（404/already_terminal の維持）。

## 6. 性能閾値（AC-8/AC-3/AC-4 の規定値）

閾値はテスト環境差を吸収できる余裕を持たせて設定する。

- AC-8: 終端job 1000件（各 metadata 約27KB）+ 現在group 3件の構成で、キャッシュミス時 `snapshot()` ≤ 150ms、キャッシュヒット時 ≤ 10ms、返却 job 数 ≤ 非終端 + group + 20 batch + released 上位分。
- AC-3: 同構成のサービス稼働中に、プレビュー30フレーム・軽量 GET 並行時のイベントループ最大遅延（10ms tick の実測遅れ）≤ 150ms、`GET /api/generation/preview/{job_id}` 応答 ≤ 300ms。
- AC-4: 実行中・待機中jobがある状態で、`POST /api/generation/cancel`（単件/一括）が上流応答を含めて ≤ 2秒で返る。

## 7. トレードオフとリスク

- **窓の固定値 K=20 / released 10**: 小さすぎると、古い Studio batch を開いたままの画面で進捗が欠ける。現DBの分布（最大25件/batch、Studio 20件）に加え、条件2/3 で非終端と現在groupを常に含めるので実害は小さい。代替案として期間窓（直近T時間）も検討したが、長時間放置で空になるため件数窓を採用した。
- **revision キーのキャッシュ**: 全書込みが revision を増やす前提に依存する。将来 revision を増やさない書込みを追加すると古い snapshot を返す恐れがある。repository テストで全書込みメソッドの無効化を固定する。
- **`to_thread` 不採用**: 同期処理は残るが有界（数ms）になる。スレッド化すると `asyncio.Lock` 下の状態読込と書込みの順序保証の再検証が必要になり、変更範囲とリスクが大きい。
- **WAL**: `-wal`/`-shm` ファイルが DB 隣に生成される。バックアップ時は3ファイル一体で扱う必要がある（WALは使い捨てキャッシュではない）。ネットワークドライブ上のDBでは WAL を使えない（本環境はローカル）。
- **ログ抑制**: 失敗の詳細 stack trace は初回だけになる。障害解析時は初回レコードと回復ログで区間を特定する。
- **性能テストの揺らぎ**: 実時間閾値は CI 負荷で揺れ得るため、余裕を持たせた閾値と構造的アサーション（DB行読込数・キャッシュヒット）を併用する。

## 8. Rework 1（受入 FAIL を受けた改訂。2026-10-25）

本節は §1〜§7 を**削除せず**、受入 FAIL（`docs/logs/REQ-387/qa-code-report.md`、`qa-doc-report.md`）への対応として §4-2 / §5 / §7 の一部を改訂する。承認済みの記述は履歴として残し、矛盾する場合は本節が優先する。設計監査（ba-audit design）は利用者決定により保留のまま進める。

### 8-1. 発端

- Gate 2 回帰: `test_generation_api.py::test_generation_state_read_failure_returns_typed_503_without_partial_state` が `generation_jobs` を DROP した後の `/state` に 503 を期待するが、T2 の snapshot キャッシュ（キー `(revision, normal_group_id)`）がヒットして 200 を返す。
- 原因は実装の欠陥ではなく仕様の欠落である。§4-2 は「キーが同じならキャッシュを返す」とだけ定め、状態取得の失敗条件を契約にしていなかった。
- 選択肢: (a) 契約を明確化して既存テストを更新、(b) ヒット時にも `generation_jobs` の生存確認クエリを足す、(c) キャッシュ導入を見直す。利用者は **(a)** を決定した。

### 8-2. 改訂する契約（§4-2 への追記）

- **503 契約**: 状態取得が失敗したら 503 とする。状態取得には、キーである `revision` と `normal_group_id`（`app_settings`）の読込を含む。`GenerationRepository.snapshot()` はキー読込を含む処理全体を例外変換の範囲内に置き、失敗を `HTTPException(503)` にする。`GET /api/generation/state` はそれを型付き 503（`generation_state_unavailable`、`outcome=unconfirmed`）にし、部分的な state を返さない。
- **キャッシュヒットの前提**: キャッシュは、キー読込が成功し、かつキーが一致した場合にだけ返す。キー読込が失敗した場合はキャッシュの有無にかかわらず 503 とする（キャッシュを先に参照しない）。
- 実装変更は不要である。現行の `snapshot()` は `app_settings` の 2 キー読込を `try:` の内側で行い、`except Exception` で 503 に変換している。設計側で次を確認済み: 温まったキャッシュのまま `app_settings` を読込不能にすると、現行コードで型付き 503（部分 state なし）が返る。したがって T7 の所有に `generation_repository.py` を**含めない**（テストが緑にならない場合だけ設計へ差し戻す）。

### 8-3. 許容リスク（利用者決定）

- `generation_jobs` だけが壊れる障害（テーブル欠損・破損・当該テーブルのみのロック）は、キャッシュ有効の間は隠れ得る。次の書込みで revision が変わり、キャッシュが無効になって初めて 503 として顕在化する。
- 受け入れる理由: ヒット時に `generation_jobs` へ触れないことが、AC-2（プレビュー中の `generation_jobs` SELECT ≤ revision変化+2）と AC-8（ヒット時 ≤ 10ms）の根拠である。生存確認クエリ（案 b）は、プレビューで `generation_jobs` の SELECT 回数を増やすか、別テーブルの読込で代替する形になり、検出できる障害の範囲が限られる割に AC-2 の構造を複雑にする。DB 障害は通常 `app_settings`（同一 SQLite ファイル）にも及び、キー読込で検出される。
- このリスクを固定するテストは書かない（将来、生存確認を導入しても契約違反にしないため）。仕様文書（SPEC_GENERATE）にはリスクを書かず、503 契約の 1 文だけを追記する。リスクは本節と受入報告にだけ記録する。
- AC-2 / AC-8 の閾値と構造的アサーションは変更しない。
