# REQ-239 詳細設計書: WSL2 ComfyUI ポート疎通確認およびプロセス状態・停止・再起動ライフサイクル管理の正常化

## 1. 概要と目的
本設計は、`tools/server-manager` において一括起動（`start`）、状態確認（`status`）、停止（`stop`）、および再起動（`restart`）時に生じる以下の構造的課題を根本解消することを目的とする。
1. WSL2 上で動作する ComfyUI が正常稼働しているにもかかわらず、ポート確認がタイムアウトして fail 扱い（`[STOPPED]`）となる問題。
2. 停止処理が非同期かつ完了待機を行わないため、再起動時に古いプロセスのポート解放前に新プロセスの起動判定が走り「起動済み」と誤認して起動をスキップし、結果的に停止したまま放置されるレースコンディション（空振り）。
3. ウィンドウ付き起動（Windowed モード）時に停止を行っても、Windows 側の親 `cmd.exe` がクローズされず空プロンプトとして画面上に残留・増殖する問題。
4. プロセスハング等で `pkill` (SIGTERM) が効かない場合の強制終了（SIGKILL / pkill -9）安全装置の欠如。

---

## 2. 根本原因の構造的分析
1. **WSL2 仮想化ネットワークと Windows TCP スタックの差異**:
   - Backend (8000) や Frontend (5173) は Windows OS 上のネイティブプロセスであるため、Windows の TCP テーブルに `State: Listen` かつ `OwningProcess: <PID>` が直接記録される。
   - ComfyUI (8188) は WSL2（Linux VM）内部で稼働しており、Linux 側カーネルで `0.0.0.0:8188` がリッスンされている。
   - Windows ホスト上には `8188` をリッスンする Windows ソケットは存在せず、WSL2 の localhost proxy / NAT 機構により、Windows から `127.0.0.1:8188` に向けた能動的な接続（TCP Connect）が行われた際に初めて動的転送・確立される。
2. **`Get-NetTCPConnection` 依存による判定欠陥**:
   - `server-manager.ps1` の `Test-PortOpen` は `Get-NetTCPConnection -LocalPort $port | Where-Object State -eq "Listen"` のみに依存していたため、WSL2 プロセスに対して常時 `$false` を返していた。
   - この結果、`Wait-For-Port` による待機ループ（最大120秒超）がタイムアウトし、`Failed to open port 8188` と赤字で失敗出力されていた。
3. **PID 取得とステータス判定の不整合**:
   - `Get-PidsFromPort` も `Get-NetTCPConnection` に依存していたため、WSL2 の PID は一切取得できず空配列 `@()` となっていた。
   - `Get-StatusObject` は `$comfyRunning = ($comfyPids.Count -gt 0)` としていたため、ComfyUI が起動中であっても常に `STOPPED` と誤判定されていた。
4. **停止・再起動時におけるレースコンディション（空振り問題）**:
   - `Stop-ComfyUIProcess` は `pkill` を投げた直後に待機せず復帰する。
   - ComfyUI は VRAM やモデルの解放に 1〜3 秒要することがあるため、`Restart-ServiceByName` 内の固定 `Start-Sleep -Seconds 1` ではポートが閉じきらない場合がある。
   - ポートが閉じきらない状態で `Start-ComfyUIProcess` が呼ばれると、多重起動ガード（`if (Test-PortOpen $cfg.wsl.port) { return }`）が「稼働中」と判定して起動を中止。その直後に古いプロセスが消滅するため、サービスが完全に停止状態のまま放置される。
5. **プロセス停止の不徹底**:
   - `Stop-PortProcesses 8188` は Windows 側 PID が空のため何も kill できない。
   - ウィンドウ起動時の親プロセス `cmd.exe /k title ComfyUI (WSL2)` は子プロセスの終了後も居座り続ける。

## 3. アーキテクチャ設計・改修方針

### 方針 1: ポート疎通判定のハイブリッド化 (`Test-PortOpen`)
`Test-PortOpen` を Windows ネイティブ判定と TCP ソケット接続テスト（フォールバック）の2段階構成とする。

1. **第1段階 (Windows ネイティブソケット検証)**:
   - `Get-NetTCPConnection -LocalPort $port -ErrorAction SilentlyContinue | Where-Object State -eq "Listen"`
   - Windows プロセス（Backend, Frontend）の場合、即座に `$true` を返す。
2. **第2段階 (.NET TcpClient によるローカル接続検証)**:
   - 第1段階が `$null` の場合、`System.Net.Sockets.TcpClient` を用いて `127.0.0.1:$port` へ非同期接続（タイムアウト 500ms）を試行する。
   - WSL2 localhost proxy 経由で ComfyUI がリッスンしていれば、即座（数ミリ秒）に接続が成功し `$true` を返す。
   - サービスが停止している場合は、即座に接続拒否または 500ms タイムアウトで `$false` を返す。

```powershell
function Test-PortConnect ([string]$host = "127.0.0.1", [int]$port, [int]$timeoutMs = 500) {
    $tcp = New-Object System.Net.Sockets.TcpClient
    try {
        $iar = $tcp.BeginConnect($host, $port, $null, $null)
        if ($iar.AsyncWaitHandle.WaitOne($timeoutMs)) {
            $tcp.EndConnect($iar)
            return $true
        }
        return $false
    } catch {
        return $false
    } finally {
        $tcp.Dispose()
    }
}

function Test-PortOpen ([int]$port) {
    $conn = Get-NetTCPConnection -LocalPort $port -ErrorAction SilentlyContinue | Where-Object State -eq "Listen"
    if ($null -ne $conn) {
        return $true
    }
    return (Test-PortConnect -host "127.0.0.1" -port $port -timeoutMs 500)
}
```

### 方針 2: ポート閉鎖待機関数の新設 (`Wait-For-Port-Closed`)
サービス停止時、ポートが完全に閉鎖されるまで確実に待機する共通関数を導入する。

```powershell
function Wait-For-Port-Closed ([int]$port, [int]$timeoutSec = 10, [string]$serviceName = "") {
    $namePrefix = if ($serviceName) { "[$serviceName] " } else { "" }
    $elapsed = 0
    while ($elapsed -lt $timeoutSec) {
        if (-not (Test-PortOpen $port)) {
            return $true
        }
        Start-Sleep -Milliseconds 500
        $elapsed += 0.5
    }
    return (-not (Test-PortOpen $port))
}
```

### 方針 3: WSL2 プロセス PID 取得関数の追加 (`Get-WslComfyPids`)
WSL2 内の ComfyUI プロセス（`python.*main.py`）の PID を取得する専用関数を実装する。
- `wsl $wslPrefix bash -c "pgrep -f 'python.*main.py'"` を呼び出し、Linux 側のプロセス PID リストを安全に取得する。
- WSL が利用不可または未起動の場合はエラーを抑制し、空配列を返す。

### 方針 4: `Get-StatusObject` の WSL2 稼働判定の堅牢化
1. まず `Get-PidsFromPort $cfg.wsl.port` を確認（Windows ネイティブ動作の場合の互換維持）。
2. PIDs が空かつ `Test-PortOpen $cfg.wsl.port` が真の場合、`Get-WslComfyPids` から WSL 側 PID を補完取得する。
3. ComfyUI の稼働状態フラグ `$comfyRunning` を `(Test-PortOpen $cfg.wsl.port) -or ($comfyPids.Count -gt 0)` で判定する。
4. これにより、CLI ステータス画面および Web マネージャー API（`/api/status`）において、ComfyUI が確実に `LISTEN` (稼働中) かつ正確な PID とともに表示される。

### 方針 5: ComfyUI 停止処理の堅牢化とウィンドウクリーンアップ (`Stop-ComfyUIProcess`)
1. **SIGTERM 送信と閉鎖待機**:
   - まず `pkill -f 'python.*main.py.*8188' || pkill -f 'python.*main.py'` を送信。
   - `Wait-For-Port-Closed -port $cfg.wsl.port -timeoutSec 5 -serviceName "WSL ComfyUI"` で最大 5 秒間閉鎖を待機。
2. **SIGKILL フォールバック**:
   - 5 秒経過してもポートが開いたまま、またはプロセスが残留している場合、`pkill -9 -f 'python.*main.py'` を実行し、さらに 2 秒待機。
3. **ウィンドウ起動時の `cmd.exe` クリーンアップ**:
   - `Get-Process cmd -ErrorAction SilentlyContinue | Where-Object { $_.MainWindowTitle -like "*ComfyUI (WSL2)*" }` を検出し、`taskkill /PID $_.Id /T /F` で確実にウィンドウを閉じる。
4. **Windows ホスト側のソケットクリーンアップ**:
   - 既存の `Stop-PortProcesses $cfg.wsl.port "ComfyUI"` も実行し、万が一 Windows 側に残存したプロセスを解放。

### 方針 6: 再起動フロー (`Restart-ServiceByName`) のアトミック化
- `Restart-ServiceByName` において、`Stop-*Process` 完了後に `Wait-For-Port-Closed` を挟み、ポートが解放されたことを確認してから `Start-*Process` を呼び出す。
- これにより、ComfyUI、Backend、Frontend すべてにおいて再起動時のレースコンディション（多重起動ガードによる起動スキップ・ポートバインド失敗）を完全に排除する。

### 方針 7: ドキュメント同期 (SSoT)
- `docs/specs/server_manager_guide.md` に、WSL2 のポート疎通判定機構、停止時の閉鎖待機・SIGKILL フォールバック、ウィンドウクリーンアップ仕様を追記する。

## 5. トレードオフ・リスク開示 (Trade-off Disclosure)

1. **停止時のタイムアウト時間 (Graceful vs Force)**:
   - 正常時は `pkill` (SIGTERM) 後、1秒未満でポートが閉じ即座に終了する。ハングアップ時のみ最大5秒待機後に `pkill -9` で強制終了するため、無用なフリーズを防止しつつ安全な終了猶予を確保する。
2. **ウィンドウプロセスのクリーンアップスコープ**:
   - タイトルに `*ComfyUI (WSL2)*` を含む `cmd.exe` のみを特定して `taskkill` するため、ユーザーが別作業で使用している通常のコマンドプロンプトや PowerShell ウィンドウには影響しない。
3. **Backend/Frontend への無影響**:
   - Backend (8000) および Frontend (5173) は引き続き第1段階の `Get-NetTCPConnection` で即座に判定されるため、既存の Windows ネイティブプロセスの挙動・パフォーマンスには一切影響しない。
