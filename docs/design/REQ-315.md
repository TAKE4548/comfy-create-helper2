# REQ-315 詳細設計

## 実現可能性と境界

AC-1〜10 は既存の React コンポーネントと翻訳 API で実現可能。タグ編集の保存形式、翻訳エンドポイント、バックエンドは変更しない。ユーザーの「リアルタイム」は、PBI の確定した解釈に従い、入力中の逐次翻訳ではなく Enter または入力欄からのフォーカス移動で確定した直後の自動更新とする。初回はサブメニューを開くとカードを表示し、確定済みのタグ本文の英日翻訳を開始する。

## 上流・下流と SSoT 影響

- 上流: `REQ-315` の AC-1〜10、完了済み `REQ-304` のドラッグ可能な和訳カード、`SPEC_COMMON.md` 第3章のタグチップ編集契約。`SPEC_SETTINGS.md` の翻訳プロバイダー設定は参照のみで、今回の変更対象ではない。
- 下流: `TagChipEditor/index.tsx` が `TagChip` の `onEdit` と `text` を供給し、プロンプトの確定値を更新する。`TagChipTranslationCard` は `translateApi.translatePrompt` を利用する。カード内コピー・ドラッグ・画面内クランプ・再試行は維持する。Generate の PC/モバイル両レイアウトなど、同じ `TagChipEditor` の利用箇所に共通して作用する。
- 仕様同期: T1/T2 の実装を確認後、マージ前に T3 で `SPEC_COMMON.md` 第3-5節の「サブメニュー内タグ名入力」と和訳カードの開閉・取得状態へ、初回自動表示、確定後更新、入力途中とキャンセル、古い結果の排除を反映する。`REQ-304` は完了時点の履歴として書き換えない。
- `doc_mapper.py docs/specs docs/backlog/pbi/archive/REQ-315.md` は「No mapped documents found」を返した。既存の `REQ-304` と実装から `SPEC_COMMON.md` を手動で特定した。`docs/system/openapi.yaml` は存在せず、既存エンドポイントの契約は `frontend/src/api/types.ts` と `client.ts` を根拠にする。API 定義を変更しないため OpenAPI 同期は発生しない。

## 状態とイベントの設計

1. `TagChip` はサブメニューを開く操作と同時に `isTranslationOpen=true` とする。手動の「翻訳」ボタンは、開いているカードを閉じた後の再表示もできる表示切替として残す。カードの閉じるボタン、親メニューの閉鎖、チップ切替は現行どおりカードを閉じる。
2. `wordInput` は編集中の値、`parseTagWeight(text).baseText` は親から渡された確定値として区別する。カードの `text` には確定値を渡す。入力欄の `onChange` では翻訳を開始しない。`handleWordSubmit` は trim 後の非空かつ変更された値だけ `onEdit(id, formatTagWeight(...))` に渡す。親の `text` が更新された時点でカードの取得対象が変わる。重みだけの変更ではベース本文が同じため再取得しない。
3. Enter と blur が連続しても、`text` が同じならカードの effect は再実行しない。Escape は編集中の値を戻し、現行どおりサブメニューとカードを閉じる。「訳を維持」は取り消した文言の訳で確定値を上書きしない意味と解釈し、再度開いた際には確定値の訳を取得する。空欄確定は現行の巻き戻し規則を維持する。
4. カードの外側クリック判定は、カード自身と親サブメニューを一つの操作領域として扱う。`menuRef?: React.RefObject<HTMLDivElement>` をカードに渡し、サブメニュー内での入力・ボタン操作ではカードを閉じない。真の外側操作では親メニューとカードが閉じる。カードは現行のメニュー DOM 子要素なので、カード内のクリックは親メニューの外側判定にも該当しない。
5. カードは `text` の変化・再試行ごとに単調増加するリクエスト番号を割り当てる。レスポンス、失敗、`finally` は現在の番号に一致し、カードが表示中の場合だけ状態へ反映する。`text` 変更時とアンマウント時に旧番号を無効化する。これにより旧文言の結果やタグ A のアンマウント後の結果がタグ B の表示を上書きしない。
6. 新しい取得を始めると旧訳文・旧エラーを消し、取得中を表示する。成功は空白を除いた `translated_prompt` がある場合に限る。空応答は「訳文を表示できません」、拒否・HTTP エラーは失敗、規定時間内に応答しない場合はタイムアウトとして表示し、再試行を許す。期限はカード側で10秒とし、期限後に届いた応答は無視する。翻訳 API の入力は `{ prompt: baseText, source_lang: 'en', target_lang: 'ja', repack: false }` のまま。

## AC 対応

| AC | 設計上の根拠 | 検証の焦点 |
| --- | --- | --- |
| 1 | メニュー展開でカード表示、確定本文の取得開始 | ボタン不要で初回訳が表示される |
| 2, 3 | Enter/blur → `onEdit` → `text` 更新 → カード取得 | 確定値のみ自動更新される |
| 4, 5 | 編集中値と確定値の分離、Escape 巻き戻し | 未確定値は API に送られない |
| 6, 10 | 取得失敗・空応答・10秒タイムアウトの明示 | タグ本文が維持され再試行できる |
| 7, 8 | リクエスト番号とアンマウント時無効化 | 古い結果は現行カードに出ない |
| 9 | 新規取得時の旧訳消去とローディング | 旧訳を新本文の訳に見せない |

## 依存・リスク・選択理由

- `TagChipTranslationCard` の操作領域と取得状態を先に整え、その API に合わせて `TagChip` を連携する。両者が同時に変更されると型不整合が見えにくいため Task Card の依存を設ける。`SPEC_COMMON.md` の同期は実装結果を確認した後に行う。
- カード側の10秒期限は UI が永久に取得中になることを防ぐ。正当に遅い翻訳も失敗扱いにする可能性があり、現行 `translateApi.translatePrompt` は `AbortSignal` を受け取らないので通信自体は継続し得る。結果は番号照合で必ず無視する。API シグネチャを広げて中断を伝播させる案は変更面積が増えるため、この PBI では採用しない。
- 自動表示はタグを開くたびに翻訳を呼ぶ。バックエンドの既存キャッシュは重複推論を抑えるが、初回リクエスト数は増える。入力中の逐次翻訳を避け、確定時のみ再取得する。
- 翻訳ボタンを残すと利用者が任意にカードを閉じて再表示できる。ボタンを削除する案は、カードを閉じた後の同じメニュー内での復帰経路がなくなるため採用しない。

## BA 監査記録

2026-10-03、`local_model_adapter.py ba-audit docs/design/REQ-315.md` を実行。モデルは `qwen3.5-9b-claude-4.6-highiq-thinking-heretic-uncensored`、終了コード0。監査の結論は「データフローは論理的に整合、クリックとフォーカスの境界を厳密に確認すべき」。採用した確認事項は T1/T2 のメニュー内操作テストと、T3 をマージ前の仕様同期にすること。監査の「ネストしたタグメニュー」「親のデバウンス」「10秒はバックエンド側」という前提は現行実装と異なる。通信キャンセルと HTTP ステータス別表示は API 変更を伴うため本 PBI の範囲外とし、カード側タイムアウトの制約は上記に明記した。監査後の `unload` は終了コード0で、LM Studio は全モデル解放を報告した。
