# REQ-235: 未カバー画面・主要モーダルのテスト新設 (Phase 2) 設計仕様書

## 1. 概要とアーキテクチャ方針

本設計は、テスト監査（`tmp/test_framework_implementation_plan.md`）の「Phase 2: 未カバー画面・主要モーダルのテスト新設」に基づき、Prompt Surgeon フロントエンドにおいてこれまで統合テストが欠落していた画面（`LoRAsPage`, `TagsPage`）および主要モーダル（`LoraModals`, `TagSetModals`, `CategoryManagerModal`, `BypassSettingsModal`, `ParamSyncModal`）の自動統合テストを新設するものである。

### 1-1. 他Phaseとの並行性および競合防止（厳守方針）
- **対象ブランチ**: `feature/test-phase2-coverage`（Phase 1 マージ後の最新親ブランチから分岐）
- **非破壊・完全新規作成**:
  既存のテストファイル（`useGenerationStore.test.ts`, `GeneratePage.test.tsx`, `HistoryPage.test.tsx` 等）およびプロダクションコードは一切変更しない。
  本Phaseでの作業は **新規テストファイルの作成（7ファイル）のみ** で完結させ、Phase 3（異常系・Red Teaming）や Phase 4（ストアテスト分割）とのコンフリクトを原理的に排除する。

```
[Phase 1: テスト基盤の構築 (REQ-234)] (Merged)
       │
       ├────── [Phase 2: 未カバー画面・モーダルテスト (REQ-235)] ← 本ブランチ (feature/test-phase2-coverage)
       │         ├── 画面テスト: LoRAsPage.test.tsx, TagsPage.test.tsx
       │         ├── 管理モーダルテスト: LoraModals.test.tsx, TagSetModals.test.tsx, CategoryManagerModal.test.tsx
       │         └── 設定モーダルテスト: BypassSettingsModal.test.tsx, ParamSyncModal.test.tsx
       │
       ├────── [Phase 3: 異常系・耐障害性テスト (REQ-236)] (Parallel)
       └────── [Phase 4: 巨大テスト分割・隔離検証 (REQ-237)] (Parallel)
```

## 2. テスト対象と詳細仕様

### 2-1. 画面統合テスト仕様 (Task 1)

#### A. `frontend/src/pages/__tests__/LoRAsPage.test.tsx`
- **テスト基盤構成**:
  - `QueryClientProvider`（`retry: false`）によるクエリコンテキスト供給。
  - MSW v2 (`server.use`) または `api/client` モックによる API 応答制御。
  - `@dnd-kit/core` の `DndContext` モック/スパイによる並び替えイベント捕捉。
- **検証項目**:
  1. **初期描画 & カードグリッド表示**:
     - LoRA カード一覧が正しくグリッド描画されること。
     - サムネイル画像（`thumbnail_path`）、モデル名、説明、推奨強度バッジ（`0.8 - 1.2` 等）が表示されること。
  2. **複合フィルタリング (AND条件)**:
     - 検索テキスト入力（モデル名・説明での絞り込み）。
     - カテゴリドロップダウン選択によるカテゴリ ID 絞り込み。
     - BaseModel チェックボックス選択による Base Model 絞り込み。
     - 複合条件で API が適切なクエリパラメータで呼び出されること、およびクライアント側フィルタが正しく動作すること。
  3. **複数選択 & 一括操作 (MultiSelectToolbar 連携)**:
     - チェックボックスクリックによる複数選択モード開始。
     - 全選択 / 選択解除の動作。
     - 一括削除クリック時に確認ダイアログが表示され、API `lorasApi.delete` が各選択 ID に対して呼び出されること。
  4. **D&D 並び替え呼び出し**:
     - ドラッグ終了イベント発生時に `lorasApi.reorder` が並び替え後の ID 配列で呼び出されること。

#### B. `frontend/src/pages/__tests__/TagsPage.test.tsx`
- **テスト基盤構成**:
  - `QueryClientProvider`、MSW v2 / API クライアントモック、DndContext スパイ。

  1. **初期描画 & タグセット一覧表示**:
     - タグセット一覧、タグチップ、バリエーションサブセットバッジ（`+2 Subsets` 等）が表示されること。

## 3. トレードオフ・リスク開示 (Trade-offs & Constraints)

1. **DOM レンダリング負荷とテスト実行速度**:
   - `LoRAsPage` や `TagsPage` は多数の子コンポーネント（`ImageCarousel`, `TagChipEditor`, `MultiSelectToolbar` 等）を持つため、フルマウント時に React のレンダリングコストが増加する。
   - **対策**: 必要最小限のモックデータ（2〜3件）でテストシナリオを構成し、1ファイルあたりのテスト時間を 2 秒未満に抑える。
2. **既存テストとの並行実行における Vitest 隔離保証**:
   - Phase 1（REQ-234）で `vite.config.ts` に `isolate: true`, `restoreMocks: true`, `clearMocks: true` を導入済みであるため、新規テストスイートが他テストに影響を与えるリスクはゼロである。
3. **競合ゼロの維持**:
   - 既存ファイルは 1 行も変更しないため、後続の Phase 3, Phase 4 ブランチとのマージ競合は発生しない。
