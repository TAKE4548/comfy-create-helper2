# Technical Design: REQ-417 ノードマッピング再設計：Master/Variant/判定定義の3層分離とスキャンロジック刷新

## 1. 概要とアーキテクチャ方針

### 1-1. 背景と課題
現行の `MappingMaster` は値の型定義とワークフロー内ノード・パラメータの判定条件を1つのテーブルに併せ持っており、以下の構造的問題を抱えている：
1. **role の一意性未保証**: `MappingVariant` に `UNIQUE(master_id, stage_id)` や `UNIQUE(role)` 制約がなく、同じ role が重複登録されても DB レベルで防止できない。
2. **判定条件の非構造化**: `expected_class_types` と `param_name` / `fallback_param_names` が独立したリストとして保持されており、「KSampler なら seed、KSamplerAdvanced なら noise_seed」のような個別ノードとパラメータの組を表現できない。
3. **判定結果の非永続化**: `WorkflowMapping` には `node_id` のみが保存され、適用時に毎回フォールバック解決をやり直しているため、決定論的なパラメータ注入が担保されない。

### 1-2. 3層分離アーキテクチャとテーブル制約
これを解決するため、マスタおよび判定構造を以下の3層に再構成する：
1. **Master層 (`mapping_masters`)**: 値の意味と型のみを定義（`base_key`, `name`, `input_type`, `group_id`）。`UNIQUE(base_key)`。
2. **Variant層 (`mapping_variants`)**: role の最小単位。永続化された `role NOT NULL` 列を持ち、`UNIQUE(role)`、`UNIQUE(master_id, stage_id)`、`UNIQUE(master_id, node_selector_id)` 制約を持つ（※SQLite では NULL 同士は重複扱いにならないため、`node_selector_id` が NULL の Variant は同一 master 内で複数共存可能）。新設された `binding_rule_set_id NOT NULL` および `node_selector_id` (NULL許容) により新定義を参照する。
3. **判定定義層**:
   - **入力候補定義 (`binding_rule_sets`, `binding_rule_entries`)**: 「どの入力か」を定義。`binding_rule_sets`: `id`, `name (UNIQUE)`, 参照中は削除不可。`binding_rule_entries`: `id`, `rule_set_id`, `class_type`, `param_name`, `priority`, `UNIQUE(rule_set_id, class_type, param_name)`。同一 Master の複数ステージ間で共有。
   - **ノード特定定義 (`node_selectors`, `node_selector_patterns`)**: 「どのノードか」を定義。`node_selectors`: `id`, `name (UNIQUE)`, 参照中は削除不可。`node_selector_patterns`: `id`, `selector_id`, `pattern`, `match_type` (`exact` / `contains`), `priority`, `UNIQUE(selector_id, pattern)`。同一ステージの複数 Master 間で共有。
4. **マッピング割当 (`workflow_mappings`)**: `input_name NOT NULL` 列を追加し、`master_id` 列を削除。
5. **マイグレーション・データ移行計画**:
   - フェーズ2: `binding_rule_sets`, `binding_rule_entries`, `node_selectors`, `node_selector_patterns` テーブル新設。既存マスタ条件を展開して新構造へ無損失で移行：
     - **Entry展開**: `param_name`（カンマ区切り順に priority 1, 2...）および `fallback_param_names`（後続 priority）を `expected_class_types` の各クラスと直積展開して `binding_rule_entries` を作成。
     - **Selector展開**: クラス名と一致するタイトルパターンは Entry 側に吸収し、固有のタイトルパターンは `exact`、`StageMaster.search_keywords` は `contains` として `node_selector_patterns` に展開。
     - **Role永続化**: `computed_role` を `mapping_variants.role` 列へ永続化し、`MappingVariant` が新定義を参照するように更新。
   - フェーズ5: 旧経路（旧スキャン分岐、旧系統フィールド、`master_id`、`m:<id>` スロットキー）の削除。
     - **事前整合性検証**: テーブル再作成前に既存 DB 内の `role` 重複を検査し、重複検知時は安全に例外を送出してロールバックする。
     - **テーブル再作成**: 重複がないことを確認した上でトランザクション内で SQLite テーブル再作成を行い、`mapping_variants` に `UNIQUE(role)`、`UNIQUE(master_id, stage_id)`、`UNIQUE(master_id, node_selector_id)` 制約を物理適用。

### 1-3. スキャン判定ロジック
- Entry（`class_type` × `param_name`）の一致を必須条件（候補抽出の足切り）とし、タイトルのパターンは順位付けにのみ使用する。
- 段階と優先度による辞書式比較（段階 -> Entry priority -> パターン priority -> ノードID昇順）で決定する：
  - 段階1: Entry一致 ＋ 自分のセレクタに完全一致（1件なら自動確定）
  - 段階2: Entry一致 ＋ 自分のセレクタに部分一致（`contains`）（1件なら自動確定）
  - 段階3: Entry一致 ＋ セレクタ未設定またはどのセレクタにも不一致（1件なら自動確定、複数なら `duplicated` 警告）
  - 段階4: Entry一致 ＋ 同じMasterの別Variantのセレクタにのみ一致（除外）
- 1つのノードが複数ステージのセレクタに一致した場合は、より具体的に一致した側（完全一致 ＞ 部分一致、部分一致同士ならより長いパターン文字列）のステージに割り当てる。
- 確定した `node_id` と一致した入力名を `WorkflowMapping.input_name` として永続化する。

## 2. Seam Map [W-DD-SEAM]

1. **Integrated (real code)**:
   - `workflow_scanner.py`: 辞書式比較アルゴリズム、Entry照合、NodeSelectorPattern照合
   - `models.py`: SQLAlchemy モデルおよびテーブルリレーション
   - `migrations/steps.py`: DB スキーマ移行ステップおよびデータ変換
   - `routers/binding_rules.py`, `routers/node_selectors.py`: CRUD API エンドポイント
   - `workflowParamInjector.ts`: フロントエンドでの `input_name` 直接適用
2. **Severed (external I/O only)**:
   - ComfyUI API / WebSocket 通信（テスト時はモックまたは fixture ワークフロー JSON を使用）
   - 実ブラウザレンダリング（UIコンポーネントテストは jsdom / vitest、E2EはPlaywright）
3. **Mock Level**:
   - 内部ビジネスロジック・スキャン関数のモンキーパッチは禁止。DB は SQLite インメモリ / テストDBを使用し、ワークフローデータは実 JSON fixture を渡して検証する。
4. **PBT Decision (Property-Based Testing)**:
   - スキャナの辞書式ソートロジック（段階、Entry priority、パターン priority、node_id）について、任意の順序で候補が渡されても同一の最優先候補が決定論的に選定されることをプロパティテスト（Hypothesis）で検証する。
5. **Fault Injection**:
   - 複数ノードが同一優先度で競合した場合の `duplicated` 警告ハンドリング
   - セレクタ未設定（NULL）時の複数ノード競合ハンドリング
   - 共有定義削除時の参照中ロールによる 400 エラーハンドリング

### D2: タスク間の依存関係とその理由
- `T1 -> T2`: スキャン判定が参照する新テーブルモデル（`BindingRuleSet`, `NodeSelector` 等）が DB に存在する必要があるため。
- `T2 -> T3`: スキャナ結果（`input_name`）を返却する API スキーマと CRUD ルーターを整備するため。
- `T3 -> T4`: フロントエンド型定義（`types.ts`）に `input_name` が反映されてから値適用ロジックを更新するため。
- `T3 -> T5`: 新設された CRUD API をフロントエンドの設定画面 UI から呼び出すため。
- `T4, T5`: ファイル所有権が完全に分離されており、並行または任意の順序で実行可能。
