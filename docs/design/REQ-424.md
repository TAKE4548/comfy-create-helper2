# REQ-424 詳細設計書: 生成キューの単一キャンセル即時実行と3秒間アンドゥ機能

## 1. アーキテクチャ概要と背景

### 1.1 背景と課題
現在、生成キュー（`queuePending`）に存在する待機中ジョブを個別にキャンセルしようとすると、誤操作防止を目的とした固定の3秒間事前ディレイ（`reserveQueuedCancel` によるカウントダウン）が発生し、キャンセルボタンを押してから実際にサーバーへリクエストが送信されキューから除外されるまでに3秒の待機を強いられていた。
意図的に即座にキャンセルしたい通常の操作テンポを著しく阻害しており、ユーザーの即応性ニーズと安全ガードが相反していた。

### 1.2 解決アプローチと受入基準 (AC)
誤操作ガードを従来の「事前待機ディレイ」から「即時実行＋事後救済（3秒間Undo）」へ刷新し、以下の受入基準をアーキテクチャ全体で満たす。
1. **即時キャンセル実行 ([REQ-424/AC-1])**: 単一待機ジョブのキャンセル操作（ごみ箱アイコン押下）時、事前待機ディレイ（3秒待機）を挟まず即座にバックエンド/上流へのキャンセルAPI（`generationApi.cancelJob(promptId, false, true)`）を発行し、待機キューから即時除外する。
2. **3秒間Undo通知UI ([REQ-424/AC-2])**: 単一キャンセル実行直後から3秒間、画面上に取り消し（Undo）ボタンおよび有効期限カウントダウンを伴う通知UIを表示し、3秒間の有効期限タイマーを開始する。
3. **安全な設定復元 ([REQ-424/AC-3])**: ユーザーが3秒以内に「取り消し」を押下した場合、キャンセルされたジョブのスナップショット（ワークフロー、プロンプト、パラメータ設定）を保持した状態で即座に再投入（`queuePrompt`）し、元の状態のままキューに復元する。
4. **自然確定 ([REQ-424/AC-4])**: 3秒経過または明示的閉じる操作（[×]ボタン）により、Undo通知を消去・タイマー破棄し、キャンセルを恒久確定とする。
5. **一括キャンセルおよび実行中中断の非退行 ([REQ-424/AC-5])**: キュー全件の一括キャンセル操作や、実行中ジョブの緊急中断（停止）処理は本Undo機能の対象外とし、既存の確認モーダル・即時停止仕様と安全性をそのまま維持する。

### 1.3 異常系・フォールバック設計方針
1. **API呼び出し失敗時の挙動 ([REQ-424/AC-1])**: 単一キャンセル操作時にバックエンドAPI通信障害（503エラーやネットワーク例外）が発生した場合は、ジョブをキューから除外せず待機状態を維持し、ユーザーにエラー通知（トースト）を表示するがUndo UIは表示・武装しない（孤立したUndoスロットや不正な二重復元の防止）。
2. **復元時再投入失敗の挙動 ([REQ-424/AC-3])**: Undo復元処理時にキュー再投入API（`queuePrompt`）が失敗した場合は、エラー通知を表示してUndoバナーを消去し、最新のサーバーステートへキュー同期を行う。

## 2. コンポーネント連携フロー

単一待機ジョブのキャンセル操作におけるUI・Store・Backend間の連携フローは以下のシーケンスに従う。

```
[User]                 [JobManagementModal]           [useGenerationStore]           [generationApi / Backend]
  |                             |                              |                                    |
  |-- 単一キャンセル押下 ------>|                              |                                    |
  |                             |-- cancelQueuedJobWithUndo ->|                                    |
  |                             |                              |-- キャッシュ退避 (Snapshot)        |
  |                             |                              |-- cancelJob(promptId) ------------>|
  |                             |                              |                                    |-- 上流キューから即時除外
  |                             |                              |<-- CancelResult -------------------|
  |                             |                              |-- 3秒タイマー起動                  |
  |                             |<-- queuedCancelUndo 保持 ----|                                    |
  |                             |-- 即時キュー除外反映 -------->|                                    |
  |<-- 3秒間Undo通知UI表示 -----|                              |                                    |
  |                             |                              |                                    |
  |== パターンA: 3秒以内にUndo ==|                             |                                    |
  |-- 「取り消し」ボタン押下 -->|                              |                                    |
  |                             |-- restoreCancelledJob ------>|                                    |
  |                             |                              |-- タイマー解除                     |
  |                             |                              |-- queuePrompt(wf, metadata) ------>|
  |                             |                              |                                    |-- キューへ再投入
  |                             |<-- 復元完了 -----------------|                                    |
  |<-- キュー復帰反映 ----------|                              |                                    |
  |                             |                              |                                    |
  |== パターンB: 3秒経過/閉じる =|                             |                                    |
  |-- (3秒経過 or [×]押下) ---->|                              |                                    |
  |                             |-- dismissQueuedCancelUndo -->|                                    |
  |                             |                              |-- タイマー解除 & Undo情報破棄      |
  |<-- Undo通知UI非表示 --------|                              |                                    |
```

### フロー詳細と受け入れ基準 (AC) との整合
1. **即時キャンセル実行 ([REQ-424/AC-1])**:
   - ユーザーが待機中ジョブのごみ箱アイコンをクリックした際、事前の待機カウントダウン（3秒遅延）を一切挟まず、即時に `cancelQueuedJobWithUndo` を呼び出す。
   - ストアはキャンセル対象ジョブのスナップショット（`jobId`, `promptId`, `workflow`, `metadata`）を退避した上で、直ちに上流キャンセルAPI（`generationApi.cancelJob(promptId, false, true)`）を発行し、待機キューからジョブを即座に除外する。
2. **3秒間Undo通知表示 ([REQ-424/AC-2])**:
   - キャンセル処理開始直後に、3秒間有効なUndo通知UI（残り時間プログレス/カウントダウンおよび「取り消し」ボタン付き）を表示する。
   - バックグラウンドで3秒のカウントダウンタイマーを起動する。
3. **アンドゥ実行時の完全復元 ([REQ-424/AC-3])**:
   - ユーザーが3秒以内に「取り消し」を押下した場合、ストアのタイマーを即座に停止し、`restoreCancelledJob` を実行する。
   - 退避されていたスナップショットからプロンプト構成、パラメータ値、ワークフロー設定を完全に復元し、`queuePrompt` 経由で生成キューへ再投入する。
4. **自然確定・明示的クローズ ([REQ-424/AC-4])**:
   - 3秒間操作がない場合、またはユーザーが通知の閉じるボタン（[×]）を押下した場合は、`dismissQueuedCancelUndo` によりタイマー解除とスナップショットの破棄を行い、通知を非表示にしてキャンセルを恒久確定とする。
5. **一括キャンセルおよび実行中中断の非退行 ([REQ-424/AC-5])**:
   - キュー全件キャンセル（一括キャンセル）や実行中ジョブの緊急中断は本Undoシーケンスの対象外とし、既存の確認モーダル・即時停止仕様をそのまま維持する。

## 3. シームマップ (Seam Map [W-DD-SEAM])

本機能におけるコンポーネント間の切断境界（Seam）、モック化方針、障害注入（Fault Injection）およびPBT適用判断は以下の通り設計され、AC-1〜AC-5を確実に充足する。

| 区分 | 対象レイヤー / モジュール | 内容と責務 |
|---|---|---|
| **Integrated (本物コード)** | JobQueueSlice (Zustand Store) | 単一キャンセル時、ジョブのワークフロー・プロンプト・パラメータ等の全構成情報を退避し、Undo実行時にそのデータを完全に復元してキューに再投入（queuePrompt）するロジックおよびタイマー管理（setTimeout）の実行ステート管理 ([REQ-424/AC-1]〜[REQ-424/AC-4]) |
| **Integrated (本物コード)** | JobManagementModal (単一操作) | 単一キャンセルボタンのクリックハンドラ、即時反映表示、3秒間Undo通知バナー/トーストの表示・インタラクション ([REQ-424/AC-1], [REQ-424/AC-2]) |
| **Integrated (本物コード)** | JobManagementModal (一括・緊急操作) | clearPendingQueue / cancelAllJobs（全件キャンセル確認モーダル）および confirmRunningCancel（実行中ジョブ中断確認モーダル）の既存呼び出しフローを完全維持し、単一Undo機能と非干渉で共存させる責務 ([REQ-424/AC-5]) |
| **Severed (切断対象)** | generationApi.cancelJob | 外部HTTP/REST API通信。トランスポート層でモック化し、実バックエンドへの不要なI/Oを遮断 |
| **Severed (切断対象)** | generationApi.submitBatch / submitBatchWithLookup | 復元時のキュー投入API通信。トランスポート層でモック化 |
| **Severed (切断対象)** | ComfyUI WebSocket / EventSource | テスト時は comfyWsService のモックを使用 |
| **Mock Level** | トランスポート境界（HTTP/WS） | 内部ビジネスロジックや状態遷移のモンキーパッチは厳禁。generationApi の関数モックで境界切断 |
| **PBT Decision** | 不要 (Not Applicable) | 本機能は状態機械（待機中 → キャンセル即時除外 → 3秒Undo猶予 → 復帰/確定）とタイマー制御であり、広範な数値・パーサー入力空間を持たないためPBTは対象外 |
| **Fault Injection** | API障害・例外系 | 1. キャンセルAPIが503/例外を返した場合: Undoステートを武装せずエラー通知を表示<br>2. 復元APIが失敗した場合: 復元失敗通知を表示しキュー状態を再取得 |

### シーム設計と受入基準 (AC) の充足
1. **本物コードでの状態遷移検証 ([REQ-424/AC-1]〜[REQ-424/AC-4])**:
   - Store層（`JobQueueSlice`）およびUI層（`JobManagementModal`）はモック化せず本物コードを使用し、単一キャンセル即時実行、Undo通知表示、復元再投入、自然消去の一連の状態遷移を忠実に結合検証する。
   - **データ退避と完全復元ロジック ([REQ-424/AC-3])**: 単一キャンセル実行時、対象ジョブのワークフロー・プロンプト・パラメータ等の全構成情報を `CancelledJobSnapshot`（`{ promptId, jobId, workflow, metadata, timerId, cancelledAt }`）に退避する。Undo実行時は `queuedCancelUndo` スナップショットから退避データを読み出し、`queuePrompt(workflow, metadata)` に渡して全設定を完全に保持した状態でキューへ再投入する（復帰順序はComfyUIのAPI仕様に従いキュー末尾への再追加となる）。
   - **タイマー管理と明示的閉じ・自然消去ロジック ([REQ-424/AC-4])**: 3秒（3000ms）タイマー満了時、またはユーザーによる通知UIの「×」閉じるボタン押下（明示的閉じ操作）時に `dismissQueuedCancelUndo()` を呼び出し、タイマーを安全に解除（`clearTimeout`）した上で `queuedCancelUndo` を `null` に破棄し、Undo通知UIを非表示にしてキャンセルを確定状態とする。
2. **既存操作の保護 ([REQ-424/AC-5])**:
   - 一括全件キャンセルおよび実行中ジョブ緊急停止の既存確認モーダル・実行ロジックは一切変更せず本物コードのまま動作させ、単一キャンセル機能追加に伴う回帰を完全に防止する。
3. **トランスポート境界の切断とフォールトインジェクション**:
   - 外部通信境界（`generationApi`）のみを切断対象とし、ネットワーク障害・サーバーエラー時にもUIがクラッシュせず適切にエラー通知へフォールバックすることを保証する。

## 5. 境界設計契約: 共有インターフェース・型定義 (D4 [W-DD-BOUNDARY])

### D4: 共有インターフェース・型定義
```typescript
// frontend/src/store/types.ts
export interface CancelledJobSnapshot {
  jobId: string;
  promptId: string | null;
  workflow: Record<string, unknown> | null;
  metadata: {
    paramValues?: Record<string, string>;
    appliedAssets?: Record<string, any>;
    workflowId?: number;
  } | null;
  cancelledAt: number;
  timerId?: ReturnType<typeof setTimeout> | null;
}

export interface JobQueueState extends GenerationServerState {
  // ...既存プロパティ
  queuedCancelUndo: CancelledJobSnapshot | null;
}

export interface JobQueueActions {
  // ...既存アクション
  cancelQueuedJobWithUndo: (promptId: string) => Promise<CancelResult>;
  restoreCancelledJob: () => Promise<string | null>;
  dismissQueuedCancelUndo: () => void;
}
```

### D4 共有メソッドの振る舞い契約と状態遷移フロー
1. **即時キャンセル実行 (`cancelQueuedJobWithUndo`) ([REQ-424/AC-1], [REQ-424/AC-2])**:
   - 既存タイマーを `clearTimeout` で停止。
   - 対象待機ジョブのスナップショット（`CancelledJobSnapshot`: jobId, promptId, workflow, metadata）を退避。
   - 事前遅延（カウントダウン待機）を挟まず直ちに上流キャンセルAPI `generationApi.cancelJob(promptId, false, true)` を発行し待機キューから即座に除外する ([REQ-424/AC-1])。
   - 退避スナップショットを `queuedCancelUndo` に保持し、直ちに 3000ms の自動消去タイマーを開始してUndo通知UIを表示状態（武装）にする ([REQ-424/AC-2])。
2. **アンドゥ復元実行 (`restoreCancelledJob`) ([REQ-424/AC-3])**:
   - 3秒タイマーを直ちに解除（`clearTimeout`）。
   - `queuedCancelUndo` から退避されていた `workflow` および `metadata` を取り出し、`queuePrompt(workflow, metadata)` を呼び出して元設定のままキューへ再投入する ([REQ-424/AC-3])。
   - `queuedCancelUndo` を `null` にクリアしてUndo通知UIを非表示化する。
3. **自然確定・明示破棄 (`dismissQueuedCancelUndo`) ([REQ-424/AC-4])**:
   - 3秒タイマー満了時、またはユーザーによる通知UIの「×」閉じるボタン押下時に発火。
   - タイマーを解除し、`queuedCancelUndo` を `null` に破棄して通知UIを消去し、キャンセル確定とする ([REQ-424/AC-4])。
4. **一括キャンセルおよび緊急停止との共存整合性 ([REQ-424/AC-5])**:
   - 一括全件キャンセル（`clearPendingQueue`, `cancelAllJobs`）や実行中ジョブの緊急停止（`confirmRunningCancel`）は、本単一待機Undoインターフェースとは完全に独立したアクションとして既存の動作・確認フローを維持し、相互に干渉しない ([REQ-424/AC-5])。

- 実行中ジョブ（running）の緊急停止（Abort/Interrupt）フローの変更禁止（実行中ジョブはリソース解放優先のためUndo不可で即時停止を維持）。
- 一括キャンセル（`cancelAllJobs`, `clearPendingQueue`）のAPIペイロードおよび確認モーダル動作の変更禁止。
- バックエンドファイル（`backend/*`）の変更禁止（本改修はフロントエンド完結）。
- APIスキーマ（`frontend/src/api/schema.ts`）の独自変更禁止。
- プリセット管理、バイパス設定、マッピング設定など無関係なモーダル/画面コンポーネントの変更禁止。

## 7. トレードオフ・リスク開示

本機能設計におけるトレードオフおよびリスクは以下の通り整理され、受入基準 ([REQ-424/AC-1]〜[REQ-424/AC-5]) の完全性を損なわないことを確認している。

1. **復元ジョブのキュー投入順序 ([REQ-424/AC-3])**:
   - キャンセルされたジョブを再投入（`queuePrompt`）すると、ComfyUI/バックエンドの仕様上、キューの末尾に追加される。元の待機順序（インデックス位置）への厳密な差し戻しは上流APIが非対応であるため行わない。ただし、設定・パラメータ・ワークフローを100%保持した状態でキューへ即時復元するユーザー救済目的は完全に達成される（PBI Inferred pointに合致）。
2. **ページリロード時の確定フォールバック ([REQ-424/AC-2], [REQ-424/AC-4])**:
   - 通常利用時は [REQ-424/AC-2] に従い、単一キャンセル直後に通知UIが画面に表示され3秒間の有効期限タイマーが開始される。
   - 3秒間のアンドゥ猶予タイマーはクライアント内インメモリ管理とする。もしユーザーが3秒の猶予期間内に意図的にブラウザリロードやタブ閉じを行った場合、セッション切断に伴い [REQ-424/AC-4]（キャンセル確定状態の維持）の自然確定フォールバックが適用され、Undoスロットは破棄されてキャンセル確定扱いとなる。3秒という短時間の事後救済において過剰な永続化ストレージは不要であり、通常時の3秒猶予（AC-2）を担保しつつ安全なクリーン設計を維持する。
3. **他セッションの待機ジョブ ([REQ-424/AC-1], [REQ-424/AC-5])**:
   - `filterOwnSession` が有効な場合、自端末セッション以外の待機ジョブはそもそもキャンセルボタンが非活性または操作対象外となる既存仕様を維持し、誤キャンセルや競合を防止する。
4. **単一キャンセル以外の操作（一括全件キャンセル・実行中緊急停止・バッチ処理等）との排他整合 ([REQ-424/AC-5])**:
   - AC-5が対象とする「単一キャンセル以外の操作」には、待機キュー全件の一括キャンセル（`clearPendingQueue`, `cancelAllJobs`）、実行中ジョブ（running）の緊急中断・停止（`confirmRunningCancel`, `interruptJob`）、および他モジュール連携によるバッチ処理が含まれる。
   - これらの操作は、本単一キャンセル即時実行およびUndo機能によって一切阻害されない。Undo通知UIが表示されている最中であっても、ユーザーは一括キャンセルや緊急停止、バッチ操作を制約なく実行可能である。
   - もしUndo通知武装中に一括全件キャンセルや実行中中断が呼び出された場合、保留中の単一Undoスロットおよびタイマーは即座かつ安全にクリア（無効化）され、既存の確認モーダル（「待機中の全キューをキャンセルしますか？」ダイアログや緊急停止確認ダイアログ）の表示および各API呼び出し順序が完全に維持される。UIレイアウト変更による他操作ボタンの遮蔽やフォーカス奪取も発生せず、既存動作・確認仕様の正常稼働を完全に保証する。
5. **Undo通知UIの表示領域と非ブロッキング設計 ([REQ-424/AC-2])**:
   - 3秒間表示されるUndo通知UIはモーダル内の待機キュー一覧上部に非ブロッキングなインラインバナーとして表示され、画面全体の操作性や他ジョブの閲覧スクロールを阻害しない。
