# REQ-229: 端末間（マルチデバイス）でのプリセット同期不具合の修正とSSoT整合性の確立 - 詳細設計書

## 1. 概要 (Overview)
本設計は、複数端末（PC、スマートフォン、タブレット等）で同一ワークフローを操作した際に、一方の端末で編集・保存されたプリセットの内容が他方の端末に同期・反映されない不具合を解決し、バックエンドDB（`workflow_presets`）を絶対的なSSoT（Single Source of Truth）として機能させるとともに、**オフライン・通信不良時のローカル編集保護および競合解決モーダル（`PresetConflictModal`）** を提供するための包括的な詳細設計である。

---

## 2. 背景と根本原因の構造 (Problem Structure & Root Cause)

### 2.1 不具合の発現メカニズム
```
【端末A (PC)】                         【バックエンドDB (SSoT)】               【端末B (スマホ)】
 プリセット更新 (Set 1)                                                       
   param_values: "新プロンプト" ──► PUT /api/workflow-presets/1 ──► [DB更新]
                                                                        │
                                                                        ├─ 端末B起動時: LocalStorageキャッシュから古いSet 1を復元
                                                                        │  (App.tsx: PersistQueryClientProvider)
                                                                        │  isFirstSync = true で古いキャッシュをストア展開
                                                                        │
                                                                        ├─ 直後にサーバーから最新データ到着:
                                                                        │  GET /api/workflow-presets (DB最新値)
                                                                        │
                                                                        └─ usePresetState の同期処理で破壊:
                                                                           isFirstSync が false に移行済み
                                                                           existingSet?.paramValues (古い値) が
                                                                           p.param_values (最新値) を上書き！
                                                                           loadPresetData も呼ばれず、
                                                                           最新データが完全に破棄される！
```

### 2.2 通信不良・オフライン並行編集時の競合課題
- 両端末が一時的に通信不良・オフラインとなり、それぞれローカルでプリセットを編集した場合：
  - 端末Aが復旧して先にサーバーへ保存（DBの `updated_at` が進む）。
  - 端末Bが復旧して保存を試みると、サーバーのOCC（楽観的並行性制御）により `409 Conflict` が返される。
- **解決方針**:
  - 勝手に「早い者勝ち」でどちらかの編集を消すのではなく、端末B側で **「競合解決モーダル (`PresetConflictModal`)」** を表示。
  - PCでは左右2カラムで「サーバー最新版」と「この端末の編集（ローカルドラフト）」のプロンプト・パラメータを並べて比較。
  - モバイルではタブ切り替えで両者を比較。
  - ユーザーは「サーバー版を採用」「ローカル版で上書き」「別名で両方保存（Auto-Fork）」を自在に選択可能とする。

## 3. アーキテクチャ設計 (Architecture & Data Flow Design)

### 3.1 3重ガード同期アーキテクチャ
```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. SSoT優先マージ ＆ 未保存ガード (Dirty Guard)                         │
│    - 非アクティブセット: 常にサーバー最新値（p）をマージ               │
│    - アクティブセット: 未保存編集（isDirty === true）中は上書きを保護  │
│    - lastSavedStateRef の更新は onSuccess（保存完了後）に限定           │
├────────────────────────────────────────────────────────────────────────┤
│ 2. キャッシュ永続化除外 (No Stale Query Cache)                         │
│    - App.tsx: shouldDehydrateQuery で workflow-presets を除外         │
│    - 起動時は常にサーバーの最新DBデータを取得して初期化                │
├────────────────────────────────────────────────────────────────────────┤
│ 3. 競合検知と解決モーダル (Conflict Resolution UX)                     │
│    - 409 Conflict 受信時、ローカル編集とサーバー最新値をモーダルに提示   │
│    - Desktop: 左右2カラム比較 / Mobile: タブ切替比較                  │
│    - 3通りの解決アクション:                                            │
│      (1) サーバー版を採用 (2) この端末で上書き (3) 別名で両方保存       │
│    - 複数プリセット競合への拡張性（競合プリセット切替タブ完備）        │
└────────────────────────────────────────────────────────────────────────┘
```

## 4. 詳細コンポーネント設計 (Detailed Component Design)

### 4.1 `usePresetState.ts` の是正
- **クエリオプション**:
  `refetchInterval: 5000`（5秒ポーリング）、`refetchOnWindowFocus: true` を設定。
- **未保存ガード（`isDirty`）とマージ**:
  - 現在のステートが `lastSavedStateRef` と異なる場合、そのセットは `isDirty: true`。
  - `rawMappedSets`: サーバーから取得した `p.param_values`, `p.applied_assets`, `p.batch_size`, `p.seed_mode`, `p.seed` を直接正としてマッピング。
  - サーバーの `activePreset.updated_at` が更新された場合：
    - `!isDirty`: サーバー最新データを `currentStore.loadPresetData` で即時反映。
    - `isDirty`: 競合状態と判定し、`conflictState`（`{ serverPreset, localState }`）をセットして `PresetConflictModal` を起動。
- **409 Conflict ハンドリング**:
  - `updatePresetMutation.onError` で 409 を捕捉した際、勝手に初期化・上書きせず、`setConflictData` を呼び出してモーダルを起動。

### 4.2 `PresetConflictModal.tsx`（新規コンポーネント）
- **UIレイアウト**:
  - **ヘッダー**: 競合通知タイトルおよび、複数プリセットが競合した場合のタブ切り替え（`[Set 1 ⚠️] [Set 2 ⚠️]`）。
  - **PC表示 (`md:grid-cols-2`)**:
    - 左カラム: **サーバー最新版（他端末の編集）**
      - 更新日時、プロンプトテキスト、主要パラメータ（CFG, Steps, Batch, Seed, LoRA等）。
    - 右カラム: **この端末の編集（未保存ローカル）**
      - ローカルのプロンプトテキスト、主要パラメータ。
      - 差異のある項目を視覚的にハイライト（差分バッジ）。
  - **モバイル表示 (`md:hidden`)**:
    - タブ切替: `[サーバー最新版]` / `[この端末の編集]` で各内容を表示。
  - **フッター（アクション）**:
    1. **「サーバー最新版を採用」**: ローカルを破棄し `loadPresetData(serverPreset)` を実行。
    2. **「この端末の編集で上書き」**: サーバーの最新 `updated_at` を `base_updated_at` に差し替えて強制更新。
    3. **「別名で両方保存」**（推奨）: ローカル編集を `Set 1 (別端末の編集)` として新規プリセット登録し、両方をDBに安全保持。

### 4.3 `multiSetSlice.ts`
- `loadPresetData` において、`mergedParamValues` から生成した `initialPromptChips` を常に適用（古いチップ残留を防止）。

### 4.4 `App.tsx`
- `shouldDehydrateQuery` の除外リストに `'workflow-presets'` を追加。
