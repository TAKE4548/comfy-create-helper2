# REQ-380 詳細設計

## Scope and feasibility

AC-1〜6は既存の8899 Manager操作境界を拡張して実現する。設定画面とManager画面から同じメモリ解放処理を呼び、外部ツールはComfyUIのネイティブAPIを直接利用する。コードと仕様文書のmixed変更として独立した実装・受入担当を割り当てる。現在は設計レビュー前であり、実装・受入検証・コミットの完了を示すものではない。

## Boundary audit

- WORKSPACE_ROOTとGit rootは本リポジトリで一致する。編集対象はこのroot内の承認済み所有ファイルに限定する。
- frontendはfrontend/src、Managerはtools/server-manager、試験はtests/unitとfrontend/e2eを使用する。8000 Backendの実装は変更しない。
- installed GLOBAL_HELPERSのdoc_mapper、openapi_parser、local_model_adapterを読取・実行依存として用いる。配布済み共通定義は編集しない。
- doc_mapperの実行結果は「No mapped documents found」。PBIが列挙したSPEC_SETTINGS.mdとserver_manager_guide.mdを手動で影響対象として確認した。
- OpenAPIの実在パスはdocs/openapi.yaml。既存/api/settings/vram GETの応答型を抽出済み。8899 Managerの/api/actionは同OpenAPIの管轄外で、運用ガイドが契約の正本となる。
- 既存tools/server-manager/config.jsonのユーザー変更、REQ-381等の文書は所有外。読取時点の構成を保全し、設定保存やサービス起動を設計作業の副作用にしない。

## Existing framework constraints

Managerは標準ライブラリのThreadedTCPServerを使用する。全操作共通の_active_actionとロック、2秒のstatus cache、Origin検証を持つ。サービス操作は現在PowerShell経由だが、メモリ解放はPythonのHTTP transportを直接使用し、プロセス操作へ流さない。

FEはsystemManagerApi、2秒共有pollのuseManagerStatus、ServiceConnectionCardのbusyRefで管理操作を統合している。VRAMはResourceMonitorServiceの2.5秒SYSTEM_STATS配信を優先する。VramGuardSectionには現在取得失敗表示がなく、保存用queryと同じsettings-vram queryで初回値を取得する。

## Contracts

### Manager status

既存GET /api/statusのcomfyへ次の追加フィールドを入れる。既存fe/be/comfyのrunning/status/pidsの意味を変更しない。

~~~ts
type ComfyExecutionState = 'idle' | 'executing' | 'queued' | 'unknown'
type ComfyExecutionStatus = {
  execution_state: ComfyExecutionState
  queue_running: number | null
  queue_pending: number | null
  execution_error?: string
}
~~~

LISTEN時に127.0.0.1と既存config.jsonのwsl.portへGET /queueを送る。HTTP timeoutは2秒、受信上限は2MiBとし、失敗・上限超過・不正JSON・必須配列欠落をunknownへ落とす。queue_running非空をexecuting、running空かつpending非空をqueued、両方空をidleとする。停止中はHTTP要求せずunknown/カウントnull。旧Managerでフィールドがない場合もFEはunknownとして解放を抑止し、既存の起動・停止・ログは維持する。

comfy_memory.pyにtransportと厳密なenvelope判定を集約し、server_status.pyのTCP死活判定とは分離する。内部ロジックの試験用差替えは設けない。既存GET全体の7秒予算に収まるよう、queueは1回だけ取得する。

### Action and outcomes

~~~http
POST http://<current-host>:8899/api/action
Content-Type: application/json

{"action":"free-memory","service":"comfy"}
~~~

このactionはservice=comfyに限定する。既存の許可Origin、JSON検証、全操作ロックを通し、_active_actionを確保後にstatus cacheを無効化する。直前のGET /queueはcacheを使わず、TCP稼働確認とidle確認を両方満たす場合だけ、固定loopback/configured portのPOST /freeへJSON {unload_models:true,free_memory:true}を1回送る。POSTのtimeoutは5秒。redirectを追跡せず、固定された接続先以外へ転送しない。設定URLやブラウザー由来URLを受け取らない。

| Result | HTTP / body | UI behavior |
| --- | --- | --- |
| Native 200 | 200, status=ok, action=free-memory, outcome=accepted | 解放要求の受付を通知する |
| Invalid target/action | 400, status=error, request_sent=false | 理由を表示する |
| Another operation / executing / queued | 409, status=error, request_sent=false, code=ACTION_BUSY/COMFY_BUSY | 状態を再取得し、生成中・待機中等の理由を表示する |
| Stopped / queue unknown | 503, status=error, request_sent=false, code=COMFY_STOPPED/COMFY_STATE_UNKNOWN | 未送信であることと理由を表示する |
| Native non-2xx / redirect | 502, status=error, code=COMFY_FREE_REJECTED | 失敗を通知する |
| POST timeout / response disconnect | 504, status=timeout, outcome=unconfirmed | 結果未確認を通知し、再取得のみ行う |

全経路でfinallyから_active_actionを解除しstatus cacheを無効化する。メモリ解放actionはsubprocess.run、PowerShell、stop/restartへ到達しない。HTTP 200の空本文をJSON解析しない。ComfyUIの/freeはflagを受け付ける非同期APIなので、物理解放完了や解放量を成功応答から断定しない。

### UI controls

両画面でLISTEN、execution_state=idle、他操作なし、ローカル要求なしの全条件を満たす場合だけComfyUIの「メモリ解放」ボタンを有効にする。executingは「生成中」、queuedは「キュー待機中」、停止は「停止中」、unknown/Manager不通は「状態を確認できません」をボタンに隣接して示す。disabled buttonのtitleだけに理由を置かない。

SettingsはComfyUIサービス行の操作領域へ配置し、既存busyRefで連打を抑止する。action unionをfree-memoryまで広げるが、freeMemory専用APIメソッドでserviceをcomfyに固定する。409/503でもrequest_sent=falseの有効な応答を受けた場合は確定した拒否として表示する。従来actionの503/504/通信失敗は既存の未確認規約を維持する。

Manager埋込dashboardはローカルisActionPendingと最後のstatus snapshotの両方からdisabledを再計算する。poll中のDOM再生成やfinallyで無条件に全ボタンを有効化する処理がguardを解除しないようにする。action_in_progressも反映する。res.ok/statusを判定し、受付・拒否・未確認を常時見えるstatus領域で通知する。

UI分類はForms & ControlsとShell & Page Layout。行の折返し、44×44pxの有効操作域、11px以上の個別文字サイズ、touch manipulation、長い理由の折返しを守る。重要な状態・エラーをtruncateしない。新しいmodalは追加しない。

### VRAM synchronization

解放受付後にManager状態とsettings-vram queryを再取得する。通常は既存SYSTEM_STATSの2.5秒更新を表示する。WS断時は古いstore値を最新値として優先せず、表示中のVramGuardSectionでGET /api/settings/vramを2.5秒間隔で取得する。既存Backend monitorの2.5秒更新と合わせ、正常な取得で最大5秒以内に新しい監視値へ追従する。query retry=false、refetchIntervalInBackground=falseとし、監視失敗は「VRAM情報を更新できません」を表示する。直前値を残す場合は最新ではない旨を明示する。閾値draftと未保存フラグをpoll応答で上書きしない。

Manager dashboardには現状VRAMメーターがないため新設せず、状態再取得と受付結果を表示する。AC-5の容量反映はSettings既存メーターで検証する。

## Verification and endpoint constraints

最終受入は.agents/verification.jsonを唯一の機械可読Gate契約として使う。T0でidentity.input_dirsにtools/server-managerを追加し、tools/server-manager/logs/を除外する。現在のsandboxは.agentsをread-onlyとしているため、実装担当は利用可能な正式な許可手段を確認し、拒否時はpendingとして返す。設定を別場所へコピーして回避しない。

Gate 1→Gate 2 full discovery→Gate 3 fixed E2Eと追加scenarioを独立担当が新規実行する。詳細argvとAC対応はtest plan参照。テストはCPU/RAMのみで、実GPU生成・実/free・サービス停止/起動は行わない。最終Gate記録はCard status doneと追跡文書の凍結後に作る。

承認endpointはsource-only。root implementation_plan.mdの既存REQ-377計画を保全し、今回の計画はcoordinatorが採用したdocs/design/REQ-380-implementation-plan.mdへ保存する。自動commit/pushや配布は含まない。

## Trade-offs and risks

- idleでも/freeは非同期受付であり、次回生成にはモデル再ロードの待ち時間が生じる。実空き容量は監視値で判断する。
- UI pollには遅延があるためManagerが直前に再検証する。それでも外部クライアントによるGET /queue後の新規投入とは原子的に排他できない。ComfyUIのqueue flag方式は実行中ジョブを中断しないが、後続のモデル再ロードを招く可能性は残る。
- queuedも抑止する。PBIが明記したExecutingより安全側の条件であり、待機ジョブを消す操作は提供しない。
- statusへのHTTP取得追加で従来のsocket-only監視より遅くなるが2秒に制限する。queue失敗が他サービスの状態をunknownに変えないよう、ComfyUI追加フィールドだけへ閉じ込める。
- 外部直接/freeは本ツールのguardを経由しない。呼出し元がidleを確認する運用を明記する。
- バージョン差で/freeや/queueがないComfyUIは明示エラーとなる。停止/再起動へfallbackしない。

## Response and recovery boundaries

ブラウザーUIはSettings/Managerの両方とも8899の既存/api/actionを使い、Managerが常にJSONを返す。ComfyUIネイティブ/freeだけが空本文HTTP200を返し得る。Managerはこのnative応答を{status:ok,action:free-memory,outcome:accepted}のJSONへ包む。外部localツールのloopback8188直接利用は別consumerで、Managerのguardを経由しない。通常のLANブラウザー/スマートフォンへ8188接続を要求しない。

UIは応答直後に『解放要求を受け付けました。空き容量は監視値で確認してください』というacknowledgementを表示する。『完了』『解放成功』とは表示しない。解放後にも古い/高いVRAM測定値が残り得るため、数値は監視で取得した測定値として表示し、低下を検出して完了を宣言する永続的なcompletion detectorは追加しない。応答後はfresh GET statusが既知idleかつcounts0/0と確認できる場合だけ再有効化する。unknownはdisabledのまま、後続GETで既知idleへ回復した場合だけ解除する。古いidle cacheでunknownを上書きして操作可能にしない。

同一タブはクリック直後のbusyRef/isActionPending、別タブはManager共通_active_action lockで排他する。先行actionの実行中に別タブactionが到達した場合はHTTP409、code=ACTION_BUSY、request_sent=falseを必ず返す。キューイングしない。試験では異なる2clientから同時要求し、2件目409/ACTION_BUSYとnative POST1件をassertする。

自動再送禁止は操作POSTだけ。background status/VRAM GET pollとWS再接続は継続し、操作POSTを再生しない。WS切断時はGET statusとVRAM refreshだけ行う。実ComfyUIの/free処理とGET /queueの間は外部clientの新規投入に対して非原子的であり、完全な外部排他は保証しない。

試験のCONFIG_FILEはtest-owned TemporaryDirectory内の新規JSONを使う。production pathを先に保存し、temp_path.resolve()!=production_path.resolve()をassertしてから、testプロセス内でserver_api.CONFIG_FILEをtemp_pathへbindする。production configのbytes/hashを試験前後で確認し、書込み・rename・backup・restoreを一切しない。fixtureの全HTTPはephemeral loopback port、サービス起動停止要求は0とする。テスト失敗時もtemp以外をcleanupしない。

文書Card T4はAC-1〜5に関する文書の意味・参照・適用範囲の整合確認と、文書要件AC-6だけを担当する。AC-1〜5の機能実装・試験はT1/T2/T3が担当し、T5はユーザー承認済みのAC-5期限試験だけを補う。doc PASSはcode ACのPASSを成立させない。T5は新しい機能要件や重複した実装責任を追加しない。ComfyUI最小versionは要件未指定なので推測せず、/free非対応は明確なエラーとして既存契約に従う。
