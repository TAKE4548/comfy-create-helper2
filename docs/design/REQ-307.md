# REQ-307 詳細設計

## 実現性と境界

AC-1〜5 は既存の `/api/comfy/prompt` 応答と生成画面の通知経路で実現可能。API の URL・HTTP スキーマと backend proxy は変更しない。対象は生成ボタンから `/prompt` に投入する単一生成と複数セット生成。投入成功後の実行エラー、生成前のスキーマ不足・VRAM 待機、ユーザー中断は対象外。既存 REQ-141 の `セット名 (件目/セット内総数)`、pending/failed 状態、後続ジョブの継続を保つ。

## 現状と原因

`backend/app/routers/comfy.py` は ComfyUI の `/prompt` 応答を原則そのまま返し、接続例外は HTTP 502 の `detail` にする。`frontend/src/api/client.ts` の共通 `request` は非 2xx 本文を `API error 400: {…}` 形式の Error にする。`jobQueueSlice.queuePrompt` は Error をグローバルトーストへ書いて `null` を返す。複数セット側は `null` を汎用文で再通知するため対象と理由が同じ通知に残らない。単一生成側は戻り値を調べない。トーストは単一文字列・5 秒自動消去であり、長文や多数件の読了を保証できない。

## 設計決定

1. フロントエンドに純粋関数 `parseQueueSubmissionFailure(error: unknown): { reason: string; outcome: 'failed' | 'unconfirmed' }` を設ける。HTTP Error の本文が JSON なら `error.message` → `error.details` → `detail` → `node_errors` の説明可能な文字列を選ぶ。平文の具体的説明も受け入れる。空文字・空白・`null`・`undefined`・ステータス番号のみ・`API error 400` のような番号だけの文字列は `理由を特定できませんでした` にする。未知のオブジェクトを丸ごと JSON 表示しない。長さや繰り返しだけを理由に説明を切り捨てない。表示は React のテキストノードとして行い HTML を解釈しない。
2. `QueuePromptOptions` に `onSubmissionFailure?: (failure: QueueSubmissionFailure) => void` を追加する。`queuePrompt` は実際の失敗時に上記を一度呼び、コールバック指定時は単独のグローバルトーストを出さず `null` を維持する。既存の呼び出し元には従来どおり単独トーストを出す。`AbortError` または signal 中断時は失敗として通知しない。`prompt_id` が無い成功応答は理由不明の失敗とする。
3. `handleGenerate` は各投入の戻り値とコールバックを確認し、バッチサイズ 1 なら `キュー投入に失敗しました: 理由`、複数回投入なら `単一生成 (i/N): 理由` として記録する。`handleGenerateSets` は失敗時点のセット名・セット内番号・理由を同じレコードに固定し、REQ-141 の failed 状態遷移を維持する。両経路とも投入処理の終了時に失敗レコードを一つのトーストにまとめる。部分成功は失敗の通知を優先し、全件失敗時に成功通知は出さない。既存コードに成功トーストはなく、新設しない。例外がフックへ直接伝播した場合も同じ正規化を使う。
4. 通信タイムアウト・応答未確認のネットワーク異常は `outcome: 'unconfirmed'` とし、該当する各行に `キュー投入を確認できませんでした` と表示する。理由は `応答がなく時間切れになりました` など観測可能な範囲に留める。サーバーが受理済みの可能性があるため、断定した失敗・自動再投入はしない。ComfyUI から明示的な拒否応答がある場合は `failed` とする。両種が混在するときは行ごとに状態を明示する。
5. `errorToast` に生成失敗通知用の `persistent?: boolean` を追加する。共通オーバーレイは `whitespace-pre-wrap`、折り返し、画面幅内の最大幅・最大高さ・縦スクロール、キーボードで閉じられるボタンを設ける。生成失敗の集約通知だけ `persistent: true` とし、Desktop/Mobile の 5 秒タイマーを掛けない。複数失敗は一つの通知内に失敗対象と理由を対応づけた各行としてすべて表示し、件数による切り捨てをしない。複数セットの各行は `セット名 (i/N): 理由`、単一生成はバッチサイズ 1 のとき番号なしとする。トーストが次の別通知に上書きされる可能性は残るため、画面上の読了保証は現在の通知が表示されている間に限定する。

## データ経路と依存

`ComfyUI /prompt → backend proxy → frontend api request → queuePrompt → onSubmissionFailure → useGenerateAction → errorToast → GenerateModalsOverlay`。上流の proxy と共通 request の契約は維持。下流の単一・複数セット、Desktop/Mobile 通知タイマー、REQ-141 の failed 状態に影響する。`docs/specs/SPEC_GENERATE.md` にキュー投入失敗理由・通知寿命・応答未確認境界を実装後同期する。

## AC 対応

| AC | 設計箇所 | 検証 |
|---|---|---|
| AC-1 | 理由正規化と単一生成の集約通知 | ComfyUI 400 ノード説明を同一トーストに表示 |
| AC-2 | 空値・状態番号のみのフォールバック | `理由を特定できませんでした`、推測表示なし |
| AC-3 | 失敗レコードの作成時に対象と理由を固定 | 異なる 2 セット・順番の対応を検証 |
| AC-4 | 全件終了時に失敗通知を集約 | 全件 failed、成功通知なし |
| AC-5 | オーバーレイの折返し・スクロール・永続表示 | 長文全文、PC/モバイルの読了可能性 |

## トレードオフとリスク

- 既存 `Promise<string | null>` を維持し、追加コールバックで理由を渡す。戻り値を判別共用体へ変更するより既存呼び出しへの影響は小さいが、コールバックの記録漏れで理由が失われ得る。`null` 時のフォールバックをフックで必須にする。
- 一つの通知に全件を収めると画面を占めるため最大高さとスクロールを設ける。件数制限は AC-3/4 の全件対応を損なうため採用しない。
- 永続通知は手動で閉じる必要がある。5 秒消去では長文の全文読了を保証できないため生成投入失敗だけ永続にする。
- 応答なしは実際の投入成否を特定できない。失敗と断定する表現を避け、二重投入を防ぐため自動再試行しない。
- 非 2xx 応答の形式は ComfyUI と proxy で異なる。パーサーは既知の説明フィールドに限定し、説明がない場合は理由不明とする。
