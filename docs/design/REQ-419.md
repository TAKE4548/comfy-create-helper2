## 2-1. スキャナの旧フォールバック廃止（Q1 承認済み）
- `_get_variant_patterns` は NodeSelector のパターンのみ。未設定／0件は段階3「セレクタなし」。`_match_binding_entries` は RuleSet の Entry のみ。Entry 0件は候補なし。
- DB 列・API フィールドは削除しない。旧関数 `scan_workflow` は変更しない。

## 2-2. 判定プレビュー（非永続 dry-run API）
- `POST /api/mapping-masters/scan-preview`。未保存定義をインラインで受け、DB は workflow の `json_body` と StageMaster を読むだけ。dataclass の一時オブジェクトで本番スキャナ（新関数 `scan_master_variants_detailed`）を実行する。書き込み・ORM 属性変更は禁止。段階4は候補から除外。
- 不採用案: TS へのスキャナ移植（二重実装による乖離）。

## 2-3. 原子的保存（Q4 不採用を受けた再設計）
- 新 API `POST /api/mapping-masters/{master_id}/atomic-save`。1回のユーザー保存を **1トランザクション** で適用する: Master 値定義の更新、RuleSet/NodeSelector の作成（新規・複製）と更新（共有更新・非共有の変更）、Variant の作成・更新（参照の付け替え、有効状態）。
- 処理順: ①全件の事前検証（失敗は 422、DB 無変更）→ ②定義の作成・更新（flush）→ ③`ref` を新 id に解決 → ④Variant 更新（セレクタ付替えは一旦 NULL→flush→最終値の2段階）→ ⑤`commit` は最後に1回。②〜⑤のどこで例外が起きても `db.rollback()` で全て取り消す（422 以外は 409/500 を返す）。部分適用は発生しない。
- 「共有定義を更新」= 当該定義への `update`、「複製してこのVariantだけ変更」= 変更後内容の `create`（名前 `${元名} (${role})`、衝突時 ` 2`, ` 3`）と編集元 Variant の参照付け替え。元定義は更新しない。どちらもクライアントの下書きから要求本文を組み立てる（判定規則は §2-5）。
- 既存の `PUT /api/mapping-masters/{id}`、`/api/binding-rules`・`/api/node-selectors` の CRUD は変更しない（モーダルは使わなくなる）。
- 不採用案: 既存 CRUD の逐次呼び出し（部分失敗が残る。ユーザーが不受容）。

## 2-4. 一意性検証（AC-6）
- クライアント（一次）: 下書きで同一 `stage_id` が2行以上、同一の非 null セレクタ参照が2行以上 → 該当全行にエラー、送信しない。セレクタなし（null）は複数可。RuleSet 未選択・定義名の空／重複もエラー。
- サーバ（原子的保存の事前検証）: 最終状態で同じ検査に加え、id の帰属、stage/定義 id の存在、`ref` の解決可能性、新規 Variant の role の全体一意、定義名の一意（既存・同一要求内）を検査。違反は 422 `MASTER_SAVE_VALIDATION_FAILED`、DB 無変更。
- 既存 Variant のステージは画面で変更不可（role 保護）。重複ステージは「Variantを追加」の新規行のステージ選択で起こり得る（全ステージを選択肢に出す）。

## 2-5. 画面構成と共有判定
- 編集モード: Master 値定義（表示名・入力型・グループ・基本有効）＋ステージ（`sort_order`、同順位は stage_id）順の Variant 行＋判定プレビュー。旧判定入力・Role上書き・旧プレビュー・ノードピッカーは撤去。
- 作成モード（Q3 承認済み）: 値定義＋「初期RuleSetのパラメータ名」。作成は既存 `POST /api/mapping-masters` のまま（Variant 行は保存後に編集）。
- 共有判定: 永続化済み定義の内容が保存時点から変わり、他の参照元が1件以上なら選択を要求。他の参照元 =（サーバの `referenced_roles` − この Master の保存済み Variant の role）∪（この Master の下書きで編集元以外かつ同じ定義を参照する Variant の role）。選択 UI はモーダル内の行内 `role="alertdialog"`。

## 2-6. フロントの候補ランク付け・ステージ検出の3層化（Q2 を本PBIに含める）
- **データ源**: 追加クエリを増やさず、`MappingVariantRead` に読み取り専用の追加フィールド `rule_entries`（参照 RuleSet の Entry、priority 昇順）と `selector_patterns`（参照 NodeSelector のパターン、priority 昇順。未設定は null）を加える（T2）。既存フィールドは不変（追加のみ）。
- **候補ランク付け**: `CandidateDefinition` に任意フィールド `entryPairs`・`containsPatterns` を追加（T9）。`entryPairs` があるときクラス一致は「Entry の class_type 一致かつ param_name がノード入力に存在」、tier 1 には「正規化タイトルが contains パターンを含む」を加える。新ヘルパー `candidateDefinitionForVariant(variant)` が `rule_entries`/`selector_patterns` から定義を作り、Master の旧列・`extra_title_patterns` は読まない（`rule_entries` が無い Variant は空定義）。呼び出し側3ファイルは Master 単位ではなく **Variant 単位** の定義でランクする（T10）。`entryPairs` を渡さない旧呼び出し（`WorkflowMappingPreview.tsx`、本PBIで未使用化）は従来挙動。
- **ステージ検出**: `detectActiveStages` は `search_keywords` を読まず、各ステージの有効 Variant の `selector_patterns` でノードタイトル（無ければ class_type）を判定する（exact=正規化一致、contains=部分一致。スキャナと同じ規則）。ビルトイン／main の常時表示は維持（T9, 呼び出し側は T10）。
- 対象外: `seedBatch.ts`・`seedInputResolver.ts`・`workflowParamInjector.ts` の `WorkflowMapping.param_name/fallback_param_names` 参照（保存済みマッピングの値注入フォールバックであり、ランク付け・ステージ検出ではない。REQ-417 AC-4 の領域）。`SettingsComponents.tsx`（未参照）。

## 3. Seam Map [W-DD-SEAM]
1. **Integrated (real code)**: Backend は router → service（`scan_preview.py`, `mapping_master_save.py`）→ scanner → SQLAlchemy（テスト用 SQLite セッション）。Frontend はコンポーネント → `variantDraft.ts` → `api/domains/*` → `request()` → fetch、候補は `candidateDefinitionForVariant` → `rankWorkflowNodeCandidates`。
2. **Severed (external I/O only)**: Frontend の HTTP は MSW（既存の API モジュール `vi.mock` 済みテストはその方式を維持してよい）。E2E は Playwright `page.route`。Backend の DB はテスト用セッション。ComfyUI 不要。
3. **Mock Level**: 下書きロジック・スキャナ・保存サービス・ランク関数のモンキーパッチ禁止。
4. **PBT Decision**: スキャナは Hypothesis（詳細関数と既存出力の一致、段階4不在、確定＝候補先頭、入力順不変）。原子的保存は Hypothesis で「ランダムな要求（妥当／違反混在）に対し、200 なら要求どおり、非200 なら DB が事前状態と完全一致」を検証。フロントのランク付けは fast-check を使わず例示テストで足りる（入力は定義の形のみで、既存 REQ-358 テストが広い入力を網羅）。
5. **Fault Injection**: 原子的保存で、定義作成後・Variant 更新中に DB 層の失敗を注入（テスト用セッションの `before_flush` イベントで例外を送出。業務ロジックのパッチではない）し、全件ロールバックを確認。プレビューの 404/422/500・ネットワーク断・古い応答の破棄。保存の 422/409/ネットワーク断でモーダルが閉じず下書きを保持。

## 11. トレードオフとリスク
- **原子的保存 API の追加**: 部分失敗を無くす代わりに、定義・Master・Variant を横断する新しい公開契約とサーバ検証ロジックが増える。既存 CRUD と検証規則が二重になるため、名前一意・参照削除ガード等は既存ルーターと同じ規則であることをテストで固定する。
- **旧フォールバック廃止と3層化の挙動変化**: 再スキャン・アップロード・配線画面の推奨ノードとステージ表示が、RuleSet/NodeSelector の内容に従って変わる。保存済みマッピングは変わらない。Variant 単位の定義になり、同一 Master でもステージごとに候補順位が異なり得る（意図どおり）。
- **`MappingVariantRead` の拡張**: 一覧取得のたびに Entry/パターンを含めるため応答が大きくなる（Master×Variant×Entry 数に比例。現行規模では軽微）。代替の追加クエリ方式は、呼び出し側テストの API モック体系（`vi.mock` 済み）を広く改修する必要があり不採用。
- **他 PBI との直列化**: §4-1-1（REQ-413-T3）と UploadWorkflowModal/scanner（REQ-416）で順序制約が生じる（§2-7）。
- **リスク分類 high**: 公開 API 契約・トランザクション・判定挙動・共有フィクスチャ（複数テストファイルの fixture 更新）を含む。V1 Baseline（全スイート）必須。
