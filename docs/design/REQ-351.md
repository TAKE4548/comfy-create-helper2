# REQ-351 設計書: ParamSyncで同一ロールの別ステージを個別選択して同期する

## 1. 目的と前提

本書の表記「Stage/Role」は REQ-336 の2軸（ステージ × セマンティックロール）に従う。例: `Main/Steps` は Main ステージの Steps マスター、`Rough/OtherSteps` は Rough ステージの別マスター（同一 `input_type`）。

現行実装の調査結果（コード読取りによる推定。実行による再現は未実施）:

- `GET /api/workflows/{id}` の `WorkflowMappingRead.role` は、バリアントがある場合 `variant.computed_role`（例: `Sampler_Steps_Rough`）、ない場合はマスターの legacy `role` を返す（`backend/app/routers/workflows.py` L116）。生成入力値 `paramValues` と ParamSync の `master_role` / `slave_roles` もこの role 文字列をキーにする。
- `ParamSyncModal.tsx` L79-L96 は、候補の型判定を `mappingMastersApi.list()` が返すマスターの legacy `role`（基底ロール）をキーとする `roleMasterMap` で行う。そのため、ステージ接尾辞付きの `computed_role` は `roleMasterMap` に存在せず、`if (!m || !masterInputType) return false` で候補から除外される。これが「同一ロールの別ステージを選べない」原因と推定する。
- 候補表示は `display_name`（マスター名）と role 文字列だけで、ステージ名がない。Main/Steps と Rough/Steps は同じ表示名になるため区別しにくい。
- 同期の適用は生成時に `useGenerateAction.ts` の `applyParamSync`（L157-L177）で行う。有効グループの `master_role` の値を `slave_roles` の各キーへコピーした実効値を作り、ストアの `paramValues` は書き換えない。Seed を含むグループは対象外（REQ-353 の Seed 同期経路が別にある）。
- 保存は `param_sync_groups` テーブル（`master_role` 文字列、`slave_roles` JSON 文字列配列）。任意の role 文字列を保存・返却するため、ステージ付き role もそのまま保存・復元できる。

結論: **バックエンドの API・スキーマ・DB は変更しない。** 修正対象はフロントエンドの候補生成と表示（ParamSyncModal）に限る。AC-3〜AC-5 の同期挙動は既存の `applyParamSync` で満たせる見込みのため、回帰テストで確認する（characterization）。

## 2. 方式

### 2.1 ステージ付き候補の導出（純関数）

`frontend/src/utils/mappingStageGroups.ts` に純関数 `buildParamSyncCandidates` を追加する。既存の `groupMappingsByStage` でワークフローの mapping をステージへ射影し、role 単位で重複を除いた候補を返す。

```ts
export interface ParamSyncCandidate {
  role: string                 // WorkflowMapping.role（computed_role または legacy role）
  stageName: string | null     // 解決できたステージ名。未解決は null
  displayName: string | null   // mapping.display_name（欠落・空は null。補完はモーダル側）
  inputType: string | null     // mapping.input_type（WorkflowMappingRead の実効マスター値）
}

export function buildParamSyncCandidates(
  mappings: readonly WorkflowMapping[],
  masters: readonly (MappingMaster | MappingMasterV2)[],
  stages: readonly StageMaster[],
): ParamSyncCandidate[]
```

規則:
- `role` が null または空の mapping は除外する。
- 同じ role が複数 mapping（複数ノード）にある場合は、最初に現れた1件だけ候補にする（重複キーを防ぐ）。根拠: 入力値 `paramValues` と同期設定は role 文字列をキーにするため、同じ role の mapping は同じ1つの入力値を共有し、ステージごとに別々の値を持てない。通常はステージ接尾辞で `computed_role` が分かれる（`Sampler_Steps` / `Sampler_Steps_Rough` / `Sampler_Steps_Detail`）ので、同じロールの別ステージは別候補として並ぶ（AC-1）。`custom_role_override` などで2つのステージが同じ role 文字列になった場合だけ1候補にまとまり、ラベルには最初に現れたステージ名を使う。この場合の個別同期は入力キーが1つのため原理的にできず、本 PBI の対象外とする（設定側の role 重複の扱いは変更しない）。
- 並び順は `groupMappingsByStage` の返却順（有効ステージの sort_order 順、未解決は元の出現順）とする。
- `stageName` は、そのグループが `stageId` を持つ場合だけグループの `stageName` を使い、持たない場合は null にする（`Unknown` 等の補完名は表示しない）。
- 入力オブジェクトは変更しない。

### 2.2 ParamSyncModal の候補・型判定

- 起動時に `stageMastersApi.list(true)` を取得する（既存の `mappingMastersApi.list()` と同じ useEffect の形）。失敗時は `console.error` して stages を空配列とする。その場合も `groupMappingsByStage` はバリアントの `stage_name` へフォールバックするため、ステージ名は可能な範囲で表示される。
- 候補は `buildParamSyncCandidates(activeWorkflow.mappings, mappingMasters, stages)` で作る。
- 型判定は `resolveType(role) = candidate.inputType ?? roleMasterMap.get(role)?.input_type ?? null` とする（legacy フィクスチャや `input_type` 欠落時の互換のため、既存の `roleMasterMap` を2番目の参照先として残す）。
- サブ候補 = `candidates.filter(c => c.role !== 代表role && resolveType(c.role) !== null && resolveType(c.role) === resolveType(代表role))`。代表そのもの（AC-2）と異なる型は除外する。
- `handleMasterChange` の同期先絞り込みも同じ `resolveType` を使う（現行は `roleMasterMap` を使うため、代表変更時にステージ付き同期先が消える不具合がある）。
- 表示名は `name(role) = candidate.displayName ?? roleMasterMap.get(role)?.display_name ?? role`（既存テストの legacy フィクスチャはマスター側の表示名を使うため）。
- 候補ラベル: `stageName` があれば `「{stageName} / {name}」`、なければ `name` だけ。2行目に従来どおり `Role: {role}` を表示する。代表選択 `<select>` の option も同じラベルに `({role})` を付ける。
- `checked` は `activeGroup.slave_roles.includes(role)` のまま（AC-6 の復元はこの判定で成立する）。
- 新規作成時の代表初期値（`workflowMappedRoles[0]`）、グループ一覧、改名・削除・有効切替は変更しない。

### 2.3 同期適用（変更なし・回帰確認）

`applyParamSync` は role 文字列キーで動くため、ステージ付き role でも次が成り立つ:
- AC-3: `slave_roles=[Rough]` なら Rough の実効値だけ代表値になり、Detail は自分の保存値のまま。
- AC-4: 同一型の別ロール `Rough/OtherSteps` も同じ処理で代表値になる。
- AC-5: `slave_roles` から Detail を外すと、Detail は以後同期されない。生成時には Detail 自身の入力欄の値（ストア `paramValues['Sampler_Steps_Detail']`）がそのまま使われる。これが AC-5 の「解除時の値」である。
  - 具体例: 初期値 Main=20、Rough=30、Detail=40。Rough と Detail を同期先に選び、Main を 60 にして生成すると、送信値は Rough=60、Detail=60 になる。ただしストアの Rough=30、Detail=40 は変わらず、同期中の両入力欄は無効化された状態で 30・40 を表示している。ここで Detail だけ同期先から外すと、その時点の Detail の入力欄は 40。続けて Main を 70 にして生成すると、送信値は Rough=70、Detail=40 になる（60 や 70 にはならない）。
  - ストアを書き換えない理由: `applyParamSync` は生成時に送信用のコピー（`merged`）だけを代表値で上書きし、ストアの `paramValues` には書き戻さない（C4）。ストアへ書き込む方式は §12 の2のとおり範囲外。DB に保存される値ではない点に注意する（「保存値」は本書ではストアの値を指す）。

テストが失敗した場合に限り、T2 の範囲で `applyParamSync` を最小修正する（D6）。

## 12. トレードオフと代替案

1. **候補の型判定を WorkflowMapping.input_type 優先にする（採用）** vs マスター一覧のバリアント `computed_role` から逆引きする: 前者はバックエンドが実効マスターから解決済みの値を使え、カスタム role 上書きにも追従する。`roleMasterMap` を予備として残すため legacy データも従来どおり動く。
2. **同期を生成時の実効値に適用する現行方式を維持（採用）** vs 代表の入力変更時にストアの同期先値も書き換える方式: 後者は表示が直感的だが、プリセット保存・スナップショット・Seed 経路に影響が広がり、本 PBI の範囲を超える。維持の代償として、同期中の同期先入力欄は無効化されたまま自分の保存値を表示する（既存挙動）。
3. **AC-5「解除時の値」の解釈（設計レビューで確認済み）**: 同期先から外した時点で Detail 自身の入力欄にある値（§2.3 の例では 40）を保持する、と解釈した。「外すときに代表の値（例では 60）を Detail の入力欄へ書き込み、以後その値を使う」解釈も考えられるが、ストアを書き換える新しい挙動になるため採用しない。
4. **純関数を既存 `mappingStageGroups.ts` に追加（採用）** vs 新規ユーティリティファイル: テスト配置規約（既存テストファイルの拡張）とステージ射影の再利用を優先した。

## 13. リスク

- リスク分類: **low**（フロントの候補生成と表示のみ。スキーマ・API・依存・共有フィクスチャ・検証基盤の変更なし）。ただし検証プロファイルは V1 既定で、Gate 2 のフルスイートを新規実行する。V2 は採用しない。
- 同じ表示名の候補が並ぶため、ステージ未解決（バリアントなし legacy mapping）の場合は区別がつきにくい（`Role:` 行で区別）。
- 同期中の同期先入力欄が代表値でなく保存値を表示する既存挙動は残る（§12-2）。ParamPanel の「Synced: {表示名}」も同名マスターでステージが分からない。いずれも本 PBI の範囲外として記録する。
- 既存 `ParamSyncModal.test.tsx` のフィクスチャは `input_type` のない mapping を使う。`roleMasterMap` 予備参照で互換を保つ。
