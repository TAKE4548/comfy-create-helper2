# REQ-280: プロンプト編集オートセーブ競合（OCC）誤発火およびポーリングタイマーリセット遅延の解消 設計書

- **PBI**: REQ-280
- **改訂日**: 2026-09-20
- **作成者**: Architect
- **ステータス**: 設計完了 (Design Completed based on Forensic Log and Static Analysis)

---

## 1. 概要 & 目的

単一クライアントでプロンプト編集やパラメータ調整を行っている際に、他端末が一切関与していないにもかかわらず「他セッションで更新されました」という競合モーダル（`PresetConflictModal`）が頻発する問題が継続していた。
さらに、定期ポーリング（5秒周期）を受信するたびにオートセーブのデバウンスタイマーが不意に延命リセットされ、1秒待った直後の生成で旧パラメータが ComfyUI に投入される実害（REQ-278 の実害要因の一つ）も確認された。

本設計書では、解析報告書（`tmp/Prompt_Surgeon_Prompt_Edit_Conflict_and_Autosave_Analysis.pdf`）および `logs/app.jsonl` のログ検証に基づき、原因と影響範囲が異なる以下の2つの独立した課題を明確に峻別し、恒久的是正を行う。

1. **【直接要因①】通信中（In-flight）の多重送信による 409 Conflict 根絶**:
   - `updatePresetMutation.isPending` 中は新規 PUT リクエストを待機させ、先行リクエストの完了レスポンス（最新 `updated_at`）受領後に最新差分を1回だけ送る直列化（In-flight ガード）を導入。
2. **【直接要因②】キー順序不整合による「偽の isDirty 残留」と定期ポーリング衝突の根絶**:
   - `isStateEqual` での `JSON.stringify` を廃止し、キー順序に依存しない浅い等価比較関数（`isRecordEqual`）を導入。
3. **【直接要因②】テキストモード入力時の空白正規化ギャップ解消**:
   - オートセーブ送信時およびテキスト変更ハンドラにおいて正規化文字列との同期を安全に行い、空白差分による偽の未保存判定を排除。
4. **【独立した別問題】ポーリングによるタイマーリセット・保存遅延の解消**:
   - オートセーブ用 `useEffect` の依存配列から `presets` を除外し、`presetsRef.current` 経由での参照に変更することで、定期ポーリングによるタイマー延命を根絶。

## 2. 根本原因の構造的分析と是正設計

### 2.1 直接要因①: 通信中（In-flight）の連続保存による BE の 409 Conflict
- **該当箇所**: `frontend/src/pages/GeneratePage/hooks/usePresetState.ts` L154–L209, L1054–L1097
- **メカニズム**:
  タイピング中やスライダー調整中、1回目の PUT リクエストがネットワーク通信中（In-flight）の間に、デバウンスタイマーまたは即時フラッシュにより2回目の保存が走る。
  1回目の保存がコミットされるとバックエンド（`presets.py`）の `updated_at` は T1 に進むが、2回目は1回目のレスポンス（T1）を受信する前に送信されるため、古い `base_updated_at: T0` のまま BE に届く。
  BE の `(db_updated_at - base_updated_at).total_seconds() > 0.01` に引っかかり HTTP 409 Conflict が返却され、フロントの `onError` が競合モーダルを表示してしまう。
- **是正方針**:
  - `pendingSaveArgsRef` を新設し、`updatePresetMutation.isPending` 中に保存要求が発生した場合はその引数をキューに保持。
  - `updatePresetMutation` の `onSettled`（成功／失敗問わず）において、キューされた `pendingSaveArgsRef` があれば、最新の `presetUpdatedAtRef`（最新 `base_updated_at`）を注入して直列に1回だけ再実行する。

### 2.2 直接要因②: キー順序差分による「偽の isDirty 残留」とポーリングの衝突
- **該当箇所**: `frontend/src/pages/GeneratePage/hooks/usePresetState.ts` L91–L99, L951–L995
- **メカニズム**:
  `isStateEqual` が `JSON.stringify(a.paramValues) === JSON.stringify(b.paramValues)` で比較している。
  JavaScript オブジェクトはスプレッド構文マージ（`{ ...defaults, ...preset }`）や Python BE の JSON シリアライズ順によってキーの出力順序が入れ替わる。キー順が異なるだけで `false` と判定され、保存完了直後でも `isDirty = true` と誤認され続ける。
  この状態で BE から 5秒周期で取得した `updated_at`（自端末の直前の更新で進んだ時刻）をポーリングが拾うと、「サーバー側で時刻が進んだ」＋「手元が isDirty（未保存）」の2条件が揃い、他セッションが更新したと誤認して競合モーダルが表示される。
- **是正方針**:
  - キー順序非依存の等価比較関数 `isRecordEqual` を実装し、`paramValues` の比較に適用する。
  ```typescript
  export const isRecordEqual = (a?: Record<string, any>, b?: Record<string, any>): boolean => {
    if (a === b) return true
    if (!a || !b) return false
    const keysA = Object.keys(a)
    const keysB = Object.keys(b)
    if (keysA.length !== keysB.length) return false
    return keysA.every((k) => a[k] === b[k])
  }
  ```

### 2.3 独立した別問題: ポーリングによるタイマークリア・保存遅延
- **該当箇所**: `frontend/src/pages/GeneratePage/hooks/usePresetState.ts` L1097
- **メカニズム**:
  オートセーブ用 `useEffect` の依存配列に `presets` が指定されている。
  5秒ごとの定期ポーリングで React Query が `presets` を再フェッチすると、データ同一であっても新しい参照配列となり、`useEffect` のクリーンアップが走って `clearTimeout(autoSaveTimerRef.current)` が実行される。
  結果として、1秒デバウンスタイマーが不意にリセット・延命され、1秒待った直後の生成ボタン押下時に未保存の旧値でジョブが飛んでしまう。
- **是正方針**:
  - `const presetsRef = useRef(presets); presetsRef.current = presets;` を定義。
  - オートセーブ用 `useEffect` の依存配列から `presets` を除外。`activePreset` の特定には `presetsRef.current` を参照する。

## 3. トレードオフ・リスクの開示 (Trade-off Disclosure)

| 項目 | トレードオフ / 潜在リスク | 対策・緩和策 |
|---|---|---|
| **In-flight ガードによる保存遅延** | 通信中に連続編集された場合、通信完了を待ってから次の保存が走るため、ネットワークが極端に遅い環境で最後の保存完了まで数十ms〜数百ms長引く可能性がある。 | 前回の通信完了直後に最新のスナップショットを1回だけ送る直列キュー（Coalescing queue）方式を採用し、中間の無駄な多重リクエストを破棄して通信負荷を最小化する。 |
| **テキストモードでの即時正規化** | 入力中にカンマ直後の空白などを強制削除するとタイピング感が阻害される。 | 入力中（onChange）は生文字列を許容し、保存送信時（debounce 発火時）および onBlur 時に正規化を同期させることで快適なタイピングを担保する。 |
| **`useEffect` の ESLint ルール** | `presets` を依存配列から除外すると `react-hooks/exhaustive-deps` 警告が出る可能性がある。 | `presetsRef` パターンを採用し、安全な参照維持を行う。明示的なコメント（`// eslint-disable-next-line react-hooks/exhaustive-deps`）で意図を記録する。 |
