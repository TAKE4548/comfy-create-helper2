# Design Document: REQ-102 スナップショット保存時の重複LoRAによるユニーク制約エラーの修正

## 1. Summary
本ドキュメントは、スナップショット保存時（`POST /api/snapshots`）および更新時（`PATCH /api/snapshots/{id}`）において、適用されたアセット（LoRA/タグセット）情報に重複が存在する場合に、データベースのユニーク制約 `UNIQUE(snapshot_id, lora_id, role)` 等に反して `IntegrityError`（`500 Internal Server Error`）が発生する問題を解消するための設計を定義します。

## 2. Design Principles & Changes

### 2-1. バックエンド側での重複排除（デデュープ）の導入
データベースへのデータ挿入前段階で、送信されたアセット情報の重複を同一の `(asset_id, role)` の組み合わせに基づいて自動的に排除します。これにより、クライアントからのリクエスト内に重複するアセットデータが含まれていた場合でも、データベース制約違反（IntegrityError）を発生させずに安全に登録・更新を完了させます。

#### 変更点：`SnapshotService.create_snapshot` (`backend/app/services/snapshot_service.py`)
- `payload.loras` を登録する際、同一の `(lora_id, role)` キーの組み合わせでデデュープ処理（辞書型等を用いた上書き・一意化）を行います。
- `payload.tag_sets` を登録する際、同一の `(tag_set_id, role)` キーの組み合わせでデデュープ処理を行います。

#### 変更点：`SnapshotService.update_snapshot` (`backend/app/services/snapshot_service.py`)
- `payload.lora_ids` を登録する際、リストを一意化（`set` による重複排除）してから登録します。
- `payload.tag_set_ids` を登録する際、リストを一意化してから登録します。

## 3. Impact Range & Risks
- **データ整合性**: 重複するLoRA/タグセットがあった場合、最後の項目が適用されます（強度の重複がある場合、最後に入力された強度が有効になります）。実用上、同じスナップショットに対して同じ役割で同じLoRAを複数登録することには意味がないため、この挙動で問題ありません。
- **既存データへの影響**: データベーステーブルのスキーマやユニーク制約自体の変更は行わず、アプリケーションロジック層での対応となるため、既存のデータ破壊やマイグレーションの必要性はありません。

## 4. Verification Plan
- 重複するLoRA/タグセットを含むペイロードを用いた単体テストコードを `backend/tests/test_snapshots.py` に追加します。
- テスト内で、重複データが正常にデデュープされて登録され、データベース上でエラーにならずに保存できることを検証します。
