# Prompt Surgeon — 詳細設計書 (REQ-361)

## 1. 概要 (Overview)
- **PBI ID**: REQ-361
- **タイトル**: テストアーキテクチャ再配置・チケット名全廃＆多層ステート隔離 (Frontend / Backend)
- **種別**: refactor / test-architecture
- **関連仕様書 (SSoT)**: [SPEC_TEST_ARCHITECTURE.md](../specs/SPEC_TEST_ARCHITECTURE.md) (v2.2)
- **対象ディレクトリ**: `frontend/src/` (全44レガシーテストファイル、未規約89テストケース), `backend/tests/` (legacy/test_prompt_metadata.py, governance/test_openapi_contract.py)

### 1.1 背景と目的
REQ-356 において Backend のテストディレクトリ再構成および多層防護基盤が構築されたが、Frontend 側に 44 件のチケット名テストファイルが残存し、89 件のテストケース名で規約未遵守となっていた。
さらに、Backend 側にもモジュール直下でインメモリDBを初期化し `unittest.TestCase` を用いるレガシー実装 (`test_prompt_metadata.py`) が残存していた。
本設計では、全 44 Frontend テストファイルを対象コンポーネント・Hook・API の隣接 `__tests__/` ディレクトリへ安全に再配置し、`test/utils` の 5 層ステート隔離ヘルパーを適用するとともに、Backend レガシーテストを `conftest.py` の多層防護（SAVEPOINT ロールバック、`clean_dependency_overrides`）へ完全リファクタする。これにより、テスト衛生リンター (`scripts/verify_test_naming.py --strict`) 違反 0 件、テスト間副作用漏洩ゼロ（フレーキー防止 100%）、逆引きトレーサビリティ 100% を達成する。

### 3.6 フレーキーテスト根絶のためのフィクスチャ＆多層ステート隔離規約 (SPEC_TEST_ARCHITECTURE v2.2 準拠)
単なるリネームや移動にとどまらず、テスト間の副作用・状態リークによるフレーキー化を根絶するため、Backend / Frontend 双方で以下の規約を厳格に義務付ける。

#### 3.6.1 Backend Fixture 規約 (境界H / conftest.py 統合)
- **レガシー `unittest.TestCase` の全廃**: `backend/tests/integration/legacy/test_prompt_metadata.py` (T1対象) に残存するモジュール直下の `create_engine("sqlite:///:memory:")`、`connection`、`TestingSessionLocal`、`setUp`/`tearDown` 内の `Base.metadata.create_all`/`drop_all`、および手動 `dependency_overrides` を完全に撤廃する。
- **標準フィクスチャ統合**:
  - `conftest.py` の `db_session` フィクスチャを採用し、セッション共通の `db_engine` 上でテスト毎に SAVEPOINT (`nested = connection.begin_nested()`) を切り、テスト終了時に完全ロールバックする。
  - テスト用クライアントは `app.dependency_overrides[get_db] = override_get_db` を行う `client` フィクスチャとして定義し、`conftest.py` の `clean_dependency_overrides` (autouse) によってテスト終了時に自動クリアを保証する。
  - `verify_db_pool_clean` (autouse) により、テスト終了時の DB コネクションリークを 0 件と検証する。

#### 3.6.2 Frontend 5層ステート隔離規約 (境界C, D, E, F / test/utils 導入)
再配置・リネーム対象のテスト（特に旧 `e2e_req317_storage`, `e2e_req332_storage`, `e2e_req332_recovery`, `e2e_req260_vram_guard` など localStorage / IndexedDB / Zustand / QueryClient を操作するもの）において、テスト間の状態汚染を根絶するため `frontend/src/test/utils/` の共通ヘルパーを各テストスイートの `beforeEach` および `afterEach` で必須適用する。
1. **Zustand Store 隔離 (境界C)**: `resetTestStore()` を呼び出し、`useGenerationStore.setState(..., true)`（第2引数 `replace=true` による完全置換）および `usePromptClipboardStore`、WebSocket 接続フラグを初期化。
2. **Web Storage 隔離**: `resetTestStorage()` で `localStorage.clear()` および `sessionStorage.clear()` を実行。
3. **IndexedDB サンドボックス (境界C/F)**: `resetTestIndexedDB()` で `globalThis.indexedDB = new IDBFactory()` による新規インスタンス置換を実施。
4. **WebSocket 隔離 (境界E)**: `MockWebSocketController.clear()` で登録ハンドラ・キューを消去。
5. **React Query キャッシュ隔離 (境界D)**: `createTestQueryClient({ gcTime: 0, retry: false })` を使用し、テスト終了時に `clearTestQueryClient(queryClient)` を実行。
- **総合ヘルパー**: 原則として `cleanupAllTestState({ queryClient })` を各テストスイートの `beforeEach` / `afterEach` に組み込むことで、多層防護によるゼロ・ステート・リークを保証する。

- **Backend アプリケーション層**: FastAPI ルーター、Pydantic v2 スキーマ、SQLAlchemy モデル、サービス層ロジック。

### 5.2 切断・モック化する層 (Severed - External I/O & State Isolation)
- **Frontend ネットワーク通信**: `api/client.ts` 内の各 API 関数（`generationApi`, `workflowsApi`, `comfyApi` 等）を `vi.spyOn` または mock でトランスポート層切断。
- **Frontend WebSocket 通信**: `systemWsService` を `MockWebSocketController` で決定論的制御。実ソケット接続は 100% 遮断。
- **Frontend IndexedDB**: `fake-indexeddb/auto` サンドボックス内で完全隔離。テスト毎に `resetTestIndexedDB()` で初期化。
- **Frontend Zustand / Storage**: 各テスト前後で `cleanupAllTestState()` により完全クリア。
- **Backend DB トランザクション**: `db_session` (SAVEPOINT rollback) で永続化を遮断。テスト間のデータ漏洩ゼロ。
- **Backend 外部通信**: `mock_external_services` (respx) で ComfyUI/LM Studio への HTTP トランスポート層を完全遮断。

### 5.3 モックレベル規約 (Mock Level)
- 内部ヘルパーやビジネス関数のモンキーパッチは厳禁。
- モックはトランスポート層（HTTP / WebSocket / IDB）の境界のみに適用し、リファクタリング耐性を担保する。

### 5.4 プロパティベーステスト判定 (PBT Decision)
- 本 PBI はテストファイルの再配置とケース名規約化であり、新規の構文解析器・数値計算ロジック導入は含まないため、新規 PBT は不要。
- 既存の `seedBatch.test.ts` 等に含まれる PBT (`fast-check`) は 100% 保持・回帰ゼロを担保する。

### 5.5 異常系・フォールトインジェクション (Fault Injection)
- 移行対象テストに含まれるネットワーク切断、500/502/503 エラー、クォータ超過、OCC コンフリクト (409) のテストケースは漏れなくすべてそのまま移行・維持する。
