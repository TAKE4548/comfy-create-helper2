## 実現可能性と判定

AC-1〜6 は現行構成（React 18.3、react-router-dom 7.17、Vite 5.4.21、TanStack Query 5）で実現可能。新規 dependency・API 変更・保存形式変更は不要。

実現可能性の事前証拠（受入証拠ではない）: 作業ツリーの scratch コピー（`docs/logs/REQ-309-design/` 配下、アプリ source は無変更）で App.tsx の 6 画面だけを `React.lazy` + `Suspense` に置換して `vite build` した。警告閾値は未変更で、500 kB 超の警告は出ず、Vite 表示の最大チャンクは GeneratePage 357.73 kB、entry は約 348 kB だった（チャンク一覧: `docs/logs/REQ-309-design/exp-route-split-chunks.txt`）。したがって AC-2 の主手段は route 分割で足りる見込みが高い。一方、AC-1 は「`/` で取得する JS」に Generate chunk とその静的依存（モーダル群）が含まれるため、Generate 内部のモーダル分割で上積みする。これらの見込みは T5 の実測で確定し、満たさなければ設計改訂へ戻す。

## アーキテクチャ決定

- **D1 route 単位の遅延読込（T2）**: `App.tsx` の 6 画面を `lazy(() => import('./pages/X').then((m) => ({ default: m.X })))` に変更する。`createAppRoutes()` の JSX 要素形式、`AppShell`、ルートの `errorElement`、`PersistQueryClientProvider` の persist 設定、`useGenerationStore.initialize` の起動は変更しない。各 route 要素は `<Suspense fallback={<RouteLoadFallback/>}>` で個別に囲み、`AppShell` のナビゲーションは常に表示される。
- **D2 離脱保護は静的のまま（T2）**: `SettingsDraftBoundary` は静的 import のまま route 要素の外側に置き、その **内側**に `Suspense` と lazy `SettingsPage` を置く。blocker と `beforeunload` は Settings chunk の取得前から有効で、離脱判定は chunk の取得状況と独立する。`SettingsDraftContext` は entry chunk に常駐し、Settings chunk 側と単一インスタンスを共有する（Rollup は同一モジュールを複数 chunk に複製しない）。
- **D3 例外境界の継承（T2）**: chunk の取得失敗は `React.lazy` の reject として route 描画中に throw され、既存の `RethrowRouteError` → `GlobalErrorBoundary`（再読み込み導線）に流れる。新しい route 用 boundary は追加せず、REQ-381/AC-12 の経路を維持する。自動 reload（`vite:preloadError` での強制再読込）は未保存入力の喪失と無限ループの危険があるため採用しない。
- **D4 モーダル共通部品（T1）**: 新規 `components/common/LazyBoundary.tsx` に `RouteLoadFallback` と `LazyModalHost` を置く。`LazyModalHost` は 2 つの寿命モードを持つ。
  - `latch`（現状の「常時 mount・`isOpen` で null」を保つモーダル向け）: 初めて `isOpen=true` になるまで何も mount せず、一度 mount した後は閉じても mount を維持する。これにより初回オープン後の内部 state の寿命が現行と同一になる。
  - `while-open`（現状の「条件 render」向け）: `isOpen` の間だけ mount し、閉じれば unmount する。現行挙動と同一。
  - 共通: `Suspense` fallback は `isOpen` が true の間だけ表示（読み込み中に閉じた場合に後から現れない）。モーダル専用の局所エラー境界を持ち、取得失敗時は `role="alert"` の局所メッセージ、「閉じる」「ページを再読み込み」を出す。ページ全体（入力中のプロンプト）を `GlobalErrorBoundary` に落とさない。
- **D5 Generate 本体のモーダル境界（T3）**: `GeneratePage.tsx` の 10 種を D4 で置換する。常時 mount の 5 種は `latch`、条件 render の 5 種は `while-open`。`PresetManagerPanel` は外側の overlay `div` を静的に残し、内側のパネルだけを `while-open` で包む（既存の `data-testid`・背面クリック閉じは維持）。
- **D6 overlay のモーダル境界（T4）**: `GenerateModalsOverlay.tsx` の `BypassSettingsModal`・`ParamSyncModal`・`SaveAsTagSetModal` は `while-open`、`PromptTranslationModal` は `latch`（`promptTranslation.isOpen` を `isOpen` とする。`promptTranslation` が `{}`/未定義のテスト fixture でも従来どおり安全に動く）。コピー作成ダイアログと通知トーストは静的のまま。
- **D7 計測と検証の基盤（T0, T5）**: Gate 3 は dev server 用のため、本番配布物専用の Playwright 構成 `playwright.prod.config.ts` と `frontend/e2e/prod/` を追加する。既定構成には `testIgnore: ['**/prod/**']` だけを足し、既定の Gate 3 は収集件数も実行内容も変えない。本番配信は backend の `SPAStaticFiles` に倣い **圧縮なし**の小さな Node 静的サーバ（SPA fallback は拡張子なしのパスのみ）を使う（`vite preview` は圧縮 middleware を持つ可能性があり、実本番と転送条件が異なるため使わない）。
- **D8 チャンク警告（AC-2）**: `vite.config.ts` と `package.json` の build script は変更しない。`chunkSizeWarningLimit`・`onwarn`・`logLevel`・`manualChunks` は追加しない。警告の解消は実際の遅延境界による実チャンクの縮小のみで判定し、ビルドログ全文と config のハッシュ一致を証拠に残す。

## Seam Map

1. **Integrated (real code)**
   - `createAppRoutes()` と実 `React.lazy` + 実 `Suspense`。
   - `SettingsDraftBoundary`・`SettingsDraftContext`・`useBlocker`、`GlobalErrorBoundary`。
   - `PersistQueryClientProvider` + IndexedDB persister（`fake-indexeddb`）。
   - 実 `GeneratePage` + 実 `useGeneratePageState` + 実 Zustand store + 実モーダル + `LazyModalHost`。
2. **Severed (external I/O only)**
   - HTTP: API モジュール境界（既存テストの `vi.mock('../../../api/client'...)` 規約）または Playwright `page.route`。
   - WebSocket: 既存の `MockWebSocketController` または Playwright `routeWebSocket`。
   - ブラウザの取得: Playwright の request 制御（delay / abort）。
   - コード取得（`import()`）: `vi.mock(modulePath, async () => { await gate; ... })` のモジュール境界ゲート。
   - このゲートは「読み込み完了時刻」の制御に限定し、業務ロジックの置換には使わない。
3. **Mock level**
   - 内部 hook・store・`LazyModalHost`・modal 内部のモックは禁止。
   - 既存 `ROUTE`/`PERSIST` テストが page 本体を軽量 stub にしているのは route 配線の検証が目的のため許容する。
   - page 本体を実体で動かす受入は GEN と本番 E2E が担う。
4. **PBT decision**
   - パーサ・DSL・数値処理は変更しない。
   - `LazyModalHost` は open/close/読込成功/読込失敗/再 open の離散状態遷移を持つ。
   - そのため `fast-check`（devDependency 済み）の状態列モデルテストを T1 で必須にする。
   - 不変条件は「latch は一度 mount したら unmount されない」「`while-open` は閉じたら必ず unmount」「fallback は `isOpen` 中のみ」「失敗後も親は破壊されない」。
5. **Fault injection**
   - chunk の 404 / abort / 遅延。
   - 読込中の遷移・クローズ。
   - 再デプロイによる旧ハッシュ chunk の 404。
   - IndexedDB 復元中の chunk 遅延。
   - 詳細はテスト計画の Red Team 節。

## 検討した代替案とトレードオフ

| 案 | 判断 | 理由 |
|---|---|---|
| A. route 単位 `React.lazy`（採用） | 採用 | 既存の `createAppRoutes()` JSX 形式・REQ-381 テスト・`RethrowRouteError` 経路を保てる。scratch 実験で最大 chunk 357.73 kB |
| B. Data Router の `Route lazy` | 不採用 | 遷移完了前に chunk を取得でき `useNavigation` で待機表示ができるが、エラーの経路が loader/route error になり REQ-381/AC-12 の再 throw 経路と離脱保護の検証を作り直す必要がある。blast radius が大きい |
| C. `manualChunks` による vendor 分割のみ | 不採用 | 警告は消せるが初回に全 chunk を取得するため AC-1 を満たさない（PBI も明示的に禁止） |
| D. Desktop/Mobile レイアウトの遅延分割 | 今回は不採用 | 「プロンプトが編集可能」に至る経路に chunk 取得の直列段が 1 つ増える（Generate chunk → layout chunk）。節約量は片方のレイアウト固有コードに限られ、共有部品は両方が静的 import する。T5 の chunk 報告で AC-1/2 が不足した場合に限り設計改訂で再検討する |
| E. 他画面の idle prefetch | 不採用 | 編集可能時点の計測を変えずに初回後の待ちを減らせるが、「初回に不要な JS を取らない」という要求の意図と計測の解釈を曖昧にする。別 PBI の判断事項 |
| F. 読込失敗時の自動 reload | 不採用 | 未保存入力を失う・無限ループの危険。再読み込みは利用者の操作に限る |

主なトレードオフ:

- `/` の初回表示は「entry → Generate chunk」の 2 段の直列取得になる（現状は 1 本）。往復遅延は増えるが、取得 JS 総量は大幅に減る見込み。判定は転送量だが、編集可能になる**時間**も T0/T5 で併記し、悪化していれば人間レビューに提示する。
- 他画面への初回遷移は chunk 取得を待つ。React Router v7 の遷移は `startTransition` で行われるため、既に表示中の画面は chunk 取得中も維持され、新規 Suspense 境界の fallback が出る/出ないは React の挙動に依存する。仕様としては「ナビゲーションは常に表示され、最終的に最後に選んだ画面が表示される」だけを保証し、中間表示は実測値を記録する（固定仕様にしない）。
- `TagsPage → LoRAsPage` の静的結合により `/tags` の初回遷移で LoRAs chunk も取得する可能性がある。`formatBaseModelSummary` の移設は他ファイル所有を広げるため今回は行わず、T5 の chunk 報告に載せて必要なら別 PBI とする。

## リスクと対応

| ID | リスク | 対応 |
|---|---|---|
| R1 | 基準の汚染（作業ツリーに他 PBI の変更が混在し、前後差が本 PBI の効果だけにならない） | T0 でビルド済み dist・ソース manifest（sha256）・本 PBI 所有 3 ファイルの原本を凍結。T5/最終検証でソース manifest の差分が所有ファイル以外を含む場合は、所有 3 ファイルだけ原本に戻した統制基準を再ビルドして再計測する |
| R2 | モーダルを条件 mount にすると内部 state の寿命が変わる | 常時 mount だった 5 種は `latch`（初回オープン後は mount 維持）。初回オープン前の副作用（例: `JobManagementModal` の `clearReservation`）は no-op だったため同値。GEN で初回/再オープン/オープン中クローズを検証 |
| R3 | 本番で chunk 取得失敗（再デプロイで旧ハッシュ 404、通信断） | route: 既存 `GlobalErrorBoundary`。モーダル: 局所エラー。どちらも利用者の再読み込み操作で回復。再試行の自動化はしない。失敗時の未保存プロンプトの扱いは E2E で観測して記録 |
| R4 | Settings chunk の取得中/失敗時に離脱保護が壊れる | D2 により boundary は静的。ROUTE/E2E で「離脱ブロック → chunk 未取得のまま止まる」「キャンセルで draft 維持」「破棄で遷移後に取得」を検証 |
| R5 | `React.lazy` が reject を cache するため、同一セッションの再試行では回復しない場合がある | 回復操作は reload と明記。失敗後の再 open で無限 spinner にならず、局所エラーが再表示されることをテスト |
| R6 | 直列取得の増加で編集可能時間が悪化する | 時間も記録（判定は転送量）。悪化時は人間判断。代替案 D/E は採らない |
| R7 | 型/Prop の複雑化（generic lazy host） | T1 に型契約を固定し `npm run typecheck` を gate に含める。モーダル props 型は loader の戻り型から導出 |
| R8 | 既存テストが同期 `getBy*` で modal を期待している | T3/T4 の所有テストは `findBy*`/`waitFor` に更新。非所有テストで失敗した場合は編集せず設計へ報告 |
| R9 | 計測環境差（拡張機能・Service Worker・DevTools cache 設定・並行負荷） | 毎回新規 browser context（空 cache）、同一 viewport、5 回実行、環境メタデータ記録。差分が揺れる場合は判定保留 |

## リスク分類と検証プロファイル

- **リスク分類: high**。理由: 配布物（public build artifact）とエントリポイントの構造変更、`playwright.config.ts` の検証基盤変更、検証インフラの追加（`playwright.prod.config.ts`）。

## 計測の判定規則（AC-1）

- **凍結**
  - T0 が実装前の候補（他 PBI の変更がコミット済みの clean HEAD。`git status --porcelain -- frontend/src` が空であることを確認して凍結。2026-10-28 に REQ-402 コミット後で再凍結し、旧凍結物は `baseline-superseded-20261028/` に履歴保存）から本番ビルドし、dist・ソース manifest・所有 3 ファイルの原本を `docs/logs/REQ-309/baseline/` に保存する。
  - 以後の比較基準はこの凍結物のみ。2026-10-26 の 1,761.64 kB や過去の 1,261.71 kB は基準に使わない。
- **同一条件**
  - 同じ Node 静的サーバ実装（圧縮なし）、同じ Chromium、毎回新規 context（空 cache）。
  - 同じ viewport（主: 1280x800、副: 375x667）、同じ初期 route `/`、同じ API stub（形は T0 カードの GET 固定 fixture 表。配列型 endpoint に `{}` を返さず、`/generation/state` の `epoch` は string、`/workflow-presets` は 1 件の preset）、同じ判定点。
- **判定点**
  - プロンプト入力欄が visible かつ enabled かつ editable になった時刻（`locator.isEditable()`）。対象は既定の Chips Mode で最初から操作できる `<input type="text">`: desktop（1280x800）は `#prompt-positive input[type="text"]`、mobile（375x667、`innerWidth < 768` で MobileLayout）は `#prompt-mobile-positive input[type="text"]`。locator は `frontend/e2e/prod/support/promptInput.ts` の `promptChipInput` が唯一の定義（2026-10-28 訂正: 旧記述 `#prompt-positive textarea` は、textarea が「テキスト入力モード切替」押下後にのみ存在し、mobile は ID も異なるため、現行コードでは初期表示に存在しなかった。AC の文言「プロンプト入力欄が編集可能」は不変）。
  - Network 記録の開始（`page.goto` 前に CDP `Network.enable`）から判定点までに完了した JS 応答の `encodedDataLength` を合計する。
  - 判定点で取得中の JS は受信済み byte を加える（部分取得分を落として小さく見せない）。
  - 静穏後（500 ms 無通信）の合計も記録し、判定点を遅らせて JS を隠していないことを確認する。
- **比較**
  - 5 回実行の中央値で `after < before`（判定点合計と静穏後合計の両方）。
  - ビルド表示の kB・生成ファイルの bytes・転送 bytes は別指標として表に併記し、混同しない。
  - `index.html`・CSS・API・画像は合計に含めない。`modulepreload` による先読みは合計に含める。
- **主張範囲**
  - 本番の実配信条件（圧縮なし、`SPAStaticFiles`）以外（gzip/br、HTTP/2、CDN）での転送量は不明であり、AC-1 の主張範囲外とする。
  - この点は検証報告に明記する。
