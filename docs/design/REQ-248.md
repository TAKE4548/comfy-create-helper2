# Technical Design Document: REQ-248

## 1. Overview & Architectural Goals

本設計書は、PBI `REQ-248`（OpenAPI JSONへの一本化とopenapi-typescriptによるFE型生成・同期チェック）の技術設計を定義する。

### 1.1 背景と課題
- バックエンド（FastAPI）のAPI定義、`backend/openapi.json`、`docs/openapi.yaml`、およびフロントエンドの型定義（`frontend/src/api/types.ts` 等）の間で多重管理とスキーマ乖離（Contract Drift）が生じていた（JSON: 115 path, YAML: 120 path, 稼働app: 139 path）。
- サーバーを起動せずに決定的なOpenAPI JSONを静的出力する公式スクリプトが存在せず、フロントエンド向け自動型生成パイプラインやCI同期検査が存在しなかった。
- 一部の既存ガバナンステスト（`test_openapi_contract.py`）が廃止予定の `docs/openapi.yaml` を参照していた。

### 1.2 設計目標
1. **サーバーレス静的JSON出力**: Uvicorn起動・HTTP通信・DBアクセス・worker起動を行わずに `app.openapi()` から決定的（再現可能）な `backend/openapi.json` を生成・更新するスクリプト `scripts/export_openapi.py` を整備する (AC-1)。
2. **公式ツールによるFE型生成**: `openapi-typescript` (^7.13.0) を導入し、保存済み `backend/openapi.json` から `frontend/src/api/schema.ts` を手編集不要で自動生成する (AC-2)。
3. **API層手書き型の生成型移行**: `frontend/src/api/types.ts` および `frontend/src/api/domains/generation.ts` をリファクタリングし、手書き型を `components['schemas'][...]` への型参照・エイリアスへ移行する。UI専用型は契約外として明示的に分離し、既存通信・照合・再送防止・エラー制御との型互換性を100%維持する (AC-3)。
4. **差分検出・非更新チェック (Contract Drift Guard)**: バックエンド（FastAPI vs openapi.json）およびフロントエンド（openapi.json vs schema.ts）の両層で、差分検出時に非ゼロ終了しファイルを書き換えない `--check` コマンドを整備し、統合検査 `scripts/verify_openapi_sync.py` として Gate 1 / CI に組み込む (AC-4)。
5. **YAML完全廃止とJSON一本化**: `docs/openapi.yaml` を廃止・削除し、現行テストおよび仕様書の参照先を `backend/openapi.json` に統一する (AC-5)。

## 2. Seam Map [W-DD-SEAM]

本設計における統合レイヤー、外部I/O遮断境界、モックレベル、PBT採否、異常系注入の方針は以下の通りである。

```
+-----------------------------------------------------------------------------------+
| [Integrated (Real Code)]                                                          |
|  - FastAPI app router & schemas (in-memory AST reflection via app.openapi())      |
|  - JSON serializer & comparator (scripts/export_openapi.py)                       |
|  - openapi-typescript CLI parser & AST type generator                             |
|  - TypeScript compiler (tsc -b --noEmit) & Vitest client unit/integration tests   |
|  - Pytest governance contract tests (backend/tests/governance/)                   |
+-----------------------------------------------------------------------------------+
                                          |
                                          | (SEVERED BOUNDARY)
                                          v
+-----------------------------------------------------------------------------------+
| [Severed (External I/O Only)]                                                     |
|  - HTTP Network / Uvicorn server startup (NO network binding)                     |
|  - Database persistence (SQLite/SQLAlchemy create_all, migrations, seed: NOT run) |
|  - ComfyUI WebSocket & Bridge execution (Bridge & workers: NOT started)           |
|  - LLM / External inference services (Completely isolated)                        |
+-----------------------------------------------------------------------------------+
```

1. **Integrated (real code)**:
   - FastAPI アプリケーションインスタンス (`app.main:app`) のスキーマ定義・ルーター群。
   - `scripts/export_openapi.py` による辞書走査および JSON シリアライザ。
   - `openapi-typescript` による OpenAPI スキーマパースと TypeScript 型定義生成。
   - フロントエンド API クライアント、型参照定義、および Vitest テストスイート。
   - バックエンドのガバナンステスト（`test_openapi_contract.py`）におけるスキーマ検証ロジック。
2. **Severed (external I/O only)**:
   - `app.main` インポート時は ASGI lifespan (`lifespan(app)`) を一切起動しないため、DBエンジン初期化、マイグレーション実行、シーディング、ComfyGenerationBridge、GenerationService、ResourceMonitor は完全に遮断される。
   - 外部通信（HTTP/WebSocket）および Uvicorn プロセスは起動しない。
3. **Mock Level**:
   - 内部ヘルパーやビジネスロジックのモンキーパッチは厳禁。CLI チェックおよび同期検査は実ファイルと実メモリ内スキーマの比較を行う。APIクライアントのテストでは既存の MSW (Mock Service Worker) による HTTP トランスポート遮断を継続利用する。
4. **PBT Decision (Property-Based Testing)**:
   - OpenAPI スキーマ出力および型生成は、静的構造の決定論的シリアライズ・構文チェックであり、広域入力空間を持つ数式計算やDSLパーサーではないため、Property-Based Testing (Hypothesis / fast-check) は新規採用せず、決定論的な完全一致テストおよび差分検知ユニットテスト（異常系含む）で担保する。
5. **Fault Injection (異常系・境界系)**:
   - バックエンド実装のみ変更され保存JSONが更新されていないケースをシミュレートし、`--check` が非ゼロ（exit 1）で終了しファイルを書き換えないことをテストする。
   - 保存JSONのみ変更されFE型が古いケースをシミュレートし、`openapi-typescript --check` が非ゼロ（exit 1）で終了することをテストする。
   - 不正なパス・存在しないファイル指定時のエラーハンドリングを検証する。

## 3. Subsystem Architecture & Detailed Component Design

### 3.1 Backend: 静的出力・検査スクリプト (`scripts/export_openapi.py`)
FastAPI の `app.openapi()` を直接呼び出し、インメモリでスキーマ辞書を取得して JSON 形式で出力・比較する。

- **CLI オプション**:
  - `--output <path>` (デフォルト: `backend/openapi.json`): 出力先パス。
  - `--check`: ファイルを更新せず、現在のファイル内容とインメモリ生成内容を比較。差分がある場合は差分サマリーを出力して `sys.exit(1)`、一致していれば `sys.exit(0)`。
  - `--indent <int>` (デフォルト: 2): JSON インデント幅。
- **決定論的シリアライズ要件**:
  - `ensure_ascii=False`, `indent=2`, 行末 `\n` (UTF-8 without BOM)。
  - 不要なキー並び順の揺らぎを防ぐため、FastAPI が構築した順序を尊重しつつ決定的なフォーマットを維持する。
- **無副作用要件**:
  - `from app.main import app` のみを行い、`lifespan` コンテキストに入らない。DB接続やバックグラウンドタスクが動作しないことをユニットテストで保証する。

### 3.2 Frontend: openapi-typescript 導入と型生成・同期チェック
- **依存関係の追加**:
  - `frontend/package.json` の `devDependencies` に `openapi-typescript` (`^7.13.0`) を追加。
- **npm スクリプトの定義**:
  - `"openapi:generate"`: `openapi-typescript ../backend/openapi.json -o ./src/api/schema.ts`
  - `"openapi:check"`: `openapi-typescript ../backend/openapi.json -o ./src/api/schema.ts --check`
- **生成アーティファクト**:
  - `frontend/src/api/schema.ts`: `openapi-typescript` により生成される完全自動生成ファイル。手編集禁止（ヘッダーに自動生成コメント付与）。`paths`, `components`, `operations` 等をエクスポートする。

### 3.3 Frontend: API層の型移行設計 (`types.ts`, `domains/generation.ts`)
既存の画面コンポーネント・ストア・フックへの破壊的変更を防ぎつつ、手書きAPI型の二重管理を解消する。

1. **基本方針**:
   - `frontend/src/api/schema.ts` から `components` をインポートし、APIスキーマに該当する手書き型を `components['schemas'][<SchemaName>]` への型エイリアスまたは拡張型として再定義する。
   - 例:
     ```typescript
     import type { components } from './schema'
     export type Schema<T extends keyof components['schemas']> = components['schemas'][T]

     // API型: 生成スキーマへのエイリアス
     export type MappingMasterV2 = Schema<'MappingMasterV2Read'>
     export type MappingMasterCreate = Schema<'MappingMasterCreatePayload'>
     export type Workflow = Schema<'WorkflowRead'>
     export type WorkflowCreate = Schema<'WorkflowCreate'>
     export type WorkflowUpdate = Schema<'WorkflowUpdate'>
     ```
2. **画面専用型（UI-Only Types）の明示的分類と境界**:
   - API契約に含まれないフロントエンド固有の状態（例: ダイアログの開閉状態、選択中タブ、UIドラッグ&ドロップの一時座標、クライアント専用の表示ヘルパーフラグなど）は、`// [UI-Only Type]: Not part of OpenAPI contract` と明記し、API型と明確に区別して維持する。
3. **通信制御・クライアントの互換性維持**:
   - `api/client.ts` や `domains/generation.ts` の `reconcile`, `unconfirmed`, `cancelled` などの応答不明照合や再送防止ロジック、エラーハンドリングは一切変更せず、型定義のみを整合させる。

### 3.4 Governance: YAML廃止と契約テストのJSON一本化
- **`backend/tests/governance/test_openapi_contract.py` の改修**:
  - `docs/openapi.yaml` の読み込み（`yaml.safe_load`）および `docs_snapshot` に対するアサーションを全て削除する。
  - `backend/openapi.json` に対する比較のみを正本として維持・強化する。
  - `scripts/export_openapi.py --check` の実行結果を検証するテストケースを追加する。
- **`docs/openapi.yaml` の削除**:
  - リポジトリから `docs/openapi.yaml` を物理削除する。
- **仕様書・ドキュメントの同期**:
  - `docs/specs/SPEC_SETTINGS.md`, `README.md`, `SKILL.md` 等で `docs/openapi.yaml` を参照している現行記述を `backend/openapi.json` に更新する。
  - 過去の完了PBI（archive）やレビューログ等の履歴文書は変更せず、現行SSoTのみを対象とする。

### 3.5 System Tooling: 統合同期検査コマンド (`scripts/verify_openapi_sync.py`)
- バックエンドおよびフロントエンドの両方の同期状態を一括検証する Python スクリプト `scripts/verify_openapi_sync.py` を作成する。
- 実行内容:
  1. `backend\.venv\Scripts\python scripts/export_openapi.py --check` を実行。
  2. `npm run openapi:check`（frontend ディレクトリ）を実行。
  3. いずれかが失敗した場合はエラー概要を出力し、exit code 1 を返す。両方パスした場合は exit code 0 を返す。ファイルへの変更は一切行わない。
- `.agents/context.md` の Gate 1（Static Typecheck & Invariant Check）および CI 検証フローに `python scripts/verify_openapi_sync.py` を組み込む。

## 4. Delegation & Boundaries [W-DD-BOUNDARY]

### D1: Task Responsibilities, Scope, and Completion Conditions
- **REQ-248-T1 (Backend Export & Check Script)**:
  - 責務: `scripts/export_openapi.py` の実装と `backend/openapi.json` の初回最新化。
  - スコープ: `scripts/export_openapi.py`, `backend/tests/unit/test_export_openapi.py`, `backend/openapi.json`。
  - 完了条件: サーバー起動なし・DB副作用なしで `backend/openapi.json` が出力され、`--check` による差分検知が正常動作し、単体テストが PASS すること。
- **REQ-248-T2 (Contract Test JSON Unification & YAML Abolition)**:
  - 責務: `test_openapi_contract.py` の JSON 一本化、`docs/openapi.yaml` 削除、仕様書同期。
  - スコープ: `backend/tests/governance/test_openapi_contract.py`, `docs/openapi.yaml` (削除), `docs/specs/SPEC_SETTINGS.md`, `README.md`, `SKILL.md`。
  - 完了条件: `docs/openapi.yaml` が削除され、`test_openapi_contract.py` が `backend/openapi.json` のみを正本として検証し、全テストが PASS すること。
- **REQ-248-T3 (openapi-typescript Setup & Initial Type Generation)**:
  - 責務: `openapi-typescript` 依存追加、npm スクリプト作成、`frontend/src/api/schema.ts` の生成。
  - スコープ: `frontend/package.json`, `frontend/package-lock.json`, `frontend/src/api/schema.ts`。
  - 完了条件: `npm run openapi:generate` および `npm run openapi:check` が動作し、再現可能な `schema.ts` が生成されること。
- **REQ-248-T4 (FE API Types Migration & Compatibility Assurance)**:
  - 責務: `types.ts` および `domains/generation.ts` の手書き型を生成型参照へ移行。
  - スコープ: `frontend/src/api/types.ts`, `frontend/src/api/domains/generation.ts`。
  - 完了条件: `npm run typecheck` および `npm test` がエラーなく通過し、既存コンポーネント・通信ロジックとの互換性が維持されること。
- **REQ-248-T5 (Integrated Sync Check Script & Verification Pipeline Integration)**:
  - 責務: `scripts/verify_openapi_sync.py` の作成と `.agents/context.md` への Gate 1 登録。
  - スコープ: `scripts/verify_openapi_sync.py`, `.agents/context.md`。
  - 完了条件: 統合チェックスクリプトが BE/FE の同期漏れを検知して非ゼロ終了し、正常時に exit 0 となること。

### D2: Task Dependencies & Rationale
- **T1 → T2**: T1 で最新かつ決定論的な `backend/openapi.json` が生成できる状態になって初めて、契約テストの YAML 依存を削除し JSON 一本化に移行できる。
- **T1 → T3**: T3 の `openapi-typescript` が入力とする `backend/openapi.json` は T1 で最新出力されている必要がある。
- **T3 → T4**: T4 で手書き型を移行するためには、T3 で `frontend/src/api/schema.ts` が生成されている必要がある。
- **T1, T3, T4 → T5**: 統合チェックスクリプト T5 は、T1 の BE `--check` と T3 の FE `openapi:check`、および T4 の型整合性が完了した後に検証・統合される。

### D3: File Ownership Map
- **REQ-248-T1**: `scripts/export_openapi.py`, `backend/tests/unit/test_export_openapi.py`, `backend/openapi.json`
- **REQ-248-T2**: `backend/tests/governance/test_openapi_contract.py`, `docs/openapi.yaml` (削除), `docs/specs/SPEC_SETTINGS.md`, `README.md`, `SKILL.md`
- **REQ-248-T3**: `frontend/package.json`, `frontend/package-lock.json`, `frontend/src/api/schema.ts`
- **REQ-248-T4**: `frontend/src/api/types.ts`, `frontend/src/api/domains/generation.ts`
- **REQ-248-T5**: `scripts/verify_openapi_sync.py`, `.agents/context.md`

### D4: Shared Contracts
- **OpenAPI Schema Contract**: `backend/openapi.json` (OpenAPI 3.1.0, UTF-8, JSON indent=2, newline `\n`)。
- **TypeScript Schema Types**: `frontend/src/api/schema.ts` (`paths`, `components['schemas']`)。
- **CLI Drift Exit Contract**: 差分なし時は exit code `0`、差分あり時は exit code `1`（ファイル書き換えなし）。

### D5: AC-to-Task & Verification Mapping
| AC | 対応タスク | 検証方法 |
|---|---|---|
| **AC-1** | REQ-248-T1 | `python scripts/export_openapi.py` 実行後に副作用（DB/worker）がないこと、再実行で差分ゼロであることを単体テストおよび git status で検証 |
| **AC-2** | REQ-248-T3 | `npm run openapi:generate` で `src/api/schema.ts` が再現可能に出力され、手編集不要であることを検証 |
| **AC-3** | REQ-248-T4 | `npm run typecheck` および `npm test` が成功し、公開型シグネチャが維持されることを検証 |
| **AC-4** | REQ-248-T1, T3, T5 | 実装変更またはスキーマ変更を擬似注入した際に `python scripts/verify_openapi_sync.py` が exit 1 を返し、ファイルを書き換えないことを検証 |
| **AC-5** | REQ-248-T2 | `docs/openapi.yaml` を削除した状態で `pytest backend/tests/governance/test_openapi_contract.py` が 100% PASS することを検証 |

### D6: Delegated Judgment to Engineer
- Engineer に委任される事項:
  - `scripts/export_openapi.py` および `verify_openapi_sync.py` の内部実装詳細（標準ライブラリの `argparse`, `difflib`, `subprocess` の実装組み立て）。
  - `frontend/src/api/types.ts` において、`components['schemas']` の型名と手書き型名が完全一致する場合の直接エイリアス化（`export type Foo = Schema<'Foo'>`）と、プロパティ名に一部相違がある場合の互換インターフェース拡張（`interface Foo extends Schema<'Foo'>`）の選択。
  - ログ出力メッセージの微調整（CLI での差分箇所の分かりやすいフォーマット表示）。
- 委任されない事項（設計変更不可）:
  - ファイルの追加・削除・所有範囲の変更。
  - HTTP クライアントや React Query フックの全面自動生成（スコープ外）。
  - API エンドポイントや Pydantic モデル自体のシグネチャ変更。

### D7: Prohibited-Change Scope
- **バックエンドのビジネスロジック・ルーティング**: `backend/app/routers/*`, `backend/app/services/*`, `backend/app/models.py` の変更は厳禁（本PBIはスキーマ出力と型同期のみを対象とする）。
- **フロントエンドのランタイム通信ロジック**: `frontend/src/api/client.ts` や `domains/generation.ts` の通信・エラー復旧・リトライ・再送防止アルゴリズム自体の変更は禁止。
- **過去の履歴文書**: `docs/backlog/pbi/archive/*`, `docs/logs/*` などの履歴ファイルの変更は禁止。
