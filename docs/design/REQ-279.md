# REQ-279: パラメータ変更直後のインメモリ同期的確定とジョブ投入先行競合の是正 設計書

- **PBI**: REQ-279
- **改訂日**: 2026-09-19
- **作成者**: Architect
- **ステータス**: 設計完了 (Design Completed based on Race Condition Analysis)

---

## 1. 概要 & 目的

ユーザー実機検証により、REQ-278 の改修（`rawMappedSets` のインメモリ保持）によって「サーバー保存完了後の store 破壊」は防止されたものの、「パラメータ変更直後にオートセーブ完了を待たずに生成を実行すると、1回目の生成では古いパラメータのままジョブが投入され、リロードなしの2回目になって初めて新値が反映される」というレースコンディション（順序逆転事象）が残存していることが立証された。

本設計の最重要原則は以下の通りである：
> **「ComfyUI へのジョブ生成（キュー投入）は、サーバーへの非同期 HTTP 通信完了（バックエンド保存）に一切依存してはならない。」**
> 画面でユーザーが入力した最新値はすでにブラウザのメモリ上に存在するため、ジョブ発行の直前に同期的かつ確実にストア（`paramValues`, `appliedAssets`, `batchSize`, `seedMode`, `seed` 等）へ反映させきること、およびジョブ生成パイプラインが画面の最新状態を最優先で参照してペイロードを構築することを保証する。

---

## 2. 根本原因と構造的課題の分析

### 2.1 要因①: ジョブ発行と非同期サーバー通信の競合（Race Condition）
- **該当箇所**: `frontend/src/pages/GeneratePage/hooks/useGenerateAction.ts` L132
- **メカニズム**:
  `options?.onBeforeGenerate?.()`（`flushAutoSave`）は同期的に呼び出されるが、`flushAutoSave` 内部のサーバー更新 `updatePresetMutation.mutate(...)` は fire-and-forget の非同期通信である。バックエンド DB 保存およびその後の React Query キャッシュ更新・`useEffect` による store 反映を待たずに次行のジョブ投入ループが先行実行されるため、1回目は古いパラメータでキュー投入される。

### 2.2 要因②: インメモリ即時確定（`updateActiveSet`）のガード落ち
- **該当箇所**:
  - `frontend/src/pages/GeneratePage/hooks/usePresetState.ts` L1016–L1023
  - `frontend/src/store/slices/multiSetSlice.ts` L456–L461
- **メカニズム**:
  `flushAutoSave` および `updateActiveSet` において、`targetActiveId` が未確定（`null`）でセットが複数（`currentStore.sets.length > 1`）存在する場合、ガード条件（`targetActiveId === null`）によって早期 `return` され、インメモリ `sets` の即時更新が空振りする。

### 2.3 要因③: 下流の `isActive` 判定落ちおよびプロパティ未同期
- **該当箇所**: `frontend/src/pages/GeneratePage/hooks/useGenerateAction.ts` L190–L202, L211–L227
- **メカニズム**:
  複数セット選択時かつ `currentActiveSetId === null` の状況下で、`isActive` が `false` と誤判定され、最新の `currentParamValues` がマージされず `setItem.paramValues`（旧値）が使用される。さらに、バッチサイズ（`batchSize`）やシード（`seedMode`, `seed`）も画面の最新 state ではなく `setItem` の旧値が固定参照されていた。

## 3. 恒久是正アーキテクチャ

### 3.1 是正方針 1: `usePresetState.ts` における確実なインメモリ同期
`flushAutoSave` において、`currentStore.activeSetId` が未確定であっても、`currentStore.sets?.length > 0` であれば先頭セットをアクティブとみなしてフォールバック解決する。非同期通信 `mutate` の前に、必ず `currentStore.updateActiveSet?.(currentState)` を即座に同期的実行する。

```typescript
// frontend/src/pages/GeneratePage/hooks/usePresetState.ts
const flushAutoSave = useCallback(() => {
  if (autoSaveTimerRef.current) {
    clearTimeout(autoSaveTimerRef.current)
    autoSaveTimerRef.current = null
  }
  if (!isInitialSyncRef.current) return

  const currentStore = useGenerationStore.getState()
  let targetActiveId = currentStore.activeSetId
  if ((targetActiveId === null || targetActiveId === undefined) && currentStore.sets?.length > 0) {
    targetActiveId = currentStore.sets[0].id
  }
  if (!selectedWorkflowId || targetActiveId === null || targetActiveId === undefined) return

  const activePreset = presets?.find((p) => String(p.id) === String(targetActiveId))
  if (!activePreset) return

  const currentState: HistoryState = {
    paramValues: currentStore.paramValues,
    appliedAssets: currentStore.appliedAssets,
    batchSize: currentStore.batchSize,
    seedMode: currentStore.seedMode,
    seed: currentStore.seed,
  }

  // 【同期的フラッシュ】ジョブ発行前にインメモリ sets を即座に確定
  currentStore.updateActiveSet?.(currentState)

  // バックグラウンド非同期保存（変更がある場合のみ）
  const currentLastSaved = lastSavedStateRef.current[targetActiveId]
  if (currentLastSaved && isStateEqual(currentLastSaved, currentState)) return
  updatePresetMutation.mutate({ ... })
}, [selectedWorkflowId, presets, updatePresetMutation, updateActiveSet])
```

### 3.2 是正方針 2: `multiSetSlice.ts` における `updateActiveSet` ガードの安全化
`updateActiveSet` においても、`activeSetId` が未確定の場合、`currentSets.length > 0` であれば先頭セットを更新対象として安全にフォールバックする。

```typescript
// frontend/src/store/slices/multiSetSlice.ts
updateActiveSet: (updates) => {
  const activeSetId = get().activeSetId
  const currentSets = get().sets

  let targetId = activeSetId
  if ((targetId === null || targetId === undefined) && currentSets.length > 0) {
    targetId = currentSets[0].id
  }

  if (targetId === null || targetId === undefined) return

  const updatedSets = currentSets.map((s) => {
    if (String(s.id) === String(targetId)) {
      return { ...s, ...updates }
    }
    return s
  })

  set({ sets: updatedSets })
}
```

### 3.3 是正方針 3: `useGenerateAction.ts` におけるプロパティ完全同期とジョブ枠整合性
`handleGenerateSets` において、`resolvedActiveSetId` を安全に特定し、アクティブセットには画面の最新パラメータ・バッチサイズ・シードを最優先で適用する。また、先行して登録される `newBatchJobs` のプレースホルダー枠数も最新の `effectiveBatchSize` と一致させる。

```typescript
// frontend/src/pages/GeneratePage/hooks/useGenerateAction.ts
const resolvedActiveSetId = currentActiveSetId ?? (checkedSets.length > 0 ? checkedSets[0].id : null)

      promptId: `pending-${setItem.name}-${i}-${Date.now()}`,

// キュー投入ループ
```

## 4. 影響分析・トレードオフ開示

### 4.1 変更ファイル一覧
1. `frontend/src/store/slices/multiSetSlice.ts`: `updateActiveSet` のフォールバック安全化
2. `frontend/src/pages/GeneratePage/hooks/usePresetState.ts`: `flushAutoSave` のインメモリ即時確定
3. `frontend/src/pages/GeneratePage/hooks/useGenerateAction.ts`: `handleGenerateSets` の `resolvedActiveSetId` 解決・プロパティ同期・プレースホルダー枠同期

### 4.2 トレードオフ開示 (Trade-off Disclosure)
- **インメモリ優先によるバックエンド未保存状態の生成**:
  ComfyUI へのキュー投入は即座に行われるが、バックエンド保存（`updatePresetMutation`）はバックグラウンドで行われるため、ネットワーク切断時に DB 保存が失敗してもローカル生成は実行される。これは「UI のレスポンス性と生成の即時性」を最優先する Web アプリケーションの正当な仕様であり、ComfyUI ジョブの実行をブロックしないための最適なトレードオフである。
- **複数セット未選択時のアクティブフォールバック**:
  `activeSetId` が明示選択されていない場合、先頭の `sets[0]` が画面入力と紐づくアクティブセットとして扱われる。これは単一セットおよび初期複数セット時の直感的な操作感と完全に一致する。
