# REQ-077: バックエンド schemas.py のリソース単位分割リファクタリング 設計書

## 1. 概要
バックエンドの `backend/app/schemas/` フォルダ配下に存在する Pydantic スキーマ定義を整理し、リソースごとに分割配置する。
特に `snapshot.py` に混在している `Album` 関連のスキーマを `album.py` に分離し、`tagset.py` を `tag_set.py` に名前変更（またはコピー）して命名を統一することで、保守性を向上させる。

## 2. 現状と課題
現在、`backend/app/schemas/` ディレクトリ内は以下のようになっている：
- `snapshot.py`: `Snapshot` 関連と `Album` 関連のモデルが同一ファイル内に混在。
- `tagset.py`: スネークケース命名規則（`tag_set.py`）に反するファイル名になっている。

これらを綺麗に整理・分割することで、1ファイルあたりの肥大化を防ぎ、責務を明確にする。

## 3. 設計詳細

### 3.1. ファイル配置の変更
- **[NEW]** `backend/app/schemas/album.py`
  - `snapshot.py` から以下のモデルを移動する：
    - `AlbumCreate`
    - `AlbumOrderUpdate`
    - `AlbumItemsDelete`
    - `AlbumItemsAdd`
    - `AlbumItemRead`
    - `AlbumRead`
    - `AlbumSummary`
- **[MODIFY]** `backend/app/schemas/snapshot.py`
  - `Album` 関連スキーマを削除し、`Snapshot` 関連のみに絞る。
- **[NEW]** `backend/app/schemas/tag_set.py` (かつ **[DELETE]** `backend/app/schemas/tagset.py`)
  - `tagset.py` の内容を `tag_set.py` に移行する。
- **[MODIFY]** `backend/app/schemas/__init__.py`
  - 分割・リネームしたスキーマを正しくインポート・re-export するよう修正する。

### 3.2. インポート互換性の維持
ルーター等で以下のようにインポートされているため、`__init__.py` での `__all__` による公開を引き続き行う。
また、レガシーエントリポイントである `backend/app/schemas.py` も `from app.schemas import *` を継続するため、既存コードの書き換えを最小限に抑えることができる。

```python
# 例
from app.schemas import SnapshotCreate, AlbumCreate, TagSetCreate
```

---

## 4. 懸念点と対策
- **循環参照リスク**: 分割によってスキーマ間で相互参照が発生する場合、循環インポートが発生する。
  - 対策: `Snapshot` が `Album` を参照する、またはその逆がないか依存関係を確認し、必要に応じてインポートを遅延させるか、基本型定義を同一に保つ。今回 `Snapshot` に `album_id` があるが、これは `int` なので問題ない。
- **インポートの不整合**: 他のルーターやサービスで `app.schemas.tagset` など直接モジュールを指定してインポートしている箇所があるかもしれない。
  - 対策: `grep_search` で `app.schemas.tagset` や `from app.schemas.snapshot import` のような直接的なインポート記述を調査し、必要に応じて修正する。
