# REQ-432: VRAMガード 自セッション残留判別 詳細設計書

## 1. 背景と確定した事実

- 対象 PBI: `docs/backlog/pbi/active/REQ-432.md`（AC-1〜AC-4）。インシデント: `docs/incident_report_vram-guard-wait.md`。
- 実機計測（`docs/logs/REQ-432/vram-measurement.md`、2026-11-16）により分類は **Type B（仕様欠落）で確定**した。
  1. SDXL 1 件生成後に残る約 7GB は ComfyUI 自身（WSL2 の `vmwp.exe`）であり、他プロセスではない。
  2. 2 枚目のアダプタは常に 0MB。全アダプタ合算は本環境の原因ではないが、潜在的な実装欠陥として AC-3 で是正する。
  3. ComfyUI `/free` 後、ComfyUI 内部の free は即時に回復するが、Windows PDH の値は約 12 秒遅れて反映された。2.5 秒キャッシュの再サンプリングだけでは AC-4 の直後判定に不十分である。
  4. 生成後の PDH 上の空きは約 5GB で、`vram_min_free_gb`（既定 6.0GB）を下回りうる。これが無期限待機の直接要因である。
- 環境: ComfyUI は WSL2（ROCm）上で動作し、Windows PDH からは `vmwp.exe` として見える。そのため Windows 側のプロセス別カウンタから ComfyUI だけを確実に特定することはできない。

## 3. 設計判断: 自セッション残留 VRAM の扱い

### 3.1 候補

- **(a) 生成完了後の自動 /free（またはオプトイン）**: キュー空き時に Backend が ComfyUI `/free` を呼ぶ。
- **(b) 自セッション残留をガード判定から除外**: ComfyUI `/system_stats` の torch 予約量を自セッション残留（ComfyUI が自分で回収できる量）とみなし、判定用の空き容量に加算する。

### 3.2 採用: (b)。(a) は採用しない（既定でもオプトインでも実装しない）

| 観点 | (a) 自動 /free | (b) 残留除外（採用） |
|---|---|---|
| 次生成までの待ち | 毎回モデル再ロード（SDXL で数秒〜十数秒）が発生する | 再ロードなし。同一モデルなら即時に投入できる |
| AC-1 の充足 | `/free` 後も PDH は約 12 秒遅れるため、PDH 判定のままでは 12 秒前後の保留が残る。(b) 相当の補正が別途必要 | ComfyUI 側の値は即時に更新されるため、残留だけを理由に保留しない |
| 外部占有の検知（AC-2） | 変化なし | ComfyUI が見るデバイス空き（他プロセス使用分を含む）で判定する |
| 他クライアントとの競合 | `/free` が他クライアントの実行と競合しうる（SPEC_SETTINGS L111 の既知制約） | `/free` を呼ばないため競合しない |
| 実装範囲 | worker 完了フック、キュー空き判定、設定項目、OpenAPI 拡張 | monitor の算出と bridge の読み取り専用 GET の追加のみ。REST/OpenAPI 変更なし |

結論: AC-1 は (b) だけで満たせる。(a) は再ロード遅延を毎回招き、PDH の遅延も残るため単独では AC-1 を満たさない。手動「メモリ解放」（REQ-380/REQ-412）は変更せず現状のまま残す。自動 /free のオプトインが必要な場合は別 PBI とする（§10 Q4）。

### 3.3 判定用空き容量の算出（契約 C1）

ComfyUI `/system_stats` の `devices[0]` を使う（ComfyUI は使用中の torch デバイスを先頭に返す）。単位はバイトである。

- `vram_total`(T)、`vram_free`(F) = `mem_get_info` の空き + torch 予約内の未使用量、`torch_vram_total`(R) = torch の予約量、`torch_vram_free`(Rf) = 予約内の未使用量。
- **自セッション残留** `own_residual = R`（ComfyUI が保持するモデルとキャッシュ。ComfyUI は次の prompt の実行時に必要に応じて自分で退避・回収する）。
- **判定用空き** `guard_free = clamp((F - Rf) + R, 0, T)` = デバイス上で torch 予約外にある空き + 自セッション予約量。
- 計測値で検証すると、生成後 B 点（R=7.216GiB、F=6.76、Rf を 0.2 と仮定）では guard_free は約 13.8、アイドル A 点では約 13.1 となり、閾値 6.0 では保留しない。`/free` 直後（D 点）も R と Rf が相殺するため値はほぼ一定になり、PDH の遅延の影響を受けない。
- GiB 換算は `bytes / 1024**3`（既存 PDH 換算と同一）とし、小数第 2 位で丸める。

### 3.4 フォールバック

- ComfyUI の値が取得不能（timeout 1.0 秒、接続失敗、HTTP エラー、非 JSON、`devices` 欠落、負値・非有限値・bool、`Rf > R`、`F > T`、`T <= 0`）の場合は、ホスト空き（primary LUID に限定した PDH、または rocm-smi）で従来どおり判定する。占有元は区別できないため、保留理由は `unattributed` とする。
- ホスト値も取得できない場合は従来どおり「判定不能のため保留しない」（L715 の既存方針を維持）。

## 4. 保留理由の区別（AC-2）と表示

- `vram_hold_reason`: `null`（保留しない）/ `"external"`（ComfyUI 基準で判定し、自セッション残留を除いても不足 = 他プロセス等の占有）/ `"unattributed"`（ComfyUI 値が無くホスト値で判定したため占有元を判別できない）。`"own_residual"` は保留理由として発生しない。自セッション残留だけで保留しないことが AC-1 の契約だからである。
- 配信: `SYSTEM_STATS` に追加フィールドとして載せる（既存フィールドの型は維持）。`vram_safe` は判定用空き（guard_free）に基づく値へ意味を改訂する（SPEC 改訂対象）。
- Backend ログ: 10 秒継続時の警告に `reason`、`guard_free_gb`、`min_free_gb`、`source` を含める。
- Frontend 表示: `unattributed` のときだけ文言を「占有元を判別できません」に変える。`external` と理由欠落（旧 Backend）は既存文言（「他プロセスの終了待機中」）を維持する。待機表示の「空き」は `vram_guard_free_gb` を優先して表示する（判定値と表示値を一致させるため）。
- Settings のメーター（`GET /api/settings/vram` の `vram_free_gb`）はホスト物理空きのまま変更しない。ガード判定とは基準が異なることを SPEC_SETTINGS に注記する（§10 Q3）。

## 5. primary LUID 限定（AC-3）と判定直前サンプリング（AC-4）

### 5.1 primary LUID 限定（契約 C2）

- PDH `\GPU Adapter Memory(*)\Dedicated Usage` のインスタンス名（例: `luid_0x00000000_0x0000d1b5_phys_0`）のうち、小文字化した名前に `f"luid_{primary_luid_hex}_"` を含むものだけを合算する。同一 LUID の複数 `phys_N` は合算する。
- `primary_luid_hex` が未解決（DXGI 失敗）の場合、または一致するインスタンスが 0 件の場合は、全インスタンスを合算する（従来と同じ。使用量を過大側に見積もる安全側の扱い）。その旨を初回のみ debug ログに出す。一致 0 件のときに 0 を返すことは禁止する（空きを過大評価して保護を失うため）。
- `SYSTEM_STATS` の `vram_used_gb` と `vram_pct` も同じ primary 限定値になる（ヘッダー表示も同一基準に揃う）。

### 5.2 判定直前サンプリング（契約 C5/C6）

- `ResourceMonitorService.sample_guard_status()`（async）は、呼び出しのたびにホスト値を新規収集（PDH `PdhCollectQueryData` または rocm-smi）し、ComfyUI 値を新規取得（timeout 1.0 秒）して判定する。キャッシュ値（`_last_*`）は読まずに更新だけ行う。
- worker は `vram_probe` が注入されていればそれを await し、判定の直前に取得した値で判定する。保留中の再評価は 1 ジョブあたり最短 `vram_recheck_seconds`（本番 1.0 秒）間隔とし、各再評価のたびに新規サンプルを取る（0.2 秒ポーリングごとの /system_stats 呼び出しを避けるため）。初回判定は即時に行う。
- OS 側の反映遅延（PDH 約 12 秒）は制御できない。ComfyUI 基準の値は即時に更新されるため、通常経路では遅延の影響を受けない。ホストフォールバック時は OS が反映した時点で次の再評価（1 秒以内）に投入する。
- `vram_probe` 未注入時（既存テスト・旧構成）は従来の同期 `vram_status` を使う（互換）。

## 7. Seam Map（`[W-DD-SEAM]`）

1. **Integrated（実コード）**: `evaluate_vram_guard` / `parse_comfy_system_stats` / `sum_adapter_dedicated_usage` → `ResourceMonitorService.sample_guard_status` / `_collect` / `_run` → `ComfyGenerationBridge.system_stats` → `GenerationService` worker（`_is_vram_blocked`、再評価間隔、保留・投入・キャンセル）→ `MemoryRepository`。FE は `useGenerateAction` → `useGenerationStore` → `DesktopLayout` / `MobileLayout`。
2. **Severed（外部 I/O のみ）**: ComfyUI HTTP は `httpx.MockTransport`（bridge 単体・統合）、または conftest の `respx` で遮断する。PDH/DXGI の DLL 読み出しは `WindowsGpuMonitor._read_counter_items`（I/O のみの境界）。ホスト計測全体は `ResourceMonitorService._get_gpu_stats`（PDH/rocm-smi の I/O 境界。既存テストと同じ）。upstream 投入は既存 `FakeBridge`。FE の WS は store への `systemStats` 注入。
3. **Mock Level**: `evaluate_vram_guard`、`_is_vram_blocked`、`sample_guard_status`、worker 内部をモック・パッチすることは禁止する。I/O 境界以外のパッチは不合格。
4. **PBT 判断**: 必須。数値判定（C1）とインスタンス名フィルタ（C2）は入力空間が広いため、Hypothesis（`backend/requirements.txt` に `hypothesis>=6.100.0` が既存）で不変条件を検証する。
5. **Fault Injection**: `/system_stats` の 503、timeout、接続拒否、非 JSON、非 object、`devices` 空、負値・NaN・Infinity・bool、`torch_vram_free > torch_vram_total`、PDH のアダプタ一致 0 件・LUID 未解決、probe の例外。いずれも安全側（ホストフォールバックまたは従来の判定不能扱い）に倒れ、上流ヘルス表示を変えないことを検証する。

### 8.1 影響分析の補足: モジュールレベル `resource_monitor` のテストダブル

## 10. トレードオフ・リスクと未解決事項

### 10.1 トレードオフ

- **(b) 採用による利点と代償**: 再ロード遅延がなく PDH の遅延にも影響されない。代償として、ComfyUI が自分のモデルを退避すれば足りる前提に立つ。ComfyUI 自身の割り当てが外部占有と合わせて不足する場合の OOM 回避は、ComfyUI の model management に委ねる。
- **ComfyUI 値を主、PDH を従とする**: 判定の主値を ComfyUI の `mem_get_info` 系にした。PDH は WSL の VM ワーカー単位でしか見えず、遅延も大きいためである。代わりに、WSL 内の `mem_get_info` が Windows ネイティブの他プロセス使用量を含むという前提を置く（計測 A 点では整合するが 1 標本のみ。Q1）。
- **表示値の分離**: `vram_free_gb`（物理空き）と `vram_guard_free_gb`（判定用空き）を分けて配信する。ヘッダー・Settings は物理値を表示するため、物理空きが閾値未満でも生成は保留されないという見え方の差が生じる（Q3）。
- **再評価間隔 1.0 秒**: 判定のたびに新規サンプルを取るが、保留中の判定頻度は 1 秒に 1 回へ抑える。回復から投入まで最大約 1.2 秒遅れうる。

### 10.2 リスクと対策

| リスク | 対策 |
|---|---|
| WSL の `mem_get_info` が Windows 側他プロセスを反映しない（外部占有を見逃す） | Gate 3 R-2 で LM Studio 等の実占有を用いて確認する。不成立なら判定式を `min(ComfyUI 基準, PDH空き + R)` に切り替える代替案（§10.3 Q1）で再設計する |
| `/system_stats` 呼び出しが worker ロック保持中に最大 1.0 秒かかる | timeout 1.0 秒で上限を設ける。キャンセル応答が最大約 1 秒遅れうることを受容リスクとして記録する |
| 監視ループ（2.5 秒）と worker 判定の値が一時的に食い違う | 双方とも同じ評価関数を使う。FE は従来どおり snapshot と `vram_safe` で待機表示を更新し、表示は最大 1 周期遅れうる |
| 同じ ComfyUI を外部クライアントも使う場合、その残留も「自セッション」扱いになる | ComfyUI が自ら回収できる量であるため許容する。SPEC に明記する |
| テスト時に lifespan が実 ComfyUI へ接続する | conftest の `respx` が全 HTTP を遮断し、ホストフォールバックになる。既存 REQ-260 テストの期待値は不変 |
| PDH のインスタンス名形式の差異で primary が一致しない | 一致 0 件は全合算（安全側）。0 を返さない |

### 10.3 未解決事項（ユーザー確認事項）

- **Q1**: WSL 内 ComfyUI の `vram_free` が Windows ネイティブの他プロセス（LM Studio 等）の使用量を即時に反映するかは未計測（1 標本の整合のみ）。Gate 3 R-2 を必須の受入証跡とし、不成立時は設計に差し戻す。
- **Q2**: Frontend の文言・表示値変更（T3）を本 PBI に含める（AC-2 の「区別できること」をユーザーが見て判別できる形で満たすため）。不要であれば T3 を除外し、Backend のログと `SYSTEM_STATS` フィールドによる区別に留める。
- **Q3**: Settings の VRAM メーターは物理空きのまま変更しない（SPEC 注記のみ）。メーターも判定用空きに揃えたい場合は別 PBI とする。
- **Q4**: 自動 /free（a）は採用しない。オプトイン設定が必要なら別 PBI とする。
