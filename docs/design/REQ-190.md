# REQ-190: ComfyUIジョブ削除・キュー投入のレスポンス遅延解消と通信オーケストレーション最適化 詳細設計書

## 1. 概要 (Overview)

ComfyUIサーバの起動後、生成を繰り返すうちに「キュー投入」および「ジョブ削除」のレスポンスが徐々に悪化し、特にジョブ削除（キュー待機ジョブの削除や中断）に顕著な遅延が発生する問題を解消する。
不要な HTTP 通信（待機中ジョブへの `deleteHistory`）の排除、冗長な直列 `fetchQueue` 同期待ちの撤廃（WebSocket `status` イベント駆動への一本化）、楽観的ローカル更新の導入、および `fetchHistory` の重複多重発火の制御（デバウンス/重複排除）を行う。

---

## 2. 課題とアーキテクチャ方針 (Problem & Architectural Strategy)

### 2.1 現状のボトルネックと課題
1. **ジョブ削除（`cancelJob`）における 3 連直列 HTTP 通信**:
   - `deleteQueue`（または `interrupt`） ➔ `deleteHistory` ➔ `fetchQueue` の 3 つの HTTP リクエストが完全直列（Sequential `await`）で実行されている。
   - 待機中（Pending）のジョブは ComfyUI の History には存在しないため `deleteHistory` は完全に無駄な通信であり、ComfyUI のキュー排他ロック競合を増やしている。
   - さらに、ComfyUI はキュー操作時に WebSocket `status` メッセージを配信しフロントエンド側ハンドラが自動で `fetchQueue()` を行うため、関数末尾の `await get().fetchQueue()` は完全に冗長であり、UI の処理完了を数秒間ブロックしている。
2. **待機キュークリア（`clearPendingQueue`）および全ジョブ中断（`cancelAllJobs`）の直列通信**:
   - 同様に末尾で `fetchQueue` を直列待機しており、モーダルが閉じるまでの体感速度が低下している。
3. **ジョブ完了時（`executed` / `execution_complete` / `executing: node=null`）の多重 `fetchHistory` 発火**:
   - ComfyUI の `/history` は生成回数に伴って数MB〜数十MBに肥大化する。ジョブ1件の完了に対して複数箇所から `fetchHistory(100)` が同時発火し、ComfyUI のシングルスレッドイベントループおよびプロキシのコネクションプールを占有して後続の `/prompt` や `/queue` を待たせている。

### 2.2 `fetchQueue` の適用・削除境界の厳格な分類 (CRITICAL)

状態不整合（キューの同期漏れ・進捗停止・画面復帰時の不整合）を起こさないよう、以下の通り **「削除対象（Redundant）」** と **「保持必須（Essential）」** の境界を厳格に定義する。

| 分類 | 箇所・トリガー | 方針 | 理由 |
|---|---|---|---|
| **削除対象 (Redundant)** | `cancelJob` の末尾 (L1347) | **削除** | 楽観的UI更新（`queuePending` から即時除外）を行い、ComfyUI からの WS `status` メッセージにより非同期同期されるため直列待機は不要。 |
| **削除対象 (Redundant)** | `clearPendingQueue` の末尾 (L1376) | **削除** | 楽観的UI更新（`queuePending: []`）を行い、ComfyUI からの WS `status` メッセージにより非同期同期されるため直列待機は不要。 |
| **削除対象 (Redundant)** | `cancelAllJobs` の末尾 (L1430) | **削除** | 楽観的ステートリセットを行い、ComfyUI からの WS `status` / `execution_interrupted` で同期されるため直列待機は不要。 |
| **保持必須 (Essential)** | `reconcileState` (L369) / `ws.onopen` (L595) | **保持** | アプリ起動時および WebSocket 再接続時の初期キュー同期に不可欠。 |
| **保持必須 (Essential)** | WS イベントハンドラ (`status`, `execution_start`, `executing`, `executed`, `execution_complete`, `execution_error`, `execution_interrupted`) | **保持** | ComfyUI サーバ側で状態変化が確定した際のリアクティブな唯一の同期トリガー。 |
| **保持必須 (Essential)** | `useGeneratePageState.ts` (L755: タブフォーカス/可視化時) | **保持** | 他タブ・他画面から復帰した際のキュー状態同期に不可欠。 |
| **保持必須 (Essential)** | `useGenerateAction.ts` (L312: `handleGenerateSets` の `finally`) | **保持** | セット一括投入完了時に最終キュー状態を同期するために必要。 |
| **保持必須 (Essential)** | `queuePrompt` (L1118: `!skipQueueFetch` 時) | **保持** | 単体生成時に確実にキューを反映するフォールバックとして必要。 |

## 3. 詳細設計仕様 (Detailed Specifications)

### 3.1 `frontend/src/store/useGenerationStore.ts` の改修

#### 1. `cancelJob(promptId: string)` の最適化
- **楽観的UI更新**:
  - `get().queuePending` 内に `promptId` がある場合、即座に `set({ queuePending: get().queuePending.filter(j => j[1] !== promptId) })` を実行。
- **分岐処理と通信削減**:
  - `isCurrentRunning` または `isInQueueRunning` の場合:
    - `await comfyApi.interrupt()` を発行。
    - 実行中ジョブの履歴クリーンアップのため `comfyApi.deleteHistory({ delete: [promptId] })` を非同期発行（UIブロック防止）。
  - 待機ジョブ（Pending）の場合:
    - `await comfyApi.deleteQueue({ delete: [promptId] })` のみを発行（`deleteHistory` はスキップ）。
- **`fetchQueue()` 直列同期待ちの削除**:
  - 末尾の `await get().fetchQueue()` を削除（WebSocket `status` ハンドラに任せる）。

#### 2. `clearPendingQueue()` の最適化
- **楽観的UI更新**: `set({ queuePending: [] })` を即時適用。
- `await comfyApi.deleteQueue({ clear: true })` を発行。
- `deleteHistory({ delete: pendingIds })` および末尾の `await get().fetchQueue()` を削除。

#### 3. `cancelAllJobs()` の最適化
- 楽観的ステートリセット（`isGenerating: false`, `queuePending: []`, `currentPromptId: null` 等）。
- `comfyApi.deleteQueue({ clear: true })` と `comfyApi.interrupt()` を発行。
- 実行中だったジョブID（`runningIds`）が存在する場合のみ `deleteHistory` を非同期発行。
- 末尾の `await get().fetchQueue()` を削除。

#### 4. `fetchHistory()` の重複呼び出し制御
- 連続して `fetchHistory()` が呼ばれた場合に多重実行を防ぐため、実行中（In-flight）の Promise がある場合はそれを再利用（Coalescing）する。

## 5. 受け入れ基準 (Acceptance Criteria)

- **AC-1**: 待機中ジョブ（Pending）の削除（`cancelJob`）時、不要な `deleteHistory` を呼び出さず、かつ末尾の直列 `fetchQueue` 同期待ちを排除して WebSocket 駆動および楽観的更新により即座に UI から削除されること
- **AC-2**: 「キューのみクリア（`clearPendingQueue`）」および「すべて中断（`cancelAllJobs`）」においても、冗長な末尾 `fetchQueue` 同期待ちを排除し、非同期に即座に応答すること
- **AC-3**: ジョブ完了時における `fetchHistory` の重複呼び出しを整理・間引きし、不要な多重履歴フェッチによる ComfyUI / バックエンドの負荷集中を防止すること
- **AC-4**: アプリ初期化、WebSocket 再接続、WS イベント（`status` 等）、画面フォーカス復帰、およびバッチ生成完了時の必須 `fetchQueue` は確実に維持され、キュー同期・進捗表示・生成完了ハンドリングにデグレーションが発生しないこと
