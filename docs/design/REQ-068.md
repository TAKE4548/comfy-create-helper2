## 2. アーキテクチャ概要

### 2-1. バックエンド変更

#### 新規エンドポイント
| Method | Path | 説明 |
|---|---|---|
| `POST` | `/api/workflows/{id}/copy` | ワークフローをコピー（スナップショット除外）。JSON body: `{ "name": string }` |
| `PUT` | `/api/workflow-presets/reorder` | プリセットの並び替え。JSON body: `{ "ordered_ids": [int] }` |

#### 既存エンドポイント（変更なし・利用拡大）
| Method | Path | 利用 |
|---|---|---|
| `PUT` | `/api/workflows/{id}` | 名前変更（name フィールドのみ送信） |
| `PUT` | `/api/workflow-presets/{id}` | プリセット名変更（name フィールドのみ送信） |
| `DELETE` | `/api/workflows/{id}` | 削除（Settings のみから呼出） |

#### モデル変更
- `WorkflowPreset` モデルに `sort_order: int` カラムを追加（DB マイグレーション必要）
- `WorkflowPresetRead` スキーマに `sort_order` フィールドを追加

### 2-2. フロントエンド変更

#### Generate Page の変更
- ワークフロー `<select>` 横に「⋯」メニューボタンを追加
  - 「名前を変更」→ インライン or モーダル入力
  - 「コピー」→ 名前入力モーダル（デフォルト: `{name}_copy`）
- プリセット（プロファイル）リスト UI に
  - 名前クリックでインライン編集
  - D&D による並び替え（`@dnd-kit/sortable` 既存利用）

#### Settings Page の変更
- 既存のワークフロー管理セクション（現状はリストと削除のみ）を拡充
  - 各行に「名前変更」「コピー」「プロファイル管理」「削除」ボタン
  - 削除は2段階確認ダイアログ（チェックボックス + 赤ボタン）
  - 「プロファイル管理」クリックで展開パネル or モーダルを表示し、名前変更・並び替えが可能

#### 新規コンポーネント
| ファイル | 役割 |
|---|---|
| `frontend/src/components/WorkflowManageModal.tsx` | 名前変更・コピー共通モーダル（Generate / Settings 両方から使用） |
| `frontend/src/components/PresetManagerPanel.tsx` | プリセット名変更 + D&D 並び替え（Generate / Settings 両方から使用） |

## 3. データモデル変更詳細

### WorkflowPreset に sort_order を追加

```python
# backend/app/models.py — WorkflowPreset
sort_order: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
```

```python
# backend/app/schemas/preset.py — WorkflowPresetRead / WorkflowPresetBase
sort_order: int = 0
```

**DB マイグレーション方針**: SQLite `ALTER TABLE` で `sort_order` 列を追加（デフォルト 0）。既存の presets.py `list_presets` のソート順を `id.desc()` → `sort_order.asc()` に変更。

### コピー API のロジック

```python
# POST /api/workflows/{id}/copy
def copy_workflow(workflow_id, name, db):
    src = db.query(Workflow).filter(id == workflow_id).first()
    # 1. 新しい Workflow レコードを作成
    new_wf = Workflow(name=name, json_body=src.json_body,
                      default_applied_assets=src.default_applied_assets)
    db.add(new_wf); db.flush()
    # 2. WorkflowMapping を複製
    for m in src.mappings:
        db.add(WorkflowMapping(workflow_id=new_wf.id, master_id=m.master_id, node_id=m.node_id))
    # 3. WorkflowPreset を複製（sort_order 維持）
    for p in src.presets:
        db.add(WorkflowPreset(workflow_id=new_wf.id, name=p.name,
                              param_values=p.param_values, applied_assets=p.applied_assets,
                              batch_size=p.batch_size, seed_mode=p.seed_mode, seed=p.seed,
                              sort_order=p.sort_order))
    # 4. Snapshot は複製しない
    db.commit(); db.refresh(new_wf); return new_wf
```

## 4. UIコンポーネント設計

### 4-1. WorkflowManageModal（共有モーダル）

**目的**: 名前変更・コピー両対応の軽量モーダル

```
Props:
  mode: 'rename' | 'copy'
  currentName: string
  onSubmit: (newName: string) => void
  onClose: () => void
  isPending: boolean
```

- `mode === 'copy'` の場合、input のデフォルト値を `${currentName}_copy` にする
- 重複エラー（API 409）を `error` ステートとして表示

### 4-2. PresetManagerPanel（共有パネル）

**目的**: プリセット一覧 + 名前変更 + D&D 並び替え

```
Props:
  presets: WorkflowPreset[]
  onRename: (id: number, name: string) => void
  onReorder: (ordered_ids: number[]) => void
  isPending: boolean
```

- 内部で `@dnd-kit/sortable` を使用（GeneratePage と同じライブラリ）
- 名前変更はインライン編集（ダブルクリック or 鉛筆アイコン）

### 4-3. Settings Page ワークフロー削除確認ダイアログ

2段階確認の実装:
1. ユーザーが削除ボタンをクリック → ダイアログを開く
2. ダイアログ内に「関連するすべてのプロファイルと生成履歴（スナップショット）が削除されます。この操作は取り消せません。」の警告文
3. チェックボックス「上記の内容を理解しました」をONにすると「削除」ボタンが活性化
4. 「削除」ボタン（赤色）クリックで API DELETE を実行

## 7. トレードオフ開示（Trade-off Disclosure）

| 項目 | トレードオフ |
|---|---|
| **sort_order 追加 (DB マイグレーション)** | SQLite での `ALTER TABLE` は安全だが、既存の全プリセットに `sort_order=0` が設定され、初回並び替えまで順序が不定になる。初期値として `id` 順を割り当てるマイグレーションスクリプトが望ましい。 |
| **プリセット並び替えを DB 永続化** | リオーダー API の呼び出しは UI ドラッグ完了時に都度発生する。重い操作はないが、ネットワーク遅延でUIと実際の並び順が一瞬ずれる可能性がある（楽観的UI更新で対応）。 |
| **削除は Settings 限定** | Generate Page で誤削除リスクを排除できる設計。ただし、Generate Page でワークフローを誤ったまま使い続ける可能性は残る（将来の警告 UI 拡張で対応可能）。 |
| **WorkflowManageModal と PresetManagerPanel の共有化** | Generate/Settings 両面で使うため共有コンポーネント化。柔軟性と再利用性は高いが、将来どちらかに特殊な挙動が必要になった場合に Props が複雑化するリスクがある。 |
